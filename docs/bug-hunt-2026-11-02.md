# CodeHarbor bug-finding report — 2026-11-02

## Scope and reading guide

This round began with a clean main branch. The repository was mapped first, then thirteen section owners investigated and fixed separate parts of the codebase. Cross-section findings were routed to the relevant owner; shared interfaces and documentation were integrated centrally. This report includes every delivered fix, documentation correction, and added coverage item from the round. IDs beginning with **BH26-** identify findings in this round only.

CodeHarbor has a Qt/C++ desktop client, a native QML mobile client, browser-based editor/terminal/Markdown components, and a TypeScript service on the SSH server. The remote service owns the workspace database, files, and persistent tmux shells. A separate bridge carries coding-agent status. Local Unix sockets let coding agents request viewer actions through the connected desktop client.

Terms used below:

- A **pane** is one editor, file viewer, or terminal surface. A **Dev Session** is a stored remote workspace containing those panes.
- A **tmux target** is the exact server-side session name identifying a persistent shell. Reusing a different pane's target can expose the wrong running work.
- A **layout** is a saved tree describing split panes, proportions, and pane identities.
- A **revision** is the server's file-version token used to prevent overwriting concurrent changes.
- A **generation** is a changing identifier used to reject replies from an older load or connection.
- **Dirty** means the editor contains unsaved changes, independently of whether its file is disconnected, read-only, or in an error state.
- A **recovery snapshot** is a separate copy of unsaved text, not a successful save of the original file.
- An **agent runner** is a program such as Oh My Pi or Claude Code that invokes the integration hooks.

Section records retain their original before/after evidence and the checks requested during investigation; those requests are not additional passing-test claims. Final integration results supersede earlier notes that an owner had not yet run a suite. Source symbols and test names are included so findings remain identifiable if line numbers move.

A comprehensive review is not proof that no other bugs exist. Confirmed findings are separated from unverified concerns and platform limits. No unknown result is presented as a pass.

### BH26-SSH-01 — Route release could return while its log sink still used a dying owner

**Severity:** High; lifetime safety under an explicitly runtime-handled threading-contract violation.

**Affected locations:**

- `SshLogRouter::release`, `src/ssh/SshConnectionPool.cpp:163`, especially the new drain barrier at lines 173–179.
- `SshLogRouter::dispatch`, `src/ssh/SshConnectionPool.cpp:212`, invocation lock at line 262.
- `SshLogRouter::Route::Entry`, `src/ssh/SshConnectionPool.h:118`, invocation mutex at line 127.
- Threading-contract explanation in `src/ssh/SshConnectionPool.h:71–88` and the corrected per-thread logging explanation near `src/ssh/SshConnectionPool.cpp:1009`.
- Regressions at `src/ssh/tests/tst_sshlogrouter.cpp:536` and `:587`.

**Original behavior and trigger:** A route is created on thread A, and a libssh log line enters its sink. While that sink is still running, thread B releases/destroys the route. `release()` cleared an atomic active flag and returned immediately. The flag stopped later calls but did nothing to drain a callback that had already passed `dispatch()`'s active check.

**Impact:** The releasing thread could immediately destroy the object captured by the sink while the sink was still accessing it. The in-flight callback/release overlap was reproduced directly. A resulting captured-owner use-after-free is an [INFERENCE] from that observed overlap, not a deliberately executed crash. The existing comments claimed wrong-thread deactivation prevented the dying-owner hazard; that claim was too strong.

**Root cause:** Entry allocation lifetime was protected by shared ownership, but the separate lifetime of the sink's captured owner was not synchronized with callback invocation. An atomic eligibility flag is not a callback-completion barrier.

**Exact fix:** Each entry now contains a recursive invocation mutex. Dispatch holds it across the active check and sink call. Release first marks the entry inactive, then briefly acquires the same mutex before returning. This prevents new calls and drains an existing call. Recursive locking preserves the supported case where a sink releases its own route. The header now states the synchronization and the requirement not to make a sink wait for another thread synchronously releasing that same route. Also corrected the stale `connectToHost()` comment that called libssh's logging state process-global; it is thread-local rather than session-local.

**Regression coverage added:**

- `wrongThreadReleaseWaitsForAnInFlightSink`: holds a real libssh-routed callback behind a semaphore, releases on another thread, and verifies release cannot finish while the callback is blocked.
- `aSinkCanReleaseItsOwnRouteDuringDispatch`: destroys the inner route from its own sink and emits a nested diagnostic, verifying that recursive release does not deadlock and attribution returns to the outer route.

These project tests have not been run or compiled by this worker.

**Standalone reproduction and observed results:** A small C++ program compiled the actual SSH sources, created a route on a worker thread, blocked its sink on a semaphore, and attempted release on a second thread. The harness waited 250 ms for release to return before allowing the sink to exit.

Before:

```text
release returned while callback blocked: YES
```

After:

```text
release returned while callback blocked: NO
```

The expected wrong-thread warning remained visible. The reproduction exercised the real libssh `_ssh_log` dispatcher, not a replacement router implementation.

**Integration checks requested during investigation:** Integrated compilation and execution of `tst_sshlogrouter`; ideally also a sanitizer run of its concurrent and self-release cases. No TSAN/ASAN claim is made.

**Shared comment correction applied:** The integration owner corrected `src/ssh/tests/CMakeLists.txt:48–50` to describe libssh diagnostic logging as thread-local rather than session-local and wrapped the adjacent explanatory comment. This is included in BH26-SSH-01 accounting. No functional build configuration changed.

### BH26-SSH-02 — Encrypted PEM keys could open an implicit terminal prompt before the application's credential callback

**Severity:** High; unbounded calling/UI-thread stall for a supported key format when a controlling terminal exists.

**Affected locations:**

- `SshConnectionPool::connectToHost`, `src/ssh/SshConnectionPool.cpp:894`; persistent callback registration at lines 996–1007.
- `SshConnectionPool` private session callback storage, `src/ssh/SshConnectionPool.h:597–599`; callbacks header included inside the existing libssh feature guard.
- New live regression `encryptedPemIdentityNeverPromptsOnTheControllingTerminal`, `src/ssh/tests/tst_livessh.cpp:618`.

**Original behavior and concrete trigger:** The normal public-key ladder calls `ssh_userauth_publickey_auto(session, nullptr, nullptr)` on its silent first attempt, but the session had no `ssh_callbacks_struct.auth_function`. Libssh passes that callback into its private-key importer. With a legacy encrypted RSA PEM key, OpenSSL therefore used its own controlling-terminal passphrase prompt. The application's `CredentialCallback` was not reached until that hidden console interaction finished. Modern encrypted OpenSSH-format ed25519 did not reproduce the console prompt in the same harness; the confirmed trigger is encrypted PEM.

**Impact:** Launching CodeHarbor from a terminal and selecting an encrypted PEM identity could hang the synchronous connection on `Enter PEM pass phrase:` without the application's expected credential flow. This interaction is local terminal input, so the SSH session's network timeout does not bound it. On headless test runners the missing tty made this path fail quickly, hiding the bug.

**Root cause:** Manual Windows identity-file import and in-memory identity import already passed `declineLibsshPassphrase`, but the ordinary libssh auto-key path was never given the equivalent session authentication callback.

**Exact fix:** The pool now owns an initialized `ssh_callbacks_struct` for the whole session lifetime and registers `declineLibsshPassphrase` as its authentication callback immediately after `ssh_new()`. This refuses libssh's implicit local prompt while retaining the existing explicit CodeHarbor passphrase/password ladder, certificate support, agent behavior, and identity-list processing. Registration failure reports a real error and closes the attempted session. Member storage is required because libssh retains the callback-structure pointer instead of copying it.

**Regression coverage added:** A Linux live case generates a throwaway encrypted RSA PEM key, removes its `.pub` file so local import must happen before the server can reject it, and runs an isolated test-process attempt under util-linux `script` (a real controlling PTY). Nothing answers the PTY. The application credential callback supplies the passphrase; the intentionally unauthorized key is then refused normally. The parent case requires prompt-free completion and checks the child result. The test skips when live SSH is disabled, on non-Linux platforms, or when `script`/`ssh-keygen` are unavailable. No shared build dependency was added.

This project test has not been run or compiled by this worker.

**Standalone reproduction and observed results:**

1. Generated a temporary ed25519 host key and encrypted RSA PEM client key using `ssh-keygen -t rsa -b 2048 -m PEM -N bh26-test-passphrase`.
2. Started a temporary unprivileged sshd bound only to `127.0.0.1` on an ephemeral port, with its `AuthorizedKeysFile` pointing at the generated client public key, `StrictModes no`, `UsePAM no`, and password/keyboard-interactive disabled.
3. Compiled a tiny application against the current SSH sources. It accepted the temporary host key and returned `bh26-test-passphrase` only through the application's `CredentialKind::KeyPassphrase` callback.
4. Executed it through `script -q -e -c '<reproducer> auth 127.0.0.1 <port> <current-user> <encrypted-pem-key>' /dev/null`, leaving stdin open and unanswered.

Before, the harness had to terminate the PTY process after 3 seconds; its stdout was:

```text
Enter PEM pass phrase:
```

After, the same scenario completed without that prompt and printed:

```text
connected=1 application_passphrase_requests=1
```

The temporary fixture and keys were removed and the sshd stopped.

**Supporting upstream source:** libssh 0.11.3 `src/auth.c` documents the default passphrase asker and passes the session callback into the key importer: https://raw.githubusercontent.com/libssh/libssh-mirror/libssh-0.11.3/src/auth.c (around lines 1263–1272, 1307–1309, 1383–1386, and 1525–1528).

**Integration checks requested during investigation:** Integrated `tst_livessh` execution with the new PTY-backed case, existing encrypted-key/config/tilde cases, and normal agent authentication. Build the no-libssh configuration and Windows configuration to verify guarded callback storage/includes and existing platform fallback compatibility. These platform checks were not run here.

### BH26-SSH-03 — Reentrant close from aboutToClose could recursively close the same device

**Severity:** Medium; deterministic reentrant notification bug, with stack-exhaustion potential.

**Affected locations:**

- Common `SshChannelDevice::closeChannel`, `src/ssh/SshChannelDevice.cpp:87–110`.
- `SshChannelDevice::acquireChannel`, `src/ssh/SshChannelDevice.cpp:286`, closing-state guard at lines 288–291.
- Closing-state storage/comment, `src/ssh/SshChannelDevice.h:142–145`.
- Regression `closingFromAboutToCloseDoesNotReenterOrReopenTheChannel`, `src/ssh/tests/tst_sshchanneldevice.cpp:133`.

**Original behavior and trigger:** `closeChannel()` called `QIODevice::close()` while the device was open. Qt emits `aboutToClose()` before changing the open mode. If a direct handler called `close()`/`closeChannel()` again, the nested call still saw an open device and called `QIODevice::close()` again. The method was documented idempotent, but was not idempotent during its own close notification.

**Impact:** Duplicate close notifications were reproduced. An unconditional handler that closes again would continue recursively and exhaust the stack [INFERENCE; the reproduction deliberately bounded recursion rather than crashing]. On a live pool a handler could also attempt a replacement start before the outer base-device close finished, allowing the outer close to invalidate that new stream.

**Root cause:** No close-in-progress latch spanned the reentrant Qt signal. Channel handle and open-mode transitions alone did not identify an active teardown.

**Exact fix:** Both libssh and no-libssh builds now use one common `closeChannel()` implementation with an explicit closing latch. Nested closes return immediately. Channel acquisition refuses a replacement while close is in progress. A live channel handle is detached before returning it to the pool. The latch is released before the final `readChannelFinished()` signal, so ordinary restart after completed teardown is still allowed. The duplicated conditional close implementations were removed rather than maintained in parallel.

**Regression coverage added:** The existing server-free opened-device helper now drives `aboutToClose` -> nested `close()` -> attempted restart. The regression checks one close notification, one read-finished notification, a refused restart, a closed final device, and continued idempotence. It runs in both feature configurations; only the libssh-specific error wording assertion is guarded.

This project test has not been run or compiled by this worker.

**Standalone reproduction and observed results:** The actual `SshChannelDevice` was opened through the same small helper pattern used by its existing unit tests. An `aboutToClose` handler called `closeChannel()` only on its first invocation, bounding the regression.

Before:

```text
aboutToClose emissions for one reentrant close: 2
```

After:

```text
aboutToClose emissions for one reentrant close: 1
```

**Integration checks requested during investigation:** Integrated `tst_sshchanneldevice`, no-libssh execution of the same test, and the existing live device-outliving-session/channel-slot-reuse cases. No live replacement-start scenario was exercised by the standalone helper.

### BH26-SSH-04 — Large-output EOF and split-stderr decoder behavior lacked direct regression cases

**Severity:** Low; coverage improvement only, not a newly discovered production failure.

**Affected locations:**

- `src/ssh/tests/tst_livessh.cpp:380`, `execChannelDrainsLargeStdoutBeforeReportingEof`.
- `src/ssh/tests/tst_livessh.cpp:396`, `stderrDecoderPreservesACharacterAcrossPumpPasses`.

**Observed gap:** Existing live channel tests used small stdout/stderr payloads. They did not directly exercise the production comments about an empty stream returning EOF while the other stream still has more than one pump's byte budget, or the persistent UTF-8 decoder across separate pump passes.

**Why it matters:** Those are precisely the data-loss/diagnostic-corruption boundaries called out by the channel implementation. Inspection shows the existing production pump already uses `ssh_channel_is_eof()` and a persistent `QStringDecoder`; no speculative production rewrite was made.

**Exact coverage added:**

- Drain 640 KiB of stdout (larger than the 256 KiB per-stream pump budget), then require the complete byte sequence before finished is considered successful.
- Write the first byte of a UTF-8 euro sign to stderr, publish a stdout marker, and have the peer wait for a client acknowledgement before sending the remaining bytes. The pump drains stderr before emitting `readyRead()`, so this handshake forces the code point across different passes without relying on sleeps or network packet boundaries. Assert exact stdout, exact decoded stderr, and successful acknowledgement.

**Reproduction evidence:** This is a test-gap finding from source/test inspection, not a reproduced current production failure. The new cases were not executed or compiled by this worker.

**Integration checks requested during investigation:** Run the two new live cases against the ordinary POSIX sshd fixture. No Node-side or daemon behavior is involved in their commands.

### BH26-RPC-01 — Logical RPC failure did not reconnect the session

### BH26-RPC-07 — Bridge child exit was hidden behind the shell stdin watchdog

**Severity:** High.

**Locations:** `SessionBootstrap.cpp:263-301`, `bridgeCommand()`. Regressions: `tst_sessionbootstrap.cpp:1759` (updated selected-entry expectation), `:1831` (early exit), and `:1870-1924` (EOF/cooperative and SIGTERM-ignoring child data rows).

**Original behavior and trigger:** The command launched `node bridge &`, then blocked in `cat >/dev/null`, and killed the recorded bridge PID only after SSH stdin closed. If the bridge exited or crashed first, cat kept the SSH channel open indefinitely. Bootstrap saw no EOF and continued claiming a live agent stream.

**Impact:** Agent events silently stopped without session recovery. Child exit status was hidden, and child/session lifetime management was unreliable.

**Root cause:** The foreground process watched stdin but did not observe the bridge child's lifetime.

**Final fix:** Use a single primary Node launcher for every bridge, including older-service fallback releases. The launcher waits for the child exit and exits with its numeric status or conventional 128+signal status. Spawn errors are surfaced on stderr and exit 127. No optional bridge flag or new remote capability is required.

**Why the design changed during implementation:** Direct exec plus a new bridge-specific EOF flag fixed the newest bridge only. An explicitly supported failed-update fallback could ignore that new flag and become orphaned on disconnect. The integration owner rejected that regression. **Regression coverage:** A tiny real Node child exits 23 while launcher stdin remains open; the launcher must finish and preserve 23. EOF cases use a legacy-style child with no stdin handler or new CLI option: one exits normally on SIGTERM, another deliberately ignores it and must produce status 137 after escalation. Both write a signal-receipt marker. Fixtures have their own finite deadline to avoid indefinite leaks when testing a broken launcher. Existing hostile-field quoting and layout selection checks remain in place without pinning the JavaScript launcher source.

**Actual reproduction evidence:** The baseline command, emitted by the real factory, remained alive after its child exited while stdin was held open; after releasing stdin its shell returned 1 instead of child status 23. - EOF/SIGTERM-ignoring child: status 137, approximately 2027 ms, child no longer alive, stop marker present;
- SIGTERM to launcher/cooperative child: status 0, approximately 30 ms, child no longer alive, stop marker present.

### BH26-RPC-09 — Concurrent installers recover and delete one another's live transactions

**Severity:** High; confirmed loss of an existing service asset and false release attribution.

**Status:** Fixed and verified in the final integrated suite. **Affected behavior:** The installation scratch directory and journal are deterministic per root, but the pre-fix script had no ownership exclusion. An existing `ready` sentinel established a complete plan, not that the writing process was dead. A second installer therefore treated an actively mutating predecessor as an interrupted install and recovered/deleted its state.

**Actual two-process reproduction:** A fresh root contained an old daemon, old bridge, `extras/keep.txt=old service asset`, unrelated notes, and an old release marker. 1. A paused immediately before displacing `root/extras`, after swapping `dist`. The shell wrapper saved original stdin as FD 3 because the swap loop redirects FD 0 to its journal.
2. B targeted the same root, interpreted A's live `ready` journal as abandoned, recovered it, staged B, and paused after moving B's staged `dist` into the live root.
3. A resumed, moved the old extras into B's backup, failed because its original staged extras had been deleted, and rolled back using B's plan. B's plan did not name extras, so recursive cleanup deleted the sole backup of that existing asset.

A FIFO is rejected before open, avoiding an indefinite blocking redirection; symlinks are not followed. Never unlink the lock inode. Mutation subprocesses inherit FD 9, so kernel ownership survives while an inherited-descriptor subprocess is still running. Ownership disappears after the final holder exits; there is no automatic PID stale-deletion/reuse race. Reject the lock filename from archive payload alongside the existing reserved names.

Existing-service fallback and manual installation remain available without it; first-time automatic installation refuses with an actionable diagnostic until it is available. The selected filesystem must support the advisory lock; the script fails closed if acquisition fails.

### BH26-TERM-01 — A nearly full renderer window bypassed output flow control

### BH26-MOB-01 — References can shadow saved credentials, and maximum-length collisions cannot be renamed

### BH26-WEB-01 — BEL prematurely ended non-OSC control strings

- **Severity:** Medium, terminal correctness and control-payload isolation.
- **Affected source:** `src/vt/VtParser.cpp:600`, `VtParser::handleByte`, shared DCS passthrough/ignore, SOS, PM, APC, and OSC branch.
- **Original behavior and trigger:** The shared string-state branch treated BEL (`0x07`) as a terminator for every kind of control string. BEL is an OSC terminator, not a DCS/SOS/PM/APC terminator. For example, `ESC P q before BEL hidden ESC \\ shown` printed `hiddenshown` instead of only `shown`. The same premature exit occurred for ignored malformed DCS strings and APC/PM/SOS.
- **User impact:** A control payload containing BEL could spill its remaining printable bytes onto the mobile terminal screen rather than being consumed through ST. Further ordinary controls following that premature exit could affect the screen. This was inconsistent with both the browser input scanner and the native terminal-controller scanner, which already document the OSC-only BEL rule.
- **Root cause:** A terminator rule specific to OSC was placed unconditionally in the shared string-state handler.
- **Exact fix:** Gate BEL termination on the existing `dispatches` predicate, which is true only for OSC. Other string states ignore BEL and remain in the string until their proper terminator or cancellation. The now-unconditional OSC dispatch within that guarded branch replaces a redundant inner condition.
- **Regression coverage:** `src/vt/tests/tst_vt.cpp:110,795`, `bellDoesNotTerminateNonOscStrings`. Byte-at-a-time feeds cover DCS passthrough, malformed/ignored DCS, SOS, PM, and APC; assert only post-ST text is displayed and no bell is emitted. Existing OSC BEL tests remain unchanged.
- **Reproduction evidence:** Confirmed by the original branch and the concrete stream above; native executable reproduction not run because this worker was instructed not to build/run the project.
- **Integration checks requested during investigation:** Build and run `tst_vt`, particularly `bellDoesNotTerminateNonOscStrings`, and the existing split-feed cases.

### BH26-WEB-04 — Releasing the mouse modifier mid-drag changed gesture ownership

- **Severity:** Medium, terminal mouse interaction.
- **Affected source:** `src/web/terminal/src/mouse.ts:68-120`, `installInvertedMousePolicy`.

### BH26-STATE-01 — Unbound terminal recovery failed when another pane adopted its canonical target

- **Severity:** Medium.
- **Affected implementation:** `remote/src/workspace.ts:1872`, `Workspace.resolveTerminalPane`; collision check and fallback at approximately `1900-1905`.

- **User impact:** A's existing layout leaf could no longer attach a terminal. Reconnecting or retrying did not help; the row could not complete its advertised null-target recovery. B legitimately owned the old target and must not be changed or made to share it.

### BH26-STATE-02 — Pane deletion could persist zero layout ratios

- **Severity:** Low; a layout-integrity edge case requiring extreme numeric input.
- **Affected implementation:** `remote/src/workspace.ts:461`, `removePaneFromTree`; normalization at `480-484`.
- **Regression:** `remote/test/workspace.test.ts:4017`, `pane deletion keeps extreme surviving layout ratios positive and finite`.

#### BH26-IO-01 — Dangling symlink saves could write the wrong file

- Severity: **high** (unrequested file creation/content written to the wrong pathname, followed by a misleading save failure).
- Locations: `remote/src/files.ts:540-619`, principally `resolveLinkChain()` at line 550 and `writeFile()` at line 616. Tests: `remote/test/files.test.ts:2246` and `:2337`.
- Original behavior and trigger: the dangling-link resolver used `path.resolve(linkDirectory, linkText)`. Given `link -> hop/../target.txt`, with `hop` itself a symlink to `elsewhere/nested`, it erased `hop/..` before the kernel could follow `hop`. The intended target is `elsewhere/target.txt`, not the neighboring `target.txt`. Saving created that neighboring file and then failed when the final stat followed the real link. A second trigger, `link -> missing/.`, normalized a directory-only target into `missing`, created a regular file there, then failed with ENOTDIR.
- User impact: a failed save could still create/write an unrelated file while leaving the requested file unsaved. A directory-shaped dangling link could be silently converted at its target into an unusable regular file.
- Root cause: lexical path normalization was used where component-by-component filesystem resolution was required, and directory-only trailing syntax was discarded.
- Exact fix: use realpath for existing paths, with a component-by-component resolver for absent targets. Resolve parent symlinks before processing `..`; count all followed links against the existing 40-link cap; propagate real lookup errors rather than treating every readlink failure as absence; preserve final `/`, `/.`, and `/..` directory semantics. Use the same canonical resolver for write-lock keys and remove the obsolete lexical-fallback `resolveWriteKey()` implementation. Updated nearby explanations belong to this fix.
- Regression coverage added: real filesystem dangling-link/parent-symlink/`..` save, preserving the link, intended target content and revision, and absence of wrong/temporary files; directory-shaped dangling targets remain absent and links remain intact after refusal. Existing maximum-depth/cycle/save-through-link cases should also be rerun.
- Reproduction evidence: created `elsewhere/nested`, `hop -> elsewhere/nested`, and `link -> hop/../target.txt`, then called `writeFile({path: link, content: 'saved', expectedRevision: ''})`. Before: `result.error='ENOENT'`, intended target `ENOENT`, wrong neighboring target `'saved'`. After: successful revision-bearing response, intended target `'saved'`, wrong target `ENOENT`. For `link -> missing/.`, before: `ENOTDIR` plus wrong file `'saved'`; after: `ENOTDIR`, wrong target `ENOENT`.
- Integration checks requested during investigation: integrated focused file suite and remote typecheck, especially existing 40-symlink/cycle/concurrent-write cases. No suite result is claimed.

#### BH26-IO-02 — Watch notifications stopped forever when a target became a symlink loop

- Regression coverage added: real FIFO, both addressed directly and through a symlink, with both create-only and matching-revision requests. Require EINVAL, preserve FIFO/link kinds, and assert no temporary files remain.
- Reproduction evidence: before fix, matching-revision save succeeded and reported `isFIFO=false,isFile=true`. After fix: `result.error='EINVAL',isFIFO=true,isFile=false`.
- Integration checks requested during investigation: focused file suite, including existing directory error, regular-file save, and symlink-save cases.

### BH26-BRIDGE-01 — Asynchronous stderr failure could make a best-effort hook exit nonzero

- **Severity:** Medium.
- **Affected code:** `remote/src/hooks/bridge-emit.ts:259-273`, `writeStderr()`; regression `remote/test/agent-hook.test.ts:339-364`.
- **Original behavior and trigger:** Launch a hook with stderr connected to a pipe, close the reader, and let the hook print a diagnostic. **Fix:** Ask keytool directly with `-list -keystore ... -storepass:env STORE_PASSWORD -alias "$KEY_ALIAS"`. Password handling remains environment-based; existing human-readable diagnostics remain. Added a short comment explaining why listing regexes are wrong.

**Observed reproduction:** A real standalone keytool-created throwaway RSA keystore with alias `release[1]` was successfully generated. The original grep check on its actual keytool listing exited 1. The new exact keytool alias query exited 0. The temporary key and directory were removed afterward.

**Regression coverage:** Targeted real-tool evidence, not a source-text assertion. No new project test was added solely to extract inline workflow code.

**Integration checks requested during investigation:** Release credential preflight/dry run with an ordinary alias and a regex-character alias, plus a deliberately absent alias. These should respectively accept, accept, and reject.

### Scope and evidence

A root `npm audit --json` run identified four vulnerable installed packages: one critical, two high, and one moderate by upstream advisory classification. The exact before inventory was DOMPurify 3.4.13, esbuild 0.23.1, source-map-js 1.2.1, and undici 8.10.0. These severities describe upstream libraries, not four demonstrated exploitable CodeHarbor vulnerabilities. The configuration and exposure distinctions below are intentional.

### BH26-DEP-01 — Privileged Markdown sanitizer used an affected DOMPurify release

**Classification:** Security dependency maintenance; highest upstream advisory severity Critical. No CodeHarbor XSS exploit was demonstrated.

**Files:** `src/web/markdown/package.json:14`; `package-lock.json` entry `node_modules/dompurify`. Relevant consumer: `src/web/markdown/src/renderer.ts`, `renderMarkdown`, which sanitizes parsed Markdown before insertion into the privileged viewer page.

**Before and risk:** The direct dependency allowed `^3.4.13`, and the lockfile installed 3.4.13. That version is affected by the five advisories listed below. A sanitizer is a security boundary, so retaining a release with known bypasses is a maintenance risk even when the documented exploit prerequisites are not enabled by the current caller.

**Exposure distinction:** CodeHarbor passes an HTML string to the sanitizer and uses its string result. Its current configuration does not enable `IN_PLACE`, DOM-returning modes, `SAFE_FOR_TEMPLATES`, custom after-sanitize hooks, or XML parser mode. The reviewed Critical advisory specifically requires non-default template/DOM/shadow-root behavior plus downstream template evaluation; those prerequisites are not established here. The other listed advisories likewise concern special DOM/hook/XML modes. This update must not be read as evidence that ordinary CodeHarbor Markdown was already executing attacker scripts.

**Fix:** Raise the allowed minimum to `^3.4.17` and lock the installed sanitizer to 3.4.17, the patched version identified by the reviewed advisory. No sanitizer-policy relaxation, alternate insertion path, or application fallback was added.

**Coverage and verification:** Existing tests exercise script removal, event attributes, dangerous links, embedded elements, relative resources, and asynchronous renderer behavior. They passed against the new library; the Markdown browser bundle rebuilt successfully. Real Chromium sanitizer/path rendering was also exercised during integration; final browser evidence is in the integration section. No test was added merely to assert a package version.

**Upstream advisories covered by the package update:**
- [DOMPurify: IN_PLACE: node-removing afterSanitize hook leaves detached subtree event handlers armed, causing DOM XSS](https://github.com/advisories/GHSA-p98j-92pf-mc4p) — upstream severity low; affected range `>=3.4.13 <=3.4.15`.
- [DOMPurify: IN_PLACE returns a force-removed rawtext root whose text carries attacker markup — pure HTML reparse executes](https://github.com/advisories/GHSA-6688-9rhm-gjv2) — upstream severity low; affected range `<=3.4.15`.
- [DOMPurify SAFE_FOR_TEMPLATES bypass: split template expressions survive in attached shadow root content on DOM output modes](https://github.com/advisories/GHSA-cg2g-xh64-v4q7) — upstream severity critical; affected range `>=3.4.4 <=3.4.16`.
- [DOMPurify IN_PLACE: hook that removes a parent or sibling leaves the detached subtree's event handlers armed (incomplete fix for GHSA-p98j-92pf-mc4p)](https://github.com/advisories/GHSA-mrv2-3pqr-j5jr) — upstream severity high; affected range `<=3.4.16`.
- [DOMPurify: SMIL attributeName=href guard is skipped when PARSER_MEDIA_TYPE is application/xhtml+xml](https://github.com/advisories/GHSA-c6gr-qvv4-5v3f) — upstream severity low; affected range `<=3.4.16`.

### BH26-DEP-02 — Build tooling retained an esbuild development-server disclosure advisory

**Classification:** Moderate upstream development-tool vulnerability; no running CodeHarbor development-server exploit was demonstrated.

**Files:** `src/web/terminal/package.json:21`, `src/web/editor/package.json:18`, `src/web/markdown/package.json:20`, and esbuild/platform-package entries in `package-lock.json`.

**Before and trigger:** All web workspaces declared `^0.23.0`; the installed version was 0.23.1. The upstream serve API in releases through 0.24.2 sends permissive CORS headers, allowing a malicious web page to read resources from a developer's local esbuild server, including source maps.

**Exposure distinction:** The repository's bundle scripts call the build API rather than esbuild's HTTP serve feature. No exposed server using that feature was found or exploited. Keeping the vulnerable development tool was still an avoidable footgun for developers using it locally.

**Fix:** Move all three manifests together to `^0.25.12` and lock the matching 0.25.12 packages. Version 0.25.0 is the first patched series; 0.25.12 is the latest observed patch in that series. This deliberately avoids an unnecessary jump to the registry's newer 0.28 series. Because esbuild is pre-1.0, this changes the allowed minor series; compatibility was checked by running the actual existing build scripts rather than assuming it.

**Verification:** Terminal, editor, and Markdown typechecks/tests and actual bundle builds all passed. No repository build-script API changes or compatibility wrappers were needed. The final audit no longer flags esbuild.

**Primary advisory:**
- [esbuild enables any website to send any requests to the development server and read the response](https://github.com/advisories/GHSA-67mh-4wv8-2f99) — upstream severity moderate; affected range `<=0.24.2`.

### BH26-DEP-03 — The DOM test environment locked an affected source-map parser

**Classification:** High upstream dependency advisory; development/test dependency exposure, not a demonstrated production denial of service.

**File:** `package-lock.json`, `node_modules/source-map-js`.

**Before and trigger:** Version 1.2.1 does not validate indexed source-map section offsets sufficiently. **Exposure distinction:** JSDOM is declared only for web-component tests. This dependency is not part of the zero-runtime-dependency remote service and is not the browser engine used by the shipped desktop client. No attacker-controlled indexed source map was demonstrated reaching this parser through the application's current runtime.

**Fix:** Refresh the existing compatible transitive range to source-map-js 1.2.2. No direct dependency, global override, or unrelated CSS-library upgrade was added.

**Verification:** All JSDOM-backed terminal and Markdown tests passed after the refresh, and the final audit has no source-map-js finding. An intentional CPU-exhaustion exploit was not run against a user process.

**Primary advisory:**
- [source-map-js allows event-loop denial of service through indexed source-map section offsets](https://github.com/advisories/GHSA-68fv-2mgg-jv7q) — upstream severity high; affected range `>=1.0.0 <1.2.2`.
