# Bug hunt — 2026-08-03

A complete sweep of the repository. The tree was divided into sixteen areas and one
reviewer was given each area, with instructions to read every file it owned from beginning
to end and to fix what it found. A seventeenth reviewer then re-checked the prose
documentation against the finished tree, because the documentation pass had run early and
several code changes landed after it. The coordinator found and fixed a further set of
problems while integrating the work and while getting a release to build.

Every label in this document (`MP3`, `SSH7`, `ORCH9`, …) is unique **within this round**.
Labels do not continue, and are not comparable with, the numbering of the earlier
`docs/bug-hunt-*.md` files. Those were treated as historical background only.

**Result: 249 labelled items. 244 were fixed, four were deliberately left, and one turned
out not to be a bug at all and was withdrawn after it broke a release build.** All five are
listed with their reasons at the end.

## How to read this document

Each entry says what the code did before, why that was wrong in terms of something a user
or another part of the program would actually observe, what was changed, and whether it is
fixed. Everything is written for a reader who has never seen this project and cannot open
the source.

## Words used in a specific way

* **Dev Session** — one unit of work: a checked-out copy of a repository on a remote
  server, plus the panes and shells opened against it.
* **Pane** — one rectangular sub-view. The window has a fixed three-part layout: a list of
  sessions down one side, an area for file viewers, and an area for terminals.
* **`codeharbord`** — a small service, written in TypeScript and run with Node, that
  CodeHarbor installs and runs on the remote server. All workspace data lives there. The
  desktop application talks to it by sending one JSON object per line over a channel inside
  an SSH connection. This style of conversation is called JSON-RPC.
* **`codeharbor-bridge`** — a second small process on the server. It listens on a local
  socket for status messages posted by coding-assistant programs and relays them to the
  desktop application.
* **tmux** — a program on the remote server that keeps a shell alive after you disconnect.
  Every terminal pane is attached to one tmux session; that is what lets terminals survive
  a dropped connection.
* **Harness** — a coding-assistant program running in a terminal. An **adapter** translates
  one harness's own vocabulary of events into CodeHarbor's shared one.
* **Qt signal** — a notification one C++ object sends to others. Qt delivers signals
  *synchronously*: sending one runs every connected handler to completion before the next
  line of the sending function executes. A handler may do anything, including destroy the
  object that sent the signal. Much of what follows is about that.
* **`QPointer`** — a Qt smart pointer that automatically becomes empty when the object it
  points at is destroyed, instead of pointing at freed memory.
* **Revision token** — an opaque string identifying the exact contents of a remote file at
  the moment it was read. A save quotes it, and the server refuses the write if the file
  has changed since. This is how two editors cannot silently overwrite each other.
* **Preset** — a named build configuration. This project has a `dev` preset (a debug build)
  and a `release` preset.

## `src/models` and `src/persistence` — the data types and the workspace client

Scope reviewed: every C++ source/header and test/build file under `src/models/` and `src/persistence/` assigned to MP. ### MP1 — Pinned-only filtering displayed empty groups

- **Severity:** active bug
- **File and line(s):** `src/models/SessionsModel.cpp:14-40`; test `src/models/tests/tst_models.cpp:1063-1085`
- **What the code does now:** Before the fix, the filter copied each group and removed sessions that were not pinned, but it appended an empty group even when pinned-only mode was enabled:

  ```cpp
  if (group.sessions.isEmpty()) {
      filtered.append(group);
      continue;
  }
  ```

- **Why that is wrong:** Enabling “pinned only” could still show a group containing no pinned session. That contradicted the filter label and made an unrelated empty group appear in the sidebar.
- **The fix:** Empty groups are retained only for the normal view. Pinned-only mode drops them:

  ```cpp
  if (group.sessions.isEmpty()) {
      if (!pinnedOnly)
          filtered.append(group);
      continue;
  }
  ```

  The regression test verifies that the empty group disappears and the populated group remains.
- **Status:** fixed

### MP2 — Item-model methods accepted foreign and stale indexes

- **Severity:** active bug
- **File and line(s):** `src/models/SessionsModel.cpp:205-304`; test `src/models/tests/tst_models.cpp:1434-1451`
- **What the code does now:** Before the fix, `index()`, `parent()`, `rowCount()`, and `data()` trusted the incoming `QModelIndex` model, column, internal identifier, and row. A model index from another `SessionsModel`, or an index whose row had become stale after a reset, could be interpreted as an index into this model.
- **Why that is wrong:** Qt views and delegates can pass indexes from another model or retain indexes across model changes. Trusting those values could expose another model's row, read outside the current group, or create a parent/child relationship that did not belong to this model. It also violated the `QAbstractItemModel` contract.
- **The fix:** Every entry point now validates the model and column, checks the top-level sentinel, bounds-checks group and session rows, and rejects oversized internal identifiers before converting them to `int`:

  ```cpp
  if (parent.isValid() && parent.model() != this)
      return {};
  if (!hasIndex(row, column, parent))
      return {};
  ```

  ```cpp
  if (parent.model() != this || parent.column() != 0)
      return 0;
  if (parent.internalId() != kTopLevel)
      return 0;
  if (parent.row() < 0 || parent.row() >= groups_.size())
      return 0;
  ```

  ```cpp
  if (!index.isValid() || index.model() != this || index.column() != 0)
      return {};
  ```

  The test passes foreign indexes to all four methods and verifies that they are rejected.
- **Status:** fixed

### MP3 — Palette expansion could index past a one-colour seed

- **Severity:** active bug
- **File and line(s):** `src/models/GroupPalette.cpp:186-227`; test `TstModels::paletteHandlesSingleSeedAndNonFiniteValues` in `src/models/tests/tst_models.cpp`
- **What the code does now:** Before the fix, palette generation selected two entries (`first = 0`, `second = 1`) and eventually interpolated `converted.at(second)` without handling a one-colour seed. `canGenerate()` correctly allowed a one-colour seed when a second colour was requested.
- **Why that is wrong:** A valid user preference containing one seed colour could take the out-of-range path. In a debug build Qt can abort on the vector bounds assertion; in a release build the access is invalid and can corrupt the result or crash.
- **The fix:** A one-colour palette now takes a separate deterministic diversification path before any pair selection:

  ```cpp
  if (converted.size() < 2) {
      palette.append(oklchToSrgb(diversified(converted.first())));
      continue;
  }
  ```

  The test requests two colours from a one-colour seed and checks the result is finite and in the sRGB range.
- **Status:** fixed

### MP4 — Non-finite OKLCH input produced non-finite colours

- **Severity:** latent bug
- **File and line(s):** `src/models/GroupPalette.cpp:29-34,157-178`; test `TstModels::paletteHandlesSingleSeedAndNonFiniteValues`
- **What the code does now:** Before the fix, `oklchToSrgb()` passed caller-provided lightness, chroma, and hue directly through the conversion. NaN values could survive the arithmetic and return NaN colour channels; infinities could make intermediate values infinite.
- **Why that is wrong:** Palette settings come from editable preferences. A malformed settings value could propagate NaN into QML colour properties, making the palette unusable and making later comparisons or serialization unreliable.
- **The fix:** The conversion now maps non-finite values to safe defaults and clips finite components at the conversion boundary:

  ```cpp
  const double lightness = clamp01(color.lightness);
  const double chroma = std::isfinite(color.chroma)
          ? std::clamp(color.chroma, 0.0, 1.0)
          : 0.0;
  const double hue = std::isfinite(color.hue) ? normalizeHue(color.hue) : 0.0;
  ```

  `clamp01()` itself rejects non-finite input, and the test verifies that all returned RGB channels are finite and bounded.
- **Status:** fixed

### MP5 — Zero-sized palette lookup asserted before its fallback

- **Severity:** footgun

- **Why that is wrong:** Palette size is ultimately a user preference. A zero-sized or temporarily uninitialized palette should use the documented fallback, not terminate a debug application before the fallback can run.

### MP6 — Split ratios could overflow their sum

- **Severity:** active bug
- **File and line(s):** `src/models/SplitTree.cpp:46-64,184-205`; test `src/models/tests/tst_models.cpp:420-435`
- **What the code does now:** Before the fix, parsing and serialization checked that each ratio was finite and positive, but did not check whether the sum of individually finite ratios overflowed to infinity.
- **Why that is wrong:** Pane geometry uses each ratio divided by the sum. If the sum is infinite, every normalized extent becomes zero or otherwise invalid. A remote or hand-edited layout with two maximum floating-point ratios could therefore load as a tree that cannot lay out its panes.
- **The fix:** Both parser and serializer accumulate the sum and reject it as soon as it becomes non-finite, while still requiring a positive final sum:

  ```cpp
  ratioSum += ratio;
  if (!std::isfinite(ratioSum))
      return false;
  ```

  ```cpp
  if (ratioSum <= 0.0)
      return false;
  ```

  The test covers overflow on both read and write paths.
- **Status:** fixed

### MP7 — Unknown split orientations silently became horizontal

- **Severity:** active bug
- **File and line(s):** `src/models/SplitTree.cpp:74-88,161-168`; test `src/models/tests/tst_models.cpp:399-418`
- **What the code does now:** Before the fix, serialization used a horizontal fallback for any orientation other than vertical, and parsing treated any string other than `"vertical"` as horizontal. Missing, misspelled, or future orientation values were therefore accepted as a different layout.
- **Why that is wrong:** A corrupted or newer remote layout could be silently rewritten with the wrong pane arrangement. The user would see a valid-looking layout that no longer matched the saved tree, making the original error difficult to diagnose.

  ```cpp
  switch (node.orientation) {
  case SplitOrientation::Horizontal:
      orientation = QStringLiteral("horizontal");
      break;
  case SplitOrientation::Vertical:
      orientation = QStringLiteral("vertical");
      break;
  default:
      return false;
  }
  ```

  ```cpp
  else if (orientation == QStringLiteral("vertical"))
      node.orientation = SplitOrientation::Vertical;
  else
      return false;
  ```

  Tests cover unknown and missing orientation values in both directions.
- **Status:** fixed

### MP8 — Custom-title truncation could leave an invalid UTF-16 surrogate

- **Severity:** latent bug
- **File and line(s):** `src/models/SplitTree.h:63-78`; test `src/models/tests/tst_models.cpp:1606-1632`
- **What the code does now:** Before the fix, truncation removed a final high surrogate but did not remove a final low surrogate that had no matching high surrogate. A 128-code-unit title could therefore be persisted with a dangling low surrogate.
- **Why that is wrong:** `QString` stores UTF-16 code units, while JSON and user-visible pane headers need valid Unicode text. A dangling surrogate can be replaced, rejected, or displayed inconsistently by Qt, the JSON encoder, or the remote service.
- **The fix:** After trimming to the limit, the normalizer removes either a final high surrogate or a low surrogate that is not preceded by a high surrogate:

  ```cpp
  const int last = title.size() - 1;
  if (last >= 0
      && (title.at(last).isHighSurrogate()
          || (title.at(last).isLowSurrogate()
              && (last == 0 || !title.at(last - 1).isHighSurrogate()))))
      title.chop(1);
  ```

  Tests cover a complete supplementary character at the boundary and a lone low surrogate.
- **Status:** fixed

### MP9 — Malformed record responses became blank records

- **What the code does now:** Before the fix, record decoders returned default-constructed model values for `{}` or an object with no usable identity. The generic response handler checked only that the JSON result was an object, then passed the default record to the callback.

### MP10 — Wrong-shaped nested arrays were silently treated as empty

- **Severity:** active bug
- **File and line(s):** `src/persistence/WorkspaceDb.cpp:132-191,203-215`; test `src/persistence/tests/tst_workspacedb.cpp:759-804`
- **What the code does now:** Before the fix, calling `toArray()` on a scalar or object yielded an empty array, and calling `toObject()` on a scalar or array yielded an empty object. A response such as `"viewerPanes": {}` therefore looked like a session with no viewer panes, and malformed nested entries could become default records.
- **Why that is wrong:** The client could show an incomplete workspace while reporting success. A malformed server response and a genuinely empty workspace became indistinguishable, and bad nested records could leak into the model.
- **The fix:** Optional arrays are now type-checked before conversion. Nested entries must be JSON objects and must pass the identity-checked record parser; malformed entries are dropped, while a wrong array shape rejects the containing record:

  ```cpp
  bool readOptionalArray(const QJsonObject &obj, const QString &key, QJsonArray &out)
  {
      if (!obj.contains(key))
          return true;
      const QJsonValue value = obj.value(key);
      if (!value.isArray())
          return false;
      out = value.toArray();
      return true;
  }
  ```

  ```cpp
  if (!readOptionalArray(obj, QStringLiteral("viewerPanes"), viewers))
      return std::nullopt;
  for (const QJsonValue& viewer : viewers) {
      if (!viewer.isObject())
          continue;
      const std::optional<ViewerPane> pane = parseViewerPane(viewer.toObject());
      if (pane)
          node.viewerPanes.append(*pane);

  ```

  The regression fixture includes scalar, null, object, and malformed nested entries and verifies that only the valid pane records remain.

### MP11 — Strong identifier wrappers could not be used as hash keys

- **Severity:** footgun
- **File and line(s):** `src/models/Ids.h:13-62`; test `src/models/tests/tst_models.cpp:1740-1763`
- **What the code does now:** Before the fix, the five strong identifier structs defined equality but no `qHash()` overload. Any code that wanted a `QHash<GroupId, ...>` or equivalent had to unwrap the value to `QString`, losing the type distinction or failing to compile.
- **Why that is wrong:** These wrappers exist to prevent mixing identifier kinds. Requiring callers to unwrap them makes that protection optional and encourages untyped maps in precisely the code that indexes sessions, panes, and terminals.
- **The fix:** Each wrapper now hashes its underlying string while preserving the wrapper type at call sites:

  ```cpp
  inline size_t qHash(const GroupId &id, size_t seed = 0) noexcept
  {
      return ::qHash(id.value, seed);
  }
  ```

  Equivalent overloads exist for `DevSessionId`, `ViewerPaneId`, `TerminalId`, and `ServerId`. The test uses all five wrappers as `QHash` keys.
- **Status:** fixed

## `src/app` core — the application controller, settings, logging and notifications

### AC1 — Injected Qt objects could dangle during late callbacks

- **Severity:** active bug
- **File and line(s):** `src/app/AppController.h:266-302`; `src/app/AppController.cpp:168-230, 232-414`
- **What the code does now:** Before this sweep, the controller kept injected monitors, factories, and connection-spine objects as raw pointers. Their signal handlers and delayed server callbacks dereferenced those pointers after the owning object could already have been destroyed. The risk was especially high during application shutdown, because the stack objects in `main()` are intentionally destroyed in a different order from the controller.
- **Why that is wrong:** A monitor/factory or connection object destroyed while a queued signal or `server.info` reply is still pending could leave the controller reading freed memory. This is a use-after-free that is timing-dependent and can crash on exit or during test reconfiguration.
- **The fix:** The injected QObject references are now guarded and callbacks use lifetime checks. The relevant declarations are:
  ```cpp
  QPointer<AgentStatusMonitor> m_agentMonitor;
  QPointer<TerminalFactory> m_terminalFactory;
  QPointer<EditorFactory> m_editorFactory;
  QPointer<SshConnectionPool> m_pool;
  QPointer<SessionBootstrap> m_bootstrap;
  QPointer<ServerProfiles> m_profiles;
  QPointer<SessionLayouts> m_layouts;
  ```
  Async operations also capture `QPointer<AppController>` and return when it is null.
- **Status:** fixed

### AC2 — Workspace replies could outlive the controller or overwrite newer data

- **Severity:** active bug
- **File and line(s):** `src/app/AppController.h:232-249`; `src/app/AppController.cpp:1184-1309`
- **What the code does now:** Every mutation asks `WorkspaceDb` to refresh the authoritative workspace. Multiple list requests can be outstanding, and callbacks can remain alive in the shared RPC client after the controller is gone. The old callbacks captured `this` directly and accepted results without a generation check.
- **Why that is wrong:** A late reply could call methods on a destroyed controller. Even without destruction, an older response could arrive after a newer response and put stale groups and sessions back into the sidebar.
- **The fix:** The common mutation callback now captures a guarded pointer, and refreshes carry a monotonic generation:
  ```cpp
  QPointer<AppController> self(this);
  return [self](Payload..., std::optional<RpcError> err) {
      if (!self)
          return;
      if (self->reportIfError(err))
          return;
      self->refresh();
  };
  ```
  ```cpp
  const quint64 generation = ++m_refreshGeneration;
  QPointer<AppController> self(this);
  ...
  if (generation != self->m_refreshGeneration)
      return;
  ```
  The tests `refreshResultAfterControllerDestroyedIsNoop()` and `staleRefreshResultDoesNotClobberNewer()` defend both contracts.
- **Status:** fixed

### AC3 — Terminal status cache retained closed panes and old factories

- **Severity:** latent bug
- **File and line(s):** `src/app/AppController.cpp:193-222, 1228-1257`; `src/app/AppController.h:270-275`
- **What the code does now:** Terminal lifecycle state is keyed by server Dev Session id and terminal-pane row id. The cache is cleared when the injected factory changes, and each successful authoritative workspace read removes sessions and pane ids no longer present in that tree.
- **Why that is wrong:** Without eviction, closing a pane left its status in memory. A later pane with a reused id, or a new connection using the same ids, could inherit the old `Ready`/`Disconnected` state and paint a false sidebar status. Keeping state from a replaced factory also let a reconfigured graph inherit stale statuses.
- **The fix:** The cache now follows the current source and authoritative tree:
  ```cpp
  m_terminalStates.clear();
  m_terminalFactory = factory;
  ```
  ```cpp
  for (auto sessionIt = self->m_terminalStates.begin();
       sessionIt != self->m_terminalStates.end();) {
      ...
      if (!liveSessionIt->contains(stateIt.key()))
          stateIt = states.erase(stateIt);

  ```
  Events are still stamped with the current server id before they are merged. `terminalConnectionStateMergesIntoSidebar()` covers the live-state path and stale-server events are ignored.

### AC4 — Disconnect teardown used a raw object in a re-entrant scope guard

- **Severity:** active bug
- **File and line(s):** `src/app/AppController.cpp:834-910`
- **What the code does now:** Disconnecting the session synchronously emits bootstrap state signals and fails pending RPC requests. A listener is allowed to destroy the controller while those signals are being delivered. The old scope guard captured raw `this` and the function also continued after `activeSessionChanged()`.
- **Why that is wrong:** If a signal handler deleted the controller, the scope guard would later write `m_tearingDown` through freed storage. The function could also emit connection state through a destroyed object. This makes a normal disconnect path crash only when a re-entrant listener runs.
- **The fix:** The guard and all post-signal work use a `QPointer`:
  ```cpp
  QPointer<AppController> self(this);
  const auto restore = qScopeGuard([self] {
      if (self)
          self->m_tearingDown = false;
  });
  ...
  emit activeSessionChanged();
  if (!self)
      return;
  ```
  Pending state is cleared before teardown, so a held credential or host-key attempt cannot leak into the next connection.
- **Status:** fixed

### AC5 — Refusing an incompatible server could use `this` after the error signal

- **Severity:** active bug

### SSH2 — `canReadLine()` ignored the channel’s private read buffer
- **Severity:** active bug
- **File and line(s):** `src/ssh/SshChannelDevice.h:75-84`; `src/ssh/SshChannelDevice.cpp:62-74`; `src/ssh/tests/tst_livessh.cpp:194-211`
- **What the code does now:** The channel stores received bytes in `m_readBuffer`, but the class did not override `QIODevice::canReadLine()`. The base implementation only knows about QIODevice’s own buffer, which is empty because this device is unbuffered.
- **Why that is wrong:** A consumer using the normal QIODevice line-reading contract could receive `readyRead()`, see a complete newline in the SSH buffer, and still get `false` from `canReadLine()`. It would fail to read a complete JSONL or terminal line until some unrelated event occurred.

### SSH3 — A continuously noisy remote could monopolize the Qt event loop and grow memory without bound
- **Severity:** active bug
- **File and line(s):** `src/ssh/SshChannelDevice.cpp:11-21, 430-454`
- **What the code does now:** The read pump repeatedly called `ssh_channel_read_nonblocking()` until the channel reported no data. It could remain in one timer callback forever for a command such as `yes`, and it appended all stdout into an unbounded QByteArray when the consumer stopped reading.
- **Why that is wrong:** A remote process can starve the GUI/event loop and make the client retain unbounded output. This affects both responsiveness and process memory safety.
- **The fix:** Each stream is limited to `kMaxPumpBytes` per pass, so the timer yields. The readable buffer is capped at `kMaxReadBufferBytes` (8 MiB); once full, the SSH channel’s own flow-control window provides backpressure. New code includes `constexpr qsizetype kMaxPumpBytes = 256 * 1024;` and bounds stdout reads by `kMaxReadBufferBytes`.

### RPC1 — A synchronous write could orphan a response callback

- **Severity:** active bug
- **File and line(s):** `src/remote/CodeharbordClient.cpp:305-349`; regression test `src/remote/tests/tst_rpcclient.cpp:1419-1448`
- **What the code did before the fix:** The client wrote the JSON line first and inserted the callback afterward. The relevant sequence was effectively:

  ```cpp
  const qint64 written = m_transport->write(line);
  // ...
  m_pending.insert(id, std::move(cb));
  ```

  A `QIODevice` implementation is allowed to emit `readyRead()` or a close signal synchronously from `writeData()`. In that case, the response or close was processed while the request ID was absent from `m_pending`.
- **Why that was wrong:** A synchronous response was warned as an unknown ID and the caller's callback remained pending forever. A synchronous close could also finish the transport-loss sweep before this request was registered, leaving a callback that could never fire. If a synchronous response callback deleted the client, the later insertion was a use-after-free.
- **The fix:** The callback is now registered before the write, and the write-failure path removes it again if the write does not complete:

  ```cpp
  const QPointer<QIODevice> writeTransport = m_transport;
  ```

### RPC2 — The line-size cap was bypassed by delimited oversized frames and by `readAll()`

- **Severity:** active bug
- **File and line(s):** `src/remote/CodeharbordClient.cpp:352-488`; regression tests `src/remote/tests/tst_rpcclient.cpp:1661-1690` and `1335-1368`
- **What the code did before the fix:** `onReadyRead()` called `readAll()`, then checked the cap only after all complete lines had already been dispatched. Consequently, a line larger than 16 MiB was accepted if it ended in a newline. The old check only rejected an unterminated remainder.
- **Why that was wrong:** A peer could send a complete oversized JSON frame and force the client to allocate and parse it even though the protocol says the stream is no longer trustworthy above the cap. `readAll()` also allowed the temporary read result itself to be arbitrarily large before the cap check ran. This defeated the memory bound the cap was intended to provide.
- **The fix:** Reads are limited to one cap-sized chunk, and a complete line is rejected before it is copied or parsed:

  ```cpp
  m_readBuffer.append(m_transport->read(kMaxLineBytes + 1));
  // ...
  if (newline - m_readPos > kMaxLineBytes) {
      m_readBuffer.clear();
      m_readPos = 0;
      m_scanOffset = 0;

          QStringLiteral("RPC line exceeded %1 bytes; resetting "
                         "transport")

      if (!self)
          return;
      if (m_transport == sourceTransport && !m_closed)
          onTransportClosed();
      return;
  }
  ```

  If a valid burst spans several bounded reads, a queued `onReadyRead()` drains the remaining bytes. `oversizedDelimitedInputIsRejected()` covers a newline-terminated over-cap line, and `closeDrainProcessesAllBoundedChunks()` covers a response that is beyond the first bounded chunk during EOF handling.
- **Status:** fixed

### RPC3 — A close callback could reconnect and then receive a stale close signal

- **Severity:** active bug
- **File and line(s):** `src/remote/CodeharbordClient.cpp:700-748`; regression test `src/remote/tests/tst_rpcclient.cpp:1040-1078`
- **What the code did before the fix:** `onTransportClosed()` failed pending callbacks and then unconditionally emitted `transportClosed()`. A failure callback could call `setTransport()` and bind a new device before the old close handler reached that emit.


### RPC4 — EOF handling stopped after one bounded read

- **Severity:** active bug
- **File and line(s):** `src/remote/CodeharbordClient.cpp:700-719`; regression test `src/remote/tests/tst_rpcclient.cpp:1335-1368`
- **What the code did before the fix:** The last-gasp close path called `onReadyRead()` once. After reads became bounded, that was no longer enough to consume every byte already waiting in a device.
- **Why that was wrong:** A complete response in the second read-sized chunk was discarded when the close path immediately cleared the buffer and failed pending calls. A response that physically arrived before EOF could therefore be reported as a transport failure.
- **The fix:** The close path now repeats the bounded read while each iteration makes progress, while still stopping if the device changes, closes, or the client is destroyed:

  ```cpp
  while (m_transport && m_transport->bytesAvailable() > 0) {
      const qint64 availableBefore = m_transport->bytesAvailable();
      onReadyRead();
      if (!self || m_closed)
          return;
      if (m_transport != closingTransport)
          return;
      if (m_transport->bytesAvailable() >= availableBefore)
          break;
  }
  ```

  `closeDrainProcessesAllBoundedChunks()` places a response after a full first chunk and verifies that it is delivered before `transportClosed()`.
- **Status:** fixed

### RPC5 — Responses with the wrong or missing JSON-RPC version were accepted

### RPC6 — Heartbeat failure could invoke a callback through a destroyed client

### RPC7 — Request IDs could collide after sequence wraparound

- **Severity:** latent bug
- **File and line(s):** `src/remote/CodeharbordClient.cpp:234-241`
- **What the code did before the fix:** ID allocation advanced from the current counter and wrapped directly to 1. If the wrapped value were still in `m_pending`, a new request could reuse an existing ID.

  ```cpp
  if (!m_recoveryClearPending || m_recoveryWritesInFlight > 0)
      return;
  m_recoveryClearPending = false;
  clearRecovery();
  ```
  and:
  ```cpp
  if (m_recoveryClearInFlight)
      return;
  ```

- **Why that was wrong:** A save could start a truncate, a newer report could write a new snapshot, and a second save could finish while those operations overlapped. ### VW1 — Failure signal could invalidate the WebEngine request job

- **Severity:** active bug
- **File and line(s):** `src/viewers/InternalUrlSchemeHandler.cpp:326-335,406-416`
- **What the code did:** Each refusal emitted `requestFailed` and then called `job->fail(error)`. A slot receiving `requestFailed` could synchronously destroy the WebEngine view and its `QWebEngineUrlRequestJob` before the second statement ran.

  ```cpp
      guard->fail(error);
  ```

  The asynchronous path applies the same check after its signal. This preserves the user-facing error while making cancellation safe.

### VW2 — Alternate authorities were accepted for internal resources

  ```ts
  ...

  ```

### BD10 — WITHDRAWN: the misspelled variable in the libssh patch is not a bug

**Severity:** withdrawn — not a defect
**File and line(s):** `packaging/vcpkg-ports/libssh/0001-export-pkgconfig-file.patch:10`

**What was reported:** One line of the patch names a variable with three consecutive `S`
characters, while the rest of the file uses two:

> `set(LIBSSSH_PC_REQUIRES_PRIVATE "")`
> `string(APPEND LIBSSH_PC_REQUIRES_PRIVATE "zlib")`
> `Requires.private: @LIBSSH_PC_REQUIRES_PRIVATE@`

The report claimed the generated description of the library would therefore be missing the
libraries it needs to link against, and the spelling was changed to two `S`.

**Why the report was wrong, on two counts.** First, the claimed consequence does not
follow. In CMake, `string(APPEND ...)` creates a variable that does not yet exist, so the
correctly spelled variable is populated regardless and the generated file is correct. The
misspelled line is simply dead.

Second, and far worse, the line must not be touched at all. It is a *context* line of a
patch: it is quoted from the original library source so that the patch tool can find its
place, and it must match that source exactly. The misspelling is genuinely present
upstream — libssh 0.12.2's own build file has it on line 44. Changing it stops the patch
matching, and the edit also removed the single leading space that marks the line as
context, which by itself makes the patch tool reject the whole thing.

**Outcome:** The change was reverted, so the file is byte-for-byte identical to the version
that last released successfully, and a comment was added next to it explaining why these
patches must never be "corrected". This is recorded in full as `ORCH10`, together with the
failed release it caused and the new automated check (`ORCH15`) that now prevents a
repeat.

**Status:** withdrawn and reverted; see `ORCH10`

### ORCH1 — A signal arriving while the remote service was already leaving killed it

- **Severity:** latent bug (pre-existing)
- **File and line(s):** `remote/src/codeharbord.ts:802-821`; test `remote/test/files.test.ts:1518-1597`
- **What the code did:** When told to stop, the remote service releases its file watches,
  stops reading requests, sets its exit status to zero and then lets the program end
  naturally once there is nothing left to do. It deliberately keeps its signal handlers
  installed so that a second stop signal is simply ignored, and there is a comment
  explaining that removing them would let a second signal kill the process.
- **Why that was wrong:** Keeping the handlers installed is not enough. When Node ends
  because there is no work left, it first shuts down its own internal signal watchers and
  only then finishes taking the process apart. A signal that arrives inside that gap finds
  no handler and kills the process. Anything supervising the service then records "died on
  a signal" instead of "stopped cleanly" — which is exactly the distinction a supervisor
  uses to tell a clean stop from a crash loop, and exactly what the existing code was
  written to guarantee. It is easy to trigger: a supervisor that sends one stop signal and,
  a few tens of milliseconds later, an impatient second one.
  I measured it rather than assumed it. A test for this already existed and was passing, but
  only because it sent all its signals in one tight burst; under load the bursts spread out
  and the test failed roughly one run in five. Reverting to the pre-sweep version of the
  file showed the same failure rate, confirming this was not introduced by this round.
- **The fix:** The service now leaves through an explicit exit rather than by running out of
  work. `process.once("beforeExit", () => process.exit(process.exitCode ?? 0))` is armed as
  part of shutting down. `beforeExit` fires at exactly the moment the program would have
  ended naturally — every request handler has finished and every write has been flushed,
  because either would still be keeping it alive — and exiting from there skips the orderly
  teardown that opens the gap, so the handlers stay armed until the process is gone.
- **Proof:** A stress harness that started the service, answered a request, then signalled
  it repeatedly showed 8 failures in 40 runs before and 0 in 40 after. The existing test was
  also rewritten to keep signalling every few milliseconds until the process is actually
  gone, so it lands in the gap deliberately instead of by luck: it now fails 15 times out of
  15 with the fix removed, and passes 15 out of 15 with it.
- **Status:** fixed

### ORCH6 — Building one preset left the other one unbuildable

- **Severity:** footgun (pre-existing, made visible by this round)
- **File and line(s):** `src/qml/CMakeLists.txt:278-298`
- **What the code did:** The three small web pages the application embeds — the terminal, the
  code editor and the Markdown viewer — are built by the configure step, into one output
  directory per page that every build shares. A debug configure asks for "source maps", the
  extra files that let a browser's developer tools show original source; a release configure
  does not. The exact list of files to embed is decided during configure. Only the *inputs*
  to those pages were registered as things that should trigger a fresh configure.
- **Why that was wrong:** Configuring or building the release preset rewrites that shared
  directory without source maps, which deletes files the debug build's plan still refers to.
  Nothing then asks the build system to look again, so the next debug build stops with
  `editor.js.map ... missing and no known rule to make it`. That is a dead end, because the
  only thing that can produce that file is the configure step, which is not going to run.
  Anyone who builds a release and then goes back to debugging hits it. I hit it myself
  during this round.
- **The fix:** The embedded output files are now registered as reconfigure triggers as well
  as the inputs. Deleting them makes the next build re-run configure, which rebuilds the
  pages the way that build wants them. It cannot loop, because the pages are rebuilt during
  configure and so are always older than the marker configure writes when it finishes.
- **Proof:** I reproduced the failure, applied the fix, then ran the exact sequence again:
  the release build removes the source maps (three files, then none), and the following
  debug build re-runs configure automatically, restores all three, and succeeds.
- **Status:** fixed

### ORCH10 — A "typo fix" corrupted a patch and broke the Windows build

- **Severity:** active bug (introduced by this round; caught by a failed release build)
- **File and line(s):** `packaging/vcpkg-ports/libssh/0001-export-pkgconfig-file.patch:10`;
  explanation added to `packaging/vcpkg-ports/libssh/portfile.cmake:12-22`
- **What the code did:** The Windows installer builds its own copy of the SSH library from
  source and applies four patches to it. One line of one patch reads
  `set(LIBSSSH_PC_REQUIRES_PRIVATE "")` — with three S where the rest of the file uses two.
  A reviewer corrected the spelling.
- **Why that was wrong:** Two separate faults in one small edit. First, a patch of this kind
  is a description of a file: lines that begin with a space are *context*, quoted from the
  original so the patch tool can find its place, and they must match the original exactly.
  The misspelling is genuinely present in the upstream library — I downloaded version 0.12.2
  and confirmed the typo is on line 44 of its build file — so correcting it stops the patch
  matching. Second, the edit also removed the single leading space that marked the line as
  context, which by itself makes the patch tool reject the whole thing as corrupt. That is
  what actually happened: the Windows release build stopped during extraction with
  `corrupt patch at ...:10`, before anything was compiled. The upstream misspelling is in
  any case harmless — the line it initialises is simply never used again.
  This had been invisible because the Windows machine reuses a cached copy of the built
  library. Another fix from this round (`BD9`) added the patch directory to the key for that
  cache, which is what made the machine apply the patch again and expose the damage.
- **The fix:** The line is restored, and the file is now byte-for-byte identical to the
  version that last released successfully. A prominent comment in the neighbouring
  `portfile.cmake` explains why these patches must never be "corrected".
- **Proof:** Not by inspection this time. I downloaded libssh 0.12.2, checked its checksum
  against the one the project pins, and applied all four patches to it with `git apply`. All
  four apply cleanly, and the patched result substitutes the correctly spelled variable into
  the generated file as intended.
- **Status:** fixed

### ORCH11 — The Windows installer script would not compile

- **File and line(s):** `packaging/windows/codeharbor.iss:171-219`
- **What the code did:** This round added a safety check to the installer (see `BD11`): before

### ORCH16 — A log route identified its owning thread by a number the system reuses

- **Severity:** active bug (introduced by this round; observed only on Windows)
- **File and line(s):** `src/ssh/SshConnectionPool.h:122-135, 157-161`;
  `src/ssh/SshConnectionPool.cpp:78-82, 114-120, 154-160`; test
  `src/ssh/tests/tst_sshlogrouter.cpp`
- **What the code did:** The SSH library has exactly one place to hook its diagnostic output,
  so CodeHarbor installs a router that hands each component only its own lines. The router
  saves the previous logging settings for a thread and must put them back when that thread's
  last user goes away, so it records which thread claimed each route. It recorded the
  operating system's own thread number.
- **Why that was wrong:** An operating system may reuse a thread number as soon as the thread
  it belonged to has finished, and Windows does so eagerly. A route can outlive the thread
  that took it. So a route belonging to a thread that no longer exists could be compared
  against a live, entirely unrelated thread that had been given the same number, be judged
  to belong to it, and take the "same thread" path — tidying that other thread's list of
  routes and restoring saved logging settings that were never its own. Linux does not reuse
  numbers over the few hundred milliseconds a test run takes, which is why only Windows
  showed it. It was intermittent, as reuse is a matter of timing.
- **The fix:** Ownership is now a process-wide counter value that is never handed out twice,
  held both in per-thread state and in each route, so a later thread cannot match it
  whatever the operating system does with numbers.
- **Two wrong diagnoses before the right one, recorded because the process matters more
  than the answer.** This fix did not stop the Windows failure. I believed it had, because
  the next three Windows runs passed — but at a rate of roughly two failures in five, three
  passes in a row happen about one time in five by chance, so that was never evidence. It
  failed again on a commit that changed nothing but a Markdown file.
  My second diagnosis was also wrong. I reasoned that the test produced no output because
  the process had crashed before its output was flushed, and concluded it was crashing
  during shutdown. That produced `SSH20`, which is a genuine latent bug and worth having,
  but it was not this.
  The right answer only came once I made the automated build repeat a failed test until it
  failed again. That showed the eight passing runs each took **55.17 seconds**, to the
  hundredth of a second, against a tenth of a second here — and the failing run took 0.15
  seconds. A constant like that is a network timeout being waited out. Three of these tests
  connected to port 1 on the local machine purely to provoke some log output. That is
  refused instantly on some machines and left hanging until a timeout on others; when it was
  refused instantly there was no output to route and the test failed. Recorded as `SSH25`,
  and the tests now feed the router directly instead of touching the network.
- **What each fix was worth:** this one removes a real unsound comparison; `SSH20` removes a
  real shutdown-ordering hazard; `SSH25` is what actually cured the failure and also removed
  55 seconds of dead waiting from every Windows run. Chasing it also turned up `SSH24` — the
  test added for this very bug had no declaration, so it had never run at all.
- **Status:** fixed; see `SSH25` for the actual cause of the observed failure

  seam for substituting a fake one. Adding that seam would be a larger design change than
  this review should make unannounced. The behaviour is covered indirectly by the live SSH
  tests.
* **`VW14`** — the Markdown viewer's protection against a slow load from one document
  overwriting a newer one is implemented and type-checked, but has no automated test,
  because the current test setup cannot load the browser page's entry point without a
  browser and a stylesheet loader.
* **`RPC11`** — the desktop side does not name the five standard protocol error numbers that
  the remote side names. This is deliberate: they are the standard JSON-RPC numbers, the
  desktop side passes any number it receives through unchanged, and adding unused constants
  would not change behaviour. Recorded so the asymmetry is not mistaken for an oversight.
* **`SSH23`** — a route released from a thread other than the one that took it can still
  have a log line in flight, which is then delivered after the release has returned, to
  something that may already be gone. Two repairs were considered. Making the release wait
  for deliveries in progress would put a wait inside the SSH library's logging path, which
  is entered from arbitrary places inside that library including its own shutdown, and
  getting it wrong would deadlock the whole SSH stack — worse than the fault. Keeping the
  destination object alive does not help, because what it refers to can still be destroyed.
  A correct repair needs a proper ownership and synchronisation design, which is not
  something to bolt on at the end of a review. It also requires a caller to break the
  documented rule about which thread releases a route, which already produces a loud
  warning. The analysis is recorded in full at `SSH23` so the next maintainer inherits it.
