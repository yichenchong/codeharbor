## RD — Daemon output and local control sockets

**Post-fix check:** Passed in the final remote suite; the remote TypeScript typecheck and compiled daemon build also passed.

### RD1 — Medium: bridge output failure was not terminal for future producers

- **Location:** `remote/src/bridge.ts`, `makeStreamSink` (approximately line 461; output error listener/write catch).
- **Prior behavior/scenario:** An output `'error'` destroyed sockets already paused at that instant, but a new producer arriving afterward still called the failed stream's `write()`. A false return paused that new socket waiting for a drain that would never happen. Separately, a synchronous write throw destroyed only the current producer, leaving other paused producers retained forever if the writable did not subsequently emit `'error'`.
- **Root cause:** No persistent failed-output state, and synchronous versus emitted failure used different cleanup paths.
- **Fix:** Added sticky failure state and one failure cleanup closure; both output `'error'` and throwing `write()` release all stalled producers. Subsequent producers are destroyed without writing; a later spurious drain does not resume them.
- **Tests:** Added `a bridge output error disconnects both stalled and future producers` and `a throwing bridge output releases producers already awaiting drain` to `agent-hook.test.ts` (near existing sink tests around line 830 after the new startup regression). Cases assert producer disconnection, no post-failure writes, no drain resurrection, and cleanup of an earlier stalled source after a later source's throwing write.
- **Residual risk:** Output failure remains fatal to that sink instance, deliberately; reconnecting transport must construct a new sink. Existing per-source backpressure and server connection cap are unchanged.

### RD2 — Medium: a producer's request FIN canceled an asynchronous viewer answer

- **Location:** `remote/src/control.ts`, `startControlListener`, server creation and producer `'end'` handler (approximately lines 427 and 532).
- **Prior behavior/scenario:** A conventional Unix-socket producer could send its one newline-terminated request with `socket.end(payload)` and continue reading. Node's default `allowHalfOpen: false` ended the daemon's writable half upon the producer FIN, closing the connection before a later desktop result and releasing its pending command. The requester got no answer despite a valid accepted operation.
- **Root cause:** Transport read EOF was implicitly treated as full bidirectional cancellation even when the protocol's response was asynchronous. The existing `answer()` also immediately called `destroySoon()` after `socket.end()`, prematurely closing the readable half while later producer bytes/FIN were still arriving and causing ECONNRESET.
- **Fix:** Listener allows half-open sockets. Complete requests retain their writable half until result/timeout/shutdown. Incomplete-request EOF explicitly destroys the socket. The final production change removes `destroySoon()` from `answer()`: `socket.end()` now permits incoming bytes/FIN to drain naturally. An absolute, unref'd close deadline using the existing handshake duration bounds peers that refuse to finish; its timer is cleared on close.
- **Tests:** Added real Unix-socket half-close round trip and incomplete-EOF cleanup coverage in `control.test.ts`. The strengthened regression changed the existing later-packet test to collect and parse the exact first response, while asserting only one command was relayed and pending count returned to zero. The earlier reset-tolerant close observer workaround is superseded, not accepted as a fix.
- **Residual risk:** A FIN after a complete request is necessarily treated as a possible legitimate half-close, not immediate cancellation. If the peer actually abandons both sides without an observable reset, its entry can remain until the existing bounded five-second request timeout. This is intrinsic to preserving half-close replies; in-flight/connection limits remain intact.

**Final integration detail:** A strengthened real-socket test first failed with ECONNRESET after the response writer called destroySoon(). After removing that premature destruction and retaining a bounded close deadline, the focused control/protocol checks passed 65/65, followed by the complete 457-test remote run. The test parses the first real reply; it does not ignore connection resets.

### RD3 — Low: the control framing limit counted the newline and ignored suffix against the wrong boundary

- **Location:** `remote/src/control-client.ts`, `sendControlRequest` size preflight (line 169); `remote/src/control.ts`, data framing (approximately line 461).
- **Prior behavior/scenario:** A valid JSON request with a payload of exactly `MAX_CONTROL_LINE_BYTES` was refused by the producer because it counted the framing newline. The listener likewise compared its entire buffered chunk, including newline and any later ignored bytes, before finding the first frame boundary; acceptance could therefore depend on packet coalescing rather than the first request's actual size.
- **Root cause:** Full serialized/received buffers were measured instead of the first JSON payload.
- **Fix:** Client excludes its single framing newline; listener locates the first newline and measures only the payload preceding it, preserving the one-request-per-connection rule. The constant's comment states the payload-only convention, consistent with RPC framing.
- **Tests:** Added exact-limit real producer/listener round trip in `control.test.ts` around line 379; consumer result and relayed padding are asserted. Its harness immediately settles valid commands so a preflight regression produces an assertion failure instead of waiting on a command that was never sent.
- **Residual risk:** The 64 KiB payload limit is unchanged. Extra requests on the same connection remain intentionally ignored.

### RD4 — Medium: oversized desktop control results produced doomed response frames

- **Location:** `remote/src/control.ts`, private `responseLine` (line 298).
- **Prior behavior/scenario:** Desktop results arrive over the 16 MiB RPC transport, but control producers accept only 64 KiB replies. A sufficiently large pane inventory/result was serialized and sent without a control-channel size check. The producer rejected it while streaming with an unhelpful framing/bound error, although the desktop operation might have already completed.
- **Root cause:** Request and receiving-client bounds existed, but the daemon's outgoing control-response boundary had no corresponding bound.
- **Fix:** Serialize once, measure JSON payload bytes, and replace an oversized result with a small `failed` response explicitly stating that the operation may have completed and current viewer state must be inspected before retrying. No error-code vocabulary or successful payload shape changed.
- **Tests:** Added oversized desktop inventory round trip in `control.test.ts` around line 447. It checks the actionable refusal, bounded result, released pending entry, and a subsequent successful command on the same listener.
- **Residual risk:** Results larger than 64 KiB remain unavailable by protocol design; no invented truncation or partial-success payload is returned. Mutating operations can already have happened, hence the explicit warning.

### RD5 — High: uncertain stale-socket probes could unlink a live bridge endpoint

- **Location:** `remote/src/bridge.ts`, `startBridge` existing-socket probe (approximately line 675).
- **Prior behavior/scenario:** Any connect error or one-second timeout was interpreted as a dead listener, followed by unconditional `unlinkSync(socketPath)`. Local `EMFILE`/`EAGAIN`, permission denial against an endpoint in a writable parent directory, or a stalled probe says nothing about listener liveness. Against an existing listener without a bridge ownership lock (e.g. a legacy bridge), a failed new launch could delete its live endpoint. The async probe also allowed the pathname to be replaced before the unconditional unlink.
- **Root cause:** Probe failure conflated definitive refusal with uncertainty, and the probed inode was not retained for identity comparison.
- **Fix:** Only `ECONNREFUSED`/`ENOENT` establish staleness. Other errors reject startup and preserve the endpoint; a timeout also rejects preserving the socket. Before unlinking, compare current socket type/dev/inode with the original stat, rejecting if the pathname changed. Existing lock cleanup is retained on every rejection. Refactored the touched probe completion to `Promise.withResolvers()`.
- **Tests:** Added `bridge socket probes preserve live endpoints on permission and resource errors` near `agent-hook.test.ts:554`. A real live Unix listener is paired with injected `EACCES`, `EMFILE`, and `EAGAIN` probe failures. Assertions check startup rejection, inode preservation, released startup lock, and successful subsequent real consumer connection to the original listener. Existing real stale-socket takeover coverage remains unchanged.
- **Residual risk:** The identity check narrows the normal asynchronous race but cannot make pathname checking/unlinking atomic against an adversary with write access to the directory. Runtime-directory ownership remains an environmental security boundary. Lock-file stale-owner concurrency was inspected but not changed without a deterministic evidence-backed fix in this slice.

## RW — Remote file saves and workspace storage

**Post-fix check:** Passed in the final remote suite, including the real-filesystem symlink/guarded-save regression.

### RW1 — High: an atomic save could return an unrelated file's revision and authorize a later destructive overwrite

- **Files/symbols:** `remote/src/files.ts`, `writeFileLocked` (descriptor lifecycle around lines 783–827 and result at line 849), plus its write-lock contract comment at lines 531–536. Regression: `remote/test/files.test.ts`, `writeFile never returns a different symlink target's revision after saving` (starts at line 2385).
- **Prior behavior:** The service closed its temporary-file descriptor before renaming, then obtained the success revision with `fsp.stat(params.path)` after the rename and directory flush. That final lookup followed whatever the requested pathname named by then, not necessarily the inode the save had written.
- **Concrete failure:** An editor loads symlink `current -> first`, then saves `first`. Another process retargets `current -> second` after the rename commits but before the response revision is collected. The service returned `second`'s revision alongside a successful save of `first`. The editor's next ordinary save through `current` consequently passed the revision guard and overwrote `second`, despite never loading its contents. A pathname removal in the same interval could alternatively report a failed save after a successful commit.
- **Root cause:** The operation lost the descriptor that identified its newly written inode and subsequently borrowed the revision from a fresh, symlink-following pathname lookup. Per-path serialization cannot fence out an external symlink replacement.
- **Fix:** Keep the existing temporary-file descriptor open across the atomic rename, then creation the success revision using that descriptor's `stat()`. Close it after collecting that revision, preserving the existing failure cleanup and directory-fsync behavior. Remove the final requested-path stat. A post-commit close error is best-effort, like readFile's close, rather than replacing a committed save with an unrelated close error.
- **Regression test:** Deterministically retarget a real symlink immediately after the real filesystem rename via a test-context-scoped mock of `fs.rename`. Assert that the returned revision belongs to the saved original, differs from the unrelated target, the original contains the saved bytes, and a subsequent save conflicts without changing the unrelated file. All filesystem data are real and isolated in a freshly created temporary directory; the mock controls only the external-race timing and is restored in finally.
- **Observed reproduction before fix:** A standalone Node reproduction printed `savedRevision == unrelatedRevision`, different from `writtenRevision`; the subsequent ordinary save succeeded and `second after next save: unrelated overwritten`. Exit status 0. The reproduction used only a fresh `rw-revision-repro-*` directory and removed it in finally.
- **Observed reproduction after fix:** The same standalone scenario printed `savedRevision == writtenRevision`, different from `unrelatedRevision`; the next save was refused with `-32001 RevisionMismatchError` and printed `second after next save: second original`. Exit status 0.
- **Residual risks:** As already documented by the implementation, there is no portable atomic compare-and-rename against external writers; an external change between the final guard and rename remains possible. In-place edits of the same open inode cannot be excluded without an OS-level locking protocol. The fix does not change hard-link breaking inherent in atomic rename saves, symlink resolution policy, revision token format, or any exported API.

**Final integration detail:** The destructive pre-fix case was reproduced on a real filesystem. A symlink was redirected between replacement and revision collection; the returned revision then authorized overwriting the unrelated file. The final regression proves that the revision belongs to the still-open replacement file and that the later guarded write refuses the unrelated current file. The file-save specification was updated to explain this identity guarantee.

## RI — Remote command-line tools, hooks, and adapter tests

**Post-fix check:** Passed in the final remote suite, including the CLI/hook/adapter integration coverage.

### RI1 — Medium: failed hook writes falsely report delivery

- **Location:** `remote/src/hooks/bridge-emit.ts`, `emitHookEvent`, `socket.end` callback (line 216 at edit time). Regression: `remote/test/agent-hook.test.ts`, test `a failed hook write rejects instead of reporting delivery (RI1)` (shared-file line numbers have moved as RemoteCore adds bridge tests).
- **Prior behavior:** `socket.end(line, callback)` always resolved the returned `BridgeMessage` inside its callback. The callback can receive a write error before the socket emits its corresponding `error` event. Resolution won that race, so the later error listener's rejection had no effect.
- **Concrete failure:** A bridge accepts a producer connection and immediately closes it. A substantial but allowed event hits `EPIPE` while being written; the producer reports delivery even though the write failed. The CLI therefore omits its failure diagnostic, and the extension's ordered queue treats a failed transition as delivered.
- **Root cause:** Ignoring the Writable end callback's optional error argument.
- **Fix:** Inspect the callback error, destroy the socket and reject before the success-only resolution path. Existing best-effort callers still absorb failure; no agent-breaking exception or retry was introduced.
- **Tests:** Added a focused transport-error seam using an actual `net.Socket` and `t.mock.method` to deliver the end callback's error before its error event. It asserts rejection with the actual error and socket destruction, rather than source text or private wiring.
- **Observed reproduction:** On Node v24.19.0, started a Unix listener that immediately destroys accepted sockets; emitted an `agent_start` with a 900,000-character summary; wrapped the socket's `end` callback to print its error. Actual output:

  ```text
  end callback error: EPIPE
  socket error: EPIPE
  emit resolved: agent_start
  ```

  This establishes the incorrect success path, not merely a theoretical event ordering.
- **Residual risks:** Successful kernel acceptance still is not application-level acknowledgment; the bridge protocol intentionally has no acknowledgment. This fix does not claim otherwise or introduce a new protocol.

### RI2 — Medium: symlinked executable entrypoints silently do nothing

- **Locations:** `remote/src/tools/entrypoint.ts` (`isEntrypoint`, new helper); `remote/src/tools/viewctl.ts` bottom guard (line 131); `remote/src/mcp/server.ts` bottom guard (line 437); `remote/src/hooks/oh-my-pi-hook.ts` bottom guard (line 209 after import cleanup).
- **Prior behavior:** Each guard compared `import.meta.url` to `pathToFileURL(process.argv[1]).href`. Node normally resolves the main module's symlinks for `import.meta.url`, but retains the invoked symlink in `argv[1]`. They did not match, and the script simply exported functions and exited zero without executing them.
- **Concrete failure:** `node /path/to/symlink-to-viewctl.ts not-an-operation` exits successfully with no usage complaint. - **Fix:** Added a small shared `isEntrypoint(moduleUrl)` helper. It first preserves the existing literal-path match (also preserving `--preserve-symlinks-main` behavior), then compares the canonical `realpathSync` invocation path. Absent or unresolvable invocation paths return false, keeping imports from `node -e` harmless.   - Simplified the existing CLI hook test comment to describe behavior rather than pinning the old guard implementation.
- **Observed reproduction:** Created a temporary symlink to `remote/src/tools/viewctl.ts`, invoked it with the deliberately invalid operation `not-an-operation`, then removed the directory. Actual captured result:


- **Shared cutover:** the daemon and bridge had the same guard. `remote/src/bridge.ts` and `remote/src/codeharbord.ts` now use the shared helper too. Real daemon/bridge symlink child-process regressions are in `remote/test/rpc-mirror.test.ts`. All executable entry points were migrated; no old guard alias remains.

### RI3 — Low/test quality: adapter tests pin function identity instead of delivered behavior

- **Location:** `remote/test/adapters.test.ts`, original test `pi and oh-my-pi share one mapping rather than a copy of it` removed; first test replaced by `Pi-family bridge events deliver the expected state for each harness (RI3)` (line 35).

## SH — SSH configuration and authentication

**Post-fix check:** The final Linux build and available live SSH cases passed against the isolated loopback sshd. Platform-specific limits are stated below.

### SH1 — Medium: Windows named-pipe fallback imports an unexpanded/configured identity incorrectly

**Location:** `src/ssh/SshConnectionPool.cpp:677`, `readIdentity()` (formerly `readConfiguredIdentity()`), and `connectToHost()`'s pre/post-connect identity selection; private parameter documentation at `src/ssh/SshConnectionPool.h:547`; regression extension at `src/ssh/tests/tst_livessh.cpp:612`, `windowsNamedPipeAgentFallsBackToIdentityFile()`.

**Prior behavior / concrete failure:** When Windows `SSH_AUTH_SOCK` names the built-in OpenSSH pipe, authentication bypasses `publickey_auto()` and imports candidate files itself. A valid config such as `IdentityFile ~/.ssh/work-key` was handed to the importer before libssh expanded `~`, so it could not find the key. Any configured identity containing `%d`, `%r`, or `%%` was discarded entirely as though no identity had been configured. For example, a config path ending in `identity-100%%` should select the existing file `identity-100%`; it instead caused a default-key scan and authentication failure. Ordinary non-Windows auto authentication was unaffected.

**Root cause:** The old helper conflated *any percent escape* with libssh's built-in default identity and retained pre-`ssh_connect()` strings for the manual importer. Libssh only expands the identity list during connection setup.

**Fix:** Read the raw identity head without deleting percent-containing paths. For the named-pipe fallback only, snapshot the fresh session's unconfigured head before profile/config settings; compare the raw configured head with that baseline before connection; if it changed, retrieve the expanded path after connection. Default-key discovery remains available when no identity was configured. Non-fallback platforms no longer perform an unused identity lookup. Updated existing internal comments rather than adding an API or alias.

**Permanent regression:** Extended the existing Windows live test. After its explicit-profile-key case, it copies the real fixture identity into a temporary filename containing a literal `%`, writes a temporary `Host *` config with `IdentityFile ".../identity-100%%"`, temporarily redirects Qt's Windows `USERPROFILE` config discovery, and authenticates without a profile identity. Success requires the configured key to be expanded and imported; no source-text/log-wording assertion or fake transport is involved. The temporary home contains no default identity to accidentally satisfy the case. It restores the environment and uses the existing fixture's real SSH server.

**Actually observed:** A ctypes probe against the installed libssh showed these identity values before/after `ssh_connect()`:

| Config identity | Before connect | After connect |
| --- | --- | --- |
| none | `%d/id_ed25519` | `/home/yichen/.ssh/id_ed25519` |
| `~/.ssh/example-key` | `~/.ssh/example-key` | `/home/yichen/.ssh/example-key` |
| `%d/%r-key` | `%d/%r-key` | `/home/yichen/.ssh/example-user-key` |
| `/example/100%%/key` | `/example/100%%/key` | `/example/100%/key` |

All explicit config parses returned 0. The probe used loopback port 1 and connection returned -1; expansion occurs before that refusal. The Windows pool path itself has **not** been executed here.

**Residual risks / limits:** The manual Windows fallback still has its existing limitation of exposing only the head configured identity through libssh's public getter; this change does not claim support for every configured identity/certificate/provider. An explicit configured identity identical to libssh's raw default is indistinguishable from that default, so the existing default-key scan remains the result for that equivalent spelling. The Windows-only live case was skipped on Linux; its Windows runtime path remains unverified.

**Final integration detail:** The local libssh expansion probe used the virtual environment Python with ctypes. It checked actual library expansion behavior, not a replacement Python implementation. This is supporting Linux evidence only; the Windows named-pipe fallback itself was not run.

### SH2 — High: absent chosen SSH config permits hidden late parsing to override the saved endpoint

**Location:** `src/ssh/SshConnectionPool.cpp:1069`, `connectToHost()` config parsing.

**Prior behavior / concrete failure:** The pool explicitly parsed `QDir::home()/.ssh/config` only when it existed, then set the saved profile port and recorded that port in `m_port` for known-host verification. If the chosen file was absent, libssh still considered config processing unfinished. `ssh_connect()` could therefore parse its own default user/global config *after* the profile overrides. A `Host * / Port 2222` default changed a requested port 1 into port 2222. This is both a wrong-endpoint connection and a mismatch between the actual endpoint and the `[host]:port` identity passed to the known-hosts policy. Global configuration could likewise alter transport options after CodeHarbor's intended ordering. The default-path configuration policy also depended on whether an otherwise-empty user file happened to exist.

**Root cause:** Checking file existence skipped the libssh call that marks configuration processing complete. Absence is a successful input to `ssh_options_parse_config()`, not a reason to leave processing pending.

**Fix:** Always explicitly parse the pool's chosen config path before the profile overrides. Libssh accepts a missing file and marks config processing complete; later `ssh_connect()` no longer implicitly parses a second set of default files. The user-visible "Parsing SSH configuration" stage line remains conditional on an actual file. Existing error handling, user `ConnectTimeout` precedence, explicit saved user/port precedence, and host-key policy are retained.

### CP1 — Medium — pointer identity mistakes a fresh same-device binding for the old stream

#### Location

`src/remote/CodeharbordClient.cpp`: `setTransport` (around line 141), `call` short-write handling, `finishTransportBinding` (around line 248), `onReadyRead` (around line 428), `dropUntrustedStream` (around line 603), `onTransportClosed` (around line 823). #### Prior behavior and concrete failure scenarios

Reentrant safety checks compared `QIODevice` pointers. The public API permits detaching and rebinding the same device, and explicitly permits reviving the same device after closure. Those operations produce a new binding without a different pointer.

1. During an outer replacement, a failed old request can detach and rebind the same replacement device. The nested bind already emits `transportBound`; the outer bind sees an equal pointer and emits it again. Consumers then establish remote subscriptions twice.
2. A response delivered by the final close drain can detach/rebind that same device and start a new request. The old close resumes, sees the same pointer, and fails the fresh request/announces closure against the replacement binding.
3. A partial-write warning handler can rebind the same device and start a fresh request. The stale write-failure path then closes that fresh binding because pointer identity still matches.

Added a private monotonically increasing binding generation, bumped for each effective `setTransport` operation. Reentrant bind/drain/write/drop/close guards now compare binding generations, not just device addresses. No-op binds to the same live device remain no-ops. Read-loop checks return before mutating a newly rebound buffer. Caller ownership of the QIODevice and existing signal ordering are preserved.

- `sameDeviceRebindAfterShortWriteKeepsNewRequestsAlive` (around line 574)

A snapshot containing exactly 8 MiB of ordinary ASCII text exceeds that ceiling once the JSON envelope/path is added; JSON escaping can expand it much further. The read returned a truncated envelope, so recovery parsing silently offered nothing even though the buffer itself was editable-sized.
- **Root cause:** the editable file's byte budget was incorrectly reused for its serialized recovery representation.
- **Fix:** keep the main-file limit8MiB. Assemble recovery using2MiB byte ranges, with aggregate cap16MiB (a persisted envelope must already fit a16MiB RPC write frame), and reserve only a stat-provided size within that bound. Convert UTF-8 chunks back to bytes, strictly decode base64 chunks to bytes, and decode the assembled byte array only once, preserving codepoints split at range boundaries. Every range must share one nonempty revision. A full first response can finish immediately; multi-range probes finish with a stat that must match the accumulated byte count and revision. The aggregate16MiB bound is justified by the unchanged RPC write ceiling; payloads whose serialized write frame exceeds that ceiling cannot be persisted by today's protocol and no universal8MiB worst-case-escaped recovery guarantee is claimed. ### MV5 — High — SVG decoder reads app-local files, including through disguised nested SVG

- Locations: `src/mobile/MobileImageProvider.cpp`, new file-static resource-boundary helpers; `MobileImageProvider::requestImage` before any SVG metadata access near line 268. Public decode-subset contract added to `MobileImageProvider.h`.
- Prior behavior: `QImageReader` received untrusted SVG bytes and `size()`/transformation/read parsed SVG before any resource validation. - API investigation: installed `QtSvg::Option` enum has animation/trusted-source/Tiny12 options, not a no-external-resource flag. MIME declarations cannot authorize nested SVG. Successful raster validation also prevents QtSvg's filename fallback after a failed data decode. CSS imports, escaped resource spellings, and non-fragment CSS URLs are refused. Ordinary vector SVG, local fragment use/gradients, and verified embedded raster images remain supported.

- Regression: `tst_mobileviewers::svgImagesNeverReadLocalResourcesOrNestedSvgPayloads` creates a fresh local marker PNG and passes outer SVG, nested SVG, PNG-mislabeled nested SVG, and percent-encoded nested payloads through the real owned provider, requiring refusal. Also covers DTD/external DTD, stylesheet PI, CSS import/external URL refusal, and positive fragment-reference/embedded PNG rendering. Explicit skip when SVG plugin is absent.
- Observed minimal reproductions: an initial malformed PNG probe produced libpng CRC and `qt.svg: Could not create image from ...` messages, establishing local file access. A stronger standalone QML reproduction generated a valid fresh red PNG with `Canvas.save`; direct SVG and PNG-mislabeled nested SVG both rendered it. Actual grabbed-pixel comparisons red=255 and green=0 passed, with output `DIRECT_LOCAL_MARKER_EXPOSED` and `MISLABELED_NESTED_SVG_EXPOSED_LOCAL_MARKER`. Command: `QT_QPA_PLATFORM=offscreen QT_QUICK_BACKEND=software /usr/lib/qt6/bin/qmltestrunner -input build/dev/.tmp/tst_mvsvgmarker.qml` on Qt 6.10.2. All temporary proof files were removed.
- Residual risk: Qt image decoders remain a third-party parsing surface; this removes demonstrated filesystem resource channels, not a claim that arbitrary decoder bugs cannot exist. Safe embedded rasters are decoded twice as a necessary check against QtSvg's fallback-to-filename behavior. Future decoder changes need this boundary retained/reviewed.

**Final integration detail:** The final boundary also rejects a processing instruction hidden inside a style element, checks the original untrimmed data URL spelling, and refuses nested SVG regardless of its declared MIME type. Embedded raster work is limited to 16 million total pixels and 128 image references, charged before decode even if the SVG element has zero display size. These checks run before image metadata parsing. Positive ordinary-vector/fragment/verified-raster cases still pass.

### BR4 — High: signing a realistically sized AAB could fail after successful signing

- Location: `.github/scripts/sign-android.sh`, AAB signature-entry check around lines 227–234; `.github/workflows/ci.yml`, existing synthetic AAB signing probe expanded at lines 855–863.
- Prior behavior: under `set -o pipefail`, `unzip -l "$file" | grep -qiE 'META-INF/.*\\.(RSA|DSA|EC)$'` stopped consuming output as soon as it found jarsigner's certificate entry. Certificates are near the start; a real bundle's later long file listing fills the pipe after grep exits, so unzip dies with SIGPIPE. The negated pipeline then reports that the correctly signed AAB has no signature block and rejects the release.
- Concrete failure scenario: a real Android bundle has thousands of entries. Jarsigner succeeds and verifies it, but this final structural signature check fails, aborting the Android release job. The tiny existing CI probe had too little output to expose the broken pipeline.
- Root cause: early-exiting grep combined with a producer large enough to hit the closed pipe, interpreted as an absent-match error by pipefail.
- Fix: use non-quiet grep with stdout redirected to `/dev/null`, so the consumer drains the full listing while still returning nonzero for no signature. This preserves unzip failures instead of suppressing them.
- Regression changes: expanded the existing CI synthetic bundle to contain 2,000 payload entries before real signing with the existing throwaway RSA key. It still exercises the real `sign-android.sh`, jarsigner signing and verification, and unzip inspection; the listing is now large enough to expose the SIGPIPE regression. No new mock tool or source-wiring assertion was introduced.
- Residual risk: full signing of an actual release AAB and device install were not exercised here. This change addresses structural listing transport only; cryptographic verification remains the existing jarsigner/apksigner logic.

**Final integration detail:** The full production signing script was additionally run on a real 2,000-entry synthetic AAB, using a generated RSA key and actual jarsigner signing/verification.
