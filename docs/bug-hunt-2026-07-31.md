Vocabulary used throughout, defined once:

* **Dev Session** — one unit of work: a checkout on the remote server plus the panes
  and shells opened on it.
* **Pane** — one rectangular sub-view. The window has a fixed three-region layout:
  sessions sidebar, viewer region, terminal region.
* **tmux** — a program on the remote server that keeps a shell running after the
  client disconnects. Every terminal pane is attached to one tmux session; this is
  what makes terminals survive disconnects and restarts.
* **`codeharbord`** — the Node service running on the SSH server. The client talks to
  it with JSON-RPC: one JSON object per line over an SSH channel.
* **QPointer** — a Qt smart pointer that automatically becomes null when the object it
  points at is destroyed, instead of dangling.
* **QWebChannel** — Qt's bridge that lets JavaScript in an embedded browser view call
  C++ methods and receive C++ signals.

## MP — models and persistence

### MP1 — A "successful" reply whose body was the wrong kind of JSON became a blank record reported as success

**Files:** `src/persistence/WorkspaceDb.cpp` (new helpers around lines 357-405, every
public method body from 411 to 637), `src/persistence/WorkspaceDb.h` lines 121-134.

`WorkspaceDb` is the client's gateway to the workspace database. There is no local
database: every operation (`createGroup`, `list`, `updateSession`, `getLayout`, …) is a
JSON-RPC request. The reply carries either an `error` object or a `result` value.

The code checked only *whether an error was present*. It never checked what kind of
JSON the `result` actually was, and then called `QJsonValue::toObject()` on it. That Qt
function is deliberately lossy: for anything that is not an object — `null`, a number, a
string, an array — it returns an **empty object** rather than failing. Every decoder in
the file reads named keys out of that object, so an empty object produced a
**fully default-constructed record**: empty id, empty name, position 0, all flags false.
That record was handed to the caller through the *success* path with no error attached.

Why it matters: the same file already treats this outcome as unacceptable for *nested*
elements — `parseSessionNode()` and `parseGroupList()` skip any array entry that is not
an object, and the comment above them explains that an entry with an empty id "looks
real to the rest of the client and can collide with other id-keyed state". The same
reasoning was simply not applied at the top level. Concretely: a server, proxy, or
partially-implemented handler answers `workspace.createGroup` with `null`; the user
clicks "New group", a group with a blank name appears in the sidebar, and its id is the
empty string — which then collides with every other id-keyed piece of state.

Fixed by adding a file-local constant `kMalformedResultCode = -32603` (JSON-RPC's
reserved "internal error" code, the same one the transport layer already uses for
failures it synthesises itself, so callers need no new branch), a `malformedResult()`
helper that builds the error, and a `recordHandler()` template that replaced ten
byte-for-byte-identical inline lambdas. `list()` keeps a hand-written handler because
its result is an array. `getLayout()` keeps one because it is the single method for
which `null` is a legitimate success meaning "this region has no saved layout"; it now
distinguishes null, object, and anything-else explicitly. The helper
`parseLayoutResult(QJsonValue)` was renamed `parseLayoutRow(QJsonObject)` because it
used to swallow the "not an object" case itself, which is exactly the conflation being
fixed. Error forwarding also changed from copy to move.

### MP2 — Parsing a split layout deep-copied every subtree once per nesting level

**File:** `src/models/SplitTree.cpp` lines 104 and 124, include at 6-7.

A split tree describes how a region is divided into panes. Each node holds its children
**by value**, so copying a node copies its whole subtree. `parseNode()` did
`node.children.append(child)` (a copy) and finished with `out = node` (another copy),
both of temporaries about to be destroyed. Because the function is recursive the waste
compounds: for *n* nodes at depth *d* the parse performs on the order of *n·d* node
copies, each allocating two strings and two vectors.

This runs on data arriving over the network, the parser accepts nesting up to a hard cap
of 256 levels, and it is on the hot path of activating a Dev Session. Changed both to
`std::move`, making the parse linear. Behaviour is identical.

### MP3 — A test used `QJsonDocument` without including its header

**File:** `src/models/tests/tst_models.cpp` line 6.

It compiled only because `<QtTest/QtTest>` happens to pull `QJsonDocument` in
transitively on this Qt version. Qt trims transitive includes between releases and this
project supports 6.9 through 6.10+, so the file could stop compiling on an unrelated Qt
upgrade with an error pointing nowhere near the cause. Added the include.

### MP4 — Six untested behaviours in the models layer, now covered

Added to `src/models/tests/tst_models.cpp`:

* `updateTerminalStatesFallsBackForEveryStructuralDrift` — the fast path for live agent
  status refreshes patches rows in place instead of rebuilding the sidebar, which is
  only safe while the incoming data has the same shape. It has **three** guards (group
  count, group id, session count) plus a fourth (session id) that was the only one
  tested. A regression in an untested guard would write terminal state onto the wrong
  rows: a session would display another session's badge.
* `updateTerminalStatesStaysSilentWhenTheAggregateDoesNotMove` — the other half of that
  contract: a refresh that does not move a row's badge must emit nothing for that row.
* `sessionsModelSessionIndicesAreScopedToTheirGroup` — the model encodes a session's
  parent group as a row number inside the model index's opaque field. Nothing tested
  that with more than one group, so nothing would have caught row 0 of group 0 and row 0
  of group 1 collapsing into one index, which would show one group's sessions under
  another.
* `sessionsModelIsSingleColumn` — `columnCount()` was never called by any test.
* `splitTreeSplitUrlIgnoredOnRoundTrip` — a split node has no content of its own, so
  equality must ignore its `url` to keep "parse(serialise(x)) == x" true. There was a
  test for the analogous rule on a stray `paneId` but not for the newer `url` field; if
  equality compared it, a loaded tree would never compare equal and the layout would be
  re-written to the server on every load.
* `workspaceValueTypesCompareEveryField` — `Group`, `ViewerPane` and `TerminalPane` use
  compiler-generated equality, and these records are compared to decide whether a local
  change needs writing back, so a field omitted from the comparison is a field whose
  edits are silently discarded. The test flips each member in turn: 5 fields, 7 fields
  and 9 fields respectively.

### MP5 — Five untested behaviours in the persistence layer, now covered

Added to `src/persistence/tests/tst_workspacedb.cpp`:
`malformedResultsDeliverRpcErrorInsteadOfBlankRecords` (the regression test for MP1,
including the boundary that `getLayout` answered with `null` is still a success with no
error), `deleteSessionSerializesIdAndForwardsOutcome` (none of the four delete methods
had any test at all), `reorderSessionsSerializesGroupIdAndIdArray` (this method is keyed
by *group* id while its sibling is keyed by *server* id, and only the sibling was
tested), `moveSessionToGroupSerializesParams` (including that an explicitly-set position
of 0 is transmitted, since omission keys on whether the optional was set rather than its
value), and `createTerminalPaneSerializesOptionalsAndParsesRecord`.

## AC — application core

### AC1 — A second click on Connect while a password dialog was open destroyed the credentials already typed

**File:** `src/app/AppController.cpp`, `connectToProfile()` lines 284-299.

`m_credentials` holds everything the user has typed for the connect attempt currently
running: the key passphrase, the account password, and two flags recording which
questions have already been asked. `startConnect()` correctly refuses to start a second
attempt while one is running or parked waiting for the user — but `m_credentials.clear()`
ran **before** that guard, so the refused call still wiped the live attempt's state on
its way to doing nothing.

Concrete failure on a server configured with OpenSSH's
`AuthenticationMethods publickey,password`, which requires both a key and a password:
the client must do three handshakes, and the third must present *both* secrets. If the
user clicked Connect once more while the second dialog was up — an ordinary thing to do
when a dialog seems stuck — the third handshake went out with the password only and the
key still locked, and the "already asked" flags were reset so the passphrase was
demanded again. The account became effectively unreachable until the app was restarted.

Moved the guard above the clear. A regression test drives the full three-handshake chain
with the stray click injected, and was confirmed to fail against the unfixed code.

### AC2 — Abandoned connect attempts left state that leaked into the next attempt

**File:** `src/app/AppController.cpp` lines 413-419, 548-560, 598-607, 619-635.

`m_heldConnectError` is a failure message deliberately held back rather than shown,
because while an attempt is running a failure is often expected (the client refuses an
unknown host key on purpose so it can ask the user). Neither it nor `m_pendingProfileId`
was cleared when an attempt ended by failure, host-key rejection, credential
cancellation, or Disconnect. The next attempt's failure path shows any held message, so
cancelling a login to server A and then connecting to server B produced B's failure
toast reading out A's error text. Every ending path now clears both, and Disconnect also
resets the credential kind so the post-disconnect state matches the freshly constructed
state.

### AC3 — The connection-status change signal fired on every repeat of the same error

**File:** `src/app/AppController.cpp` lines 249-275.

`connectionStateChanged` is the change notification for two Qt properties. Every other
writer compares before assigning and stays silent when nothing moved; this one handler
emitted unconditionally. When a server is unreachable the reconnect ladder reports the
same failure text on every rung, so every rung woke every UI binding on the connection
footer even though neither property had changed. Now compares first. The separate
one-shot `error(...)` signal stays unconditional and is commented as such: it is an
event, not a property, so a repeat is a real second event.

### AC4 — Desktop notifications were permanently disabled on most Linux desktops

**File:** `src/app/Notifier.cpp` lines 32-53, `Notifier.h` lines 42-47.

At construction the class asked the message bus `isServiceRegistered(…)`, which means
"is that service **running right now**". On Linux, desktop services are normally
registered as *activatable*: not running, but the bus knows how to start them on first
use. Nearly every desktop ships its notification daemon that way, and CodeHarbor is
often the first program in a fresh session to want a notification. So the answer was
false, and because the result is fixed for the object's lifetime and the object is
created once at startup, notifications were silently disabled for the entire run on a
perfectly healthy desktop — with nothing logged, because the no-backend path is
deliberately silent.

The service now counts as available if it is registered **or** listed among the names
the bus can start on demand. The `||` short-circuits, so the extra round trip only
happens when the daemon is not already up.

### AC5 — Stale documentation describing a return value the function never had

**File:** `src/app/Notifier.h` lines 68-79. The comment claimed `deliver()` returns "the
id the backend assigned, or 0". It actually returns its `replacesId` argument straight
back, and cannot do otherwise because the backend call is asynchronous. The one caller
does `m_lastId = deliver(title, body, 0)`, which under the old comment looks like it
stores a real id (so the next repeat would replace the bubble in place) but actually
stores 0 (so the next repeat is *dropped*). Comment rewritten to state what happens.

### AC6 — Editor factory pointer could dangle across an asynchronous callback

**File:** `src/app/AppController.h` lines 222-230. The controller held
`EditorFactory* m_editorFactory` as a raw pointer to an object it does not own, declared
*after* it in `main.cpp` and therefore destroyed *before* it. It is dereferenced inside
the callback handling the server's `server.info` reply, behind an `if (…)` that looks
like a safety check but is not one for a raw pointer. The class header already spells
out this hazard for four other pointers and uses `QPointer` for them. Changed to
`QPointer`, which makes the existing check a real check.

### AC7 — The editor factory was registered after the automatic connect that can need it

**File:** `src/app/main.cpp` lines 74-101. Startup ran `setConnection`, then the
environment-driven auto-connect (which emits its "wired" signal *synchronously*, making
the controller issue `server.info` immediately), and only later constructed and
registered the editor factory. One field of that reply is forwarded to the factory so
crash-recovery snapshots go to a server-chosen directory. The file already carries a
prominent comment explaining that the auto-connect must come *after* `setConnection()`
for exactly this reason, then violated the same rule two dozen lines down. It survives
today only because the reply cannot arrive before the event loop starts. Moved the
factory declarations and registration above the auto-connect, still after the SSH pool
so the destruction ordering the file documents is preserved.

### AC8 — Duplicated Windows console setting, missing from five other console tests

**File:** `src/app/tests/CMakeLists.txt`. `qt_add_executable` marks executables as
Windows GUI-subsystem programs, which on Windows means no console and everything the
test framework prints goes nowhere. One target had the workaround applied **twice**, and
five other plain command-line test targets had it not at all — so on Windows those tests
can fail and report nothing: no assertion text, no file, no line. Consolidated into one
block listing all six, with the three QML-window tests deliberately left as GUI
executables.

### AC9 — Seven missing tests for existing behaviour

`refreshWithoutATransportIsASilentNoOp` (the entire cold-start experience: the window
opens before the user has connected to anything, and a regression here would put a
spurious error toast on every launch), `serverSideRepoRootChangeNotifiesActiveSession`
(both halves: silent when unchanged, exactly one emission when the server reports a new
path), `switchingServerDropsTheActiveSessionButKeepsItRemembered` (four distinct
behaviours, none covered), `connectWhileParkedLeavesTheChainsSecretsIntact` (AC1),
`submitCredentialWithAnUnknownKindIsIgnored` (validation exists specifically so a private
key passphrase can never be offered to a remote host's password endpoint, and had no
test), plus `negativeWindowDisablesCoalescing` and `theWindowIsMeasuredFromTheLastRaise`
for the notification anti-spam window.

### AC10 — The application never told Qt which desktop-entry file it belongs to

**File:** `src/app/main.cpp` lines 33-41. `packaging/codeharbor.desktop` declares
`StartupWMClass=codeharbor`, which is what lets a Linux desktop shell recognise a running
window as belonging to this launcher so it groups under the correct dock icon. On native
Wayland, Qt derives that identifier from `QGuiApplication::desktopFileName()` and only
falls back to the executable's base name. Nothing was visibly broken, because the
executable happens to be named `codeharbor` — but a rename, a versioned name, or a
launcher shim would silently detach the window from its icon. Added
`setDesktopFileName("codeharbor")`, deliberately without the `.desktop` suffix: Qt strips
a trailing `.desktop` for compatibility while printing a warning on every launch.

## AS — session state, layouts, settings, server profiles

### AS1 — A layout answer arriving after the user edited the layout undid the edit, and could delete it from the server

**Files:** `src/app/SessionLayouts.{h,cpp}`.

Loading a Dev Session fires two asynchronous "what is this session's split tree?"
requests, one per region. The only protection against a stale answer was a generation
counter, which handles `load(A)` then `load(B)` but not the far more common case of an
answer being overtaken by a *local edit of the same session*.

Two reachable failures. **Revert:** something reloads the session — the controller does
this after every reconnect and every time the user re-picks the session they are already
in, deliberately, with a comment saying so. Before the answers arrive the user splits a
pane; the split is applied locally and written to the server; then the stale answer lands
and reinstalls the pre-split layout. The split visibly disappears and the screen and
server now disagree. **Destruction (worse):** if the server has no stored layout yet (a
brand-new Dev Session), the load reply does not merely adopt a tree, it *seeds* — it
takes the built-in default and **writes that default back to the server**. If the user's
tree was saved a moment earlier, the seed lands on top of it: replaced on screen and
overwritten in the database, permanently.

Fixed with a per-region `superseded` flag. Every write path sets it; a load reply is only
installed when it is clear; a deliberate `load()` clears it for both regions first, so an
old edit cannot veto all future reloads. It is per region, so a region the user did not
touch still adopts the server's answer — which matters, because another client may
legitimately have changed it. A test harness reproduced both sequences and, with the one
guard removed, reproduces exactly the described damage.

### AS2 — The unattended "trust any host key" policy was installed permanently and could never be withdrawn

**File:** `src/app/SessionBootstrap.cpp` lines 1207-1240.

When the client meets a server it has never seen it must ask the user about the host key.
If no asking mechanism is installed it refuses to connect, which is the correct
security-preserving answer. There is one deliberate exception for genuinely unattended
entry points (`setTrustUnknownHostKeys(true)`), which installed an accept-everything
policy on the SSH connection pool — and **never removed it**. The pool is long-lived and
shared, so every later attempt found a policy already installed, skipped the refusal
branch entirely, and kept accepting unknown host keys blindly. Turning the opt-in back
off did nothing. A one-way door into blind trust-on-first-use, which is precisely what
the surrounding twenty-line comment says must not be possible.

The policy is now installed for the duration of one attempt and removed by a scope guard
on every exit path. A policy the attempt did *not* install is left untouched, because the
real UI relies on its prompting callback still being there for the retry after a
fingerprint prompt. Verified by removing only the restore and watching the
opt-in-withdrawn connect succeed.

### AS3 — Failing to save a newly approved host key was silently swallowed

**File:** `src/app/SessionBootstrap.cpp` lines 1246-1266. After a successful handshake
the known-hosts file was rewritten with `open()`'s result ignored and `write()`'s result
ignored. A read-only config directory, a full disk, a quota, or wrong ownership all
produce the same outcome: the approval the user just gave is not recorded and nothing
says so, so the same fingerprint prompt appears on every launch forever — which trains
the user to click through host-key prompts, the exact reflex the prompt exists to
prevent. Worse, the file is truncated before writing, so a partial failure can also
forget previously trusted servers. All three results are now checked and a failure
reports the host, the path, the operating-system reason, and the consequence.

### AS4 — A reconnect timer tick during an in-flight attempt killed the retry ladder permanently

**File:** `src/app/SessionBootstrap.cpp` lines 99-117. Retries use a backoff ladder
(1, 2, 5, 10, 30, 60 s) on a **single-shot** timer, and only the scheduling function
re-arms it. The handler dropped a tick that arrived while an attempt was in flight — and
dropping a single-shot tick with nothing to re-arm it means the ladder stops for good:
the object sits in "reconnecting…" forever with no way out but a manual disconnect. An
attempt really can sit in a nested event loop for up to 180 seconds during a remote
install, and the comment above the code says the timer can fire during one. Latent by
static analysis, but the failure mode is the worst kind. A tick arriving during an
attempt now defers the rung instead of discarding it, without consuming an attempt. The
pinned ladder schedule is unchanged.

### AS5 — The final progress line of a remote install was collected but never shown

**File:** `src/app/SessionBootstrap.cpp` lines 866-874. Progress lines from the remote
install script are republished by a line scanner, but after the wait loop the code did a
bare `readAll()` that appended bytes without scanning them. The last chunk very often
contains the `codeharbor: installed …` verdict, so during a slow download the UI's last
visible message was "unpacking …" and then nothing — indistinguishable from a hung
application, which is the exact symptom the progress reporting exists to prevent.
Replaced with a second scan.

### AS6 — Corrupt or half-written region widths collapsed a region to zero width

**Files:** `src/app/UiStateStore.{h,cpp}`. Region widths were read with
`value(key, default).toInt()`. The default is only used when the key is **absent**; if
the key is present but unparseable, `toInt()` returns 0 and 0 was returned as the width.
The settings file is plain text a user can edit, and a power loss mid-write can truncate
a line to `sidebarWidth=`. Either way the sidebar becomes zero-width — no region, and
therefore no drag handle on screen to widen it back. Added a helper used by all three
accessors that falls back to the documented default when the key is absent, unparseable,
or below a minimum (1 for the sidebar and terminal regions, whose width *is* their
presence; 0 for the viewer region, where 0 is the documented default meaning "fill
whatever is left"). Honest narrow values are untouched.

### AS7 — Remembering the selected pane with no Dev Session wrote to a shared placeholder key

**Files:** `src/app/UiStateStore.{h,cpp}` lines 90-107. The key is
`"selectedPane/" + id`; with an empty id that is the bare key `"selectedPane/"`. The
sibling API already refuses an empty server id for exactly this reason, with a comment
explaining it. The remembered pane is what a split command acts on, so a write made
before a Dev Session was picked landed on a shared key and the next empty-id read handed
that stale pane back as if it belonged to whatever the user opened next. Latent today
because the QML guards its own calls, but a footgun the neighbouring function already
knows to avoid. Now mirrors the sibling exactly.

### AS8 — One subtle "was this rejected, or is it a genuine empty layout?" rule, written twice

**Files:** `src/models/SplitTree.{h,cpp}`, `src/app/SessionLayouts.cpp`,
`src/persistence/WorkspaceDb.cpp`.

`SplitNode::fromJson()` signals "this input is not a valid tree" by returning a
default-constructed node — which is **also** a legitimate stored tree, because closing a
region's last pane persists exactly that on purpose (a region must always have a root).
So the return value alone cannot distinguish the two, and two call sites had
independently reconstructed the same work-around: re-read the input's `"type"` tag and
treat "result is a leaf but the input did not say leaf" as a rejection. Each carried its
own paragraph-long comment. If the parser ever gains a rejection case whose input *does*
declare `"type": "leaf"`, both copies become silently wrong and a rejected tree would be
accepted as a blank single-pane layout, which the user then edits — overwriting the real
layout the server still holds.

The parser already knows the answer; `fromJson()` was throwing it away. Added
`SplitNode::tryFromJson()` returning `std::optional<SplitNode>`; `fromJson()` is now a
one-line wrapper with unchanged signature and behaviour (a dozen existing assertions rely
on the empty-leaf sentinel). Both call sites use the new function and the duplicated
reasoning is gone.

### AS9 — Stale and self-contradictory comments in the server profile store

**Files:** `src/app/ServerProfiles.{cpp,h}`. Three comments claimed the store allows
"six" fields through its whitelist. It allows **seven** (`name`, `host`, `port`, `user`,
`identityFile`, `nodePath`, `repoRoot`). A reader auditing the no-secrets guarantee by
counting would find a field they could not account for. Corrected, the seven are now
named rather than counted, and the no-secrets guarantee was promoted from a passing
remark in a `.cpp` comment to a labelled paragraph in the class documentation, since
other code depends on it.

### AS10 — New test: secrets in the caller's map never reach the profile store

`src/app/tests/tst_serverprofiles.cpp`. The whitelist already guaranteed this but nothing
proved it, so a refactor to "copy every key the caller sent, then validate" could remove
the guarantee with no test going red. The test adds a profile whose map also carries
`password` and `passphrase`, asserts the stored record's key set is exactly the seven
whitelisted fields plus the minted id, asserts an update carrying a password applies its
legitimate half while dropping the secret, and then reads the settings file off disk and
asserts neither secret value nor even the words `password`/`passphrase` appear anywhere
in it. It also asserts `identityFile` — the path to the key *file*, which is legitimate
profile state — is preserved, so the test cannot be passed by dropping too much.

## SSH — transport and host-key verification

### SSH1 — Wildcard known-hosts entries stopped covering hosts whose own name contains `*`, downgrading a refusal into a trust prompt

**File:** `src/ssh/KnownHosts.cpp` lines 44-78.

A known-hosts line may name a pattern (`web*.example.com`) rather than one host. The
matcher tested its cases in the wrong order: it first asked "is the pattern character a
`?`, or equal to the current host character?" and only afterwards "is it a `*`?". So when
the looked-up host name contained a literal `*` at the offset where the pattern had its
`*`, the equality test fired first and the wildcard was consumed as an ordinary
character. The pattern had then spent its only wildcard on one character and could not
stretch, so the whole match failed.

Why it matters: verification returns one of three verdicts — `Match` (trusted key),
`Mismatch` (we trust this host but **not** with this key: hard refusal, the user is never
asked), and `Unknown` (never seen: show the friendly first-use prompt and, on approval,
permanently store whatever key was presented). A pattern entry that matches nothing
downgrades the verdict for a host it was supposed to protect from `Mismatch` to
`Unknown`. The administrator wrote one wildcard line covering a fleet of machines; a
lookup is answered "never seen this host"; the user is shown the reassuring first-use
dialog instead of the refusal; clicking Accept writes the attacker's key into the store.
The looked-up name is not a resolver-validated DNS label — it is whatever the server
profile the user typed contains — so the data being matched must not be able to steer the
matcher.

The `*` test is now the first branch, so a `*` in the *pattern* is always a
metacharacter and a `*` in the *host being looked up* is always ordinary data. Proven by
building the new test against a copy of the file with only the branch order reverted: it
reports verdict `Unknown` (the dangerous prompt) where `Match` is required.

### SSH2 — A host key could be recorded in a form that cannot be written back

**Files:** `src/ssh/KnownHosts.cpp` lines 161-171, `KnownHosts.h` lines 58-64. `add()`
accepted an empty host, key type, or key. Such an entry serialises to a line with too few
fields, which the parser then correctly discards on the next read. The user approves a
fingerprint, the client behaves as trusted for the session, and on the next launch the
same key is unknown again — an approval prompt that can never be satisfied, with no
message explaining it. Latent because the production caller already refuses empty types
and blobs, but `add()` is public API and its contract said nothing. Now returns early on
any empty field.

### SSH3 — An unknown host key with no way to ask the user failed the connection with no error reported

**File:** `src/ssh/SshConnectionPool.cpp` lines 680-693. On the `Unknown` verdict with no
decision callback installed the function simply returned false. Its caller writes a
transcript line and sets the state to `Error`, but does not emit the error signal on that
path because the two other refusal paths emit their own. So this one refusal produced no
error signal at all: anything driving the pool without a callback (a headless tool, a
test harness, an embedding that forgot) saw the state flip to `Error` with an empty
explanation. That is a swallowed failure — the operator cannot tell "I never installed a
trust hook" from "the network died". Now emits a specific message. Deliberately *not*
added for a user who declines the prompt, because the desktop controller answers "reject"
as its normal way of parking the handshake while the dialog is on screen, and an error
there would produce a spurious failure message on every first connection.

### SSH4 — A connection that died during authentication kept climbing the ladder and demanded secrets that could not be sent

**File:** `src/ssh/SshConnectionPool.cpp` lines 713-728 and 917-930. The library reports
"the request itself failed" and "the server said no" with different codes; the code
treated everything that was not success as "no". Two consequences with one root cause:
the mandatory initial dummy request's error return (which means the transport is gone —
`MaxStartups` throttling, a firewall reset, sshd restarting) fell through into the
authentication ladder; and querying the server's offered methods on a dead session
returns 0, which the code deliberately maps to "the server did not tell us, try
everything" — correct for a live server, catastrophic for a dead one.

Two of the ladder rungs ask the application for a secret, which in the desktop client
means a modal password prompt. So a server that hung up produced a passphrase prompt,
then a password prompt, then a keyboard-interactive prompt — each answered into a closed
socket — and finally a generic "Authentication failed" that blames the user's
credentials for a network event. Users retype passwords they believe are wrong. Both
checks added, strictly additive: on a healthy server neither fires, and the multi-step
behaviour the ladder exists for is unchanged. Method *names* only are recorded in the
user-visible transcript; no secret is ever written there.

### SSH5 — Keyboard-interactive authentication sent empty answers when there was no secret to give

**File:** `src/ssh/SshConnectionPool.cpp` lines 874-883. The "I have nothing for this
method" case was not handled, so an empty string was sent as the server's password. Three
consequences: it burns one of the server's `MaxAuthTries` attempts (default 6) on a
credential nobody supplied, which on a server that also wants a real method can exhaust
the budget before the method that would have worked is reached; on a login stack with
lockout counting a failed empty password counts towards locking the account out, so
merely opening CodeHarbor chips away at the user's attempts; and it is inconsistent with
the plain-password rung two cases above, which already abandons on an empty secret. Now
abandons the rung the same way.

### SSH6 — Channel failures left the standard Qt error string saying "Unknown error"

**Files:** `src/ssh/SshChannelDevice.{h,cpp}`. The class implements Qt's standard
byte-stream interface, whose documented error channel is `setErrorString()` /
`errorString()`. It never called `setErrorString()`, so `errorString()` returned Qt's
default "Unknown error" on every failure while the real message went only to a
class-specific signal a generic consumer does not know exists. The whole point of
implementing the standard interface is that code knowing nothing about SSH can use the
channel; any such consumer printed "Unknown error" for what was in fact a precise,
actionable message. Added one private helper routing every *device* failure through both
surfaces. Remote **stderr** deliberately does not go through it: stderr is the remote
program talking, not a failure of the device.

### SSH7 — Remote stderr split across read boundaries was decoded as mangled text

**Files:** `src/ssh/SshChannelDevice.{h,cpp}`. The read pump drains the channel in 16 KiB
chunks and converted collected stderr with a stateless UTF-8 decoder. A character whose
bytes straddle the seam between two passes becomes a truncated sequence at the end of one
and an orphaned continuation at the start of the next, so each half becomes a replacement
character. The existing comment claimed this was handled — true only *within* one pass,
so the comment was actively misleading. stderr is what the user is shown when something
goes wrong and what the bootstrap captures to explain a failed remote start; non-English
locales, accented filenames and box-drawing output all hit this, and corrupted
diagnostics look like transport corruption. Replaced with an incremental decoder, reset
when a new channel starts so one channel never inherits half a character from the
previous one.

### SSH8 — Opening the channel device the standard way produced an "open" device with no channel behind it

**Files:** `src/ssh/SshChannelDevice.{h,cpp}` lines 80-84 and 69-78. `open()` is the
obvious entry point on any Qt byte-stream device, and the class inherited Qt's
implementation, which records the mode and answers true. On this class that is always
wrong: what makes the device usable is an SSH channel, acquired only by `startExec()` or
`startPty()`. A caller reaching for `open()` got a device where "is open" and "is
writable" are both true, every read returns nothing forever, and every write fails — a
silent hang, not an error. The RPC client gates on exactly those two predicates before
sending, so it would accept the device as a working transport and then never get an
answer. `open()` is now overridden to set an explanatory error string and return false;
the internal path is unaffected because it calls the base-class implementation
explicitly. Confirmed nothing in the tree calls `open()` on this class.

### SSH9 — A swallowed timer tick could kill a channel's read pump permanently

**File:** `src/ssh/SshChannelDevice.cpp` lines 364-377. Reads are driven by a per-device
**single-shot** timer that each pump re-arms. The re-entrancy guard's early return did
nothing else — and a tick consumed without re-arming is a tick that ends the pump, so a
re-entrant call would silently and permanently stop reading on a channel that is still
open and still receiving. The symptom is a terminal that stops updating or an RPC call
that never answers, with no error, no state change and nothing in any log. Currently
unreachable because the flag is cleared before any signal is emitted — but a guard whose
failure mode is "stop working forever, silently" should not depend on an ordering
subtlety three statements away. The early return now re-arms at the idle cadence, and the
genuinely-finished case (no channel) is separated out.

### SSH10 — Zero-sized terminal windows were pushed to the remote pseudo-terminal

**File:** `src/ssh/SshChannelDevice.cpp` lines 252-257 and 295-301. Column and row counts
were passed to the window-size request with no floor. The values originate in a
browser-hosted terminal renderer whose measured geometry legitimately reads 0 for a frame
or two while layout settles. A zero-column remote terminal makes line-editing shells and
full-screen programs — including tmux itself — compute nonsense layouts and draw garbage
until another resize arrives. Both entry points now clamp to a minimum of 1.

### SSH11 — The built-without-libssh build did not report the end of the read channel

**File:** `src/ssh/SshChannelDevice.cpp` lines 159-174. CodeHarbor can be configured
without libssh; the classes still compile and every start call fails cleanly. In that
build, closing a channel did not emit the end-of-stream signal. That signal is not
decoration: it is the only thing that drives the RPC client's "the transport closed, fail
every request still in flight" path, so a consumer waiting on it waited forever. It is
also a documented contract the header states and one of the two builds did not honour.
The stub now mirrors the real path; verified by running the new unit test in both
configurations.

### SSH12 — New test coverage

Four new known-hosts cases (the SSH1 regression; a round-trip proving a trailing comment
and an `@cert-authority` marker survive, since this is the *user's* file and anything
dropped is data destroyed in a file the app does not own; the SSH2 guard; and
`lookupHostCanonicalizesTheEndpoint`, which had **no** test despite deciding whether a
stored key is ever found again — emitting `[host]:22` for the default port would produce
a line neither OpenSSH nor a later launch would match, and dropping the port would file
two different servers under one name so the second looks like a changed key for the
first). Two authentication cases. And a **new test target**,
`src/ssh/tests/tst_sshchanneldevice.cpp` with five cases: the channel device previously
had no unit test at all and was exercised only by the live gate, yet its server-free half
is exactly what a caller hits when the connection is down, which is most of what goes
wrong in the field.

### SSH13 — Adjudication: the claimed dangling-channel hazard does not exist

A comment in `src/app/SessionBootstrap.cpp` asserted that closing an SSH session frees
every channel it handed out, leaving any still-alive channel device holding a dangling
handle that its destructor would dereference. Traced and found false: `closeSession()`
nulls the session member, then emits its "session closing" signal, and only **then**
sweeps and frees the channels. Every device wires that signal to its own close through a
same-thread connection, so the close runs synchronously inside the emit, hands the
channel back (which also removes it from the pool's list) and nulls its own handle. By
the time the sweep runs no device holds a handle. A live test pins exactly this with a
real remote command. The comment was corrected to describe the real mechanism; the
"prefer the graceful disconnect" recommendation was kept but restated with its true
reason (deliberate close/detach ordering so the end-of-stream signal drives the RPC
client's pending-request failure while the wiring is still intact).

The libssh 0.12.0 workaround was verified and left exactly as it is: the version check is
string **equality** against `0.12.0`, not a prefix match, so 0.12.1, 0.12.2, 0.12.10 and
0.11.3 are all excluded; the mitigation subtracts one algorithm from the library's own
defaults using the leading `-` modifier rather than freezing a list, so the NIST hybrid
post-quantum exchange stays available.

## RPC — the C++ JSON-RPC client

### RPC1 — The transport pointer could dangle, and destroying the transport stranded every in-flight request forever

**Files:** `src/remote/CodeharbordClient.{h,cpp}`.

The client stored the transport as a plain raw pointer to an object it does not own — the
header says so explicitly. Nothing stopped the owner from deleting it while the client
still held the pointer, and two failures followed. **Use-after-free:** rebinding and the
destructor both call `disconnect(this)` on that pointer. **Stranded callbacks:** Qt's
byte-stream base class does *not* emit its end-of-stream signal from its destructor, so
the client was never told anything and every pending request just sat there. In user
terms: an editor pane stuck forever on "saving…", or a sidebar stuck on "loading…", with
no error ever surfaced — a direct violation of the class's own written guarantee that no
callback is ever registered that cannot fire.

Not theoretical: building the new test against the pre-fix code **segfaults**, because
the orphaned callback captured local variables by reference, outlived the function, and
was finally invoked against a stack frame that no longer existed.

The sibling agent-status class already used a `QPointer` for its transport, with a
comment explaining that a raw pointer would be a use-after-free — the RPC client, which
has strictly more to lose, had never been given the same treatment. Now a `QPointer`, and
the transport's destruction is treated as what it is (loss of the transport): every
pending callback is failed once and the closed signal is emitted. The pointer is nulled
*before* delegating to the ordinary close path, because that path's "drain any last
readable bytes" step would itself be a use-after-free while the destructor is running.

### RPC2 — Frames were still dispatched after the connection had been declared dead

**File:** `src/remote/CodeharbordClient.cpp`. One read can deliver several complete
messages. The loop hands each to the application callback, which is allowed to tear the
session down — and in this codebase it really does, from inside a response callback. When
that happened the client latched closed, failed everything pending, emitted its closed
signal, and then **kept dispatching the rest of the chunk**. So a server-initiated
notification (for example "the file you are watching changed") could be delivered *after*
the closed signal, and the editor — which handles that signal by marking its subscription
dead — would act on it as if it were live. Responses in the remainder also produced
spurious "unknown id" protocol warnings for ids the close had just failed.

Separately, the read buffer was never released on close: a half-received frame, up to the
16 MiB cap, stayed resident for the rest of the client's life with its producer gone.
Both fixed; both are load-bearing, verified by removing each independently.

### RPC3 — Reopening the same transport object after a disconnect left the client permanently dead

**File:** `src/remote/CodeharbordClient.cpp`. Rebinding began with "if you handed me the
device I already have, do nothing" — reasonable on its face. But a dropped connection
latches the client closed so nothing is written into a corpse, and only the rebind clears
that latch. So a caller recovering by reopening the **same** device object — nothing in
the API forbids it, and it is the natural thing to do with a long-lived channel wrapper —
got an immediate return, no latch clear, and a client that was permanently dead: every
call failing instantly forever, with no signal, no warning, and no recovery short of
recreating the client. The application would look connected while every operation failed.
The short-circuit now applies only when the client is not latched closed.

### RPC4 — Newline scanning used a 32-bit index into a 64-bit buffer

**File:** `src/remote/CodeharbordClient.cpp`. The frame-boundary index was declared `int`
while the search returns a 64-bit type, truncating any value at or above 2^31. The 16 MiB
cap is only enforced *after* the whole loop has run, so the loop is not entitled to
assume it. A truncating index would not merely mis-frame a message; it would feed a
negative or wrong length into the buffer operations and corrupt the stream in a way that
is very hard to diagnose.

### RPC5 — Oversize-line teardown could touch freed memory and released its buffer too late

**File:** `src/remote/CodeharbordClient.cpp`. When a peer streams more than 16 MiB with no
newline the stream is torn down. The old order emitted a public warning signal *first*,
then cleared the buffer and closed. A warning handler is allowed to delete the client —
the rest of this class is written very carefully to survive exactly that, guarding every
other emit — but here the following two statements would run against a destroyed object.
Buffer released before the emit; the existing self-guard checked before the close.

### RPC6 — Dead, misleading public API

**Files:** `src/remote/CodeharbordClient.{h,cpp}`. A public static function returned the
string `"codeharbord rpc --stdio"`, documented as the launch command. Nothing in the
repository called it. Worse than unused, it is wrong as guidance: the command the shipped
client actually runs is built elsewhere and is materially more complicated — it probes
several candidate entry points on the remote host, shell-quotes paths against injection,
and replaces the shell so the service inherits the SSH channel's input. Anyone who found
this function and used it would produce a command that only works if a `codeharbord`
binary happens to be on the remote account's search path, which the deployment model does
not assume. Removed.

### RPC7 — Four pieces of stale or incorrect public documentation

(a) The error object's optional `data` member was documented as null when omitted; it is
actually *undefined*, and Qt's "is null" test returns false for undefined, so a caller
following the comment to test "did the server send a payload?" got the wrong answer every
time. (b) The notification signal's comment claimed a message carrying both a method name
and an id is reported as a protocol warning; the implementation instead routes it on its
id like any other response, which *fails the matching caller* — deliberately, because a
garbled response echoing `method` back would otherwise be swallowed as a notification and
leave its caller hanging forever. (c) The call documentation did not mention transport
destruction and said nothing about timeouts; it now states plainly that there is no
per-request timeout, what that buys and what it costs. (d) The closed signal's
documentation now covers the new triggers and guarantees.

### RPC8 — Eight new test cases

Three defending the fixes above, plus five for pre-existing untested behaviour: a `null`
result is a success (this is the shape **every** void handler on the server answers with,
so it is the difference between "the delete worked" and "malformed response" on every
mutation the app performs); one read carrying a complete frame followed by the head of
the next (the framing case the two existing tests did not cover between them, where a
stale scan offset would hang the second frame forever); an out-of-range numeric id; a
notification with no parameters; and the undefined-`data` behaviour.

### RPC9 — Rebinding a transport from inside the destructor's failure sweep

Investigating a routed report (which turned out not to be a defect — the destructor
already latches closed *and* nulls the transport before dispatching, and the existing test
covers it) surfaced a real adjacent hole. Rebinding a transport is what *clears* the
closed latch, that being how a reconnect revives a client. A callback reacting to
destructor-time failure by reconnecting — reachable at shutdown through the controller's
error path into the session bootstrap — would un-latch a client inside its own destructor,
wire signals into a half-destroyed object, emit "transport bound", and then quietly accept
calls into a pending map nothing services. Fixed with a one-way "destroying" latch set at
the top of the destructor and honoured by both rebinding and calling. New test; with the
guard neutralised it fails on both counts.

## TS — terminal stack

### TS1 — Output produced before the terminal page finished loading was thrown away

**Files:** `src/terminal/TerminalBridge.{h,cpp}`.

The controller has a "the view is visible" flag whose real meaning is "there is a
renderer attached that is listening, so stop stashing bytes in the rolling buffer and
emit them". Three callers set it, and they do not all know the same things: the
JavaScript page (which knows it has mounted), the mount handshake, and the QML pane
(which reports the QML item's visibility and knows nothing about whether the page has
loaded). The QML value was passed straight through.

Concrete failure: the user opens a Dev Session, the pane appears, and the embedded
browser starts loading the terminal bundle — seconds on a cold start. Meanwhile the SSH
channel is already open and tmux has drawn its whole screen. If the pane is hidden and
shown during that window — switching Dev Sessions and back, collapsing and expanding a
split, minimising and restoring — the controller is told "visible" and emits every batch
at a page that has not connected a handler. Those bytes are gone: removed from the
rolling buffer, never re-sent, and the later mount handshake is a no-op because the flag
is already true. The user sees a completely blank terminal until they press a key and
make the remote shell redraw. This directly contradicted the documented design in the
same header.

The bridge now stores the reported visibility itself and computes the controller's flag
as "something wants to show it AND a renderer actually exists". The mount handshake also
resets the reported value, which is load-bearing rather than cosmetic: the outgoing page
reports "hidden" on its way out during a reload (deliberately, so a reload does not lose
output), and without the reset a reloaded page would permanently retain output behind a
renderer that is plainly on screen.

### TS2 — Trimming the hidden-pane buffer cut multi-byte characters and escape sequences in half

**Files:** `src/terminal/TerminalController.{h,cpp}`. While a pane is hidden its output
accumulates in a 2 MiB buffer; past the cap the oldest bytes are dropped. The code
dropped exactly the overflow — arithmetically correct, semantically wrong, because the
retained buffer is later replayed **verbatim** into the terminal emulator, so the first
byte kept is the first byte its parser sees. A byte offset chosen by subtraction lands
wherever it lands: in the middle of a multi-byte character (leaving continuation bytes
with no lead byte, which render as replacement glyphs) or in the middle of a colour or
cursor escape sequence (leaving `[1;31m` to be printed as literal text). A user who
leaves a pane hidden while a long build runs comes back to garbled text at the top of the
restored scrollback. The eviction point is now moved forward to the next line feed within
a bounded 4 KiB window (a line feed is ASCII and appears in no escape sequence, so the
byte after it starts both a fresh line and a fresh character), falling back to skipping
UTF-8 continuation bytes when a full-screen redraw goes that long without one.

### TS3 — A failed kill permanently orphaned the remote tmux session

**Files:** `src/terminal/TerminalFactory.{h,cpp}`. The factory remembers each pane's tmux
session name — the only handle anything in the app still has on the remote work — and
`kill()` forgot it **unconditionally, before even trying to run the command**. So if the
SSH connection had dropped (Wi-Fi hiccup, laptop resumed, server rebooting its network)
and the user clicked "Kill session", nothing was sent to the server but the name was
already erased. The remote tmux session and every process inside it — a running build, a
dev server holding a port, an agent — keeps running forever; a second attempt after
reconnecting is a silent no-op; and nothing in the UI can name that session again. The
name is now kept and the refusal reported, and it is cleared only after the command has
actually been handed to the server.

### TS4 — A failed re-attach left a pane pointing its Kill button at a *different* pane's tmux session

**Files:** `src/terminal/TerminalFactory.{h,cpp}`. The target was recorded only at the end
of a successful attach; every earlier failure left the *previous* attach's record in
place. So: a pane shows terminal `t1` of Dev Session `A`; the user retargets it at
terminal `t2` of Dev Session `B`; the re-attach fails (the server refused another
channel, the session dropped mid-call). The pane is visibly a `B`/`t2` pane, but the
factory still records `ch_A_t1`. The user clicks "Kill session" expecting to destroy the
terminal in front of them and instead destroys a *different* Dev Session's terminal,
taking its running processes with it — silent, unrecoverable loss on a pane the user
never touched. The target is now recorded as soon as it has been minted, before anything
that can fail. The success path also re-finds its hash entry rather than carrying an
iterator across calls that emit signals into QML, where anything is free to attach or
detach another pane and rehash the container.

### TS5 — Five new tests

`hiddenEvictionResumesOnACleanBoundary` (both branches of TS2),
`bridgeIgnoresAVisibleReportFromAPaneWithNoRenderer` and
`bridgeRetainsOutputForAHiddenPaneAndAcrossAPageReload` (TS1's two production shapes),
`bridgeIsInertOnceItsControllerIsDestroyed` (the bridge holds its controller weakly
because the two can die in either order, and every entry point is callable by the
embedded page for as long as the bridge lives — completely untested before), and a live
case for TS3.

### TS6 — Caller contract documented on attach

`src/terminal/TerminalFactory.h` lines 70-84 gained an explicit statement that the
terminal id must be unique **for ever**, not merely among live panes, and why this class
cannot detect a violation. This is the contract that PIR1 below was violating.

## VE — viewers and editor

### VE1 — A reload started by the system silently destroyed text the user typed while it was in flight

**Files:** `src/editor/EditorController.{h,cpp}`. When the file changes on the server and
the buffer is clean, the editor re-reads it — a network round trip. Meanwhile the editor
page reports typing back to C++ only on a 500 ms debounce, i.e. up to half a second late.
So this entirely ordinary sequence lost work: buffer clean, someone edits the file on the
server, the re-read starts, the user types a character, the debounced report arrives and
marks the buffer dirty, and then the re-read reply arrives and unconditionally clears the
dirty flag, adopts the server's revision, and makes the page **replace its whole buffer**.
The keystrokes were gone from the page, the pane believed it was clean, and the recovery
snapshot that still held them was cleared by the next successful save. Everywhere else in
the file the "never overwrite unsaved work" rule is carefully enforced; the reload reply
was the one hole.

The reload now captures an edit counter when the read is issued. If the counter has moved
by the time the reply lands: a *system*-initiated reload drops the fetched bytes, leaves
the buffer dirty and marks the pane externally-modified (the same answer the code already
gives when a change is noticed against an already-dirty buffer); a *user*-requested
reload replaces the buffer, because that is the whole point of the request. Proven by
mutation: with the guard disabled the new test fails, showing the old code really does
push the server's bytes over the user's typing.

### VE2 — An explicit reload left behind a recovery snapshot of the edits it discarded

**File:** `src/editor/EditorController.cpp` line 956. A successful save clears the pane's
crash-recovery snapshot; a reload the user asked for also makes it obsolete, but nothing
cleared it. So the next time that pane opened that file it would offer back content the
user had explicitly thrown away, and applying it would re-introduce the discarded edits
over the file. Now cleared.

### VE3 — A reloading editor page with unsaved work was never offered its recovery snapshot

**File:** `src/editor/EditorController.cpp` lines 468-484. A *second* mount handshake
means the page reloaded — a renderer crash, or a re-navigation — and its buffer is gone.
The old code responded with a plain re-read, which quietly replaced the user's unsaved
work with the server's bytes while the only surviving copy, the recovery snapshot, was
never mentioned (only a fresh open probes for one). A repeat handshake with a dirty buffer
now performs a full open, which re-subscribes the watch, re-derives writability, and
offers the snapshot back. A clean buffer still takes the cheap path.

### VE4 — The editor held the RPC client as a raw pointer and used it in its destructor

**Files:** `src/editor/EditorController.{h,cpp}`, `src/editor/EditorFactory.{h,cpp}`. The
destructor releases the server-side file watch through that pointer. The controller is
parented to a QML pane and destroyed with it, which is *not* guaranteed to happen before
the client — any owner that declares the QML engine before the client tears the client
down first, and the destructor then reads freed memory. The comparable viewer classes
already used `QPointer` for exactly this reason. Both members changed, every existing
`if (!m_client)` guard is now a real guard, and the three missing guards on chained calls
made from inside reply handlers were added.

### VE5 — The viewer profile object held the client as a raw pointer and read it much later

**File:** `src/viewers/ViewerProfiles.h`. The pointer is not *used* until someone first
asks for the privileged browser profile, which happens lazily and possibly long after
construction. If the client was destroyed in between, the stale pointer was handed to a
newly constructed URL handler whose own `QPointer` would then be initialised from a
dangling address — which a `QPointer` cannot detect. Changed to `QPointer`; the handler
is now simply constructed with no client and fails its reads honestly. An unused
forward declaration was also removed.

### VE6 — One viewer pane's file read cancelled every other pane's read, wedging those panes on "Loading…" forever

**Files:** `src/viewers/ViewerModel.{h,cpp}`. There is exactly one model object in the
application and every viewer pane calls it, but it tracked in-flight text reads with a
single **global** counter: a reply whose captured counter no longer matched was thrown
away. With more than one pane that is wrong twice over. Pane A starts reading `/a.txt`;
pane B opens `/b.txt`; the counter moves; A's reply is discarded and pane A shows
"Loading…" forever with no error and no content. Worse, the text pane's QML calls the
cancel function every time its URL changes, and that cancelled **all** in-flight reads —
so merely navigating in one pane killed the load of every other pane. The panes already
filter replies by path, so the global counter bought nothing.

In-flight reads were first re-keyed per path, which fixed the cross-path case. Review of
that fix found it still fragile for two panes on the **same** path, since one hash slot
cannot represent two concurrent reads of one file: pane A and pane B both open
`/notes.md`, B navigates away and cancels, and its cancel erases the only entry — so A's
reply *and* B's are both dropped and pane A hangs on "Loading…" forever, with the mirror
case stranding B instead. Two panes on one file is ordinary usage. Identity is therefore
now per **request**, not per file: every read is issued a token from one monotonic
counter, `readTextFile()` returns it, both reply signals carry it (the path is kept as a
second check), and `cancelTextFile(token)` cancels exactly one read. The pane remembers
its own token, cancels by it, and matches replies by it. The no-connection failure was
also made asynchronous, because reporting it before `readTextFile()` returns would carry
a token the caller has not yet been handed and could never recognise. Four new tests;
against the per-path scheme the same-path cancellation case fails with the stranded pane
stated numerically (zero replies delivered where one was expected).

### VE7 — A dead setter that silently did not work

**File:** `src/viewers/ViewerModel.h`. `setClient()` assigned the model's own pointer but
did not reach the profile object or URL handler it may already have created, which keep
their own copy taken at construction. Anyone building a model without a client and calling
this later would get one that reads text files fine but whose privileged URL handler stays
clientless forever, so every image and PDF pane would silently fail to load. Nothing in
the repository calls it, and it was not exposed to QML either. Removed, along with the
equally unused accessor.

### VE8 — The internal URL handler would read an arbitrary server path if a non-file URL were ever registered

**File:** `src/viewers/InternalUrlSchemeHandler.cpp` lines 199-225. Remote files reach the
embedded browser through opaque internal URLs whose identifier is looked up in a map to
recover the real `file://` URL. The map accepts *any* URL and the handler did not check
what came back: it took the local-file path, fell back to the raw path, and asked the
server to read it. A URL of any other scheme in the map — for example
`https://host/etc/shadow` — would have been converted into the server path `/etc/shadow`
and read off the remote filesystem. All three current call sites mint identifiers only for
`file://` URLs, so this is a latent hole rather than a live exploit, but the invariant was
written down nowhere. The handler now requires a `file://` URL and a non-empty path.

### VE9 — Clearing a recovery snapshot could write to an empty path

**File:** `src/editor/EditorController.cpp` lines 899-901. The snapshot path is built from
the pane id plus the server-reported recovery directory, both re-assignable at runtime.
Its two sibling operations bail out when the path is empty; this one did not, so it would
send a write for the path `""` — a guaranteed server error, swallowed silently, plus a
wasted round trip.

### VE10 — A stale "where to resume after the outage" state could be applied to a different file

**File:** `src/editor/EditorController.cpp` lines 552-556. When the transport drops the
controller remembers the state to return to on reconnect. Opening a different file reset
everything else belonging to the previous file but not this, so a pane that switched files
while disconnected could be restored into a state describing the file it had left.

### VE11 — The editor factory accumulated a dead entry for every pane ever opened

**File:** `src/editor/EditorFactory.cpp` lines 18-27. Entries for destroyed panes were
pruned only inside a function that fires at most once per connection, while panes are
opened and closed for the whole life of the process. Pruning moved to where the list
grows.

### VE12 — Incorrect comment about SSH channel slots

**File:** `src/editor/tests/tst_liveeditor.cpp` lines 606-626. The comment justified using
one long-lived command channel by asserting that a finished channel never gives its slot
back. False: the pool frees the channel unconditionally, and a live test runs 25
short-lived channels on one session precisely to prove slots are reclaimed. The
shared-channel design was kept — it is still right, for different reasons (avoiding a
channel-open plus exec round trip per command, and leaving the server's per-connection
session budget alone) — and the comment now says so honestly and points at the proof.

Seven new tests were added across both areas, including
`textReadFailureModes`, which covers pre-existing untested behaviour: a server error is
surfaced verbatim, a file over the inline size cap is an error rather than a partial
document, a base64 payload is decoded, and a malformed one is reported instead of
rendering as an empty file.

## QM — QML user interface

### QM1 — Every button in every region header and every pane header did nothing at all

**File:** `src/qml/Main.qml`. Each pane area draws a title strip with "split side by
side", "split top and bottom", "close the focused pane" and, for terminals, "Kill". Each
pane draws its own "×". None of those can do the work themselves by design: changing the
layout means rewriting a tree that only the top-level window owns. So the area components
merely *announce* the request with three signals, and their comments state explicitly that
the window is supposed to listen and carry it out.

The window never listened. In Qt, an emitted signal with nobody connected is discarded in
silence — no error, no warning, no log line. Every one of those buttons drew normally,
highlighted on hover, animated on press, and then nothing happened. Splitting a pane,
closing a pane, and killing a runaway remote shell were reachable **only** through a
hidden command palette. Handlers added, plus a new function that resolves the two
different meanings correctly: a pane's own "×" names *itself*, whereas the area header
sends an empty string meaning "whichever pane you would have picked anyway".

### QM2 — Dragging a divider inside a pane area was never remembered

**Files:** `src/qml/ViewerRegion.qml`, `src/qml/TerminalRegion.qml`, `src/qml/Main.qml`.
Both area components already *read* stored split fractions and applied them on first
layout, and the C++ side already had the matching writer, documented and deliberately
written not to republish the tree (which would tear down and rebuild the panes, killing
live terminals). Nothing in the entire QML tree ever called it — it was the only declared
layout method with no caller anywhere. A user drags a divider to give one terminal 80% of
the height, works that way all afternoon, switches session and back, and the panes snap
to 50/50. The outer three-region widths *were* persisted through a different mechanism, so
the inconsistency was invisible in the obvious place and only bit inside an area.

The reporting side is now implemented symmetrically: each area instance knows its own
index path from the root (`[]`, `["1"]`, `["1","0"]`), which is how the writer addresses
branches; the layout container converts child sizes to fractions and reports them;
reporting is triggered only when a real pointer drag ends, deliberately not on size
changes in general, because writing back layout-driven sizes destroys the user's stored
preference (the file already documents that hazard for the outer widths).

### QM3 — The global Refresh shortcut stole Ctrl+R from every shell

**File:** `src/qml/Main.qml` lines 617-621. A window-wide shortcut is matched *before* the
key reaches whatever has the keyboard. Ctrl+R is reverse-history-search in every
readline-based shell — and every terminal pane in this application *is* a real remote
shell — as well as "reload page" in the embedded browser widget. The very same command
list already reasons about this two entries later, explaining that Close Window uses
Ctrl+Shift+W rather than Ctrl+W "because every terminal pane is a real shell, and Ctrl+W
is delete-word in all of them"; the rule had simply not been applied to Ctrl+R. Rebound to
Ctrl+Shift+R, with the palette screenshot fixture updated so the two cannot drift.

### QM4 — The error toast rendered server-supplied text as rich text

**File:** `src/qml/Main.qml` lines 323-339. A Qt label defaults to "upgrade to styled text
if it looks like markup", and styled text honours `<img src="http://…">` by actually
fetching the URL. Every other place in this module that displays server text explicitly
sets plain text, each with a comment explaining why — the connection sheet's error banner,
the terminal status line and banner, the binary view, the directory listing, the host-key
fingerprint panel, the pane headers. The window's own error toast, which shows RPC and
libssh failures **forwarded verbatim from the server**, was the one that did not. A
hostile or compromised server controls much of that text and could make the client fetch a
URL as soon as the toast appeared. Set to plain text.

### QM5 — The sidebar group header called an application method directly, contradicting its own contract

**File:** `src/qml/GroupHeader.qml`. The sidebar has a documented rule that it owns every
call into the application object and its sub-components go through it. This file states in
its own comments that its host is "null-guarded so the header stays usable standalone" and
then called an application method directly, unguarded. The application object is not a
property of the component but a context object installed by the host; looking one up that
is not installed throws and aborts the handler, so the "usable standalone" claim was false
— every other interaction degrades gracefully, this one throws. It also meant the mouse
and the Space key took two different code paths for one action. Both now go through the
host.

### QM6 — The connection sheet discarded unsaved edits when the host changed the active server

**File:** `src/qml/ConnectSheet.qml` lines 353-364. The active-profile property is pushed
in by the host whenever the application settles on a profile — which is exactly what
pressing **Connect** does. The handler unconditionally reloaded every form field from the
*stored* profile. So typing a corrected hostname or port and pressing Connect silently
threw the edits away. The sheet's other model-change path was already written carefully to
avoid this, with a comment saying "an edit already in progress is never interrupted"; this
path had no such guard. Now returns early when the newly active profile is the one already
being edited.

### QM7 — Saved-server rows were invisible to a screen reader

**File:** `src/qml/ConnectSheet.qml` lines 805-818. The rows leave the standard text
property empty and draw a custom two-line body, so the accessible name was empty and a
screen reader announced a stack of unnamed items. This is the identical defect already
fixed for the sidebar's session rows and the palette's result rows. It matters most here
because this is the keyboard surface of the one dialog a user meets *before* any server is
reachable — on a fresh install it is the only way into the product. Role, name, description
and selected state added, matching the other two.

### QM8 — The viewer pane re-implemented the shared remote-path conversion

**Files:** `src/qml/RemotePath.js`, `src/qml/ViewerPane.qml`. Inside this application a
`file://` URL always names a file on the remote server, and the remote file service speaks
plain server-absolute POSIX paths, so converting between the two is a security-relevant
rule that `RemotePath.js` exists to hold exactly one copy of — its own comment says so and
names the three files that call it. The pane that actually *drives* navigation, because it
owns the address bar the user types into, had its own private copy of the decoder and the
only copy of the encoder. The encoder is the delicate half: it percent-encodes each path
*segment* individually and leaves the separators alone, which is what makes it an exact
inverse. Getting it wrong does not fail loudly — it reads a *different remote file* from
the one whose name is on screen (a file called `notes#1.txt` becomes a URL with a fragment
and the pane reads `notes`). Moved into the shared file, with an explicit note that a
backslash is an ordinary character in a remote POSIX filename and is encoded like any
other, never treated as a separator.

### QM9 — Typo in a user-visible sentence

`src/qml/ViewerPane.qml:473` read "Type a remote path or **a** https:// address". Changed
to "an". Every translatable string in the module was extracted and reviewed; this was the
only defect.

### QM10 — Dead duplicated CMake block

`src/qml/tests/CMakeLists.txt`. The Windows console-mode property for one test was set
twice — once correctly after the target, and again at the end of the file inside the
section configuring a *different* test, with a comment claiming it had to be applied
later. The second was a no-op left over from an earlier arrangement, sitting under the
wrong target where it invited someone to "fix" it by editing the wrong thing.

### QM11 — Three new tests

`regionRequestsReachTheHost` (loads the real shipped window and emits each of the five
region requests the way the header buttons do; before QM1 it fails on the first case),
`dragAdjustedRatiosAreReportedForTheRightBranch` (a deliberately two-level tree, because a
single-level one would pass even with wrong index-path arithmetic), and two cases for
`RemotePath.js`, which had no test of its own anywhere — round-tripping eight paths chosen
for the ways the conversion breaks: a `#` in a filename, a space, a `?`, a backslash, a
directory's trailing slash, the filesystem root, a non-ASCII segment, and a path already
containing a literal `%20`.

### QM12–QM16 — Terminal pane fixes routed from the terminal reviewer

**QM13** (`src/qml/TerminalPaneView.qml`): killing a session overwrote the failure message
it had just caused. The QML called the factory's kill and then unconditionally set the
status to "Session killed. Connect to start a new one." — but the factory's error signal
is emitted **synchronously** from inside that call and lands in the pane's error handler,
which sets the status, and was then immediately clobbered. After TS3 this matters
concretely: a kill that could not run reports "the tmux session is still running and was
not killed", and the user was shown "Session killed" instead. The function now returns
whether the kill actually reached the server, determined from the factory's own observable
(the remembered target, which detach preserves and kill clears only once the command is
away), and only then claims success. The palette command one level up had the same false
claim and was fixed too.

**QM14**: the "attaching…" header label was effectively unreachable, because it was driven
by a flag set and cleared around a *synchronous* call. The genuinely long-lived attaching
window is the connection state being "opening channel" or "attaching tmux", which the
label never tested — so a pane that really was attaching (up to a 60-second budget)
displayed "starting…". A derived property now covers both, deliberately without
repurposing the re-entrancy flag, whose comment states it is not part of the observable
contract.

**QM15**: a comment claimed the connection state publishes a machine word `notconnected`.
No such state exists; the real set is `unloaded`, `opening_channel`, `attaching_tmux`,
`ready`, `disconnected`, `error`. Both affected comments corrected against the enumeration
and its pinning test.

**QM16**: changing the working directory of a live pane is silently ignored, while changing
the Dev Session or terminal id re-attaches. Verified this is correct — the directory only
ever reaches the server as `tmux new-session -A -c <dir>`, and tmux honours `-c` only when
it actually creates the session, so re-attaching would cost a full attach and land in the
same place — and documented it, along with the second thing the handler protects (a
not-yet-attached pane adopting a late directory, which is what makes the ordered retarget
push work).

### QM17 — A build-system glob that could miss a brand-new source file

`src/qml/CMakeLists.txt` line 102. The check deciding whether to rebuild a web bundle
globbed the bundle's TypeScript sources, but CMake evaluates a plain glob only at
configure time and does not re-run configure when the *set* of matching files changes. So
adding a brand-new source file did not by itself trigger a reconfigure and could be missed
— which is exactly what happened when the web reviewer added a new file during this round.
Added the `CONFIGURE_DEPENDS` clause, and rewrote the comment to explain that the glob
catches files *appearing and disappearing* while the separate property at the end of the
function catches *edits to files that already exist*, so both are needed. Verified by
building a miniature copy of the same shape and observing the difference. A repository-wide
search confirmed this is the project's only glob.

## AGT — agent status monitoring

### AGT1 — The client accepted agent events whose Dev Session id or terminal id was blank

**File:** `src/agent/AgentEvent.h`. The parser's own comment says it mirrors the server's
validator "field for field". It did not: for the two fields saying *which terminal in
which Dev Session this is about*, the C++ side checked only "is this a JSON string?" while
the server demands at least one non-whitespace character. So an event carrying an empty id
was rejected by the daemon but **accepted** by the client.

Every other component in the chain treats a blank id as fatal at the edge and each one
documents why, naming the client as the victim: the agent hook refuses to emit and prints
an explanation because "an event carrying a blank id reaches the client as a valid event
that belongs to no Dev Session"; the bridge re-checks both ids; the event validator says an
empty identifier "is worse than a malformed event — it is structurally valid, so the bridge
relays it and the client accepts it, but it names no row". Concretely, a blank id from any
producer that is not our own hook would create a bookkeeping subtree no sidebar row can
display and, for the two attention states, raise a real desktop notification whose body
reads literally `" / "` and points at nothing. The client was the last edge in the chain
and the only one trusting its input. Whitespace is used only as the emptiness test, never
as normalisation: server-minted ids are echoed back byte for byte.

### AGT2 — Dead code with an authoritative-sounding comment

`src/agent/AgentEvent.h`. A helper sat in the internal namespace with a nine-line comment
explaining its contract; nothing called it. An earlier refactor made the token table the
single entry point and left this behind. Dead code like this invites the next maintainer to
"keep the two lists in sync" — a job that no longer exists — and offers a second, unused
entry point into the wire contract.

### AGT3 — Line framing assigned a 64-bit offset into a 32-bit variable

`src/agent/AgentStatusMonitor.cpp` line 87. Same class as RPC4: the 1 MiB oversize guard
normally keeps the buffer small, but that guard runs *after* the loop on data the loop has
already walked, so the loop is not entitled to assume it.

### AGT4 — Redundant per-line work on the only hot path

`src/agent/AgentStatusMonitor.cpp`. Every line was stripped of a trailing carriage return
and tested for blankness, both of which the parser already does unconditionally as its very
first act. One throwaway heap allocation per event, and two places that both look like they
own "how a frame is delimited". Removed, with the loop's comment updated so the behaviour
is not accidentally "fixed" back in.

### AGT5 — After an oversized unframed line was dropped, its tail was parsed as an event

`src/agent/AgentStatusMonitor.{h,cpp}`. When a producer streams past the 1 MiB cap with no
newline, the buffer is thrown away — but the bytes still arriving belong to the *same*
frame, by construction, because the buffer contained no newline when it was cut. Those
leftovers were framed as a line of their own and parsed. The client had invented a frame
boundary the producer never wrote. Normally the fragment is garbage and is rejected, but
relying on an arbitrary cut point never landing somewhere that happens to parse is exactly
the kind of thing that eventually bites, and a bogus event would silently overwrite a
terminal's real state. A discard flag now consumes everything up to the next newline
without parsing it, and is reset when a new transport is bound so a pending discard cannot
eat a new producer's genuine first frame.

### AGT6 — The desktop notification was raised before the state it describes was published

`src/agent/AgentStatusMonitor.cpp` lines 150-171. The order was state-changed →
**notify** → unseen-changed, all direct connections. So the operating-system bubble was
raised before the "this Dev Session has unseen output" flag had been announced to the UI,
and the user could see a notification pointing at a Dev Session whose sidebar row had not
yet grown its badge. A small window, but the wrong order on principle: a side effect must
not run ahead of the state publication it describes. Reordered; no signal added, removed
or gated differently.

### AGT7 — The live gate silently swallowed a failure to clean up its remote scratch directory

`src/agent/tests/tst_liveagent.cpp`. The teardown discarded both the result and the remote
error output. That directory holds the gate's private socket, and a stale socket file is
exactly the condition the bridge has to probe and recover from — a cleanup that quietly
does nothing is how that accumulates unnoticed. Now warns, without failing the test, since
a cleanup problem is not a product defect.

### AGT8 — Two documentation gaps with real caller consequences

`src/agent/AgentStatusMonitor.h`. Binding a transport drains anything already buffered on
it **synchronously**, so three signals can fire from inside the call — a caller that binds
first and connects afterwards silently loses those events, and the header never said so
(nor was there a test). And the state-changed signal is also emitted the first time a
terminal is seen even when the reported state is "unknown", which is intentional (going
from "no producer has ever mentioned this terminal" to "the producer says unknown" is a
real change of knowledge, and a test pins it) but read as a signal-without-a-change that a
future reader would delete as a bug. Both documented precisely.

### AGT9 — Fourteen new tests

Twelve unit cases taking the file from 20 to 32, including: blank identifiers rejected at
both the parser and monitor level; the buffered-bytes drain on bind, which is the only test
of the path that stops the first frames of a freshly opened channel being lost; rebinding
the same transport not duplicating delivery *and* not clearing a half-received frame; the
oversized-tail resync; error state not being a latch; only the two attention states raising
notifications while all six quiet ones do not; the notification body falling back to the
identifiers when there is no summary; out-of-order events applied in arrival order; and the
monitor being inert with no transport, which is the state it is left in between construction
and the channel existing and returned to on every disconnect. Plus two live cases covering
the "agent or hook error → error" and "shutdown → stopped" mappings the live gate never
exercised, asserting the whole chain from fake harness through the real hook, bridge, SSH
channel and monitor to the sidebar row state.

## ND — the Node daemon

### ND1 — All seven file operations accepted any payload at all, with four distinct harmful outcomes

**Files:** `remote/src/files.ts`, `remote/src/validate.ts`, `remote/src/rpc-types.ts`,
`remote/src/codeharbord.ts`.

The handler table used a TypeScript *type assertion* (`params as WriteFileParams`), which
generates no code and performs no check — it just tells the compiler "trust me". At run
time the value is whatever the client sent. The sibling workspace operations had a proper
guard on every field; the file operations had none. All four consequences below were
reproduced against the real daemon before fixing.

**A — a non-numeric permission mode chmod'ed the user's file to `000`.** The write path did
`params.mode & 0o7777` to keep the permission bits. In JavaScript the bitwise `&` first
coerces to a 32-bit integer, and any non-numeric value coerces to `0`. So a client sending
the mode as the *string* `"0600"` — an easy mistake, and what a JSON config or hand-written
script produces — ended up running `chmod 000` on the freshly written file. The save
reported success. The file was then unreadable and unwritable by its own owner.

**B — an omitted revision token was reported to the user as a save conflict that never
happened.** Every write carries the token received when the file was loaded; the server
refuses the write if it no longer matches. An absent field compares as `undefined`, which
never equals the real token, so the guard always failed and the daemon answered with the
*revision-mismatch* code — which the client treats specially by opening a "the file changed
on disk — reload or overwrite?" dialog. A plainly malformed request produced a scary and
completely fictional conflict prompt.

**C — an unrecognised encoding silently fell back to UTF-8.** For a client that meant
base64, that writes the base64 *text* into the file in place of the document's real bytes —
silent corruption reported as a successful save.

**D — a non-numeric offset produced a nonsense internal error** naming neither the method
nor the field at fault.

Fixed by adding a tagged invalid-parameters error class and four new guards (non-negative
index, integer in range, one-of a closed set, must-be-present), validating all seven
methods, and making the dispatcher answer such errors with JSON-RPC's "Invalid params"
code rather than "Internal error" — which told the client the *server* malfunctioned and
sent whoever debugged it looking in the wrong place. The five reserved error codes moved to
a module with no imports of its own so the validator can use them without an import cycle,
and are re-exported so every existing import site is untouched. The handler table's type
was tightened so a typo'd method key is now a compile error.

### ND2 — The layout operations accepted any string as the region name

`remote/src/workspace.ts`. There are exactly two regions. The handlers only checked for a
string. A bogus region *was* rejected — but by SQLite, several layers down, with a raw
constraint message naming neither the field nor the two acceptable values; and reading with
a bogus region did not even fail, it returned "this session has no layout", which is
indistinguishable from a genuine answer. The region type was compile-time only, so it could
not check a value at run time; replaced with a runtime array from which the type is
*derived*, so the two can never drift apart.

### ND3 — Setting a layout with no tree produced an opaque driver error

`remote/src/workspace.ts`. `JSON.stringify(undefined)` evaluates to `undefined` rather than
the string `"undefined"`, and passing that to the database driver raised a type error
naming no field.

### ND4 — Duplicating a Dev Session failed outright if any one stored layout was corrupt

`remote/src/workspace.ts` lines 889-910. Everywhere else in the module an unparseable layout
is treated as self-healing: it is logged and the region reports as having no layout. The
duplicate path was the one exception — it parsed bare, so a single corrupt blob threw, the
transaction rolled back, and the user's "Duplicate" action failed completely for a session
whose panes were all perfectly intact, with no recovery short of hand-editing the database.
Now skips the unreadable region, exactly as the read paths already do.

### ND5 — Every row-creating operation was a read-then-write with no transaction

`remote/src/workspace.ts`, four functions. Each reads the highest sort position in scope and
then inserts one past it, with nothing holding a lock in between. Two connections doing this
concurrently both read the same maximum and both insert at the same position — and every
listing query orders by position then id, so a tie is broken by the random primary key and
the newly created group, session or pane can appear anywhere in the sidebar rather than at
the end. The module's own comment calls this exact hazard out as load-bearing, and the
*update* operations were already wrapped for the same reason; the creates were simply
missed. Concurrency is real here: several daemon processes can have the same database file
open at once. All four wrapped in the existing helper, which takes the write lock *before*
the read.

### ND6 — Setting a layout could return a layout it did not write, and hid a possible null behind a cast

`remote/src/workspace.ts` lines 1114-1148. Three database operations with no transaction
around them: look up the parent session, write the tree, read it back to return it. A second
connection writing the same region in between made the method *return that other tree* as
though it were the one just stored, and the client renders a layout it never saved. The
read-back also ended in a cast that erased the `null` half of the return type — a lie the
compiler could not catch. Wrapped in one transaction; cast replaced with an explicit check.

### ND7 — A refused database left its connection open, locking the file for the rest of the process

`remote/src/workspace.ts` lines 411-436. The migration deliberately *refuses* a database
written by a newer build rather than corrupting it — but the throw escaped with the
connection still open, so SQLite's lock stays on the file for the process's lifetime and
every later attempt to open it fails for a second, unrelated reason. Exactly the kind of
misleading cascade that costs hours. Now closes and rethrows the original error.

### ND8 — The event bridge held on to producer sockets that disconnected while output was stalled

`remote/src/bridge.ts` lines 116-135. When the far end stops reading, the bridge pauses the
producer socket and records it in a set to resume later. Nothing ever removed a socket from
that set except a resume — so a producer that disconnected while output was still stalled,
and a permanently stalled consumer is the whole reason it was paused, stayed referenced for
the lifetime of the bridge process. Every agent that came and went during the stall added
another: an unbounded memory leak on the exact path already under stress. Now unsubscribes
on socket close, and no longer re-pauses an already-paused producer on every event.

### ND9 — The bridge socket had no maximum line length; one producer could exhaust the whole bridge

`remote/src/bridge.ts`. The line reader buffers an unterminated line with **no upper
bound**. A producer that streams bytes and never sends a newline — a wedged agent, or a
binary blob written to the socket by mistake — grows the bridge's memory until the process
is killed, taking down status reporting for *every* other agent on the machine at once. The
main daemon already defends against exactly this on its own transport; the bridge, doing the
same kind of line-framed reading, had no equivalent. Added a 1 MiB cap (smaller than the
transport's 16 MiB because a bridge message is a handful of short identifiers plus an
optional one-line summary, never file contents) and closed the line reader on socket close
rather than leaving one per connection attached for the process's lifetime.

### ND10 — tmux parameter errors were reported as server faults

`remote/src/tmux.ts`. A missing session name threw a plain error, which the dispatcher
reported as "internal error" — blaming the server for the client's malformed payload. Now
throws the tagged invalid-parameters error. The handler table type was tightened to match
the other two groups.

### ND11 — A redundant unchecked cast

`remote/src/workspace.ts`. A handler called the string guard, discarded the validated value
it returns, and then re-read the raw field with a cast. Harmless today, but it is the pattern
that produces unchecked casts everywhere else.

### ND12 — Stale type name in a comment

`remote/src/codeharbord.ts`. A comment explaining response ordering said the C++ client keys
its pending callbacks in a 32-bit-id map; it is 64-bit. Verified against the C++ header and
corrected.

Thirteen new tests were added across four files, and the pre-existing test that used the
corrupt-JSON throw as its *mechanism* for injecting a mid-copy failure was re-targeted at
the same property (atomicity) using a database trigger, so ND4 did not weaken it.

## WA — the web bundles

### WA1 — A collapsed terminal pane resized the remote shell to 2 columns by 1 row and destroyed its contents

**File:** `src/web/terminal/src/index.ts`. The terminal's "fit" helper measures the element
it draws into, computes how many character cells fit, and resizes. The page called it at
start-up and from a size-change observer with no guard. That helper does **not** bail out
when the element has collapsed: its shipped source clamps its proposal with
`Math.max(2, …)` and `Math.max(1, …)`, so a zero-sized element does not produce "no
proposal" — it produces a perfectly valid-looking **2 columns by 1 row**, and the resize
really happens.

Every terminal pane attaches to a tmux session. Telling the server "my terminal is now 2
columns wide" makes tmux re-wrap every line of the session — visible screen and scrollback
— to two characters per line. That is destructive and irreversible: widening the pane again
restores the *size*, but tmux cannot un-wrap text it already re-flowed, and any full-screen
program inside has already redrawn for a 2×1 screen. Reaching a zero-sized pane is ordinary
usage: dragging a splitter fully shut, collapsing the terminal region, or a layout that
keeps the page alive at size zero. The start-up call had the same problem from the other
direction, sending a bogus 2×1 as the *initial* size.

(An element hidden with `display:none` was already safe by accident, because the browser
reports its computed height as the string `"auto"`, which parses to not-a-number and *is*
checked. A zero-*sized* element reports `"0px"`, which parses to the number 0, and was not.
That is exactly why this slipped through.) Both call sites now go through one helper that
skips the fit when the element has no laid-out box; the observer fires again the instant it
regains one.

### WA2 — Terminal output had no flow control, so a large burst threw inside the bridge dispatch

**Files:** new `src/web/terminal/src/writer.ts`, `src/web/terminal/src/index.ts`. Output was
passed straight to the terminal emulator's fire-and-forget write, which queues data for a
parser running on the browser's main thread. That queue is **not** unbounded: the shipped
source throws once more than 50 MB of unparsed output has piled up, with the message "write
data discarded, use flow control to avoid losing data". The producer is a remote shell over
a socket and can easily out-run the parser for a sustained burst — `cat` of a large log,
`yes`, a base64 dump, a chatty build. The exception is thrown from inside the bridge signal
handler, so the batch is lost, the exception escapes into the bridge's own dispatch loop and
skips any other handler for that message, and every subsequent write keeps throwing until
the parser drains. The pane goes silent and stays wrong, and nothing caught or reported it.

Added a coalescing writer implementing the rule the library documents: hand the terminal at
most one chunk at a time and send the next only when it acknowledges the previous one;
anything arriving meanwhile accumulates and is delivered as a single coalesced chunk. The
ceiling becomes unreachable, so the failure mode is removed rather than caught and hidden;
no data is dropped (the backlog holds exactly the bytes the terminal has not consumed yet —
the same bytes that would otherwise sit inside its own queue); and coalescing many small
batches is measurably cheaper for the parser.

### WA3 — Output, clear and state updates arriving after teardown ran against a disposed terminal, and disposal was not idempotent

`src/web/terminal/src/index.ts`. Teardown disconnected the browser observers but did not
stop the bridge signals — the C++ side stays connected until the page itself is gone — so
output could still arrive and reach an already-disposed terminal, which has no disposal check
of its own. And the disposal function had no re-entry guard while the page registers a
navigation handler that calls it, so disposing explicitly and then navigating away disposed
twice. Same class of failure as WA2: an exception inside a bridge signal handler at the worst
possible moment. A disposed flag now short-circuits the three entry points and the disposal
itself, and the coalescing writer is closed first so a late acknowledgement cannot push data
into a dead terminal. The existing ordering — report "renderer hidden" *before* disposing, so
the C++ controller resumes retaining output instead of emitting it into the void — is
preserved exactly.

### WA4 / WA5 — Bridge signal handlers were connected anonymously and could never be detached

`src/web/terminal/src/index.ts` and `src/web/editor/src/index.ts`. Both pages connected their
C++ signals with inline arrow functions. The bridge library stores every handler for the life
of the channel, and because no reference was kept, disconnecting was impossible by
construction — the subscriptions were permanent. For the editor this is a concrete failure:
the pane is torn down, or *retargeted* (the host reloads the page to point at a different
file) while the channel is still open, so a content-loaded signal already in flight sets a
value on a disposed editor, which throws; and the save-conflict and save-error handlers build
DOM nodes and attach click listeners to a status bar that is being removed. Both pages now
keep named handlers and detach them on teardown, the editor through a small helper that
records the matching disconnect at each of six connect sites.

### WA6 — A read-only file opened as an editable surface when the page connected late

`src/web/editor/src/index.ts`. Read-only state was learned **only** from a change signal, and
a Qt signal fires on a transition — it does not replay. The page connects asynchronously and
can easily finish loading after the C++ controller has already opened the file, checked its
permissions and emitted the signal, which then goes nowhere. The page already solved exactly
this for the *other* piece of late-bound state by reading a cached property at start-up, with
a comment explaining why signals alone are insufficient; the read-only flag is declared as a
property right next to it and was simply never read. The user is shown an editable buffer for
a file they cannot write, types, gets a dirty buffer and a recovery snapshot, and discovers
the truth only when the save is refused — an outcome the C++ header itself names as the thing
to avoid. Added the symmetric start-up read.

### WA7 — Language detection by filename was case-sensitive while detection by extension was not

`src/web/editor/src/language.ts`. Two adjacent loops in one twenty-line function disagreed
about case. The editor ships the Docker language registered under the exact name
`"Dockerfile"`, and a file literally named `dockerfile` is completely ordinary on a Linux
server — and this application's files always live on a Linux server. Such a file silently
fell through to plain text and lost all syntax highlighting with no indication why. VS Code,
which uses the very same registration lists, matches filenames case-insensitively. Lower-cased
the basename once at extraction and each registered name at comparison.

### WA8 — Save-conflict buttons rendered as unstyled native browser buttons on a dark bar

`src/web/editor/index.html`. When a save is refused the page builds a notice containing real
buttons — "Reload", "Overwrite", "Retry" — and the stylesheet had a rule for the container but
**none for the buttons**. Chromium then falls back to its native appearance: a light-grey
bevelled slab in the platform default font, on a near-black status strip, inside an
application whose page shells carry an explicit, heavily-commented contract that every colour
must be a copy of a role in the shared theme. So the only controls a user ever sees in that
pane were also the only controls that visibly did not belong to the application — appearing
precisely when the user is asked to make a risky choice. Styled with colours verified one by
one against the theme file, plus a visible keyboard focus ring.

### WA9 — Neither web package typechecked its own tests

`src/web/terminal/tsconfig.json`, `src/web/editor/tsconfig.json`, both package manifests. Both
configs included only the source directory, so the test files were outside the compilation
entirely. They still *ran*, because Node strips TypeScript types and executes directly, but a
test whose assumptions no longer match the module — wrong argument order, a removed field, a
renamed type — would fail only at runtime and only if that line was reached, and a test
importing a type that no longer exists would not be flagged at all. These are the only
automated protection those two bundles have, so the safety net was not itself checked. Both
configs now mirror the daemon's, which already did this correctly, and the type package they
were resolving only by accident through workspace hoisting is now declared properly.

### WA10 — Sixteen new test cases

Six for the new flow-control writer, driven by a fake consumer that holds the acknowledgement
so the test decides when the parser finishes and that actively asserts it is never handed two
chunks at once. Five for language detection, including a registration with neither pattern
list, which the editor really does ship. Five for the unsaved-work snapshot scheduler,
asserting against the fake clock's armed-timer count rather than only the reporter's own flag,
so a cancel that forgot the timer would be caught.

The built bundles were confirmed **not** stale before any change (byte-identical rebuild) and
were rebuilt afterwards.

## BD — build, CI, packaging, documentation

### BD1 — The dependency lock file was a full release behind every manifest

`package-lock.json`. Every manifest said `0.1.8`, as did the build system's version, but the
lock file — the file npm actually installs from — still recorded `0.1.7` in all five places it
stores a version. The strict install used by CI does not merely read the lock, it makes the
tree match it: running it printed `change @codeharbor/remote 0.1.8 => 0.1.7`, silently
**downgrading** the manifest on disk. The release workflow then packages that directory and
publishes it, so a release tagged `v0.1.8` was shipping a server package declaring itself
`0.1.7`.

### BD2 — The version-bump script never touched the lock file, so the drift would return

`.omp/skills/bump-version/bump.sh`. The script has an explicit list of every file carrying the
release version and rewrites each one; the lock file was not in it, and npm does not update it
unless someone runs an install. That omission is the direct cause of BD1. The script now
rewrites the lock's root and per-workspace entries too, formatted exactly as npm does
(verified byte-for-byte idempotent), stages it with the release commit, and treats a missing
lock as a hard error like a missing manifest.

### BD3 — Nothing could ever catch version drift, so CI now does

New `.github/scripts/check-versions.mjs`, wired into CI. The existing comment claimed the
strict install "fails if the manifests and lock have drifted" — true only for *dependency
ranges*; for a package's own version it silently rewrites, which is exactly how BD1 survived a
release. The script reads the authoritative version out of the build system and asserts it
against every manifest and every lock entry, and runs **before** the install (running it after
would read files the install had already rewritten).

### BD4 — CI never ran the web-asset test suites at all

`.github/workflows/ci.yml`. The two web packages have real test suites covering editor
language selection, unsaved-work scheduling and terminal visibility. The daemon job tested
only the daemon; the client job built and typechecked the bundles but never ran their tests.
Typechecking does not catch logic bugs, so a regression in either bundle could reach a
published release with a fully green CI.

### BD5 — Cache action misuse produced a guaranteed post-job save collision

Both workflows. They used the *combined* cache action to restore the Windows dependency tree
and then also ran an explicit save step with the identical key. The combined action registers
its own save at the end of the job, so on any cache miss the entry is saved twice under one
key: the explicit step succeeds and the automatic one fails with "already exists", producing a
confusing red annotation on every cold run. Switched both to the restore-only action, which is
what the existing comment on the explicit save already intended.

### BD6 — The release publish gate accepted an installer with the wrong version

`.github/workflows/release.yml`. The pre-publish check globbed for the Windows installer with a
wildcard matching *any* version. If someone tagged `v0.2.0` on a tree whose version file still
said `0.1.8` — i.e. tagged by hand instead of through the bump script — the release page for
`v0.2.0` would receive an installer naming itself `0.1.8` and registering `0.1.8` in Windows'
installed-apps list. A tag is permanent, so this is unrecoverable without a new release, and a
wrong version is worse than a missing one because nothing looks broken. The check now derives
the version from the tag and requires the exact filename, listing the directory's real contents
on failure.

### BD7 — The anti-scaffolding gate passed silently when its search failed

`tests/no_scaffolding.sh`. The script greps the tree for leftover debug markers and ran the
search with `2>/dev/null || true`. Grep distinguishes three outcomes — found, not found, and a
real failure such as an unreadable tree or a missing directory — and that idiom collapsed all
three into "success" while hiding the reason. A broken search printed "no scaffolding markers
found" and passed: the precise class of false-green this gate exists to prevent. All three
paths were then exercised by hand to confirm the fix.

### BD8 — A documented build switch was undeclared and therefore invisible

`CMakeLists.txt`. Both the README and the development guide tell users to pass a flag to build
without the web bundles. The variable was only ever *read*, deep inside a subdirectory, and
never declared — and an undeclared cache variable does not appear in the CMake listing, in the
interactive configurator, or in any IDE's settings panel, so a documented switch was invisible
everywhere a user would look. Declared properly next to the existing test option.

### BD9 — CI ran duplicate full builds for superseded commits

Neither workflow declared a concurrency group, so pushing three times to a pull request started
three concurrent Qt and WebEngine builds, two against commits nobody cares about. Added a group
keyed on workflow and ref, cancelling in progress **only** for pull requests — pushes to the
main branch are deliberately never cancelled, because the dependency-cache warming job runs only
there and cancelling it would leave the shared cache cold.

### BD10 — A CI step name claimed to do three things and did one

It was named "Configure + build + test" but only configured; build and test were separate steps
below. Anyone reading a failed run's step list would mislocate the failure.

### BD11 — Following the documented live-test instructions produced a fake green run

`docs/DEVELOPMENT.md`. The document lists an environment table correctly stating that a flag
must be set or every live test skips itself — but the copy-paste command block immediately
below, the part anyone actually runs, omitted that flag and three others. None of them has a
default. Following the instructions verbatim therefore skipped every live test and reported a
passing run that proved nothing: the exact failure mode this whole section of the document rails
against. The block now exports all of them with values matching the fixture configuration it
writes two paragraphs earlier, and the prose states that omitting the flag yields a meaningless
green run.

### BD12 — The README described the persistence module as something it explicitly is not

It said "Qt SQL access to the remote SQLite workspace database". Wrong twice over and
contradicting three other places in the tree: that module links no Qt SQL component, the
top-level build file has a comment explaining that Qt SQL is deliberately absent, and the
development guide tells Linux users not to install a Qt SQL driver. All workspace persistence
goes over remote procedure calls; the client opens no database.

### BD13 / BD14 — The Windows installer was undocumented

The README's download table offered Windows users only a zip, though the release has built a
proper per-user installer for some time, uploads it as a separate asset, and now refuses to
publish without it — the single most user-friendly artifact was undocumented. The development
guide's artifact table likewise listed only the executable and its libraries. Both corrected.

### BD15 — The preset documentation omitted the preset CI and releases actually use

The guide described two build presets. There is a third, and it is the only one CI and the
release workflow ever use; it also deliberately shares a build directory with its sibling, which
is surprising behaviour explained nowhere. All three are now described with their directories and
the reason.

### BD16 — A plan document pointed readers at a number another document refuses to state

It recorded a bootstrap-era test count and added "see the development guide for the current
count". That guide says the opposite in as many words: the count is *deliberately* not pinned
there because it went stale three times. The same list also described CI as having two jobs when
it has three.

### BD17 — A specification section contradicted another section of the same document

Section 14 omitted two source directories that have existed for a long time, described a
completely fictional layout for the remote component, and listed Qt SQL among the technologies —
directly contradicting section 11.2 of the same document and the build system. Retitled from
"Proposed Code Architecture" to "Code Architecture", both trees corrected against the actual
repository, and the technology list replaced with what is actually used, carrying the real
version floors.

### BD18 — Keyboard-shortcut documentation was stale and incomplete

Both the README and the specification still listed `Ctrl+R` for Refresh after QM3 changed it, and
verifying that surfaced a second, pre-existing gap: a `Ctrl+Shift+W` binding for Close Window
existed in the command list and was documented nowhere. Worse, the specification's reconciliation
table has a row saying `Ctrl+W` (close active *pane*) is not implemented — so a reader who then
discovered `Ctrl+Shift+W` would reasonably assume it closes a pane, when it closes the entire
window. Both tables corrected, with a paragraph explaining that both deviate from their originally
suggested plain sequences for one shared reason (a window-wide shortcut is matched before the key
reaches the focused widget, and every terminal pane is a real shell where `Ctrl+R` is
reverse-history-search and `Ctrl+W` is delete-word), and an explicit warning on the `Ctrl+W` row.

## PIR — recycled pane identifiers

### PIR1 — Closing a terminal pane and splitting again gave the user back the shell they had just closed

**Files:** `src/app/UiStateStore.{h,cpp}`, `src/app/SessionLayouts.{h,cpp}`,
`src/app/main.cpp`, three test files.

Every pane in a layout has a short client-minted name, `terminal-1`, `terminal-2`, and so on.
That name is not decoration: it travels unchanged into the name of the remote tmux session
(`ch_<DevSessionId>_<paneName>`), and the client attaches with the tmux command meaning "attach
if it exists, otherwise create".

The minting rule was "one past the highest number currently in this region's tree", which
recycles. Closing a pane deliberately does **not** kill the remote shell — it detaches, which is
how a pane survives a disconnect, and that behaviour is documented at three separate layers. So:
the user has `terminal-1` and `terminal-2`; closes `terminal-2`, whose shell, scrollback,
directory and running processes are all still on the server; splits again; the highest number
left is 1, so the client mints `terminal-2` again; and that pane attaches the session that still
exists. The user asked for a new terminal and got the one they closed. The working directory the
new pane requested is silently thrown away too, because tmux honours the "start here" option only
when it actually creates a session. The worst version is emptying the terminal region completely,
where the counter restarted at 1 so the next pane opened was guaranteed to be pane one's old
shell.

The name was being treated as a property of the *current* layout when it is really a property of
the *history* of the Dev Session. A name addressing a resource that deliberately outlives the
thing that named it must never be reused while that resource can exist.

Fixed by persisting a per-Dev-Session, per-region "next number" counter in the same settings
store that already remembers per-Dev-Session client-local state, with the same empty-id guard as
its siblings. Minting takes the **larger of** the stored counter and one past the highest number
currently in the tree. Both halves matter: the counter is the actual fix, and the tree reading
protects Dev Sessions that existed before this change (or a user whose settings were cleared or
moved to a new machine), where the counter alone would say "start at 1" and mint a name the
layout is already showing. Numbers are burnt at the single point every tree assignment funnels
through, not only at mint time, because closing a pane removes it from the tree — so "any number
this Dev Session has ever shown in this region is spent". The write only happens when the counter
actually moves, so dragging a splitter costs no disk writes.

Behaviour after the fix: a new Dev Session still starts at `viewer-1` / `terminal-1`; nothing
existing was renumbered; close-then-split gives a genuinely new shell in the requested directory;
emptying a region and reopening gives a new shell; the two regions count independently; two Dev
Sessions never consume each other's numbers; and quitting and relaunching does not reset the
counter — the case that matters most, because the remote sessions outlive the client process by
design.

Two existing assertions pinned the defect. One asserted that after closing the region's last
pane, splitting minted the same name again, with a comment saying the suffix "restarts at 1
because no numbered leaf is left in the tree" — the bug written down as an expectation. It now
expects the next number, with the reason recorded. The other was still correct under the new rule
and was left, with an extended comment noting it is now also the proof that the tree half of the
maximum guards a pre-change Dev Session. Three new tests cover close-then-split, refilling an
emptied region, and per-session independence plus survival across a restart; with the maximum
reverted to the old rule, all four fail.

### PIR2 — Two comments claimed the terminal identifier was server data

`src/qml/TerminalPaneView.qml`. Two comments said the identifier is "server-derived data". It is
the client-minted layout pane name, bound fifteen lines above. This is the false belief that hid
PIR1: if the identifier comes from the server, worrying about the client reusing it is nonsense.
Both now state the real provenance and why it must never be reused within a Dev Session.

### PIR3 — Known remaining limitation (not fixed)

The counter is client-local, so two different client machines sharing one Dev Session can still
collide: client A closes `terminal-2` leaving its shell running, client B splits, has no memory of
that number and does not see it in the tree, and re-mints it. Fixing this needs an identifier
minted or reserved on the server. The obvious vehicle exists in the database — a terminal-panes
table with unique keys and a tmux-target column — but is not wired up at all on the client: the
function that would create those rows has no caller anywhere in the application, which only ever
reads them. Making the client create them is a feature, not a bug fix. The mechanism added here is
exactly the shape a server-minted identifier would replace, and the replacement is a clean cutover:
one accessor pair in the state store and one function in the layouts object.

## ORCH — found during final integration

### ORCH1 — Two expected-value lists were written in reading order but compared after sorting

`src/qml/tests/tst_paneidentity.cpp`. A new test sorted its collected values and compared them
against literals written in human order. Sorting is by character code, so `"[0]"` sorts *before*
`"[]"` (`]` is 0x5D, `0` is 0x30) and the comparison failed even though the sets matched. Both
literals are now sorted too, with the reason recorded, keeping the expectation legible without
depending on that ordering quirk.

### ORCH2 — A live layout test measured pane geometry against the wrong item, and had been failing

`src/viewers/tests/tst_liveviewers.cpp`. Six cases in the live gate asserted that every pane spans
its parent fully across the split axis and that the first pane starts at the parent's edge, but
measured against the **region root** rather than the item that actually lays the panes out. A
region draws a header strip above its panes, so the layout container is inset from the region's
top by the header height and is that much shorter. Every pane was therefore reported as about 30
pixels short across the axis, and every vertical split as starting about 30 pixels down: correct
layout described against the wrong frame.

Confirmed pre-existing by building and running the same test from a clean checkout of the commit
before this round — identical six failures. The measurement helper now resolves the layout
container and measures against that, falling back to the region if one is ever absent. All eleven
cases pass.

### ORCH3 — A reconnect test compared a dangling pointer's address and failed intermittently

`src/app/tests/tst_livereconnect.cpp`. After forcing a dropped connection, the test asserted that
the rebuilt RPC transport is a *different object* by comparing the new raw pointer against the old
one — but the old object has been destroyed by then, and the heap is free to hand its exact address
back for the replacement. It really does: the test passed in one full live run and failed in the
next with no code change, and passed five times out of five in isolation.

Replaced with a stronger and address-reuse-proof formulation: the original transport is held in a
`QPointer`, which self-clears when its object is destroyed, so the test now asserts that the
original really was torn down (an observation about the object, not a comparison of a dangling
address) and that a replacement exists. Eight consecutive runs pass, and the null assertion
confirms the destruction genuinely happens, so the check is not vacuous.

### ORCH4 — The repository virtual environment was not ignored by git

`.gitignore`. This round introduced a Python virtual environment at `.venv` for tooling and
analysis. Added an ignore rule so it is never committed.

## Follow-up round — the deferred items

The first pass deferred a set of items because each needed a design decision rather than a patch.
Those decisions were taken and a second round implemented most of them. This section records the
original reasoning and the current status of each, so nothing reads as an oversight and nothing
reads as done when it is not.

### Implemented in the follow-up round

* **No per-request timeout on the RPC client** → **solved differently, on purpose.** A per-request
  deadline was rejected and stays rejected: one client carries sub-millisecond listing calls and
  multi-megabyte transfers over slow links, so any single value is useless or aborts legitimate
  reads. Instead a transport heartbeat answers an answerable question — is the peer still reading
  and writing? A `ping` every 15 s, four consecutive misses (about 60 s of silence) declares the
  transport dead and takes the failure path a real disconnect already uses, which the reconnect
  ladder already handles. Any inbound bytes count as evidence of life, so a slow large transfer is
  never killed. The honest limit is documented on the API: it bounds "the peer is silent", not "one
  reply was lost on a healthy link".
* **libssh's log callback and level are process-global** → **fixed** with a process-wide router that
  owns the global state, attributes lines to the right connection pool, and restores the previous
  state when the last pool releases it. Serialising handshakes was rejected as the worse property.
* **Watch notifications ignore output backpressure** → **fixed.** The daemon's queue is bounded and
  coalesces repeats per subscription and path. Genuine loss is no longer silent: it raises
  `file.watchEventsLost`, and the editor consumes it and re-reads — through the same guard that
  refuses to overwrite unsaved work, so a dirty buffer is flagged rather than replaced.
* **No uniqueness constraint on tmux targets** → **fixed** as schema version 3, with a migration
  that repairs existing duplicates before applying the constraint.
* **Terminal write backpressure bounded only inside the terminal emulator** → **fixed.** The page
  now acknowledges consumed bytes and the controller applies real backpressure using the bounded
  rolling buffer it already had for hidden panes, including its safe-boundary eviction rule.
* **Paths are not confined to the repository root** → **correctly still not confined**; that is
  specified behaviour and confining them would break a feature. What *was* missing is the other half
  of the same specification line — "the UI should indicate that the file is outside the project" —
  which was computed by the daemon and consumed nowhere. That is now implemented as a themed,
  accessible marker in the viewer pane.
* **No source maps, and the bundler never clears its output** → **fixed.** Source maps are opt-in,
  on for Debug and off for Release, so debuggability costs nothing in the shipped binary. Builds
  stage into a temporary directory and swap it in, and the swap itself rolls back if it fails, so a
  failed build can never leave the tree with no bundle.
* **A tmux target containing a colon could alias onto another session** → **fixed structurally.**
  There is now exactly one place that mints a target — the server — and it validates it. The
  client no longer mints one at all, so the two sides cannot disagree.
* **The profile store rewrites its whole settings group from memory** → **fixed.** Writes re-read
  and merge, deletions are tombstoned so they are never resurrected, and the whole read-merge-write
  runs under a `QLockFile` so two processes cannot interleave. If the lock genuinely cannot be
  taken the write still happens — losing the user's just-entered profile would be worse — and the
  user is told, through the ordinary non-blocking notice, worded so it is clear the profile *was*
  saved.
* **The pane-id counter is client-local, so two client machines could still collide** → **fixed.**
  A terminal's identity is now the server-minted `terminal_panes` row id, carried in the layout leaf
  itself rather than derived from a recyclable slot label. Layouts already stored on real servers
  have no id, so those fall back to the old key exactly once and then self-migrate.

### Still not fixed, deliberately

* **A server error carrying a null id fails nobody.** It cannot be attributed to a caller, so it is
  warned about and dropped. Failing *all* pending callers would turn one corrupted byte into a mass
  failure of unrelated healthy requests.
* **Two editor panes on the same file each handle the other's change notifications**, doing two
  re-reads instead of one. Correct, just wasteful. Filtering by subscription id risks dropping a
  legitimate event that arrives before the subscribe reply is recorded — a real ordering hazard for
  a cosmetic gain.
* **No client-side idle timeout for agent status.** By design: the specification puts activity and
  idle detection on the remote side, and says loss of the SSH channel is a transport condition
  reported by the client's own connection state. A client-side timer would invent a transition the
  producer never reported.
* **The daemon does not reap dead tmux sessions.** The client owns that lifecycle and calls the kill
  operation; server-side reaping risks killing a session another client is still using.
* **No "reattach an existing terminal" affordance.** This is the one genuine gap the identity work
  leaves. Closing a pane still keeps its remote shell alive and its row enumerable, and a new pane
  can no longer silently adopt it — but nothing in the interface offers it back yet, so a closed
  shell is currently reachable only through tmux directly. Implementing it needs orphan detection
  (rows present in the session's list but absent from its layout), a way to bind a new leaf to an
  existing row, and a discard action.
* **Two remaining residual limits on the profile store**, now that it is locked: a writer that does
  not cooperate with the lock (a text editor, or an older build) can still interleave, and two
  instances editing the *same* profile resolve last-write-wins per write. Both are documented in the
  header rather than silently assumed.

### Defects found by the follow-up round itself

These are the reason the second round was worth running the gates over, and all are fixed:

* **A terminal pane could hang for ever on a brand-new Dev Session.** A QML property binding was
  read from inside the very notification that refreshes it, so with the row id already present the
  attach still saw "no identity", declined, and nothing ever called it again. This would have killed
  every terminal of a new Dev Session on any server where the reply lands one event-loop turn later
  — that is, every real server. Caught by the cold-start live gate, not by any unit test.
* **Two daemons writing concurrently failed outright.** SQLite's default busy timeout is zero, so
  the transaction hardening added in the first round meant the losing writer reported "database is
  locked" as an internal server error instead of waiting a few milliseconds. Fixed with a busy
  timeout and write-ahead logging, and contention now maps to an honest, retryable error code.
* **The very first profile save always reported itself degraded.** The new lock could not be created
  because the settings directory does not exist until the settings framework lazily creates it,
  which happens *inside* the merge. Every new installation would have shown the warning on first
  run.
* **A test wrote to the developer's real workspace database.** The live RPC case spawned the daemon
  with no database path override, so it opened the real one under the home directory: order
  dependent, able to fail for unrelated reasons, and touching real user data. Now isolated to a
  temporary directory, matching its sibling test.

### Build speed

Investigated on the maintainer's 2-core machine. Precompiled headers were implemented, measured over
three full clean builds, and then **rejected**: they cut library object time by 37% and meta-object
compilation by 46%, but bought **0% on a clean build**, because generating them costs 115 s and
1.2 GB while 55% of this tree's build is 35 single-source test executables plus QML cache generation,
which a per-module header cannot touch. Shipped instead: automatic `ccache`/`sccache` detection (a
no-op until one is installed, then free), and an opt-in reduced-debug-info switch for test binaries,
default off because debugging a failing test is exactly when full debug information is wanted. The
measurements are recorded in `docs/DEVELOPMENT.md` so the experiment is inherited rather than
repeated.
