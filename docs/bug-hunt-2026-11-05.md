### Product structure

The remote TypeScript service owns the workspace database, remote files and tmux operations. C++ desktop/mobile clients talk to it through SSH and line-delimited JSON RPC. QML defines the user interface. Desktop terminal, editor and Markdown pages use embedded browser renderers; mobile terminal/Markdown/image/PDF views use native Qt components, with an optional platform WebView for web pages. Workspace records are server-authoritative; local settings retain profiles and presentation state.

A *pane* is one displayed viewer or terminal area. A development session groups panes in a repository. A display label such as `viewer-1` is not a globally unique document identity. A *revision* is the file-service value used to reject stale saves. Request counters let a callback recognize that its connection or document has been replaced. An agent *harness* means the coding-agent integration associated with a terminal; it is distinct from an audit worker. The remote agent-event relay is also distinct from the editor's browser-to-C++ document bridge.

### Audit method

The repository was mapped first, then divided among **18 section owners**, with separate focused Android and Darwin web-policy work and **12 independent review sections**. Shared interfaces and file ownership were coordinated centrally. Incidental findings outside a worker's section were routed back for reassignment rather than prompting unrelated searches. Shared instructions required the repository's `.venv/bin/python`, never system Python, and top-level imports/includes even for function-level fixes. Implementation workers did not run competing builds or test suites while shared changes were in flight; final integration checks exercised the combined result. Follow-up reviews covered the late editor reload, terminal input-generation, terminal-row refresh and QML import corrections.

Existing conventions and behavior tests were reused. Obsolete caller signatures and ambiguous raw recovery-ID APIs were removed, not preserved as compatibility shims. Incorrect incidental assertions were removed rather than pinned to a new implementation shape. Temporary smoke programs, keys, databases and local build-cache workarounds are not part of the source deliverable.

## Detailed findings and corrections

## Remote daemon, workspace, files, and integrations

### NDA1 — Retired bridge cleanup could delete a replacement listener's files

#### Context and failure

The bridge uses a lock file and Unix socket to identify the process receiving agent events. In `remote/src/bridge.ts`, `acquireBridgeLock()` originally returned a pathname, and `startBridge()` unconditionally unlinked that pathname when releasing the lock. If the old lock was moved aside and another listener published a replacement there before the old listener closed, the old listener removed the replacement's ownership record. A separate CLI process-exit cleanup could survive listener closure and later remove a new listener's lock or socket. `ControlListener.close()` in `remote/src/control.ts` also explicitly unlinked its socket after Node had already performed native close cleanup.

These JavaScript cleanup and lifetime problems are source-derived. A separate isolated runtime probe renamed a listening Node socket, installed a regular replacement file at the original pathname, and closed the server. Its output, `{"replacementPreserved":false}`, demonstrated a native Node close limitation, not a reproduction of the repaired lock cleanup.

#### Change and reasoning

`unlinkOwnedPath(path, identity)` compares the current entry's device and inode with the acquired file before unlinking. Lock acquisition records the staging file's identity before publishing it by hard link and returns an ownership-aware release closure. `startBridge()` now owns the single process-exit cleanup, records its bound socket identity, and unregisters cleanup on release or startup failure. The duplicate CLI cleanup is removed. Control closure relies on Node's socket cleanup instead of issuing a second unlink. Lifecycle comments, including an obsolete `destroySoon` description, are corrected. No wire protocol or public listener API changes.

The fix prevents known-stale JavaScript cleanup; it is not a new atomic cross-process locking protocol. An `lstat`/unlink pair still has a race, Node's native close can unlink an arbitrary replacement at its original socket pathname, and SIGKILL, abort, or machine loss can leave stale entries. Stale-lock reclamation retains its existing check/unlink contention window. Hostile-directory safety is not promised.

#### Checks and remaining limits

`remote/test/agent-hook.test.ts` adds a real private-directory regression: keep the original lock inode alive by renaming it, publish replacement contents, close the old bridge, and require the replacement to survive. This belongs to NDA1 even though the shared integration test file received the test. The socket probe must not be presented as proof that arbitrary replacement sockets survive close. Run the bridge/control lifecycle regressions and integrated remote checks.

### NDA2 — Viewer control startup ignored failure to enforce private socket permissions

#### Context and failure

`startControlListener()` in `remote/src/control.ts` creates its parent directory with requested mode 0700 and changes the bound socket to 0600. It previously swallowed every socket `chmod` failure, assuming the parent remained private. Recursive `mkdir` does not tighten an existing directory. With an already broadly accessible directory and permissive socket creation mask, failed permission enforcement could leave viewer-control operations exposed more broadly than intended. The ignored failure is source-observed; actual exposure under those conditions is inferred, not reproduced.

#### Change and reasoning

A failed socket mode change now closes the listener and rejects startup after close. The existing daemon bind-failure path disables agent pane control while preserving ordinary RPC service. The explanatory comment no longer assumes all runtime directories were freshly created. This follows the bridge's fail-closed permission policy without introducing another directory permission framework.

Unix-socket filesystems unable to enforce socket modes now lose this optional feature rather than receive an insecure fallback. No protection against same-UID processes, hostile pathname replacement, or the native close limitation described in NDA1 is claimed.

#### Checks and remaining limits

`remote/test/control.test.ts` adds a real temporary-socket test that injects `EPERM` from `fs.chmodSync`, requires startup rejection and abandoned socket removal, restores the syscall, and verifies the address can be rebound. The filesystem seam and directory are restored in `finally`. Appropriate checks are the permission-failure test, full control suite, and integrated remote typecheck/tests.

### NDA3 — Deep viewer results could disappear while the control listener encoded its reply

#### Context and failure

A `viewer.commandResult` can contain valid deeply nested JSON within the 64 KiB control payload limit. In `remote/src/control.ts`, `ControlListener.settle()` passed this data through `answer()` to `responseLine()`, which used recursive native `JSON.stringify` before checking bytes. Exhausting the JavaScript stack caused `answer()` to destroy the producer socket: a valid result became a closed-connection error. Deep oversized data could fail before reaching the intended structured size refusal. This is a source-derived failure at the control output boundary, distinct from workspace persistence and downstream CLI encoding.

#### Change and reasoning

`responseLine()` uses the single shared iterative `stringifyJson(response, MAX_CONTROL_LINE_BYTES)` from `remote/src/json.ts`. No control depth cap is introduced. Only `JsonSizeLimitError` selects the existing bounded `failed` refusal, including its warning that the operation may already have completed and current state should be inspected before retrying. The refusal itself uses the same bounded encoder. Ordinary invalid JSON conversion retains existing guarded failure handling. Control versions, error tokens, and request/reply byte limits are unchanged; the generic encoder implementation is accounted for under NWS3.

#### Checks and remaining limits

`remote/test/control.test.ts` adds a real listener/producer test carrying a 10,000-level object, approximately 60,004 bytes before its envelope, and checking all levels iteratively. A 12,000-level result must produce the structured oversized refusal, clear the pending slot, and allow a later command. Another test accepts exactly the payload-byte limit excluding newline and refuses one byte more. Existing flat oversized-response and exact request-boundary checks remain. The fix does not make completed desktop actions reversible, nor change native Qt's separate parser limit.

### NDA4 — Deep optional bridge metadata could hide the entire desktop state event

#### Context and failure

After deep hook metadata reached the bridge successfully, `makeStreamSink()` in `remote/src/bridge.ts` could lose it again through native recursive serialization. There was also a distinct consumer boundary: valid Node JSON below the 1 MiB bridge limit could exceed Qt's JSON parser nesting limit, so optional metadata made the entire state event unreadable.

An isolated integration `QJsonDocument` probe on Qt 6.10.2 accepted depths 1,023 and 1,024 and rejected 1,025 and 2,000 with error 12, `DeepNesting`. That is observed parser evidence. Loss through the full `AgentStatusMonitor` path is source-derived, not an asserted end-to-end reproduction.

#### Change and reasoning

The sink uses shared `stringifyJson` with its existing 1 MiB byte limit and an explicit bridge-only `MAX_BRIDGE_JSON_DEPTH = 1024`. The root event counts as container one. On a byte or depth resource error it retries without metadata first, then without summary, preserving core state and identity whenever optional decoration caused the refusal. If the core alone is too large/deep, existing drop/destroy handling remains. Ordinary serialization failures, including directly encountered cycles, retain that failure policy rather than being silently converted into success.

The shared helper gains optional `maxDepth`, defaulting to unbounded, and distinct `JsonDepthLimitError(depth,maxDepth)`. Objects and arrays add a container level; primitives do not; `toJSON` conversion precedes depth checking; cycles remain ordinary `TypeError`. Workspace, RPC, MCP, and control do not opt into this limit. This is compatibility with one known native consumer, not a project-wide JSON acceptance cap. SPEC §6.4 documents the output-only depth/byte limits and optional-field shedding.

#### Checks and remaining limits

`remote/test/agent-hook.test.ts` adds checks that 2,000/10,000-container metadata is shed while state and readable summary survive, source events remain unchanged, and frames remain bounded. Exact-boundary coverage retains total depth 1,024 and sheds 1,025: metadata with 1,023 containers fits the envelope, while 1,024 does not. Existing ancestor-cycle destruction coverage remains. `remote/test/json.test.ts` covers depth-error fields, conversion before checking, a scalar at zero container budget, cycles, and accepting the same deep value when no depth budget is supplied. These shared contributions belong here, not as another finding. Bounded traversal can encounter a resource limit before discovering invalid data farther inside an unreachable subtree; no exhaustive unbounded pre-validation is added. Future Qt versions may have different parser limits.

An additional integration smoke check exercised the actual compiled `remote/dist/bridge.js::makeStreamSink` with a valid running event containing 2,000 nested metadata levels. It preserved state/summary, omitted metadata, left the producer alive, and emitted no more than 1 MiB. A baseline-equivalent native `JSON.stringify` frame and the actual repaired sink frame were then supplied to a real Qt `QJsonDocument` executable: the former returned `12 refused`, while the latter returned `0 object`. This establishes producer-to-native-parser compatibility for that case, not full `AgentStatusMonitor` adoption/rendering.

### NWS1 — Saving through a retargeted symlink could overwrite an unrelated file

#### Context and failure

In `remote/src/files.ts`, `writeFile()` originally resolved the requested path to select a process-local lock, but `writeFileLocked()` checked the original pathname and later resolved it again for the rename destination. An external process could retarget a symlink between those operations and restore it before the final revision check. Both checks authorized the original file while the save replaced an unrelated destination.

An isolated pre-fix reproduction used two temporary files, a symlink, and controlled `fs.stat`/`fs.realpath` interleaving. It printed `{"original":"original","unrelated":"saved original"}`: the unrelated file was actually overwritten. Temporary files were removed.

#### Change and reasoning

The resolved lock target is passed into private `writeFileLocked()`, used for initial stat, staging, access checks, and commit, and checked again immediately before commit. When the request pathname differs, it is also revision-checked so ordinary symlink retargeting remains a visible conflict. The obsolete second resolution is removed and the atomic-save comment updated. `withWriteLock`, `resolveLinkChain`, and `assertRevisionMatches` retain their existing roles. Public RPCs, permissions/ownership behavior, flushing, and descriptor-derived success revisions do not change.

This aligns the locked, checked, and committed destination. It does not supply an OS-level compare-and-rename primitive: external replacement in the final check-to-rename window and hostile directory-component races remain possible. Existing hard-link behavior for ordinary atomic overwrites is unchanged.

#### Checks and remaining limits

`remote/test/files.test.ts` adds a deterministic real-symlink interleaving regression requiring a revision conflict, unchanged contents in both files, and no temporary leftovers. Existing symlink revision, dangling-link, and concurrent-save tests remain relevant. Symlink behavior requires platform support. Separately, a integration real-daemon API smoke check confirmed rejection of a retargeted save with both files unchanged; this is observed post-fix evidence in addition to the isolated pre-fix overwrite.

### NWS2 — Directory listing limits were applied after allocating the whole directory

#### Context and failure

`listDirectory()` in `remote/src/files.ts` used `fsp.readdir({withFileTypes:true})` and sorted the entire array before enforcing its existing 15 MiB serialized-entry ceiling. A directory with very many short names could exhaust daemon memory before an eventual response refusal. That resource effect is inferred from the source ordering; no huge-directory memory stress was performed.

#### Change and reasoning

The service now enumerates through `fsp.opendir()` and its async iterator, measures escaped serialized name bytes before retaining each entry, and refuses at the first entry over the same ceiling. Iterator finalization closes the directory on success or error. Only accepted entries and unknown-kind indexes are retained. Existing fallback classification stays in 64-entry batches; sorting occurs after classification so the indexes remain valid. Production enumeration and the exported collection-check helper share byte accounting. Errors say `at least N entries` because the tail is no longer enumerated. RPC shape and resource-limit code remain unchanged, and no partial listing is returned.

This bounds retained enumeration by encoded entry size plus Node's internal directory buffer, not by a newly invented entry-count policy. JavaScript object overhead can still exceed wire bytes substantially. The existing string representation of non-UTF-8 POSIX names is unchanged.

#### Checks and remaining limits

`remote/test/files.test.ts` adds a finite iterator provider with realistic maximum-length escaped names and extra entries past the ceiling. It requires consumption to stop at the first over-limit entry and iterator cleanup to execute. This avoids an unreliable RSS assertion or creating huge real directories. Existing sorting, hidden-file, empty/special-file, and serialized-boundary tests remain.

### NWS3 — Accepted deep layouts could fail during duplication, repair, or reply encoding

#### Context and failure

Workspace layout trees accept arbitrary client JSON subject to a 256 KiB byte limit, not a split-depth limit. Recursive `remapPaneIds()` and `children.map()` in `remote/src/workspace.ts` made an otherwise valid 2,200-deep layout impossible to duplicate. An isolated pre-fix SQLite `:memory:` reproduction stored that depth successfully, then received `RangeError` on duplication; shallower 1,000/2,000 samples duplicated. No database files were created.

The problem extended beyond remapping. Recursive pane-reference search, deletion repair, and native `JSON.stringify` could independently fail on accepted JSON. An intermediate integrated run exposed the latter after the first traversal-only repair, demonstrating that replacing traversal alone was incomplete. A separate exact-cap case found that deleting one of 65 leaves expanded 64 terse weights from `1` to `0.015625`; reapplying the public input ceiling to that server-derived result rolled back an otherwise valid deletion.

#### Change and reasoning

Pane remapping, reference search, and bottom-up deletion repair use explicit work stacks over fresh parsed copies, rewriting in place instead of cloning every node. Existing string/reference rules, foreign terminal identity behavior, sibling promotion, and finite-positive ratio normalization are preserved.

The new shared `remote/src/json.ts` provides `stringifyJson(value,maxBytes,maxDepth?)`, with byte overflow distinguished by `JsonSizeLimitError(bytes,maxBytes)`. Explicit traversal frames avoid JavaScript recursion; scalar/key escaping alone uses native serialization. Normal object/array order, omission versus array nulls, finite/nonfinite numbers, boxed primitives, `toJSON`, getter/conversion errors, and repeated non-cyclic references retain native-style semantics. Ancestor tracking rejects cycles. Unsupported root undefined/function/symbol returns undefined; BigInt remains an encoding failure. Default depth is unbounded; NDA4's optional bridge-only depth extension is not a global restriction.

`serializeLayoutTree()` preserves InvalidParams versus ResourceLimit mappings. Public `setLayout` and initialization inputs retain exactly 256 KiB. Internally derived duplication and repair have a separate bounded 4 MiB allowance, sixteen times the public cap. This conservatively covers growth from normalized numbers (up to 24 numeric characters plus separators), child encoding overhead, and short legacy references expanding to UUIDs. Using the same derived allowance for duplication keeps repaired trees duplicable. It remains below the 16 MiB transport ceiling for one region; pathological externally injected trees beyond the derived bound still fail visibly.

`remote/src/codeharbord.ts::responseLine()` also uses this same encoder with `MAX_LINE_BYTES`, so committing deep valid JSON does not then fail while returning it. Size overflow keeps RPC_RESOURCE_LIMIT and the warning that the operation may already have completed; encoding failures/root undefined keep RPC_INTERNAL_ERROR. No second serializer, response assertion removal, or depth narrowing is introduced. Packaging compiles the whole source tree and archives the full dist directory, so no packaging-path exception was required for the helper.

#### Checks and remaining limits

`remote/test/workspace.test.ts` retains the original 2,200-deep duplication regression and adds 8,000-deep arbitrary metadata save/duplicate, deep surviving-tree deletion, JSON conversion/cycle/BigInt rejection, and unchanged-state-on-rejection coverage. The exact-cap regression uses 65 real UUID rows, deletes the middle pane, checks 64 surviving references in order, inert metadata preservation, positive normalized weights summing to one, storage above the public cap, successful duplication with fresh identities, and rejection if that expanded tree is resubmitted through public setLayout.

`remote/test/json.test.ts` covers UTF-8/escaping boundaries, conversion/getter errors, unsupported roots, cycles versus shared references, boxed/nested BigInt, and 20,000 levels below 256 KiB. `remote/test/rpc-mirror.test.ts` drives the real daemon with an isolated in-memory database and 12,000-level tree through set/get; request construction and assertions avoid recursive fixture serialization/comparison. Node deep-JSON checks do not prove native Qt can parse/render such trees: its explicit 1,024-container parser limitation remains separate. Native `JSON.parse` still handles parsing. Final integrated results, not intermediate failures or earlier passes before refinements, determine verification status.

### NWS4 — A create-only save could overwrite a competing creation

#### Context and failure

`expectedRevision: ""` means create-only, but `writeFileLocked()` previously checked absence and then used overwrite-capable rename. Another daemon or external writer could create the file between those operations and lose it. Process-local locks could not prevent that race. An isolated pre-fix reproduction exclusively created `other writer` immediately before rename; the service returned success and the final content became `our creation`.

#### Change and reasoning

In `remote/src/files.ts`, create-only publication now uses same-directory `fsp.link(tmp,target)` to claim the absent name atomically without replacing an existing entry, then removes the staging name. `EEXIST` becomes `RevisionMismatchError`, with the competitor's revision when available. Existing-file overwrites retain rename. Removing the staging name after a successful publication is best-effort so cleanup cannot misreport an already committed save as failed. Other conflict/error cleanup remains, and directory-fsync comments describe both commit mechanisms.

This is a deliberate filesystem compatibility tradeoff: new-file saves require hard-link support. Ordinary POSIX filesystems and NTFS provide it; FAT, exotic filesystems, or mounts disallowing hard links fail visibly. There is no destructive rename fallback. Existing-file overwrite compatibility and its external stat-to-rename race remain unchanged. Documentation records the requirement.

#### Checks and remaining limits

`remote/test/files.test.ts` adds a real competing creation immediately after the final absent stat result, requiring a conflict, preserved competitor bytes, and no staging leftovers. It verifies behavior rather than asserting the chosen syscall. Full file-service checks and available Windows/NTFS or supported nonstandard-filesystem checks are relevant; no platform runtime pass is inferred.

A integration real-daemon API smoke check additionally confirmed that a second create-only save conflicts and preserves the first file's bytes. This is observed post-fix behavior, distinct from the added final-check interleaving regression.

### NWS5 — Concurrent default-layout initialization could orphan terminals or overwrite a viewer layout

#### Context and failure

Two clients could both observe no initial layout, independently create default terminal rows, and save different trees through ordinary `setLayout`. The last tree won, leaving the other's newly attached shells/rows outside the accepted layout. A stale missing-layout read could likewise overwrite a newly authored viewer tree. Stored JSON null and explicit empty trees are intentional layouts, not permission to reseed. Recycled terminal labels must never substitute for terminal row identity. This race is source-derived from the shared caller/server sequence, not claimed as a live pre-fix reproduction.

#### Change and reasoning

`Workspace.ensureInitialLayout(SetLayoutParams) -> SessionLayout` in `remote/src/workspace.ts` initializes either region within one IMMEDIATE transaction. It requires the parent session and checks raw row presence. Any existing row wins unchanged, including null/empty trees; corrupt JSON fails visibly without replacement. Only an absent region accepts the proposed template. Viewer templates are stored directly. Terminal templates are bounded/cloned, validated for leaf/split structure and distinct nonempty slot labels before writes, and forbidden from supplying owned terminal IDs. Empty labels create no rows. Fresh generic-harness rows are created through `createTerminalPane()`, their returned identities are injected as `terminalPaneId`, and rows/tree commit together. No old row is looked up by label, and any later error rolls everything back. The final UUID-expanded tree is checked against the public input ceiling, and input templates remain unchanged.

The client migrates from separate create/set initialization to the one endpoint and consumes its returned accepted tree and terminal identities. A losing initializer returns the winner without minting rows. Ordinary user-authored `setLayout` remains last-writer-wins: this is not a general layout-edit conflict protocol.

The C++ method constant is `rpc::kMethodWorkspaceEnsureInitialLayout` in `src/remote/RpcTypes.h`. `WorkspaceDb::ensureInitialLayout(const ServerId&, const DevSessionId&, Region, const SplitNode&, LayoutCallback)` shares one internal `writeLayout` implementation with setLayout. #### Context and failure

### NIN2 — MCP cancellation left owned viewer requests waiting

#### Context and failure

`remote/src/mcp/server.ts::handleMessage()` ignored `notifications/cancelled`, and stdio used stateless `handleLine()` without active request ownership. A harness cancelling a stalled viewer tool therefore retained the producer socket/timer until timeout and could receive an unwanted late response. This is source-derived. MCP 2025-06-18 makes cancellation optional, but recommends stopping work, freeing resources, and suppressing responses when cancellation is supported: https://modelcontextprotocol.io/specification/2025-06-18/basic/utilities/cancellation . This is missing best-effort lifecycle behavior, not an unconditional protocol rollback guarantee.

#### Change and reasoning

`createMcpSession()` owns AbortControllers for active viewer requests; stdio dispatch uses that session. Valid cancellation references abort only the matching active integer/string ID. `handleMessage()` passes the signal to the transport; `handleLine()` suppresses a cancelled result and removes ownership in `finally`. Unknown/completed/malformed references are harmless, duplicate concurrent active tool IDs are refused instead of replacing an owner, and session close aborts its waits. Initialization is not tracked/cancelled; stateless exported handlers remain available.

The shared transport contribution in `remote/src/control-client.ts` adds an optional sixth argument to `sendControlRequest(op,args,env,socketPath,timeoutMs,signal?)`, preserving existing calls. Pre-abort returns the normal failed refusal, `the viewer command was cancelled`, before coordinate reads, serialization, connection, or dispatch. Active abort uses the exactly-once finish path to clear the timer, remove the listener, destroy its producer socket, and settle. A second check after listener registration covers cancellation during user-supplied serialization. Normal completion removes the listener as well.

Cancellation cannot undo a command already dispatched to the desktop. Closing the producer does not promise immediate server pending-slot release because producers may legitimately half-close while awaiting answers. No cancellation wire frame, new error token, or reason logging is added. All transport contributions belong to this issue, not a separate daemon finding.

### NIN3 — MCP line limits did not bound active requests or queued output

#### Context and failure

In `remote/src/mcp/server.ts::runStdio()`, `inFlight` and `pendingWrites` were only counters, and stdout backpressure did not limit response accumulation. A peer could send many legal small tool requests while desktop control stalled, or stop reading stdout while continuing input. Resource exhaustion is inferred from these source paths, not an exercised production stress incident.

#### Change and reasoning

Output errors and input line overflow also exit unsuccessfully; failed stdout no longer leaves a live input consumer. Normal EOF continues waiting for active requests and pending writes.

The 32-wait ceiling matches existing desktop-control capacity but is applied before opening sockets. Some operations can already have completed when the output transport fails; no retry/delivery guarantee or alternate framing format is invented. This is a local stdio reliability bound, not an asserted unauthenticated network exploit.

### NIN4 — The OMP extension retained an unlimited stale lifecycle-event backlog

### NRP1 — Reentrant transport reads could mix connections, lose final replies, or access a deleted client

#### Context and failure

### NRP4 — Native JSON depth rejection could leave a request pending forever

### NAC11 — A second window could collide with the first window's agent bridge and lose its connection

#### Context and failure

Multiple windows are a supported product configuration. Each native `SessionBootstrap::attemptWire()` started an agent bridge process, but `remote/src/events.ts::resolveSocketPath()` gave ordinary windows for the same user the same event address: `$XDG_RUNTIME_DIR/codeharbor.sock`, or the HOME-based fallback. The first bridge owned that listener; the second correctly refused a live owner and exited. `wireChannelSignals()` then treated its agent-channel EOF as connection loss and detached the otherwise healthy RPC session, producing reconnect churn. Separate repository roots or unique control-daemon sockets did not isolate this separate agent-event socket. The integration run observed address-in-use interference during integrated live checks against a concurrently connected GUI; the source chain establishes the same supported-two-window product failure. NBR6 separately isolates tests and does not solve this product bug.

#### Change and reasoning

The bridge now uses one per-user event relay and independent per-window stdout subscriber proxies, implemented through `remote/src/bridge.ts` and the new `remote/src/bridge-relay.ts`. Ordinary native bridge invocation remains the proxy entry; if necessary it starts a detached relay using the same installed entry's internal `--relay` mode. Producer address resolution and producer schema remain unchanged, so opening another window does not strand already-running agents or require them to acquire a new environment variable. Every live subscriber receives subsequent valid events and retains existing workspace filtering. There is no replay, durable delivery acknowledgement or event history promise.

Registration uses a bounded, versioned subscription handshake and exact protocol/version/success acknowledgement, separate from producer event schema 1. The proxy waits for acknowledgement before declaring readiness or forwarding output, preserves event bytes coalesced after the acknowledgement, and a registered reader cannot inject producer events. A legacy single-output listener that cannot acknowledge subscription causes an explicit upgrade/restart refusal: it is never mistaken for success, killed or unlinked. Socket/lock ownership and restrictive-permission protections remain in effect.

The exact internal registration is `{protocol:"codeharbor-bridge-subscribe",version:1}`; the reply uses `protocol:"codeharbor-bridge-subscribed",version:1,ok:true`. Unsupported versions receive an explicit negative acknowledgement before close. Acknowledgement parsing is capped at 1024 bytes with a one-second deadline. Absent-endpoint startup allows five seconds with 50-ms retry waits and at most one relay candidate per proxy. Atomic lock publication and existing probe/bind rules select one winner; losing candidates never clean up the winner's paths. The existing filesystem check/unlink limitations remain, rather than implying hostile-directory atomicity.

The relay survives loss of the window that started it, while each proxy owns only its subscription. It has bounded per-reader and aggregate output backlog, independent slow/failed-reader retirement and a 30-second readerless idle shutdown, including startup that never obtains a reader. Producer traffic cannot keep a readerless relay alive. Events retain their bridge-specific byte/depth trimming; generic RPC/JSON depth policy is unchanged.

`BridgeSubscribers` caps readers at 64. Each reader has at most 2 MiB/128 pending messages; the relay total is at most 16 MiB/1024 messages. Accounting includes acknowledgement and in-flight socket writes, not just queued arrays. One write runs per reader; completion releases its budget. Global pressure evicts the largest relevant backlog owner rather than whichever healthy reader receives the next event. These are ceilings, not a guarantee that all 64 readers can buffer maximum-size events together. The stdout proxy pauses its subscription on output backpressure and resumes on drain. `CODEHARBOR_BRIDGE_RELAY_IDLE_MS` intentionally allows safe integer values 1–30000; missing/invalid/zero/negative/nonfinite/out-of-range values use 30000. It changes only idle timing, not event addressing or schema.

`bridge-relay.ts` has no import cycle back to bridge.ts and uses erasable TypeScript-compatible explicit fields. `bridge.ts` shares one `encodeBridgeEvent` policy between its still-useful embedded `makeStreamSink` path and relay fanout, encoding/mapping each producer event once. The existing 1-MiB/1024-container bridge output policy and optional metadata-first/summary shedding are preserved. Ordinary no-argument CLI is completely cut over to proxy behavior; unknown arguments are refused rather than retaining an obsolete stdout-owner CLI.

Native `SessionBootstrap::bridgeCommand()` needs no changed arguments or suppressed errors. Its supervisor ignores child stdin, owns the SSH-lifetime watch, sends signals only to its proxy pid, and escalates after two seconds. The proxy correctly remains alive with `/dev/null` stdin; the relay detaches with ignored stdio and `unref()`, rather than inheriting the first SSH window's lifetime. Proxy stdout close/error and HUP/INT/TERM end only that subscription. Real proxy EOF still triggers normal diagnostics/loss handling. Deployment includes `dist/bridge-relay.js` and its `json.js` dependency via the existing complete staged-dist installation, not an invented per-module bootstrap allowlist. `docs/SPEC.md` §6.3 documents topology, independent lifetime, bounded queues/idle, subsequent-event-only delivery and older-listener restart requirements.

#### Checks and remaining limits

`remote/test/agent-hook.test.ts` replaces the obsolete immediate-listener-deletion CLI expectation with acknowledgement-backed readiness and eventual last-reader cleanup. Its real child-process cases cover two readers receiving the same genuine hook event, closing the first while the survivor receives a subsequent producer event at the unchanged socket inode, and four simultaneous starts converging on one usable relay. A real legacy listener must remain live at the same inode after explicit upgrade refusal and still accept an ordinary producer.

`remote/test/rpc-mirror.test.ts` also migrates its symlink CLI regression: it waits for actual subscription readiness, clean proxy signal exit and filesystem-observed relay/socket/lock cleanup using a private 1000-ms idle setting, rather than deleting a directory while its relay still runs. Together with `bridge.ts`, new `bridge-relay.ts`, shared `agent-hook.test.ts` and SPEC §6.3, this completes the affected implementation/test/document inventory for NAC11; the existing whole-dist packaging includes both runtime dependencies.

Additional cases pause one actual CLI stdout during a finite 64-by-128-KiB event burst while requiring each healthy-reader delivery; the stalled subscription must fail independently and the survivor must continue. Real corked sockets deterministically exercise aggregate pressure, requiring retirement of old slow history rather than the next healthy reader. Real internal-relay execution tests never-subscribed cleanup; an injected fake clock separately proves producer broadcasts do not extend idle lifetime. A real subscription exchange proves reader-role injection is rejected without disabling ordinary producers. Tests use private runtime directories, filesystem cleanup notifications and failure watchdogs, not production sockets, unknown-process kills or success sleeps.

Earlier remote-suite results before this change do not verify the relay. Final evidence must distinguish process/socket regressions from the native two-window acceptance exercise: both graphs in one isolated user namespace should retain responsive RPC and agent delivery when either window closes/reconnects. Linux/POSIX socket/pipe coverage is not proof of Windows behavior, and mixed older live bridges require explicit restart rather than silent compatibility.

Final production GUI acceptance used two real windows in the same owned remote user namespace. After closing one, the survivor changed from running to waiting-for-input on a later real hook event and opened a new directory pane that fetched a proof file created after the first window closed. Its RPC and event subscription both remained usable. This is separate from the real child-process regressions that establish independence from the process which originally starts the relay. One new handshake test callback was also corrected to return its required boolean acceptance result; its ordering assertions were retained.

### NAC13 — A new terminal did not contribute to its own window's sidebar state

#### Context and failure

The terminal initializer and discovery of an old layout's server-owned terminal had the same missing notification. #### Change and reasoning

`SessionLayouts::terminalRowsChanged(serverId, devSessionId, generation)` now reports successful current-context terminal creation or discovery. Failed, unready and superseded operations do not publish stale notifications. Callbacks recheck object lifetime and the current request after observable layout work; the notification is their final operation, so its consumer may safely replace or destroy connection objects.

`AppController` owns one subscription to its currently injected layouts. Replacement disconnects only that owned subscription, preserving unrelated observers. Before calling `AppController::refresh()`, the receiver checks the exact layout object, server, session, request counter and accepted readiness. This rereads authoritative workspace records and runs the existing registration and pending-agent-observation reconciliation. It does not call `SessionLayouts::load()` or `SessionLayouts::refresh()`, change either layout counter, replace pane/document objects, reconnect, change identities, or invent a local database record. Notifications occur on creation/discovery rather than every tree or list publication, avoiding a refresh loop.

Affected implementation: `src/app/AppController.cpp`, `src/app/SessionLayouts.{h,cpp}`; regression: `src/app/tests/tst_appcontroller.cpp`; canonical contract: SPEC §6.6. This requires no additional RPC, database or release-version change.

#### Checks and remaining limits

### NMD5 — Profile writes could fail silently or falsely claim that data was saved

#### Context and failure

### NMD6 — Windows profile locking treated a registry key as a filesystem filename

Legacy clients and external editors do not participate in the merge lock.

### NTC9 — New terminal shells could send agent events to the wrong socket

#### Context and failure

### NTC10 — Missing terminal capabilities could reappear from the tmux master's environment

#### Context and failure
Passing a correct new endpoint (NTC9) does not make absence safe. When a terminal had no control route, the command used session `set-environment -u`, which removes only the session entry. A stale value in the tmux master's global environment could then reappear in a new child. Missing provenance similarly exported nothing, allowing inherited OMP session/terminal IDs to identify the wrong pane. If only one half of the current identity was known, inherited values could form a misleading complete pair. Updating environment after `new-session` was also too late to protect its first forked shell. These are source-derived consequences, not observed native misrouting. The [tmux environment contract](https://man7.org/linux/man-pages/man1/tmux.1.html#GLOBAL_AND_SESSION_ENVIRONMENT) distinguishes `-u` from `-r`, which marks a value for removal before a new process starts.

#### Change and reasoning
`src/terminal/TerminalController.cpp::tmuxNewSessionCommand` manages exactly four application-owned variables: OMP_DEV_SESSION_ID, OMP_TERMINAL_ID, CODEHARBOR_CONTROL_SOCKET and CODEHARBOR_AGENT_SOCKET. A local table supplies all four as shell-quoted `new-session -e 'NAME=value'` arguments. An unavailable value is explicitly empty before the first shell forks, blocking stale master inheritance. If either provenance half is missing, both IDs and both routing capabilities are suppressed, even if an endpoint argument was supplied; a half-known pane cannot receive another pane's capabilities.

For future tmux-created children, each session update sets the exact current quoted value or uses session-local `set-environment -r` for absence. It never mutates the master's global environment, HOME/XDG, or unrelated user variables. Valid current routes/provenance remain unchanged. This is deliberately different from `-u`: absence must suppress both session and master fallback. Initial empty CODEHARBOR_AGENT_SOCKET is also deliberate—NTC9's producer resolver treats a present-empty override as invalid/refused, never an invitation to derive a default route. A genuinely absent override outside this managed boundary retains the ordinary XDG/HOME defaults.

The builder's required six-argument API and all controller/factory/live call migrations are recorded under NTC9; no second compatibility path is introduced here. Obsolete whole-command-template and half-known/no-variable-string tests, plus incidental quoted-argument/separator counts, are removed rather than repinned to implementation formatting. Focused shell quoting, exact target, session-only options, valid-value behavior and security contracts remain. Header/module documentation retains the exact new-child scope.

README viewer-control coordinate/endpoint guidance records the same missing-value/pair rule. PLAN's terminal workstream records initial `-e` and future-child `-r` guarantees. The documentation describes the same behavior exercised by the native environment regressions.

#### Checks and remaining limits

It reattaches with replacement endpoints and checks a newly created window reaches the current routes. It then clears both routes and requires a new child to have neither, with no connections to stale-window or event listeners.

Separate unknown, dev-only and terminal-only cases exercise first shells and future windows: first-fork values must be explicitly empty; future-child values must be absent for all four variables. ## Editor, viewer and desktop interface findings

### NED1 — A queued save could incorrectly mark newer edits as saved

#### Context and failure

`src/editor/EditorController.cpp` implements save queuing in `save()` and `issueSave()`. Before the fix, a queued entry stored its text but not the edit counter associated with that text. `issueSave()` sampled the counter only when the queued write finally started.

Consider a write of A already in flight. The user edits to B and requests another save, then edits again to C before A completes. A's successful reply starts the queued B write, but the controller records C's newer edit counter. When B succeeds, the unchanged counter appears to prove that the current buffer was saved. The controller could mark C clean and truncate its recovery record even though the server held only B. A later browser message might correct the dirty state, but close, navigation and watch-reload decisions could already have acted on the false clean state.

#### Change and reasoning

`EditorController.h` now stores an internal `QueuedSave { content, editSerial }`. `save()` captures the text and counter together, and every `issueSave()` caller passes the captured counter through the queue. Open/reset, successful dequeue and explicit reload retirement use the same representation. Same-byte coalescing and revert behavior are retained, with no bridge or RPC shape change and no extra text copy needed to solve the race.

The shared native mobile consumer now also reports exact equality after `saved` with `reportDirty(false, confirmedRevision)`, matching the desktop page. Newer text is still reported immediately. Because native signal handlers can run synchronously, the controller rechecks controller/load/save identity after emitting `saved` and lifecycle signals, then chooses its final Clean or Modified state from the **current** dirty flag. It no longer overwrites a valid inline clean reconciliation with a stale Modified decision or publishes an obsolete lifecycle update after reentrant navigation or another save.

#### Checks and remaining limits

`src/editor/tests/tst_editorcontroller.cpp` adds `editsAfterQueuingASaveRemainDirty()`: real framed-RPC controller traffic follows A → queued B → reported C → A/B replies. Assertions cover dirty/Modified state, B's confirmed revision, no recovery truncation and no replacement of C after an external change. It answers the permission-only stat introduced by NED3 rather than treating all extra RPCs as defects.

`inlineConfirmedSaveReconciliationLeavesTheControllerClean()` verifies exact inline reconciliation, both clean indicators and a later external reload reaching the consumer. Native-page coverage additionally exercises its queued-save timer and subsequent external reload; that is part of this issue, not a separate finding. The edit counter is intentionally conservative after undo; exact page equality can subsequently prove cleanliness. Recovery remains best-effort rather than a transactional backup.

### NED2 — File changes received during a save could be lost

#### Context and failure

`EditorController::applyExternalChange()` previously dropped ordinary and lost-watch notifications while `m_saveInFlight` was true. That avoided reacting to the editor's own write, but also dropped indistinguishable external changes.

A concrete ordering is: the daemon writes our bytes at revision r2; its success reply is still in transit; another writer changes or deletes the file, or the watcher reports lost events; that notification reaches the controller before the r2 reply. The notification was discarded, and the reply could leave the editor clean at r2 indefinitely because no second event was required. Permission changes in that interval were exposed to the same ordering.

#### Change and reasoning

`src/editor/EditorController.{h,cpp}` retain one pending-external-change flag for the whole save chain. After the final successful write, the controller clears the flag and invokes the existing guarded stat/reconciliation logic, renamed `reconcileCurrentFile()` because it now serves reconnect and post-save callers.

An unchanged stat revision identifies an own-write echo without rereading content. A changed or deleted clean file follows safe reconciliation; dirty content is flagged and retained rather than overwritten. Queued saves keep the flag until their chain completes. File/open changes, committed explicit reloads and failed writes retire it; a failed write stays dirty and its existing error/conflict handling owns that outcome. Comments describe both reconciliation intervals. There is no public API or protocol change.

#### Checks and remaining limits

`watchEventDuringSaveIsReconciled_data()/watchEventDuringSaveIsReconciled()` in `tst_editorcontroller.cpp` delay a real write reply until after a framed notification. Rows cover ordinary changes, lost events, own echoes, dirty changes, dirty lost events and deletion. They inspect emitted bytes/revisions and dirty/lifecycle state: external bytes reach a safe clean consumer, dirty text survives, own echoes do not reload, and deletion becomes Error while the saved revision guard remains available. One deferred stat per completed save chain is the deliberate cost of distinguishing an echo from another writer; repeated events collapse into that stat. No guarantee was added for a server that never establishes a watch subscription. Changes after reconciliation still rely on the normal established watch. The relevant integrated checks are the controller suite and isolated live-editor/reconnect suites.

### NED3 — Dirty editors did not learn that file permissions had changed

#### Context and failure

Clean watch reloads and reconnect stats refreshed permissions, but the dirty branch of `EditorController::applyExternalChange()` changed only lifecycle state. A pane with real unsaved text could therefore retain an obsolete read-only decision after the server made the file writable again. Newly revoked permissions were likewise not reflected while dirty.

For example, a permission stat can overlap the page's last debounced edit report. The editor then contains unsaved text but is read-only. Restoring permissions remotely generates a watch event; refusing to reload that dirty buffer is correct, but failing to restat permissions leaves it locked and `save()` still refuses. Reloading just to recover writability would sacrifice the unsaved text.

#### Change and reasoning

Dirty ordinary and lost-event branches now also call the existing permission-only `refreshPermissions()`. Conflict/ExternallyModified behavior stays intact. The stat does not read the main file, advance its save revision or clear recovery.

`src/editor/EditorController.{h,cpp}` add a permission request counter shared by permission refreshes and reconciliation stats. Only the newest result can update read-only state, preventing overlapping same-path chmod responses from adopting an older verdict after newer evidence. Existing load/watch guards remain. A current-load continuation still runs if its permission result has been superseded; suppressing an outdated permission update must not silently abandon the associated continuation.

#### Checks and remaining limits

`dirtyWatchChangeRefreshesPermissions_data()/dirtyWatchChangeRefreshesPermissions()` cover ordinary and lost notifications across 0444 → 0644. Assertions retain dirty text, prohibit content/recovery offers and recovery truncation, and preserve the original content revision: a normal guarded save must conflict instead of overwriting the changed file, whereas explicit overwrite can succeed and retire recovery.

`staleDirtyPermissionStatCannotRelockTheBuffer()` completes two permission stats newest-first and verifies the older read-only result cannot replace the writable verdict or alter content/revision/dirty state. Existing dirty-watch tests now answer the legitimate stat while retaining their no-reload/no-truncate assertions. None of these checks was run by the reporting owner.

The additional operation is one permission stat per dirty notification. Remote writability continues to use the server's existing POSIX `writable` result/fallback, not a local guess; a failed stat keeps the previous verdict. Controller and live chmod/read-only regressions are the relevant integrated checks.

### NED4 — An old editor document could still modify its replacement file

#### Context and failure

The native controller survives browser-document replacement in `src/qml/EditorPaneView.qml`. Previously it was registered under the fixed WebChannel name `editor`. `start()` could open B before document A had finished retiring. If B's read completed quickly, A's delayed debounce or pagehide `reportContent(A)` arrived after Loading ended and was accepted as B's text, potentially contaminating B's recovery record or enabling cross-file writes. A's delayed `save`, `ready`, `reportDirty` and reload calls could also operate on B, while B's content could be delivered to A. Server-request/load counters do not identify the browser document that issued a bridge call; simply reversing two asynchronous operations does not establish that boundary.

#### Change and reasoning

`src/editor/EditorController.{h,cpp}` introduce a document-specific `EditorPageBridge`. Host-only `createPageBridge()` creates a controller-parented adapter with a fresh, nonreused `editor-<uuid>` object name, immediately retires the previous adapter and resets current-page readiness. Retirement disconnects forwarded signals and clears the borrowed controller pointer, making all old actions inert even if a JavaScript proxy remains alive. The frozen C3 method/signal signatures and readOnly/fileState properties remain; the raw controller is no longer exposed to the page.

`EditorPaneView.start()` creates/registers the new adapter before opening the target and navigating. Each document also gets a **fresh QML-owned WebChannel**, with its unique adapter registered before the channel is bound to the view. This avoids mutating registration on an already initialized channel, which actual integration exposed as a warning. Replacement destroys the retiring QML channel rather than suppressing that warning; there remains one JavaScript QWebChannel client per document and a stable native controller/handler. QML tracks `pageBridgeOwner` alongside `pageBridge` and releases the retired adapter through `oldOwner.releasePageBridge(oldBridge)`. The native method accepts only adapters belonging to that controller. Releasing an inactive old adapter leaves the newly staged current adapter intact; releasing the active one also retires and clears its owner's current state. This explicit API replaces an invalid direct QML `deleteLater()` call exposed by integrated execution; there is no foreign-owner exception or raw alias. QObject parenting remains the final teardown owner. Initial load, retarget, bundle replacement and host reload use this contract. The browser in `src/web/editor/src/index.ts` resolves only the explicit `MountOptions.bridgeId`, supplied as `bridge=<id>` by QML. A missing ID is a fatal actionable error; there is no fixed-name alias or fallback. Readiness tracks whether any prior document was ready separately from whether the current one is ready: a newly connecting document waits for an existing host-started load rather than replacing it and losing its watch, while an early read holds delivery for the new document's own ready.

Host reload also preserves exact current RAM text rather than reopening the path. `window.captureEditorContent()` and exported `CodeHarborEditor.captureEditorContent()` use the existing BOM/EOL-preserving accessor. QML validates the asynchronous capture against the old adapter, controller, path, latest navigation/reload counter and captured native `recoveryContextRevision`, then calls the required `preparePageReload(content, expectedRecoveryContextRevision)` before rotating the adapter. There is no one-argument alias. This NED5 scope-context guard prevents a pending capture from committing after directory, recovery scope or path retirement even if document/controller pointers remain unchanged. Reload does not call `open(samePath)` or reset dirty/revision/save state. `start()` clears `pageReady` synchronously, closing the interval in which an immediate second reload could otherwise capture A's still-visible DOM while labeling it with B's new identity.

The browser capture is `JSON.stringify`-wrapped before crossing WebEngine's native callback boundary, then decoded with `JSON.parse` in QML before validation and `preparePageReload`. Actual integration found that raw STRING conversion through Qt's UTF-8-to-QString path stripped a leading BOM even though the browser accessor retained it. JSON starts with a quote or null rather than the content BOM, preserving text through that boundary without BOM-specific conditionals or normalization. An unavailable or malformed capture does not retire a dirty page.

The controller retains **one latest exact RAM string** and attempts the existing recovery report. Retained RAM survives recovery-write failure, failed/stopped replacement loading and ready delivery before the browser applies it. `hasPageReloadContent(QObject* pageBridge)` permits no-capture retry only for the native **current** adapter with retained RAM. Thus a bad replacement document can be retried after restoring the valid bundle without a nonexistent DOM capture, reopen or dirty reset. Current full reports refresh the one string; exact-clean current reports, known successful same-buffer saves, file retarget, committed content reload and destruction release it. A ready signal alone is not acknowledgment. Dirty reload without either a valid capture or current-adapter retained RAM is refused.

The additive `bufferRestored(content, baselineContent, revision, pendingSaveContent, savePending)` signal restores the visible model, actual baseline and pending write. Baseline/revision/latest queued-or-in-flight bytes are chosen **at ready time**, so save completion during navigation cannot turn older saved bytes into the baseline for newer visible text. Monaco reconstructs baseline, dirty state and pending save, reports exact equality/current revision, then rearms remaining recovery work. QML updates loadedRevision and recovery readiness from restoration. Mounted-editor disposal now restores the last live mount pointer, so temporary fixtures cannot leave capture pointing at a disposed editor or lose the remaining live one.

The real toolbar caller is also migrated. `EditorPaneView` alone declares readonly `reloadPreservesDirtyContent=true`; `ViewerPane.reloadCurrent()` bypasses its dirty-content replacement guard **only** when the currently loaded handler has both an actual reload function and that capability strictly equal to true. It still retires the pending address probe and calls the existing RAM-safe reload. Capability alone never authorizes Loader destruction, and missing/nonpreserving handlers keep the old replacement guard. Navigation and close/discard safeguards are unchanged. This makes safe host reload reachable through the user's real entry point, rather than merely through a direct child-method test.

### NED5 — Recovery records could collide across sessions and files

#### Context and failure

`EditorController::recoveryPath()` previously appended a raw local pane label such as `viewer-1` to the server-reported recovery directory. `EditorFactory::create(owner,paneId)` and the desktop/native callers did not supply a server/session context, and the saved envelope contained only file path and content. Reused labels in different Dev Sessions or devices therefore selected the same user-level recovery record. A stale-write retry could adopt its current revision and overwrite another document's unsaved snapshot. Checking the envelope path before offering recovered text prevented a wrong-file offer, but did not prevent destruction of that other file's recovery copy. Retargeting a pane also reused its slot.

Main subsequently **observed the before-case** using two real Qt/SSH/Monaco windows and a retained pre-NED5 integration binary that already contained other fixes, including NAC11, but not scoped recovery. The windows used different Dev Sessions, both labelled `viewer-1`, and different owned files. Typing `BEFORE_SCOPE_DRAFT_A` in A created the fixture-private `data/codeharbor/recovery/viewer-1` record with `document.txt` as its path. Typing `BEFORE_SCOPE_DRAFT_B` in B overwrote that **same record** with `other.txt`, while A remained open and modified with its own draft, captured in `pre-scope-dirty-A-repainted.png`. Both real project files remained unchanged. This proves a recovery-cache collision, not an actual user crash or subsequent loss of an open buffer. Every inspected/written record was inside NBR7's private fixture data root. Separately, the earlier suspected global legacy candidate was not found; this owned before-proof does not establish modification of global user recovery data.

The supported identity is one latest successful snapshot per logical **accepted server, Dev Session, pane and actual opened file path**. Separate windows representing that exact same logical pane/file intentionally share its slot. This is not independent per-window edit history.

#### Change and reasoning

`src/editor/EditorController.{h,cpp}` and `EditorFactory.{h,cpp}` require the full context: `EditorController(client,serverId,devSessionId,paneId,parent)` and `EditorFactory::create(owner,serverId,devSessionId,paneId)`. Hosts update it through `setRecoveryScope(serverId,devSessionId,paneId)` and observe `recoveryEnabled`. Old `setRecoveryId`/`recoveryId`, raw/default-only construction and compatibility aliases are removed; no hash/path getter was added for tests.

The server ID comes from **validated current** server.info via AppController's `acceptedServerId`, not a selected profile or a retained stale ID. Desktop Main keeps the stable server key for workspace reset and separately propagates acceptedServerId through nested ViewerRegions, cached ViewerPanes and EditorPaneView. Native callers also supply the actual session and pane. Nonempty IDs remain opaque; no invented UUID syntax or client-generated replacement identity is required.

`updateRecoveryPath()` caches a filesystem-safe `scope-v1-` plus SHA-256 name under recoveryDir. The input is server/session/pane/opened path in that order, each UTF-8 field preceded by its eight-byte big-endian byte length. Ambiguous concatenations, separators and platform byte order cannot alias names. Hashing occurs only when scope/path/base changes, not on each edit or property read. Envelopes now carry `version:1`, `serverId`, `devSessionId`, `paneId`, `path` and `content`. Complete version/context/path metadata must match before recovery is offered or its revision adopted. Empty unsaved content, 0600 writes, bounded revision-consistent reads, guarded writes and zero-length tombstone clearing remain supported.

A loaded document binds its **first complete** server/session/pane tuple; an initially incomplete tuple may settle once, including a late pane ID. Missing scope/path/directory disables recovery. Temporary accepted-identity gaps retire offers and disable I/O without discarding dirty RAM or the bound tuple. Reaccepting the **same** tuple restores that key. A genuinely different complete tuple cannot acquire the old loaded buffer: recovery remains disabled until explicit `open()` binds the intended new document. There is no automatic open, discard or transfer into the new workspace.

Desktop scope changes only update recovery context and invalidate pending captures; loss/reacceptance of acceptedServerId does not destroy dirty editor objects. `EditorPaneView` displays an unavailable-recovery warning in its existing state banner, advising the user to keep the editor open until saved. Failure/conflict/disconnection messages retain higher priority. The warning covers missing scope and unavailable recovery-service metadata without implying disabled recovery is durable.

Native `ViewerEditorPage` exposes acceptedServerId/devSessionId/paneId and uses only the four-argument factory. Its `retireRecoveryScope()` immediately calls `setRecoveryScope('','','')` and clears the old offer on each identity change; `applyRecoveryScope()` applies only the final tuple via `Qt.callLater`. This coalescing disables I/O during an identity transition without auto-opening or discarding the loaded document. Core PaneHost binds the actual application acceptedServerId, current session and stable pane, not an inferred identity. The visible `editorRecoveryStatus` warning explains that recovery needs the document's accepted context. Recovery dialogs record `offeredPath`; document/scope retirement clears their content/path, and acceptance checks both current path and recoveryEnabled. Disabled, retired or wrong-document acceptance cannot replace current bytes, and accepted/rejected snapshot strings are released.

`recoveryContextRevision` exposes the native slot counter. Async host capture must pass its captured value to required `preparePageReload(content,expectedRecoveryContextRevision)` and also satisfy document/controller/path/navigation guards. Open, directory and scope changes advance that counter and reset slot bookkeeping. Probe/range/write/retry/clear callbacks carry it, preventing an old response from adopting a new slot's revision, decrementing its pending counts or releasing its deferred clear. NED4's one retained RAM value is independent of recovery availability and survives these gaps/mismatches; explicit content replacement/open or confirmed clean/disposal retires it.

Wrong-owner bytes are never treated as disposable. A nonempty envelope at the scoped name must match complete metadata; rejecting it blocks writes and clears for that slot. The one existing stale-snapshot retry now performs a bounded revision-consistent ownership read instead of blindly adopting a stat revision. It accepts a matching envelope or current scoped empty tombstone, then writes guarded by that revision. Foreign, unscoped or unknown-version bytes remain untouched even if they appeared after the absence probe. The retry stays counted during its read, preserving deferred-clear safety. Raw legacy pane-name files are never enumerated, consumed, migrated, cleared or deleted: filename alone cannot establish ownership.

All constructors, factory calls, host capture signatures, inert recovery stubs and consumers are migrated. Live reconnect obtains actual server.info identity through a lifetime-guarded callback and uses an explicit test session. Live recovery files now stay under each fixture's existing unique remote directory; inspection enumerates only that owned recovery subdirectory and matches metadata. Cleanup no longer derives or deletes raw pane-name records in a global directory. This changes host APIs, not the frozen C3 page methods or RPC recovery wire shape.

## Mobile credentials, navigation, viewers, and native rendering

### NMC1 — Key import accepted containers without validating their private-key material

#### Context and failure

`src/mobile/MobileKeyStore.cpp`, especially `MobileKeyStore::describeKeyText()`, previously recognized PEM labels/base64 and OpenSSH outer lengths/magic without proving that the clear private material was a usable key. Truncated RSA DER could therefore be described as valid, retained, and explicitly saved, only to fail during authentication. An unencrypted OpenSSH key with a corrupted private check integer also passed classification. Changing the clear public blob could make the displayed fingerprint identify a different key from the private material used for authentication. The previous positive PEM test body was itself not a real key.

Encrypted containers need a different distinction: the password is required to validate their private contents, but their public envelope can still be invalid. A lone `DEK-Info` header previously bypassed clear-key validation. Invalid IVs, arbitrary encrypted PKCS#8 DER, empty mandatory password-based-encryption parameters, and inconsistent OpenSSH cipher/KDF combinations likewise must not be called valid merely because they are labeled encrypted.

#### Change and reasoning

`MobileKeyStore.cpp` now uses the existing `CH_HAVE_LIBSSH` feature definition and `ssh_pki_import_privkey_base64()` with a callback that declines passphrase prompting to validate clear keys through the authentication parser. OpenSSH public blobs are parsed through libssh even for encrypted keys. For clear OpenSSH keys, the parsed private key's exported public fingerprint must match the container's public blob. Native objects and exported strings are freed; no temporary credential file is created. `MobileKeyStore.h` documents the distinction between validated clear keys and encrypted candidates. Builds without libssh explicitly refuse cases requiring native validation rather than accepting synthetic material.

Encrypted-envelope parsing uses bounded, zero-copy `QByteArrayView` DER helpers. They reject incomplete or nonminimal lengths, malformed OIDs/integers/constructed parameters, and trailing data; recursive parameter inspection stops at 16 levels. An encrypted PKCS#8 document must contain a complete algorithm identifier and nonempty ciphertext. Supported public schemas are explicit:

- PBES2 PBKDF2 requires an octet-string salt, positive iterations, an optional positive key length, and a known PKCS#5 HMAC-MD5/SHA1/SHA2 PRF with absent/NULL parameters.
- PBES2 scrypt is supported, not categorically rejected. It requires salt, positive uint64-width N/r/p, optional positive key length, power-of-two N greater than one, `N < 2^(16*r)`, and `r*p < 2^30`. Checks avoid overflow and do not perform KDF work. PBES2 ciphers are AES-128/192/256-CBC or DES-EDE3-CBC with exact IV/block framing.
- Known PKCS#5 PBES1 MD2/MD5/SHA1 DES/RC2 families require their eight-byte salt and positive iterations. Known PKCS#12 PBE families require salt and positive iterations, with stream/block framing selected by OID.
- Unknown envelope algorithms, KDFs, external salt sources, PRFs, and ciphers receive an explicit unsupported/re-export explanation instead of a guessed interpretation.

Legacy PEM now requires complete, nonduplicate `Proc-Type`/`DEK-Info` headers, the separator, recognized cipher/IV metadata, and applicable block alignment. Recognized metadata covers AES/Camellia/ARIA modes and sizes, DES variants, SEED/SM4-CBC, Blowfish/CAST5/RC2/IDEA-CBC, and RC4 forms; recognition does not promise that every crypto provider enables them. OpenSSH checks standard none/3DES/AES-CBC/AES-CTR/AES-GCM/ChaCha20-Poly1305 framing, including authentication-tag sizes. Clear containers require no KDF/options; encrypted containers require complete bcrypt options with nonempty salt and positive rounds, no trailing options, and proper private-section alignment.

#### Checks and remaining limits

`src/mobile/tests/tst_mobilekeystore.cpp` replaces fake positives with genuine disposable RSA/PEM and OpenSSL-generated PBES2-PBKDF2, PBES2-scrypt, PBES1, and PKCS#12 ciphertext fixtures, retaining real OpenSSH/AEAD cases. `rejectsInvalidClearPrivateKeys` checks truncated DER, broken check integers, mismatched public/private keys, and absence of retained or saved rejected material. Encrypted regressions cover malformed IVs/blocks/DER, missing/zero/negative/overwide parameters, unsupported schemas, bad PRFs, bcrypt inconsistency, scrypt cost constraints, and trailing fields. Constructed negative DER is never presented as a genuine positive key.

An actually observed parent compatibility probe imported a genuine RSA-2048 OpenSSL `pkcs8 -topk8 -scrypt` key with its passphrase through libssh 0.11.3: `ssh_pki_import_privkey_base64()` returned **0**. This establishes that compatibility case, not passage of the new test suite or all platform crypto backends. Fixture-generation commands produced genuine ciphertext; they are not authentication tests.

Without libssh, only tests requiring genuine native-positive setup skip; parser-independent framing, names, passphrases, reference registration, and path-boundary checks remain active. Passphrase tests no longer import an unrelated encrypted key, and reference-name collisions use distinct real reference files. Encrypted private contents still require their real password during authentication; valid public framing is not proof of password correctness or backend legacy-algorithm availability. Android/iOS native libssh builds and credential workflows were not exercised by these source audits.

### NMC2 — Secrets and authentication dialogs survived completed connection attempts

#### Context and failure

In `src/mobile/qml/ConnectPage.qml`, a pre-entered encrypted-key passphrase was cleared when consumed or explicitly cancelled, but not after every settled connection attempt. If connection failed before a credential prompt, host trust was rejected, or another method authenticated successfully, `takePassphrase()` might never run and the one-shot secret could survive into a later attempt. Credential and host-trust dialogs could also outlive an external timeout/disconnect.

#### Change and reasoning

ConnectPage retains pending secrets only while the controller's mapped state is `connecting`. On `connected`, `error`, or `disconnected`, it forgets the armed passphrase, wipes both secret fields with the existing undo-history-purging helper, clears prompt/kind state, and closes the credential dialog. The signal handler reads the controller's actual state directly rather than depending on binding-notification order. Host-key, credential, provisioning, and reconnect intermediate states still map to `connecting`, avoiding premature erasure.

`connectNow()` transfers nonempty field contents and wipes the field before invoking the connection intent. Empty editing-finished events no longer replace an armed secret. In `HostTrustSheet.qml`, settling the attempt sets `answered=true` before closing, clears host/fingerprint/key-type/trust data, and prevents close fallback from answering an obsolete prompt. `connectingWhilePassphraseIsFocusedTransfersItBeforeDialing` uses a real encrypted disposable fixture, `MobileKeyStore`/`SshConnectionPool`, and the focused field. A recorder at the connection-intent boundary witnesses arming and field clearing before dialing; it does not fake successful SSH authentication. Real mobile timeout, host-rejection, and fallback interaction remains device coverage.

### NVW1 — An old response for a revisited path could satisfy the current page

#### Context and failure

Mobile pages matched viewer results by path, and containment results by path plus repository base. In `MobileViewerService::readFile`, `listDirectory`, `stat`, and `resolvePath`, navigation A→B→A or reloading A could let the first A reply consume the newest page's pending path. This ordering is source-derived, not a claimed runtime reproduction.

#### Change and reasoning

`src/mobile/MobileViewerService.cpp/.h` assigns every launched operation a service-wide increasing request counter. Claim removes that entry; old callbacks cannot remove newer entries, and clearing maps never resets the shared counter. The existing image/PDF request-retirement design is reused; no public token API, permanent per-path version table, or caller shim is added. Markdown retains its useful path/base checks. Distinct paths and distinct repository bases remain independent.

#### Checks and remaining limits

`tst_mobileviewers::aSupersededRequestCannotCompleteItsReplacement` orders actual RPC responses for reads/listings/stats/resolves, including old failure and old `inside=true` approval. `tst_mobileshell::revisitingATextPathDoesNotAcceptItsPreviousRead` drives the actual text page A→B→A and keeps the newest load pending until its reply. Neither was run by the source owner.

The deliberate contract is one visible mobile pane: a second independent consumer of the same operation/target supersedes the first. Outstanding maps contain distinct pending targets, not lifetime history. Server work is not physically cancelled by workspace navigation; replacement counters and page path/base checks prevent consuming obsolete results. ### NVW3 — Compressed-size limits did not bound decoded image and PDF rasters

#### Context and failure

An image within the 8 MiB transfer cap can declare a huge decoded canvas. `MobileImageProvider` previously relied on process-global Qt decoder limits; the ordinary image page supplied no target size. Returned images are limited to **16 Mi pixels and 8192 pixels per axis**: the reader receives a bounded target before decode, and a postcondition rejects ignored bounds. SVG may have a larger virtual canvas because rendering is explicitly scaled; its existing self-contained-resource checks and cumulative embedded-raster limits remain.

`ViewerPdfPage.qml` computes both target axes within the same output budget independently of aspect, zoom, and device pixel ratio. ### NVW4 — Native web views could open external applications before QML could stop navigation

#### Context and failure

The old `ViewerWebPage.qml` attempted to stop untrusted navigation after `LoadStartedStatus`. Qt's native implementation can act earlier. Inspection of the [Qt 6.10 Android controller](https://raw.githubusercontent.com/qt/qtwebview/6.10/src/jar/src/org/qtproject/qt/android/view/QtAndroidWebViewController.java) found unsupported schemes passed to `Intent.ACTION_VIEW`/`startActivity` before any page-start notification. The [Darwin implementation](https://raw.githubusercontent.com/qt/qtwebview/6.10/src/plugins/darwin/qdarwinwebview.mm) invokes `NSWorkspace`/`UIApplication` URL opening for unsupported schemes and new-window destinations before cancellation. Thus `tel:`, `mailto:`, custom schemes, and on Darwin even ordinary HTTP new-window links could leave the app before QML's response. Public [file-access settings](https://doc.qt.io/qt-6.10/qml-qtwebview-webviewsettings.html) are not a universal pre-navigation policy.

The chosen fix implements native enforcement while preserving supported mobile browsing. It does not disable the capability to avoid the issue, relax Android cleartext/iOS transport policy, or rely on JavaScript to rewrite history.

#### Change and reasoning

New `MobileWebViewPolicy.h/.cpp` and `MobileWebViewPolicyAdapter.h` provide a QML policy object and native adapter contract. Every page creates a unique owned `about:blank#ch-policy-UUID` marker and initially assigns only that inert URL. Native discovery must find exactly one matching view in its allowed scope. Installation is polled every 25 ms with a ten-second deadline; only Ready releases the requested HTTP(S) address. Active guards are checked every 250 ms without redundant status signals. Missing, failed, or lost enforcement stays fail-closed, hides the surface, and explains the refusal. Late work cannot dereference destroyed C++ owners or reopen a closed session.

`ViewerWebPage.qml` removes the old post-start stop/refusal helper, banner, misleading safety comment, and helper-echo test. It retains false file-access settings, leaves the marker view attached during discovery to avoid hidden-view discovery deadlock, stops loading on destruction, and retires the adapter on view/window destruction or reassignment. Address text tracks the current HTTP(S) URL. Existing Close, native history, reload, and navigation interfaces remain; no extra toolbar survives. Unsupported desktop-host backends or builds without QtWebView refuse browsing rather than invoke unsafe fallback behavior.

**Android:** `MobileWebViewPolicyAndroid.cpp` owns a Java session through `QJniObject` factory/poll/cancel calls, without raw C++ callback tokens. `packaging/android/src/dev/codeharbor/mobile/GuardedWebView.java` searches only the current activity's decor tree for the exact marker, then installs guarded `WebViewClient` and `WebChromeClient` in one UI job. It disables file/content access, file-origin/universal-file-origin access, and multiple windows, and finishes/reloads only the marker under guards before Ready. Both `shouldOverrideUrlLoading` overloads use the production `NavigationDecision.java` strict hierarchical HTTP(S), host, and port rules; neither calls Qt's external-opening handler. HTTP(S) popups reuse the same view under Android's `supportMultipleWindows(false)` behavior; `onCreateWindow` never creates/exports a view. Modern interception allows safe data/blob resources only off the main frame; top-level navigation stays strict, file/content/custom resources are denied, and legacy interception is conservative. Live-only Qt lifecycle/title/progress/error forwarding, weak references, and one coalesced UI job bound ownership/work. Detach, close, or guard/settings loss fails closed, reinstalls deny-only guards, stops loading, blocks network/JavaScript, and never restores Qt's external-opening client.

**Darwin:** `MobileWebViewPolicyDarwin.mm` searches only the supplied native window. Qt 6.10's manual delegate ownership and KVO teardown make ordinary delegate replacement unsafe. A bounded zero-instance-variable runtime subclass changes policy selectors only on the identified `QtWKWebViewDelegate` instance, preserving identity, inherited callbacks, KVO, and Qt release/deallocation. Both action-policy signatures and response policy reject non-HTTP(S) destinations without calling the original external-opening method. HTTP(S) nil-target/new-window actions are cancelled as new windows and reissued inside the guarded `WKWebView`; a separate `WKUIDelegate` guard similarly routes popups. A public `WKContentRuleList` blocks file/content resources before Ready, with no private file-preference KVC. The marker is bootstrap-only; fragment-stripped bare `about:blank` is allowed only as an initial response on the already identified view until first remote navigation. Associated native state has weak back references and remains deny-only after C++ cancellation. Constant-time polling checks associations, delegate/subclass identity, and resource-rule readiness. Unsupported delegate/ABI shapes or rule-compilation failure refuse clearly.

Existing CMake files conditionally register native sources and QML, Android production helpers, Apple frameworks/ARC, and the Apple test target; these build changes belong to this fix rather than a second issue.

#### Checks and remaining limits

Added common/hosted cases are `webPoliciesUseUniqueSafeBootstrapMarkers`, `aMissingNativeWebGuardNeverPublishesReady`, and `aWebPageWithoutNativePolicyRefusesToLoadAndExplainsWhy`. The prior shell test is accurately named `aWebLeafKeepsItsAddressAndClosesBackToThePicker`; it is not a native enforcement proof. `src/mobile/tests/android/NavigationDecisionTest.java` exercises the production decision helper, including inline-resource versus top-level distinctions. `tst_mobilewebviewpolicydarwin.mm` uses real WKWebView adapter seams for both action signatures, resource blocking, popups, identity/KVO, active disposal, and late completion.

Observed Linux-host verification compiled the full production Java helpers and passed the production navigation-decision test. That is **not** a full Android app/plugin build or an Android runtime result. Android device enforcement and Darwin compilation/runtime were unavailable in this environment; Apple tests are implemented but not claimed executed. No observation here proves prevention of actual OS activities/URL opening, plugin discovery, native history/progress/reload, or device teardown across supported platforms.

Plain HTTP remains subject to unchanged Android cleartext/iOS ATS restrictions. An initial inert history entry may remain and is refused after bootstrap rather than rewritten with JavaScript. Safe data/blob subresources on Android depend on native callback distinctions from later iframe navigation. JavaScript in allowed pages remains enabled. This is a navigation/local-resource containment boundary, not a general network firewall; platform runtime coverage remains an explicit release confidence limit.

### NVW5 — PDF spooling mixed service ownership and published files before checking privacy

#### Context and failure

Every `MobileViewerService` previously used the same `CacheLocation/pdf-spool` and predictable digest-of-path basename, and construction/destruction swept that shared directory. Creating service B could delete the PDF displayed by A; identical remote paths could overwrite each other. Writing opened/truncated the final path under default permissions, flushed bytes, then attempted an unchecked owner-only chmod. A permissive umask could expose document bytes before chmod, and privacy failure still allowed a ready notification. These are source-derived lifetime/privacy defects, not an observed disclosure.

#### Change and reasoning

`MobileViewerService.cpp/.h` lazily creates one private `QTemporaryDir(CacheLocation + '/pdf-spool-XXXXXX')` per service, checking owner-only directory read/write/execute permissions. SHA-256 of the remote path chooses only a basename within that unpredictable directory. `QSaveFile` has direct-write fallback disabled; its temporary file must pass checked owner read/write permissions **before** bytes are written. Only complete atomic commit publishes `pdfReady`. Open/permission/write/commit failure publishes `pdfError` without a partial new PDF.

Pane release removes its file; an empty directory may remain until service retirement. Transport replacement/loss, client destruction, and service destruction reset only that service's directory. Constructor-wide/global stale sweeps, post-write unchecked chmod, and fixed shared-path assumptions are removed. There is deliberately no global orphan sweep that could delete another live service's files.

#### Checks and remaining limits

`twoViewerServicesOwnIndependentPdfSpools` requests identical remote paths with different contents, checks distinct actual directories/full bytes, destroys B, and verifies A survives until its own retirement. `aPdfSpoolWriteFailurePublishesNothing` uses an occupied-directory publication target and checks no new ready/temp residue plus preserved existing bytes. `aPdfSpoolPermissionFailurePublishesNothing` removes private-directory owner write permission and expects refusal; it is Unix-only and explicitly skips where the account/filesystem bypasses enforcement. Existing Unix privacy checks cover group/other file and directory bits. Abandoned-request and shell lifetime tests inspect real returned URLs/directory snapshots, not the now-obsolete global path. This is an explicit temporary-storage exception for native PDF rendering, not project checkout/download/export: QtQuick.Pdf requires a URL and the full up-to-8-MiB document while a pane is open. Crash, kill, or failed removal can leave bytes until OS cache eviction. There is no startup/orphan reclamation, guaranteed crash cleanup, or secure-erasure promise. No file-sharing or OS-handler handoff receives the URL. Windows permission mapping and native open-file deletion semantics remain platform-dependent. User-facing documentation uses this exact per-service/private-but-not-crash-erased contract.

### NMM1 — Destroying a terminal screen left old pixels and property bindings behind

#### Context and failure

`MobileTerminalView` does not own its `VtScreen`; the screen may legitimately die first. In `src/mobile/MobileTerminalView.cpp::setScreen`, `QPointer` automatically became null, but there was no destruction handler to repaint or notify `screenChanged`. Already painted terminal text could remain, and QML could retain stale screen-dependent bindings.

#### Change and reasoning

The assigned screen's destruction now clears the pointer explicitly, discards the old painted cursor row, clamps scrolling to the empty screen, invalidates the whole view, and emits `screenChanged` and `maxScrollOffsetChanged`. Replacing screens still disconnects old connections. Ownership and public API remain unchanged.

#### Checks and remaining limits

`tst_mobileterminal.cpp::destroyingTheScreenInvalidatesThePaintedView` paints a screen, deletes it, checks null screen, one notification and pending damage, then verifies background-only repaint. GUI-thread lifetime assumptions remain; Android/iOS teardown timing was not exercised.

### NMM2 — Font changes could leave terminal cell-size bindings stale

#### Context and failure

`cellWidth` and `lineHeight` share `gridChanged` as their property notifier, but `MobileTerminalView::recomputeGrid()` emitted it only if rounded row/column counts changed. A font change in a small or otherwise unchanged-count view could change cell metrics without notifying gesture and coordinate bindings.

#### Change and reasoning

`MobileTerminalView.cpp` captures previous metrics and includes either metric changing in the decision to emit `gridChanged`. Truly unchanged metrics/counts do not generate an extra notification. Backend resizing remains owned by the session, not the view.

#### Checks and remaining limits

`fontMetricsNotifyWithoutChangingTheCellCount` uses 1×1 item geometry and 16→32-pixel fonts to hold cell counts constant while checking changed metrics and one notification. Device font backends are unexercised. A styling-only font change still repaints but correctly needs no metric notification if metrics/counts do not change.

### NMM3 — Full terminal repaint omitted the fractional bottom gutter

#### Context and failure

A view is often taller than an integral number of terminal rows. `MobileTerminalView::markAllDamaged()` previously delegated to row-band damage, ending at the last complete row. After default-background/theme changes, the fractional area below could keep the old background although `paint()` fills that area when asked to paint it.

#### Change and reasoning

Full invalidation in `MobileTerminalView.cpp` records complete rows for the existing test seam, records the entire item rectangle as pending damage, and calls unrestricted `update()`. Line/cursor changes retain partial row-band updates. Full repaint also works when no complete row fits.

#### Checks and remaining limits

`backgroundChangesRepaintTheFractionalBottomGutter` uses a 4.5-row item, changes white/black background, and checks both gutter damage and changed pixels after repaint. Added coverage is not an executed result. Native compositor/partial-update behavior still requires platform coverage; no terminal damage API changed.

### NMM4 — Valid Markdown image names collided with JavaScript prototype properties

#### Context and failure

In `src/mobile/qml/ViewerMarkdownPage.qml`, remote image paths indexed ordinary `{}` dictionaries. A valid extensionless image named `constructor`, `toString`, or `__proto__` could appear already present through inherited properties and never reach containment/read RPCs. `__proto__` also has special assignment semantics on ordinary objects. Image format is determined from bytes, so lack of extension does not make these paths invalid.

#### Change and reasoning

All four image dictionaries initialize/reset with `Object.create(null)`. Completion copies preserve the null prototype rather than returning to `Object.assign({}, ...)`. This removes inherited-key behavior without changing containment or one-read-per-written-path deduplication. Comments explain the otherwise unusual dictionary form.

#### Checks and remaining limits

`tst_mobileshell::markdownImagePrototypeNamesResolveAndLoad[_data]` parses actual documents for all three names, completes resolve then byte RPCs, and requires provider-decoded PNG `Image.Ready`, not merely map entries. The harness registers the real `MobileImageProvider`. Existing external-path/URL validation and containment permission remain mandatory.

### NMM5 — Backticks inside a link label did not protect their brackets

#### Context and failure

`src/mobile/MarkdownModel.cpp::findLinkTextEnd()` honored escapes and nested brackets but treated `]` inside matched code spans as the outer label's closing bracket. A label whose code spans contain `]` and `[` therefore remained malformed literal text rather than a valid link; equivalent standalone-image alt text was not recognized. Its inline scanner already understood code spans, so two parts of parsing disagreed.

#### Change and reasoning

Label search now consumes matched code spans through the existing budgeted close finder and ignores their internal brackets for label nesting. Unmatched backticks remain ordinary text. The additional search spends the same shared work allowance; it does not add unbounded rescanning or a second grammar.

#### Checks and remaining limits

`tst_markdownmodel.cpp::codeSpanBracketsDoNotCloseLinkOrImageLabels` checks visible `] and [` text, destination, code style only on the appropriate bracket runs, and recognized standalone-image kind/alt/path. Reference links and complete CommonMark grammar remain outside the documented subset.

### NMM6 — Nested quote depth was discarded by both parser and layout

#### Context and failure

For consecutive `> outer`, `>> inner`, `> outer again` lines, `MarkdownModel::parse()` calculated later depths but collected all lines in the first quote block. `ViewerMarkdownPage.qml` also used fixed quote padding without consuming the published level. The content therefore lost the intended level-1/2/1 distinction without requiring blank separators.

#### Change and reasoning

`MarkdownModel.cpp` ends a quote block when the next marked line changes depth, leaving that line for the next parse iteration. Same-depth lines still coalesce and lazy continuation remains. The QML quote row indents levels beyond the first by `MobileTheme.spacingLarge` and reduces text width accordingly, with the NMM9 bound. The existing flat block model remains; this does not introduce arbitrary recursive containers.

#### Checks and remaining limits

`quoteDepthChangesPreserveSeparateBlocks` checks three blocks with levels 1/2/1 and preserved continuation text. `tst_mobileshell::nestedMarkdownQuotesRetainTheirIndentation` compares actual outer/inner text x positions. Neither source owner ran the tests. Deep indentation intentionally saturates under NMM9, while semantic depth remains intact.

An integrated run also corrected the new geometry test’s element lookup. Its old text search could select the full-width block delegate rather than the rendered text item, making the position assertion inspect the wrong object. The fixture now selects the actual `QQuickText`; the outer/inner indentation and text assertions are unchanged. This is a fixture correction within NMM6, not another rendering feature.

### NMM7 — Markdown links and loaded images lacked working accessibility semantics

#### Context and failure

`ViewerMarkdownPage.qml` offered inline links through a `MouseArea`, but no accessible link role or press action. A screen-reader user lacked the equivalent way to open the confirmation sheet. Once an image loaded, its visible alt `Text` disappeared and the `Image` exposed no alt-derived accessible name.

#### Change and reasoning

Link runs now expose `Accessible.Link`, visible text as their name, and `Accessible.onPressAction` calling the same `offerLink()` used by pointer taps. The child text is accessibility-ignored for links to avoid duplicate announcements; non-link text retains its own accessibility. Loaded images expose `Accessible.Graphic` and the parsed alt name. Accessibility does not bypass link confirmation or web-view capability checks.

#### Checks and remaining limits

`tst_mobileshell::markdownLinksAndImagesExposeWorkingAccessibility` queries the live `QAccessible` link role/name and press action, invokes it to open the real link sheet, loads a real PNG, and checks its Graphic role/alt name. The link fixture is the meaningful **single word `Documentation`**, not a multiword phrase falsely assumed to be one flow item. This matches the actual per-word rendering and exercises the real press action. The test was added, not reported run by its source owner.

Multiword/styled links remain multiple native runs, each carrying the correct destination; this is not an inline-layout redesign. TalkBack/VoiceOver gestures, focus navigation, and announcement quality require real devices and were not exercised.

### NMM8 — Nested emphasis consumed the wrong closing delimiter

#### Context and failure

`MarkdownModel.cpp::findEmphasisClose()` previously accepted the first same-character run at least as long as the opener. For `*outer **inner** outer*`, it could consume the inner `**` as the closing outer `*`; `**outer *inner***` mishandled shared closing runs. Underscore variants had the same problem, producing literal delimiters or incorrect style coverage.

#### Change and reasoning

Opening/closing now share whitespace/punctuation-aware flanking rules, including ASCII symbols, Unicode punctuation, and underscore eligibility. Eligible closing runs take precedence and leave unused delimiters available to open another span. The multiple-of-three restriction prevents consuming a run that must instead participate in nesting. Otherwise, a differently sized eligible nested opener is matched before searching further for the outer close; a shared closing run can close both layers. Nested search has an explicit `kMaxInlineDepth` bound and uses the existing shared character-work allowance. Escape/code-span handling remains. Recursion comments describe both scanner and finder bounds.

Independent review identified an error in the initial nested-search change: `*a***b***c*` incorrectly wrapped everything in italic. The final closer-precedence/flanking/multiple-of-three logic addresses that accepted observation; the initial implementation is not presented as the finished fix.

#### Checks and remaining limits

`nestedEmphasisPreservesTextAndStyles` covers asterisk/underscore outer-italic/inner-bold and outer-bold/inner-italic shared closers. `adjacentEmphasisClosersCanOpenAnotherSpan` checks `*a***b***c*` (a/c italic, b strong), `**a***b***c**` (a/c strong, b italic), and `*a**b**c*` (outer italic, inner strong+italic). The adversarial fixture includes 10,000 alternating potential nested openers. Tests check final text/styles rather than serialized output.

This remains a defined Markdown subset, not complete delimiter-stack conformance. Excessive depth/work leaves delimiters literal under the existing safety policy rather than permitting unbounded recursion or work.

### NMM9 — Deep Markdown indentation could consume the entire text width

#### Context and failure

The list delegate in `ViewerMarkdownPage.qml` subtracted unbounded `level * spacingLarge` from phone-width content. Deep valid lists could push text outside the pane and assign negative width. Depth-aware quote rendering needs the same protection. The arithmetic defect is source-derived; an actual clipped device rendering was not reproduced.

#### Change and reasoning

List/quote rows compute bounded `nestingIndent`, reserving at least one touch-target-width text area when the pane has enough space after fixed margins. Body widths clamp to nonnegative values in extremely narrow panes. Ordinary nesting still indents normally; deep visual indentation saturates without removing text or changing semantic model levels. Semantic object names expose real layout to tests.

#### Checks and remaining limits

`tst_mobileshell::deepMarkdownIndentationKeepsTextReadable[_data]` renders 40 quote levels and 40 actual nested list items, scrolls the real ListView to the deepest row, and checks positive text width and containment in the phone viewport. Ordinary quote-level separation also has NMM6 rendered coverage. A pane narrower than its fixed margins cannot promise a full touch-target width; this is explicit rather than hidden negative geometry.

### NMM10 — Refused Markdown images could keep their old visible status

#### Context and failure

Image fallback text binds to `root.imageRefused[imagePath]` to append outside-project or resolve/read failure reasons. `ViewerMarkdownPage.qml::refuseImage()` previously mutated a JavaScript dictionary in place and assigned that same object back. QML `var` bindings observe property notification, not arbitrary member mutations, so this did not reliably notify the visible label. The stale-label outcome follows from notification semantics; it was not claimed as a device reproduction.

#### Change and reasoning

#### Checks and remaining limits

It exercises the binding, not merely the map. This is status visibility, not a new containment rule or an excuse to read denied image bytes.

## Native terminal behavior

The four terminal findings below come from inspection of `src/vt/**` and its behavioral tests. Their before-cases are concrete source-derived failure sequences, not failing executions observed by the auditing worker. Changes are internal to the existing raw-byte `VtScreen::write` interface: no external caller, transport, enum, dependency, build option or version migration is required. New tests feed commands byte by byte and examine screen behavior, rather than matching implementation text. Execution evidence belongs to the report's central verification section.

### NVT1 — Invalid scrolling margins changed the active region and cursor

#### Context and failure

`src/vt/VtScreen.cpp::VtScreen::setScrollRegion` handles DECSTBM, the command that restricts vertical scrolling to part of the terminal. On a 10×5 screen containing A through E on separate rows, `ESC[2;4r` protects rows 1 and 5. After moving the cursor to row 3, column 3, an equal or inverted request such as `ESC[1;1r`, `ESC[4;2r` or `ESC[3;3r` incorrectly reset the region to the whole screen and homed the cursor. `ESC[99999;0r` and `ESC[0;1r` also exposed invalid/default handling. The old conversion treated an explicit bottom row 1 as if the bottom were omitted. Subsequent line feeds no longer honored the previously valid region and could damage protected content.

#### Change and reasoning

Default/zero handling now happens before converting coordinates to zero-based indices. Explicit bottom 1 remains row 1; the existing clamp of an excessively large bottom to screen height is preserved. A request whose top is not strictly before its bottom returns without changing either margins or cursor. Valid requests still home the cursor, and `ESC[0;0r` still selects the full screen. This follows [DECSTBM's valid-region contract](https://vt100.net/docs/vt510-rm/DECSTBM.html), rather than inventing one-line-region support. The distinct resize policy that repairs a region collapsed by a geometry change is unchanged.

#### Checks and remaining limits

`src/vt/tests/tst_vt.cpp::invalidScrollMarginsPreserveRegionAndCursor` initializes a separate screen for each invalid request, checks cursor preservation, then feeds LF at row 4. It verifies only the original region scrolls, A/E remain intact and history stays empty. A subsequent zero/default request must home the cursor and permit full-screen history growth. No reflow or origin-mode feature was added.

### NVT2 — Unsupported CSI syntax triggered valid commands

#### Context and failure

`src/vt/VtParser.cpp::dispatchCsi` and `dispatchPrivateMode` retained CSI syntax details but did not consistently use them when deciding which command to execute. `ESC[1:2;3H` could act like ordinary cursor positioning even though colon subparameters are not coordinate separators. `ESC[?25:7l` could hide the cursor and disable autowrap, `ESC[?25!l` could hide the cursor, `ESC[?1049!h` could enter the alternate screen, and `ESC[6:1n` could produce a cursor-position reply. Unsupported intermediate or subparameter forms therefore acquired unrelated side effects.

#### Change and reasoning

CSI forms containing subparameters are now ignored unless they are ordinary SGR: final `m`, no private marker and no intermediate. That is the existing path that actually understands subparameters. Dispatch of `? ... h/l` additionally requires no intermediate. Well-formed implemented movement, mode, report and rendition commands remain supported; unsupported commands are consumed through their final byte and ignored using the existing bounded parser recovery. The change preserves command identity rather than expanding terminal features. [XTerm's control-sequence definitions](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html) distinguish semicolon-separated parameters from subparameters and intermediates.

#### Checks and remaining limits

`unsupportedCsiFormsHaveNoSideEffects` covers the examples above plus `?1$h`, after visible text, a non-home cursor and red rendition. It compares consumer-visible screen state, verifies no PTY reply, then checks that X prints at the original red cell. Existing colon-SGR and split-feed tests protect valid behavior. No new private queries or modes were introduced.

### NVT3 — Soft reset moved the active cursor to home

#### Context and failure

`src/vt/VtScreen.cpp::VtScreen::softReset` unconditionally called `moveCursor(0, 0)`. With content/history already present, setting margins using `ESC[2;3r`, positioning using `ESC[3;5H`, setting red rendition and saving the cursor, then sending `ESC[!p` and printing X placed X at row 1, column 1. DECSTR resets saved cursor state and terminal settings, but does not relocate the active cursor. Programs resuming output at their current position were displaced.

#### Change and reasoning

The active-cursor move was removed, with a comment distinguishing the saved home position from the active position. Existing rendition, mode, margin and saved-slot resets, including deferred-wrap cancellation, remain. Hard reset is unchanged. This matches [DECSTR's reset table](https://vt100.net/docs/vt510-rm/DECSTR.html); unrelated historical terminal-model defaults, including the engine's existing xterm-style autowrap behavior, were not changed.

#### Checks and remaining limits

`softResetPreservesActiveCursor` constructs history on a 10×4 screen, establishes the region and saved/red state, then sends DECSTR bytewise, requests DSR and prints X. It requires `ESC[3;5R`, X at that cell with reset foreground, unchanged existing history, `ESC 8` restoring the newly reset saved-home position, and LF at the bottom using restored full-screen margins. Existing reset and split-feed cases remain relevant.

### NVT4 — Underline style zero enabled underline instead of clearing it

#### Context and failure

`src/vt/VtScreen.cpp::VtScreen::applySgr` reduced non-color colon forms to their primary SGR code. Thus `ESC[1;4;31mA` followed by `ESC[4:0mB` applied simple SGR 4 and retained/enabled underline. B should remain bold/red but lose underline. Editors using the modern underline-style reset could leave stale decoration behind.

#### Change and reasoning

For code 4 with first subparameter 0, the implementation now clears only `VtUnderline`. Other supported nonzero underline styles retain the existing plain-underline fallback. No new style fields, rendering features or underline-color support were introduced. [The underline-style extension](https://sw.kovidgoyal.net/kitty/underlines/) explicitly defines `4:0` as no underline, so this repairs syntax already accepted by the engine rather than adding speculative features.

#### Checks and remaining limits

`underlineSubparameterZeroDisablesUnderline` verifies A is bold and underlined, bytewise `4:0` leaves B bold/red without underline, and `4:3` restores the existing plain-underline fallback for C. Full styled-underline rendering remains outside the implementation.

## Build, release and fixture infrastructure

NBR1–5 and NBR7 were derived from the release helper, CMake wiring, packaging and fixture sources; NBR6 additionally records an actual integrated failure reported by the main run. Added regressions use disposable directories, copied source or throwaway local Git repositories/remotes. They use no production database, socket, credential or tmux session. Current source requires Qt 6.10 and Node 23.6 or newer; no dependency floor or version was changed by these fixes.

### NBR1 — Fixture refresh followed redirected key and configuration paths

#### Context and failure

`tests/live/generate-fixture.sh` rejected a symlink fixture directory but used a private-key regular-file check that followed symlinks. A developer key linked at `id` or `hostkey` could therefore become the supposedly throwaway fixture key, including chmod through that path. Output publication used `mv -f temporary destination`; if a public-key/config destination was a symlink to a directory, or an actual directory, the move could write inside it instead of replacing the intended fixture file. Dangling private-key links reached key generation rather than a clear safety refusal.

#### Change and reasoning

Before chmod, key generation or output mutation, the script now validates all six managed paths: `id`, `hostkey`, their public halves, `authorized_keys` and `sshd_config`. It refuses every symlink, including dangling links, and every existing non-regular file. The narrower duplicate private-key check was removed. Normal refresh retains the private keys, regenerates public halves, replaces configuration/authorization and deliberately deletes the fixture workspace database and sidecars. The documentation warning about destructive refresh is described under NDC5; path admission and refresh deletion are separate issues.

#### Checks and remaining limits

New `tests/live_fixture_generation.sh` invokes the real generator and `ssh-keygen` without launching sshd. It checks key preservation, public/authorized-key repair and SQLite/WAL/SHM/journal removal, then redirects every managed path to an external key, directory or nonexistent target, and also tests actual directories. Refusal must leave external bytes, mode and directory contents unchanged. `tests/CMakeLists.txt` registers UNIX-only `tst_live_fixture_generation`, timeout 60 seconds, skip 77 without `ssh-keygen`. Hard links and adversarial concurrent same-user path replacement are not newly prevented. Refresh remains suitable only for a dedicated disposable fixture with connected services stopped.

### NBR2 — Release preflight could move the tag away from the verified commit

#### Context and failure

`.omp/skills/bump-version/bump.sh --push` verified committed version metadata, ran arbitrary configured preflight commands, then created an annotated tag using implicit HEAD. A preflight that checked out another commit or committed a different tree could make the tag identify an unchecked commit. A detached-HEAD push guard ran after tag creation, too late to preserve the no-mislabelled-tag guarantee.

#### Change and reasoning

The helper captures `release_commit` before archive verification, verifies an archive of that explicit commit, requires HEAD still to match after preflight, and supplies the same explicit commit to `git tag -a`. HEAD movement now fails before tag creation; pinning the target also removes the small implicit-HEAD targeting race. Existing atomic branch-plus-tag push behavior remains. `.omp/skills/bump-version/SKILL.md` documents the invariant and coverage.

#### Checks and remaining limits

`tests/bump_version_tag.sh` now creates a real disposable repository and local bare remote, configures preflight to check out the previous commit, and requires failure with neither local nor remote release tag. Moving HEAD during preflight is intentionally rejected; the helper does not lock out arbitrary external Git operations or undo intentional preflight changes. An already-created release commit remains after a failed preflight, as before.

### NBR3 — Predictable release staging names bypassed source-path safety

#### Context and failure

`.omp/skills/bump-version/bumpctl.mjs::commandApply` checked configured source paths for escaping symlinks, then wrote to predictable `${source}.bumpctl-${process.pid}` names. A pre-existing symlink at that staging path could redirect both write and chmod outside the repository, and publication could replace the source with the symlink. A preparation failure before registering the stage also left its temporary path outside cleanup tracking.

#### Change and reasoning

Each source now gets an atomically reserved, owner-private unique directory beside the target using `mkdtempSync`. The helper registers that directory for cleanup before writing the staged version inside it. Publication remains a same-filesystem rename and preserves the original mode. Complete staging directories are removed after preparation failure, successful rollback or successful publication; retained recovery data is the explicit exceptional case described under NBR5. Skill documentation explains private atomic staging.

#### Checks and remaining limits

The real-helper shell suite includes a same-process Node harness that plants the old predictable symlink pointing to a disposable outside sentinel, imports the actual helper and requires unchanged sentinel bytes, consistent rewritten versions and no untracked staging leftovers. Filesystem operations for this case are real, not mocked. Unique private directories incur small metadata overhead; they do not protect against a same-user process deliberately entering an already-reserved directory. Existing supported in-repository source-symlink replacement semantics are unchanged.

### NBR4 — Embedded web bundles ignored lock changes and missing output files

#### Context and failure

`src/qml/CMakeLists.txt::codeharbor_embed_web_bundle()` treated a bundle as absent only if `dist/index.html` was missing. Removing `terminal.js`, `editor.worker.js` or CSS while retaining the index and source timestamps could skip bundling and give `qt_add_resources` a nonexistent resource. #### Checks and remaining limits

### NBR5 — Release rollback depended on new writes after a publication failure

#### Context and failure

In `bumpctl.mjs::commandApply`, a later publication rename could fail after earlier version files had already changed. Recovery then called `writeFileSync` directly on published targets using original buffers. Disk-full, quota or I/O problems could also break those recovery writes; opening for write could truncate a target first. One recovery exception could stop remaining restoration and cleanup, leaving a partly bumped or truncated tree.

#### Change and reasoning

Before publishing any replacement, the helper prepares original-byte backups with original modes inside NBR3's private per-source staging directories. Rollback renames those prepared originals back instead of requiring another data write. If one rollback rename also fails, recovery continues for the other sources, retains the affected backup directory and reports the original's exact recovery path. It does not falsely claim complete restoration. Successful publication and successful rollback remove all reserved directories. Skill documentation describes prepared backups, cleanup and honest retained-backup diagnostics.

#### Checks and remaining limits

`tests/bump_version_tag.sh` adds deterministic I/O failure injection around the actual helper in a disposable repository: Node's filesystem entry points fail the second publication rename and reject direct data writes to configured targets. Assertions require byte-identical originals, retained executable mode and no untracked stage after successful rollback. Imports are top-level; this is real helper/filesystem behavior with injected failure, not a simulated success message. Staging a second small metadata copy deliberately spends bounded release-tool I/O to avoid recovery writes during disk trouble. This is not a multi-file crash-atomic transaction: process death, power loss or a filesystem refusing rollback can still interrupt restoration. In that case originals are retained and diagnosed; no crash journal or silent unsafe fallback was added. Supported source-symlink replacement semantics remain unchanged.

### NBR6 — Database-isolated live fixtures still shared the ordinary bridge socket

#### Context and failure

This before-case was actually observed during the main integrated run, not merely inferred from source. With an isolated `CODEHARBOR_DB` and an ordinary GUI/another fixture connected concurrently, seven live bootstrap gates failed with closed RPC transports. `tst_livereconnect` reported `codeharbor-bridge address already in use: /home/yichen/.cache/codeharbor/events.sock`; independently socket-isolated `tst_liveagent` passed.

`tests/live/generate-fixture.sh` exported only the database path through sshd `SetEnv`. The production `remote/src/events.ts::resolveSocketPath()` independently selects `$XDG_RUNTIME_DIR/codeharbor.sock` for an absolute runtime directory, otherwise `$HOME/.cache/codeharbor/events.sock`. Separate databases did not isolate bridge/hook sockets, so fixtures could collide with each other or the ordinary user session.

#### Change and reasoning

The generator now reserves `<fixture>/runtime`, refusing symlinks, including dangling links, non-directories and an existing directory owned by someone else before key/config/permission mutation. It creates or normalizes an owned directory to exact mode 0700 under umask 077. The final generated configuration uses one directive, including NBR7's data/history/tmux isolation: `SetEnv "CODEHARBOR_DB=$fixture/workspace.sqlite" "XDG_RUNTIME_DIR=$runtime" "XDG_DATA_HOME=$data" "HISTFILE=/dev/null" "TMUX_TMPDIR=$tmux"`, where `$data` and `$tmux` are `<fixture>/data` and `<fixture>/tmux`. Refresh preserves private keys and reserved-directory contents; it does not unlink sockets or kill processes.

The generator also resolves the existing physical ancestor and checks the byte length of `<fixture>/runtime/codeharbor-control-0000000000000000.sock` before any mkdir, chmod, key/config write or database change. That accounts for the production `mintControlSocketPath` suffix of eight random bytes rendered as 16 hex characters. Exactly 103 pathname bytes is accepted; longer paths fail with the required length/limit and guidance to choose a shorter private fixture root. This uses Darwin's portable 103-byte ceiling even though Linux permits 107. There is no truncation or fallback to a shared global directory. UTF-8 byte length, rather than character count, is what matters.

DEVELOPMENT replaces its potentially overlong repository-nested default fixture recipe with a short private `mktemp -d /tmp/ch-live.XXXXXX` root, passed explicitly to the generator and reused consistently for sshd, agent, key and known-hosts paths. It explains UTF-8 byte accounting, the fixed database-parent/runtime relationship rather than an external-runtime bypass, and owned-process shutdown before removing the disposable directory.

`tests/live/check-fixture-isolation.sh::remote_probe` checks the actual remote environment before bootstrap: runtime must be absolute, present, unredirected, owned by the session account, mode 0700 and canonically equal to `<canonical database parent>/runtime`. Old database-only sshd configurations therefore fail preflight instead of sharing the ordinary namespace. Existing hand-written fixtures must add the private runtime and restart their owned sshd. Generator guidance and DEVELOPMENT now require stopping only that fixture's sshd and daemon/bridge before refresh, then restarting the owned sshd. They explicitly forbid solving this by deleting a shared socket or killing unknown processes.

#### Checks and remaining limits

`tests/live_fixture_generation.sh` adds runtime creation, mode normalization, retained-sentinel and symlink/file/dangling-path refusal checks without external chmod/mutation. `tests/live_fixture_isolation.sh` exercises the real shell probe with valid, missing, relative, ordinary-cache, other-fixture, symlink/file and insecure-mode cases. New `tests/live_fixture_socket_isolation.sh` generates two disposable fixtures, uses actual `sshd -T` to resolve effective `SetEnv`, loads production `events.ts::resolveSocketPath()` with real `process.env`, and simultaneously binds both fixture sockets plus an ordinary-default socket under a synthetic home. It opens no sshd listener and every socket remains inside the temporary test tree. `tests/CMakeLists.txt` registers UNIX `tst_live_fixture_socket_isolation`, timeout 60 seconds, skip 77 without sshd, ssh-keygen, tmux or Node 23.6 or newer; tmux coverage is detailed under NBR7.

The socket regression also imports production `mintControlSocketPath` and checks that exact-103-byte ASCII and UTF-8 paths can generate and bind sockets. A 104-byte path must fail before creating a new directory and without changing an existing fixture's database, file contents or mode. The tiny generator/socket test fixtures deliberately use short private physical paths under `/tmp/chfix.*`, independent of a long build `TMPDIR`; bulk source/build test data still belongs under `build/dev/.tmp` to avoid temporary-filesystem exhaustion.

The first integrated execution of the socket regression actually failed with `sshd did not retain the private fixture runtime`. Inspection of `sshd -T` showed that two separate `SetEnv` directives retained only the first in this OpenSSH path. Combining assignments into one directive corrects that delivery error; NBR7 subsequently adds data, history and private-tmux assignments to that same directive. The effective-configuration/socket assertion remains unchanged. This observed intermediate failure explains why the test parses real sshd configuration rather than merely checking source text. It is not a separate unresolved finding; post-correction results are recorded only in central verification.

Post-fix results and armed live-preflight evidence are listed in central verification. The portable test proves effective configuration/resolver coexistence, not actual SSH environment delivery. Runtime contents are intentionally not swept: fixture owners retain responsibility for their own process/socket lifecycle. Canonical ownership/path/mode checks do not prevent adversarial same-user concurrent replacement. No shared socket was deleted or ordinary user process touched by this fix.

### NBR7 — Live fixtures did not isolate recovery files, history or tmux state

#### Context and failure

Database and socket isolation did not cover all writable session state. `remote/src/codeharbord.ts::recoveryBaseDir` and `server.info` derive the recovery location from `XDG_DATA_HOME`, independently of `CODEHARBOR_DB` and `XDG_RUNTIME_DIR`. A live fixture retaining the ordinary data directory could therefore advertise a normal-user recovery location to the client; an editor recovery write could place test content there. The main run observed unsaved GUI text, but did not observe such a recovery-file write. The write risk is established by the source path, not an invented runtime incident.

An interactive Bash launched under the ordinary HOME could also persist commands to its ordinary history file when no isolated history destination was supplied. That is a source-derived risk based on standard Bash behavior, not an observed history leak.

Supplying safe variables to a new SSH process is also insufficient if its terminal joins an already-running ordinary tmux master: that master can retain a different data/runtime/history environment. Fixture terminal processes therefore need a private default tmux namespace as well as private daemon paths. This extension closes that inherited-environment route rather than merely testing a directly launched shell.

#### Change and reasoning

`tests/live/generate-fixture.sh` now reserves `<fixture>/data` and `<fixture>/tmux` as owned directories with exact mode 0700, rejecting symlinks, non-directories and another owner's existing directory before mutation. It retains existing private directory contents and keys during refresh. The single effective sshd `SetEnv` directive supplies five boundaries together: private database, private runtime, `XDG_DATA_HOME=<fixture>/data`, `HISTFILE=/dev/null` and `TMUX_TMPDIR=<fixture>/tmux`. The account's production HOME is deliberately unchanged: preflight needs it to recognize ordinary database aliases, and moving it would silently change unrelated SSH/shell behavior. DEVELOPMENT documents those assignments, preservation rules and limits.

`tests/live/check-fixture-isolation.sh::remote_probe` additionally requires `XDG_DATA_HOME` and `TMUX_TMPDIR` to be absolute, present, non-symlink, owned by the session account, mode 0700 and canonically `<canonical database parent>/data` and `/tmux`, respectively, and requires the history sink to be `/dev/null`. Existing configurations need those assignments and an owned-sshd restart. Before refreshing, stop only the fixture-owned sshd, daemon/bridge and its private tmux master; never stop an ordinary/global master or delete its socket.

#### Checks and remaining limits

The existing generator/path regressions cover owned-0700 creation, mode normalization, preservation and unsafe-path refusal for reserved directories, unsafe data/tmux paths and absent/ordinary-history `HISTFILE`. The socket-isolation regression reads all five effective sshd assignments, applies them in isolated Node processes for two fixtures, dispatches actual `server.info`, and writes through actual `file.writeFile` to the reported recovery path. It checks snapshot bytes, file mode 0600 and recovery-directory mode 0700, closes each private SQLite workspace, and verifies no fallback recovery directory under synthetic HOME. It clears inherited `CODEHARBOR_AGENT_SOCKET` within the isolated Node process so a caller's explicit endpoint cannot contaminate default-path checks; production terminal endpoint handling is unchanged.

The same regression starts another private tmux master with different data/runtime/history values, then starts each fixture's default master using its effective `TMUX_TMPDIR`, without `-L` or `-S` overrides, and verifies a distinct server PID. A new controlled `bash --noprofile --norc -i` window reports all five inherited values, inserts a history entry and explicitly writes history. Synchronization uses `tmux wait-for`, not sleeps. Assertions require those values to match the fixture, synthetic HOME to have no `.bash_history`, and the older private master's environment/history sentinel bytes to remain unchanged. Cleanup stops only these known private masters, with EXIT fallback addressing only sockets inside their private roots. Synthetic HOME belongs only to disposable tests, not generated fixture configuration. No additional CTest target/count is introduced.

Socket-test prerequisites include actual sshd, tmux and Node 23.6 or newer with SQLite; missing prerequisites skip 77. Real handler/filesystem coverage does not certify GUI autosnapshot timers or SSH transport delivery. The controlled shell/tmux checks do not sandbox arbitrary startup commands, which can write elsewhere or override variables; preflight rejects unsafe effective values before armed gates. Recovery/private-tmux contents are preserved during refresh, and normal-user cache/recovery/history/global tmux state is never cleaned. Same-user path replacement is outside the directory checks. Untrappable termination may interrupt cleanup of a private test master, but cleanup cannot redirect to a user-global server.

The NBR6/NBR7 caller migration also updates `src/terminal/tests/tst_liveterminalfactory.cpp::severTheNetwork`. An actual integrated run failed `anUncleanNetworkDropKeepsTheSessionItsWorkAndSaysNothing` because its old guard required a standalone database-only `SetEnv` line and correctly refused the new configuration. The final `fixtureConfigurationMatches` helper requires one complete five-assignment directive in generator order—database, runtime, data, history sink, private tmux root—rooted in the validated fixture, and rejects additional directives case-insensitively, including mixed-case overrides. It retains exact port, loopback, host-key, authorized-keys and PID-file checks. Existing identity/config/PID symlink checks, listener PID greater than one, `/proc` command identity of sshd, exact listener command/config/allowed flags, and descendants-only signalling remain intact; no safety check is weakened to make network interruption run.

`fixtureConfigurationPinsEveryWritableNamespace` accepts the generated five-namespace contract and rejects each of the five missing assignments or foreign values, including explicit missing-tmux/foreign-tmux cases, mixed-case overrides, duplicate environment directives and foreign ports. This is shared fixture-policy migration, not a new terminal finding or a proved canonical-versus-lexical path-alias defect.
