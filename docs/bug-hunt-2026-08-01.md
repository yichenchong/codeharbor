## Vocabulary, defined once

The codebase uses some words in a specific way. They are spelled out here so the rest of
this document can be read without opening the source.

* **Dev Session** — one unit of work: a checkout on a remote server, plus the panes and
  shells opened against it.
* **Pane** — one rectangular sub-view. The window has a fixed three-part layout: a
  sessions sidebar down one side, a viewer region, and a terminal region.
* **`codeharbord`** — a small Node service that CodeHarbor runs on the remote SSH server.
  All workspace data lives there. The desktop client talks to it in JSON-RPC: one JSON
  object per line, over an SSH channel.
* **`codeharbor-bridge`** — a second small Node process on the server. It listens on a
  Unix socket for status messages posted by coding-assistant programs and relays them to
  the client.
* **tmux** — a program on the remote server that keeps a shell alive after the client
  disconnects. Every terminal pane is attached to one tmux session; that is what makes
  terminals survive a dropped connection.
* **Harness** — a coding-assistant program running in a terminal (Oh My Pi, Pi, Claude
  Code). An **adapter** translates one harness's own event vocabulary into CodeHarbor's.
* **Qt signal** — a notification one C++ object sends to others. Qt delivers signals
  *synchronously*: emitting one runs every connected handler to completion before the next
  line of the emitting function executes. A handler is allowed to do anything, including
  destroy the object that sent the signal.
* **`QPointer`** — a Qt smart pointer that automatically becomes null when the object it
  points at is destroyed, instead of dangling.
* **QWebChannel** — Qt's bridge that lets JavaScript inside an embedded browser view call
  C++ methods and receive C++ signals.
* **Revision token** — an opaque string identifying the exact contents of a remote file at
  the moment it was read. A save quotes it, and the server refuses the write if the file
  has moved on, which is how two editors are stopped from silently overwriting each other.
* **Write-ahead log** — a SQLite mode where changes go to a side file first, so readers are
  not blocked by a writer.

# MP — models and persistence

## MP1 — Saving a window layout reported success when the server echoed back something unusable

**Files:** `src/persistence/WorkspaceDb.cpp` lines 641–678; `src/persistence/WorkspaceDb.h`
lines 149–161 and 250–254.

**What the code did before.** `WorkspaceDb` is the client's gateway to the workspace
database that lives on the server. Every method is a JSON-RPC request; the reply is decoded
into a C++ structure and handed to a callback. That callback always receives a pair: an
optional result, and an optional error.

`setLayout` saves the split layout of one region of a Dev Session — how the panes are
divided up. The server answers by echoing back the row it stored, with the layout tree under
a key called `tree`. The old code ran that reply through a generic handler that only checked
"is this reply a JSON object at all". It then called a parsing helper which returns "no tree"
in two different situations: when the `tree` key is missing, and when it is present but
structurally invalid. That "no tree" answer was passed to the caller **with no error
attached**.

**Why that is wrong.** For the sibling method `getLayout`, an empty answer is meaningful — it
is how the server says "this region has no saved layout yet". `setLayout` has no such answer:
it has just written a layout, so the row it echoes back must contain one. A reply like
`{"id":"L1","devSessionId":"s1"}` with no `tree`, or one whose tree is invalid (for example a
split with two child panes but only one size ratio), therefore reached the caller as
"success, no error, no tree" — indistinguishable from a clean save. The only caller,
`SessionLayouts`, looks solely at the error slot. So a server or an intermediary returning a
mangled row would leave the user believing their layout was saved when nothing usable had
been stored. It also contradicted this class's own stated policy, which is that every
wrong-shaped reply is turned into a synthesized error with the JSON-RPC code `-32603`
("internal error"), and contradicted the header's promise that "setLayout delivers the stored
tree on success".

**What changed.** `setLayout` now has its own explicit reply handler: a server-reported error
is passed through unchanged; a result that is not an object fails with `-32603` and the
message "expected a SessionLayout object"; a row whose tree is missing or invalid fails with
`-32603` and "expected a SessionLayout object with a valid tree". A valid tree is delivered
exactly as before. The class documentation and the declaration comment were rewritten to
match, including an explicit note that `getLayout` deliberately keeps the opposite verdict —
there, an unreadable stored tree means "no layout", so a region whose layout cannot be loaded
comes up empty rather than inviting the user to edit a fabricated one.

**Test.** New: `TstWorkspaceDb::setLayoutMalformedTreeDeliversRpcError`. A row with no tree
and a row with an invalid tree must each deliver no layout plus an error with code `-32603`
naming `workspace.setLayout`. To prove the check is selective rather than a blanket
rejection, it also asserts that a row echoing a valid tree still succeeds — including the
empty single-pane tree that legitimately gets stored when the last pane in a region is closed.

## MP2 — The sidebar model announced row changes while it was still halfway through updating itself

**Files:** `src/models/SessionsModel.cpp` lines 53–76; `src/models/SessionsModel.h` lines
63–64.

**What the code did before.** `SessionsModel` is the data model behind the sessions sidebar.
Top-level rows are groups; child rows are Dev Sessions. Each Dev Session row shows a status
badge summarising the state of that session's terminals.

`updateTerminalStates` is the cheap refresh path. Rather than resetting the whole model —
which would destroy and rebuild every on-screen row and lose the user's selection — it copies
the new terminal state into each session in place, and emits Qt's `dataChanged` signal only
for the rows whose badge actually moved. The old code did both jobs in a single loop: for
each session it computed the old badge, moved in the new terminal state, computed the new
badge, and if they differed emitted `dataChanged` **right there** before moving on to the
next session.

**Why that is wrong.** Two problems, both caused by sending a notification in the middle of a
mutation.

The first is that receivers see a half-updated model. `dataChanged` is delivered synchronously
to every connected receiver. A receiver that looks at any row other than the one named in the
signal — a sorting or filtering layer recomputing its mapping, or an on-screen row whose
appearance depends on its siblings — sees rows further down the list still reporting their
**previous** terminal state, because the loop has not reached them yet. It then caches or
draws a state that was never actually true.

The second is worse: the loop holds C++ references into two vectors, one of them the model's
own storage. Any receiver that reacts by calling `setGroups()` re-entrantly replaces that
storage wholesale, freeing the memory the loop is still walking. That is a use-after-free for
the remainder of the iteration.

**What changed.** The single loop was split into two passes. The first adopts every session's
new terminal state and records which rows changed; the second emits `dataChanged` for the
recorded rows. No container reference is alive while a signal is in flight, and the model is
fully in its new state before the first notification goes out. The signals emitted, their
order, and their contents are unchanged. The ordering guarantee is now documented on the
declaration.

**Test.** New: `TstModels::updateTerminalStatesFinishesEveryRowBeforeSignalling`. It builds one
group with two Dev Session rows, moves both from idle to error in a single refresh, and from
inside a `dataChanged` handler reads the badge of **both** rows every time a signal arrives,
asserting both already report error at the very first signal. Confirmed to fail against the
pre-fix code, where the second row still reported idle.

## MP3 — A parsing helper quietly turned a wrong-shaped reply into "the user has no groups"

**File:** `src/persistence/WorkspaceDb.cpp` lines 163–176, call site at line 422.

**What the code did before.** `parseGroupList` decodes the reply to `workspace.list`, which is
the entire sidebar: groups, their Dev Sessions, and each session's panes and layouts. It took
a `QJsonValue` — a value of *any* JSON kind — and called `.toArray()` on it. Qt's `toArray()`
does not fail on a value of the wrong kind; it returns an **empty array**. So handing this
function a number, a string, an object or JSON null returned an empty group list,
indistinguishable from a server that genuinely has no groups.

**Why that is wrong.** This was not reachable today — the single caller does check that the
value is an array first. It is a trap for the next person: nothing in the function's signature
said that check was mandatory, and the very same file's comments identify this exact
`toArray()` behaviour as the reason wrong-shaped replies must be rejected rather than decoded.
A second call site added later (a cached list, a batched reply, a new nested field) would
compile fine, skip the check, and silently report an empty sidebar for a malformed reply. It
also did the conversion twice.

**What changed.** The parameter type is now `const QJsonArray&`, so a caller physically cannot
pass anything else, and the single conversion happens at the call site that has already
established the value is an array. A comment records why the signature is deliberately narrow.

**Test.** None added — the observable behaviour is unchanged and already covered by
`malformedResultsDeliverRpcErrorInsteadOfBlankRecords` and `listSkipsNonObjectEntries`.

## MP4 — A comment claimed every identifier is a server-generated UUID; one of the five is not

**File:** `src/models/Ids.h` lines 5–10.

**What the code did before.** The comment above the five strongly-typed identifier wrappers
read: "Values are opaque UUID strings generated server-side."

**Why that is wrong.** It is true of four of them, which the daemon mints with a random-UUID
call. It is not true of `ServerId`, which names *which* server a row belongs to and is chosen
entirely on the client — real values in live code and tests look like
`live-shell-<pid>-<timestamp>` and `srv-live`, none of them UUIDs and none of them
server-generated. Someone trusting the comment could reasonably add UUID-format validation, or
assume the server guarantees these are unique. Neither holds.

**What changed.** The comment now names the four server-minted UUID types explicitly and calls
out `ServerId` as the client-chosen exception, describing it as an arbitrary opaque string.

## MP5 — The client cannot express "clear this field", and nothing said so

**Files:** `src/persistence/WorkspaceDb.h` lines 41–56 (new comment block);
`src/persistence/tests/tst_workspacedb.cpp` lines 1284–1341 (new test).

**What the code did before.** The server treats several update fields as three-valued. In
`remote/src/workspace.ts` (for example lines 1538–1548), a field that is *absent* means "leave
the stored value alone", a field that is JSON `null` means "clear the stored value", and a
string means "store that string". The database columns really are nullable. This applies to a
terminal pane's working directory, tmux target, startup command and harness, and to a Dev
Session's default working directory and task description, among others.

The client side represents those fields as `std::optional<QString>`, and every serializer
writes the key only if the optional holds a value. So a disengaged optional omits the key
("leave alone") and an engaged optional always writes a JSON string. There is no value of
`std::optional<QString>` that produces JSON `null`. The server's clear branch is therefore
unreachable from this client, and nothing anywhere stated that.

**Why that matters.** It is a contract mismatch across two languages with no marker on either
side, so the next person to need "clear this field" will reach for an engaged optional holding
an empty string and get the wrong result. On one field the wrong result is loud rather than
quiet: an empty tmux target is not read as a clear — the server's validator requires at least
one character, so the whole request fails with an "invalid params" error.

**What changed, and what deliberately did not.** No structure was widened and no sentinel value
was invented; no caller needs to clear a field today, and adding a second way to spell "absent"
would cost more than the gap. Instead the contract is now written down once, above the
parameter structures: the server's three-part rule, the two-thirds of it this class can
express, the fact that the clear path is not reachable from here, and the empty-tmux-target
case named explicitly.

**Test.** New: `TstWorkspaceDb::updateOptionalsOmitUnsetAndSendEmptyStringsVerbatim`. It issues
an update with some fields engaged-but-empty and others unset, then inspects the outgoing JSON
request: each engaged-empty field must be present as an empty JSON string — not null, not
absent — and each unset field must be absent entirely. It would fail if the serializer ever
started skipping empty strings or emitting null for them.

### Investigated in this area and deliberately left alone

* **`SplitNode::toJson()` can produce a tree that `SplitNode::fromJson()` refuses.** The parser
  requires one size ratio per child, each finite and greater than zero; the writer does not
  check. Left alone for two reasons: the only producer of ratios, `SessionLayouts::setRatios`,
  already enforces exactly the parser's rules, so the bad state is unreachable; and the
  asymmetry is deliberately pinned by an existing test that serializes a two-children,
  one-ratio node and requires the round trip to reject it.
* **`resolveTerminalPane` sends an empty name when the caller supplies neither address.** The
  server rejects it and the caller gets a proper error, so nothing is silently wrong. A
  client-side short-circuit would have to invoke the callback before the function returned, a
  re-entrancy pattern no other method here has and none of the callers are written for.
* **Two identifier fields in one parameter structure are plain strings where every sibling uses
  the typed wrapper.** A real inconsistency, but tightening it requires editing a call site in
  another area.
* **Three recursive functions on the split tree have no depth guard**; only the parser enforces
  the 256-level cap. Already documented, with the reasoning: in-memory trees are built one
  level at a time by user splits and never approach the bound.
* **`WorkspaceDb` never null-checks the connection object it borrows.** The lifetime contract is
  documented and every construction site passes a live object; a check would only turn an
  immediate obvious crash into a silent no-op, which is worse.

# AC — application core

## AC1 — A failure caused by the user's own Disconnect was painted as a red error

**File:** `src/app/AppController.cpp` lines 727–736.

**What the code did before.** Every time a connection comes up — including every automatic
reconnect — the client issues a `server.info` request to ask the server for its version, its
schema level and its identity. The callback for that request started by emitting the
controller's `error` signal on any failure, which the interface renders as a red banner at the
top of the window.

Every *other* asynchronous callback in this class instead goes through a small private helper
whose entire purpose is to swallow errors while the client is deliberately tearing a session
down, i.e. while the user's own Disconnect is in progress. That is because a teardown fails
every request still in flight, by design, with a synthetic "transport closed with request
pending" error. The helper's comment says exactly that: it is "the expected consequence of the
user clicking Disconnect, not a fault to paint red".

**Why that is wrong.** `server.info` is in flight for precisely the window a Disconnect covers.
A connection comes up, `server.info` goes on the wire, and before the answer arrives the user
presses Disconnect. Every other pending request is muted; this one popped a red error at a user
who had just asked for the disconnect. Two code paths that should agree, and did not — the
helper existed and the one caller that most needed it did not use it.

**What changed.** The bare emit was replaced with a call to the helper. Behaviour outside a
teardown is identical: the helper emits the server's message unchanged.

**Test.** New: `TstAppController::serverInfoFailureDuringDisconnectIsNotPaintedAsAFault`. It
drives a real bootstrap object so that a `server.info` really is unanswered on the wire, drops
the transport at the same point in the teardown sequence the real connection would, then calls
`disconnectServer()`. It asserts the error signal never fires and that the controller ends up
reporting "disconnected". Without the fix the test sees one "transport closed with request
pending".

## AC2 — A server that reported no identity left the window looking connected with a permanently empty sidebar

**Files:** `src/app/AppController.cpp` lines 774–786, new helper at lines 806–821;
`src/app/AppController.h` lines 258–263.

**What the code did before.** The `server.info` callback has two "this server is unusable"
branches.

The first is the schema-version floor: if the server speaks an older workspace schema than the
client requires, the code shows a message naming both versions and then genuinely refuses. It
schedules a disconnect one event-loop turn later — deferred because the code is running inside
the connection object's own reply callback and the teardown destroys that object's transport
underneath it — and sets the durable connection state to "failed" with that message attached.

The second is the identity check. If the server answers without an identity string, the code
emitted a transient error banner and returned. No disconnect. No state change.

**Why that is wrong.** The consequence of both branches is identical. Without a server identity
the client cannot key a single workspace row — every group, Dev Session and terminal pane on
the remote side is stored against it — so the client deliberately does not even ask for the
workspace listing. The user was left with a healthy-looking SSH session, a footer saying
**connected**, and a sidebar that stays empty forever, explained only by a banner that fades
after a few seconds. If this happened during an automatic reconnect while the window was not in
focus, they never saw it at all. And it is not ordinary version skew: the specification records
that `server.info` has reported an identity since schema 4, and the client's floor is 6, so any
server the client will talk to at all reports one. An empty value means a broken remote.

**What changed.** The "report the reason, then drop the link and land on failed" tail of the
schema branch was factored into a new private helper, `refuseServer(message)`, and both branches
now call it. The schema branch behaves exactly as before. The empty-identity branch now refuses
identically instead of showing a banner and carrying on. The change removes more lines than it
adds, because the duplicated deferred-disconnect block is gone.

**Test.** New:
`TstAppController::serverThatReportsNoIdentityIsRefusedRatherThanLeftConnected`. It answers
`server.info` with a current schema but no identity and asserts: exactly one error mentioning
"identity"; the stored identity still empty; **no** workspace listing request on the wire (that
request *is* the empty sidebar); and, after the deferred turn, the connection state is "failed"
with the message attached. The last two assertions fail without the fix.

## AC3 — Disconnect skipped every piece of local cleanup when no connection object had been injected

**File:** `src/app/AppController.cpp` lines 651–689.

**What the code did before.** `disconnectServer()` opened with an early return if the object
that owns the SSH session was null. That object is injected at startup and may legitimately be
null in tests; because it is held through a `QPointer`, it also reads back null once that object
has been destroyed.

Everything after the early return is purely client-side state, and none of it needs the
connection object to be correct: the latch that refuses a second connect while one is already
running, the fingerprint of a host key the user is currently being asked to approve, the
password or passphrase typed so far, the identifier of the profile being dialled, a connect
error held back pending the outcome of a prompt, and the active Dev Session together with both
of its pane-layout trees.

**Why that is wrong.** Two concrete routes. The first is reachable today through AC2 and the
schema-floor branch: those defer `disconnectServer()` by one event-loop turn specifically so the
connection's transport can be torn down safely. If the connection object is null at that moment,
the call returned immediately, the "a connect is in progress" latch stayed set, and every
subsequent connect attempt was refused for the rest of the process. The only recovery is
restarting the application.

The second is simply the wrong contract. A "Disconnect" that silently keeps a typed password, an
outstanding host-key approval and a live Dev Session pointed at an unreachable server is not a
disconnect. Leaving the Dev Session active is the exact corruption a long comment further down
the same function warns about: the layout manager keeps accepting pane splits it cannot save,
and the first change that *does* reach the server writes that divergent layout over the server's
real one.

**What changed.** The early return was removed so all the client-side resets run unconditionally,
and the check was narrowed to the one statement that actually needs the connection object. The
scope guard that mutes teardown-induced failures is kept exactly as it was, so the muting window
still ends precisely when the teardown ends. The stale part of the leading comment was replaced
with one explaining why there is no gate.

**Test.** No dedicated test. It is exercised by AC1's and AC2's new tests, both of which go
through `disconnectServer`, and by the existing
`disconnectRetiresActiveSessionButStillRemembersIt`.

## AC4 — Desktop notifications carried no application identity, so notification centres could not attribute them

**File:** `src/app/Notifier.cpp` lines 23–28 and 112–125.

**What the code did before.** The notifier builds a call to the standard Linux desktop
notification service. That call takes eight arguments; the seventh is a dictionary of optional
hints. CodeHarbor passed an empty dictionary.

**Why that is wrong.** The freedesktop.org specification defines a standard hint,
`desktop-entry`, whose value is the base name of the application's launcher file. Notification
centres — GNOME Shell, KDE Plasma, mako, dunst — use it to find the application's real icon,
show its proper display name, and group and filter its notifications in per-application
settings. Without it they fall back to fuzzy-matching a free-text application name against
installed launcher files, which frequently fails.

It was also an internal inconsistency: `src/app/main.cpp` goes out of its way to tell Qt the
application's launcher file name, with a six-line comment explaining that this is what
associates the running window with its icon in the dock — but the notification path, the other
place the operating system needs the same association, did not supply it.

**What changed.** A file-local constant was added alongside the existing application-name and
icon constants, with a comment naming the two things it must stay in step with
(`packaging/codeharbor.desktop` and the call in `main.cpp`), and the hint is now passed.
Notification services that do not understand the hint ignore it, so there is no risk.

**Test.** None. The hint is only observable against a real notification service, and the existing
live gate already covers "a real notification call reaches a real service without erroring".
Asserting the argument list of a message we just constructed would test plumbing.

## AC5 — A comment asserted that a user-facing "notifications off" switch exists; it does not

**File:** `src/app/Notifier.h` line 49.

**What the code did before.** The notifier exposes an enable/disable gate, and the comment above
it read "Gate for the user-facing 'notifications off' switch."

**Why that is wrong.** There is no such switch. `main.cpp` deliberately does not expose the
notifier to the user interface layer at all — its comment calls the object "a pure C++ sink" —
nothing outside the tests ever calls the setter, and nothing persists the flag, so even if a
switch existed it would forget itself on every launch. A reader trusting the comment goes looking
for a settings control that was never built.

The specification was checked before deciding what to do: section 6.2 of `docs/SPEC.md` is
"Supported Harnesses" and has nothing to do with notifications, and neither `docs/SPEC.md` nor
`docs/PLAN.md` anywhere requires a switch to turn notifications off. So the feature is
unspecified. Building a settings surface plus a persisted setting would have been inventing
scope; deleting the gate would have removed working, tested code.

**What changed.** The comment now describes what the gate actually is — a programmatic gate on
delivery, with no control wired to it, stated as a plain fact about the current design rather
than as a to-do. The original sentence about what a disabled call does was kept verbatim. No code
changed.

## AC6 — Six comments cited a specification section that is about something else entirely

**Files:** `src/app/Notifier.h` lines 9–14; `src/app/main.cpp` lines 137–139;
`src/app/tests/tst_notifier.cpp` lines 82 and 270; `src/app/tests/tst_notifierlive.cpp` lines 10
and 47.

**What the code did before.** Six comments cited "SPEC 6.2" as the authority for the desktop
notification feature and for the agent-state names it reacts to.

**Why that is wrong.** Section 6 of `docs/SPEC.md` is "Agent Awareness", and its subsections are
6.1 Purpose, 6.2 Supported Harnesses, 6.3 Remote Agent Bridge, 6.4 Internal Event Schema, 6.5 Oh
My Pi Adapter, 6.6 Fallback Activity Detection. So 6.2 is only about which coding-assistant
programs are recognised. The state names those comments actually depend on (`waiting_input`,
`idle_unseen`) are defined in 6.4. Desktop notifications have no subsection anywhere; the only
mention in the whole document is a Phase 4 bullet in section 16, "MVP Plan". Every one of the six
pointed a reader at the wrong place.

**What changed.** Where a comment depends on the state names, it now cites 6.4 "Internal Event
Schema". Where a comment reads as though a section mandates desktop notifications, it now says
plainly that the display layer is a Phase 4 deliverable listed in section 16 and that section 6
defines only the states it reacts to — no section number was invented, because none exists. Two
of the six were not making a normative claim at all and simply lost the citation in favour of a
plain description. The specification itself was not edited: this round deliberately did not add
new normative text. The token that the build system searches for in order to report the live
notification test as skipped rather than passed was left untouched.

### Investigated in this area and deliberately left alone

* **A narrow use-after-free window in `src/app/tests/headlessquit.cpp`.** This is a shim used only
  by the live user-interface gate: a background thread waits for the application object to exist
  and then posts a quit to it. Between fetching the pointer and using it, the main thread could in
  principle destroy the object. Closing it properly needs synchronisation with the main thread
  that the shim deliberately does not have, since it must work inside an unmodified binary it
  cannot add code to. The window is a few instructions wide, in a test-only artefact never linked
  into a shipped binary, and a second null check would not narrow it — it would just make the race
  look handled.

### Checked carefully in this area and found sound

# AS — application state

## AS1 — Turning automatic reconnect off during a user's own connect left the client stuck on "Connecting" forever

**Files:** `src/app/SessionBootstrap.cpp` lines 493–520; `src/app/SessionBootstrap.h` lines
147–157 and 497–503.

**What the code did before.** `SessionBootstrap` brings the remote session up: it probes the
endpoint, performs the SSH handshake, and attaches the two data channels. It also owns an
automatic-reconnect ladder that retries after a session dies. `setReconnectEnabled(false)` turns
that ladder off. Its old body unconditionally stopped the pending retry timer, aborted whatever
attempt was running, and — only if the state happened to be "reconnecting" — moved to
"disconnected".

The abort routine does not distinguish "a retry the ladder started" from "a connect the user
clicked Connect for". Both kinds of attempt spend most of their time parked in a nested event
loop: the connect pre-flight (up to 5 seconds) or a provisioning step (up to 3 minutes).

**Why that is wrong.** The connect routine deliberately does **not** relabel a cancelled attempt
as failed, on the reasoning that whoever cancelled has chosen the end state. That is correct for
the deliberate-disconnect path, which sets "disconnected" itself, and it is the only caller for
which it is correct. When `setReconnectEnabled(false)` cancelled a user's connect, nobody set an
end state at all: no session, no error signal, no retry armed, and the state stuck on
"Connecting" for the rest of the process, with a spinner that never resolves. This is reachable —
the setter is public, non-blocking API, and both nested loops keep the event loop turning on
purpose, so a timer or any queued action can land inside the window.

**What changed.** A flag records whether the running attempt is a ladder retry (set by the
reconnect timer) or a user connect (cleared by the connect routine). `setReconnectEnabled(false)`
now aborts only a retry, and when it does it sets "disconnected" itself, which is correct because
the rung is gone and nothing will re-arm it. Turning the ladder off while a rung is merely armed
behaves exactly as before. The header documents the boundary.

**Test.** New: `TstSessionBootstrap::disablingReconnectDuringAUserConnectLeavesItAlone`. It parks
a real connect in the production pre-flight against a local server that never answers, flips the
switch 30 milliseconds in, and asserts the connect still reaches its own conclusion, that no
retry was armed, that a subsequent connect still works (so the object is not wedged), and that
reconnect really is off. Against the pre-fix code the state is "Connecting" where "Failed" is
expected.

## AS2 — A cancellation flag could outlive its attempt and permanently disable reconnection

**File:** `src/app/SessionBootstrap.cpp` lines 603–610.

**What the code did before.** The cancellation flag means "the attempt currently running was
cancelled; unwind without wiring, failing or retrying". It is cleared in exactly one place: the
top of the routine that *starts* an attempt. The scheduler that arms the next retry returns
immediately when the flag is set. The handler for a live session dying tore the session down,
told the user, reset the attempt counter, and called the scheduler without touching the flag.

**Why that is wrong.** If the flag is still set when a live session dies, the loss path unwires
both channels, reports the error, and then arms nothing. The object is left claiming to be fully
wired while both of its devices have been destroyed. Nothing can recover it, because that same
handler only acts from the wired state, so a second loss is ignored too. AS1 was one route into
this state; AS3 is another.

**What changed.** The loss handler now clears the flag before scheduling, with a comment naming
the failure mode. The invariant is simple: losing a live session is by definition not a cancelled
attempt.

**Test.** None added — this is a defence-in-depth guard behind AS1's route. Every existing
loss-path case still passes, which is what confirms the clear is not itself a behaviour change.

## AS3 — A cancellation arriving between provisioning steps was ignored, and the next step burned its whole budget

**File:** `src/app/SessionBootstrap.cpp` lines 808–823 and 1316–1324.

**What the code did before.** Bringing up a bare server runs up to three remote scripts in
sequence: inspect the server, install the remote service, inspect again to confirm. Each one
opens a throwaway SSH channel and waits in a nested event loop until the remote closes it or the
time budget elapses — 15 seconds for an inspection, **180 seconds** for an install.

The abort routine cancels a parked attempt by setting the flag *and* quitting the loop it is
parked in. Between two steps there is no loop of ours, so only the flag gets set. The
script-runner did not look at the flag on entry: it opened a channel, ran a remote command, and
waited. Separately, the wiring routine never re-checked the flag after provisioning returned, and
provisioning reports a cancellation as failure only when one of its own steps failed — a
cancellation landing between steps leaves it reporting success.

**Why that is wrong.** Two consequences. First, the user asks to disconnect during a first
connect, and the client answers by running a command on a machine it has just been told to leave
alone, freezing the window for up to three more minutes before noticing. The interruptibility
this area was built for does not cover the gaps between steps. Second, and worse: with
provisioning reporting success, the wiring routine would go on to open both channels, attach both
consumers and announce the session as wired — resurrecting the very session the user just tore
down, and leaving the cancellation flag set on a live wired session, which is exactly AS2's
input.

**What changed.** The script-runner now returns "cancelled" before touching the connection pool if
the flag is already set. The wiring routine re-checks the flag immediately after provisioning
succeeds, before anything is executed.

**Test.** None added. Driving a cancellation into the exact gap between two steps needs a seam
that does not exist, and the existing test seam short-circuits the nested loop entirely, so a
substitute cannot reproduce the timing. All fifteen existing provisioning cases and both
cancellation cases still pass, which covers the "does not change the ordinary paths" half.

## AS4 — Integer overflow in the pane-label counter could hand out a label a visible pane is already wearing

**File:** `src/app/SessionLayouts.cpp` lines 79–110, 213–239 and 596–604.

**What the code did before.** Every pane in a region carries a label like `viewer-3` or
`terminal-2`. The number is chosen as the larger of a counter stored in a local settings file and
one more than the highest number already present in the layout tree; after a split, the counter is
stored as the chosen number plus one.

Neither input belongs to this client. The layout tree is fetched from the remote server and other
clients write to it too. The counter is read out of a hand-editable settings file. Both were used
in "plus one" arithmetic with no bound.

**Why that is wrong.** With either input at the maximum value a 32-bit signed integer can hold,
"plus one" is signed overflow — undefined behaviour, and in practice a wrap to the most negative
value. The wrapped value is stored as a negative; the settings store then applies its documented
floor and repairs it to 1; and the next split therefore mints `viewer-1`, the label of a pane that
is still on screen. This was confirmed end to end: with the fix reverted, two consecutive splits
over such a store mint the *same* label. Two panes wearing one label is confusing on its own, and
it is also what makes a stale "resolve this terminal by its slot label" answer plausible again —
the class of bug the pane-identifier scheme exists to close.

**What changed.** A ceiling of one billion was introduced: far above any real Dev Session, and far
enough below the integer maximum that every addition here is representable. Labels above the
ceiling are ignored when scanning the tree. A *stored* counter above the ceiling is treated as
corrupt and the code falls back to the tree — deliberately not clamped to the ceiling, because the
ceiling is a fixed point and clamping would make every later split mint the identical label. (That
version was written first and the new test caught it.) The stored value is capped so the next read
never has to treat it as corrupt.

**Test.** New: `TstSessionLayouts::anAbsurdPaneCounterCannotHandOutALabelAlreadyOnScreen`. It seeds
the counter at the integer maximum through the production interface, loads a one-pane layout,
splits twice, and asserts each minted label is a well-formed positive suffix, that neither is a
label already on screen, that the two do not collide with each other, and that the published tree
contains each pane identifier exactly once. Against the pre-fix arithmetic, the two minted labels
are identical.

## AS5 — The settings writer accepted values its own reader refuses

**Files:** `src/app/UiStateStore.cpp` lines 127–137; `src/app/UiStateStore.h` lines 85–88.

**What the code did before.** The reader for the pane-label counter enforces a documented floor: a
stored value that is absent, non-numeric or below 1 reads back as 1. The writer applied no floor at
all — it dropped an empty Dev Session identifier and otherwise stored whatever it was handed,
including zero and negatives, and then flushed it to disk.

**Why that is wrong.** A check applied in one place and missing in its twin. The two halves
disagree about what the store contains: a caller stores zero, the reader silently repairs it to 1,
and the counter has quietly forgotten every label already spent — which is a duplicate pane label,
the one thing the counter exists to prevent. It also spent a synchronous disk write (which the
surrounding code goes out of its way to avoid elsewhere) on a value that can never be read back.
And it made AS4's wrapped negative *look* like a stored value rather than a rejected one.

**What changed.** The writer now returns without writing for a value below the floor, mirroring the
reader exactly, and the header documents that a write below 1 is dropped for the same reason a read
below 1 is repaired. No current caller changes behaviour.

**Test.** None added; this is a hardening of an internal invariant with no observable change for
any current caller. AS4's test defends the end-to-end property it supports.

## AS9 — An out-of-range stored port number had no test coverage

**Files:** finding in `src/app/ServerProfiles.cpp` lines 76–108 and 197; test added at
`src/app/tests/tst_serverprofiles.cpp` lines 722–806.

**The routed premise, and its correction.** This was routed in from the application-core reviewer,

validate: the save path rejects anything outside 1 to 65535, and the load path substitutes the SSH

been exactly the duplicated rule this class avoids.

## AS10 — The cold-start walkthrough compared terminal output that now legitimately contains colour codes

**File:** `src/app/tests/tst_coldstart.cpp` — `paneText()`, lines 658–682.

Found by the coordinator's live run, *after* `SSH2` was fixed and after the round's first commit. It is a
consequence of `SSH2`, so it is recorded here rather than being folded into it silently.

**What the code did before.** The cold-start gate is the full first-run walkthrough against a real server. One of
its steps proves the terminal pane's shell opened in the Dev Session's checkout rather than in the user's home

for that marker with a pattern that captures everything up to the end of the line, trims the whitespace, and
compares the result against the expected path.

**Why that is wrong.** It assumed the captured line is plain text. That held only because of the very bug `SSH2`
fixed: the pane used to negotiate a plain `xterm` terminal, so a shell that colours its prompt mostly did not
bother. Now that the pane really gets `xterm-256color`, the shell writes colour and erase-to-end-of-line control
sequences in among its output, and they land on the same line as the value being scraped. The comparison then failed
with the right path followed by an escape sequence — an assertion failure that says nothing about the property under
test, on a gate whose whole purpose is to be trusted.

This is worth stating plainly rather than dressing up: the fix was correct and the test was fragile, and the
fragility was invisible for exactly as long as the bug was present.

**What changed.** `paneText()`, the one helper every step scrapes through, now strips terminal control sequences
before returning: escape-bracket sequences, operating-system commands, and the two-character escapes. Deliberately
not a terminal parser — a comment says so — it only has to stop escape bytes reaching a comparison. Nothing in this
gate is testing terminal rendering; every assertion wants the text the remote printed. No assertion was changed and
no other step was touched.

**Verification.** The cold-start gate was re-run on its own after the change and passes, and the whole live gate was
then run twice consecutively, 13/13 both times. The failure was also traced to its cause rather than assumed: the
captured value was the correct path followed by an erase-to-end-of-line, a green and a bold sequence, which is a
coloured prompt being redrawn.

### Investigated in this area and deliberately left alone

* **A re-entrancy guard in the profile store is currently unreachable.** Nothing inside the locked
  region emits a signal — the one signal is emitted after the guard is cleared, explicitly so a
  handler may mutate the store. Left in place: it is a correct and cheap safety net against a future
  emit moving inside the locked region, and deleting it would trade a dead branch for a file-lock
  self-deadlock the first time somebody does that.
* **Dropping the last child of a one-child split leaves an empty node nested inside a branch.** The
  parser permits a split with exactly one child, so a server-supplied tree can contain one. The
  result renders as a blank pane slot rather than crashing or losing data. Fixing it properly means
  recursively collapsing the parent chain, a real behaviour change to the one function every close
  path goes through, out of proportion to a cosmetic outcome on input this client never produces.
* **The layout publisher takes its tree by value and every internal caller passes the member.** This
  looks like a needless copy and is not: the copy is what makes the subsequent move safe, since
  moving the member onto itself would be a self-move. Left untouched rather than "optimised" into a
  bug.
* **A terminal-pane creation that never answers blocks that region's writes indefinitely.** Declining
  to write while any pane is still waiting for its server row identifier is load-bearing and
  documented. In practice the connection object fails every pending request when the transport
  closes, so the callback always arrives; adding a timeout here would duplicate that mechanism in the
  wrong layer.
* **Profiles with an empty host or user survive a hand edit.** Read-side normalisation is deliberately
  limited to the port; dropping rows on read is the opposite of what the merge contract promises.

# SSH — the SSH layer

## SSH1 — The 15-second connection timeout was switched off for anyone who has an SSH config file

**Files:** `src/ssh/SshConnectionPool.cpp` lines 588–645; documentation at
`src/ssh/SshConnectionPool.h` lines 130–137.

**What the code did before.** CodeHarbor opens SSH connections *synchronously on the user
interface thread* — the whole window is frozen until the connection succeeds or gives up. To bound
that freeze the code sets the SSH library's timeout option to 15 seconds. It did that **after**
parsing the user's personal OpenSSH configuration file, and it *skipped the setting entirely*
whenever that file existed at all. The stated reason: the file might carry the user's own connect
timeout, the library offers no way to ask whether one was read, and overwriting the user's choice
would be rude.

**Why that is wrong.** The mere *existence* of the file was treated as "the user configured a
timeout". Almost every developer has that file, for host aliases and key paths; almost none of them
set a connect timeout in it. For all of those users **no timeout was set at all**, and three things
followed.

First, the 15-second bound simply did not apply. Second, and confirmed by reading the installed
library's own source, when the timeout option is unset the library resolves its internal default to
*infinite* for channel writes — so writing to a remote peer that has stopped reading blocks
**forever** on the calling thread. The channel device's own comment claims the opposite ("each write
is bounded by the session timeout"), so the code's stated safety property was false for the common
case. Third, the workaround was unnecessary anyway: the library's configuration parser *does* set
the timeout option for a `ConnectTimeout` directive, so a value set beforehand is simply overwritten
by the user's.

Both claims were measured against the installed library rather than assumed. With the value pre-set
to 6 seconds and the config saying 2, the connect gave up after 2.00 seconds — the user's value
wins. With the value pre-set to 2 and the config silent, it gave up after 2.00 seconds — our value
survives. End to end through the real connection pool against a black-holed address: with a config
file that has no connect timeout, 15.02 seconds (the bound now applies; before the fix, none did);
with `ConnectTimeout 2`, 2.00 seconds.

**What changed.** The timeout is now set immediately after the host option and **before** the
configuration file is parsed, and the conditional and its flag were deleted. A user's own setting
now overrides ours because the parser runs later; everyone else keeps the bound. The class
documentation describes the new ordering and why it is correct.

**Test.** No automated test — reproducing it needs a black-holed network endpoint and a 15-second
wall-clock wait, which does not belong in a unit suite. Verified by the two measurement tables
above, produced by a standalone program driving the real connection pool.

## SSH2 — Remote terminals ran with the wrong terminal type, so everything was in 16 colours

**Files:** `src/ssh/SshConnectionPool.cpp` lines 1187–1197; `src/ssh/SshChannelDevice.cpp` lines
259–271; documentation at `src/ssh/SshConnectionPool.h` lines 374–382 and
`src/ssh/SshChannelDevice.h` lines 60–66.

**What the code did before.** Opening an SSH channel (one independent stream inside the single SSH
connection) went through the pool. If the caller labelled the channel as a terminal channel, the
pool immediately asked the server for a pseudo-terminal using the library's convenience function.
Afterwards the channel device noticed a terminal had already been negotiated and therefore only sent
a window-resize request, deliberately not a second terminal request — because the SSH protocol
allows exactly one such request per channel.

**Why that is wrong.** That convenience function is literally defined as "request a pseudo-terminal
of type `xterm`, 80 by 24". The terminal type is hard-coded. The application asks for
`xterm-256color`, and because the one allowed request had already been spent by the pool, that ask
was silently dropped — only the geometry could still be applied. Every remote program that reads the
terminal type to decide its colour capability — tmux, vim, coloured directory listings, anything
built on the ncurses library — therefore believed it was on a 16-colour terminal, while the terminal
emulator in the pane is fully 256-colour capable. There was no error, no warning, and no way for the
caller to find out.

**What changed.** Pseudo-terminal negotiation was removed from the pool entirely; the channel kind is
now purely a label. The channel device unconditionally issues the single pseudo-terminal request,
with the requested type and size, for every channel kind. The pool's channel-opening function has
exactly one caller in the whole repository, so this is a complete cutover with no compatibility
shims. Both header comments were rewritten to state the new contract.

**Test.** New: `TstLiveSsh::ptyChannelRunsWithTheRequestedTerminalType`. It opens a terminal channel
asking for `xterm-256color`, runs a tiny shell command on it that prints the terminal type, and
asserts the remote echoed `<xterm-256color>`. This lives in the live gate because only a real remote
shell can observe which terminal type was actually negotiated. **The coordinator confirmed this test
really executes and passes against the fixture server** — this was the specific case verified by
running the binary directly rather than trusting a summary line.

## SSH3 — On Windows the private-key fallback pointed at a filename that cannot exist, and never looked at the user's real keys

**File:** `src/ssh/SshConnectionPool.cpp` lines 394–414.

**What the code did before.** The routine that builds the list of private key files to try takes, in
order: the key path saved in the server profile; the key named in the user's SSH config, obtained by
asking the library; and only if *both* produced nothing, a scan of the user's `.ssh` directory for
the three standard key names.

**Why that is wrong.** The second step never produces nothing. The library seeds every new session's

**What changed.** A value returned by the library is now dropped if it still contains one of the

**Test.** No automated test: the routine is a file-local helper needing a live session object, and its

## SSH4 — A corrupted line in the known-hosts file was silently repaired and then trusted

**File:** `src/ssh/KnownHosts.cpp` lines 15–40.

**What the code did before.** OpenSSH can store host names in the known-hosts file in hashed form, so
the file does not reveal which machines you connect to. The stored token looks like
`|1|<encoded salt>|<encoded hash>`. To decide whether such a line refers to the host being connected
to, the code decoded the two parts and recomputed the hash. It used Qt's *lenient* base64 decoder.

**Why that is wrong.** Qt's lenient decoder **silently discards any character outside the base64
alphabet**. Confirmed directly: a clean token and the same token with a stray hyphen inserted decode
to the identical result under the lenient decoder, while the strict decoder refuses the dirty one. So
a known-hosts line whose hashed token had been corrupted — by a bad edit, a truncated sync, a mangling
text tool, or deliberately — still resolved to a real host name, and its host key was then treated as
the trusted key for that host. OpenSSH itself rejects such a line outright, so the two tools disagreed
about which lines in the user's file count. This is a security-relevant file, and every other base64
decode in the same file and in the host-key verification path already uses the strict decoder for
exactly this reason — so it was also one strict check with a lenient twin.

**What changed.** Both decodes now use Qt's strict decoder and the function reports "no match" if
either refuses. The line is still preserved verbatim when the file is written back; it is the user's
file.

**Test.** New: `TstKnownHosts::malformedHashedHostTokenNeverMatches`. It builds a genuine hashed
token, asserts the intact token matches so the fixture is sound, then inserts a stray character into
the hash, then into the salt, then tries outright garbage — asserting all three yield "unknown host"
rather than "match", and that each corrupt line still survives being written back out. Confirmed to
fail against the lenient decoder, where the first case reports "match".

## SSH5 — The read pump kept writing to its own memory after emitting signals that are allowed to destroy it

**File:** `src/ssh/SshChannelDevice.cpp` lines 417–449.

**What the code did before.** The timer-driven loop that pulls bytes off an SSH channel emits, in
order, a channel-error signal, then possibly a failure signal, then a data-ready signal, and finally a
stream-finished signal. Between and after those emissions it reads and writes its own member
variables.

**Why that is wrong.** Qt signals run their handlers synchronously, and any handler may destroy the
object that emitted the signal. That is not hypothetical here: the session bootstrap's unwire routine
runs from inside this device's own stream-finished signal and tears the device down — its comment says
so explicitly and it uses a deferred delete rather than an immediate one *specifically* to dodge this.
In other words the hazard is already known and is currently avoided only by every consumer remembering
to be careful. A consumer that used an immediate delete, or a future one wired to the data-ready
signal where the danger is far less obvious, would make this loop write to freed memory the moment the
handler returned. The JSON-RPC client already defends itself against exactly this pattern with a
`QPointer`; this device did not.

**What changed.** The loop now takes a `QPointer` to itself before the emission sequence and guards the
remaining steps on it. A `QPointer` is cleared automatically when its object is destroyed, so the
function stops touching itself the instant a handler deletes it. This matches the convention already
used in the JSON-RPC client.

**Test.** No automated test: constructing the failure needs a live SSH channel delivering bytes *and* a
consumer that deliberately misuses immediate deletion, i.e. a test that asserts against knowingly
wrong caller code. The change is provably behaviour-preserving when nobody deletes — the pointer is
non-null, so every branch is taken exactly as before.

## SSH6 — The authentication-method query got the right answer for its error case by accident

**Files:** `src/ssh/SshConnectionPool.cpp` lines 498–520; documentation at
`src/ssh/SshConnectionPool.h` lines 283–289.

**What the code did before.** After the handshake the client asks the server which authentication
methods it will accept. The library returns a bit mask, or the value −1 if the query itself failed. The
code cast the result to an unsigned integer and then compared against zero to detect "the server did
not tell us".

**Why that is wrong.** It is not wrong today, and that is the problem. Reinterpreting −1 as unsigned
yields a value with every bit set, which happens to make every method look "offered", which happens to
be the same answer the deliberate "we were not told, try everything" fallback gives. So the error case
lands on correct behaviour purely by a two's-complement coincidence, through a path nobody wrote on
purpose and no test covered. The day a method bit is added that this client must *not* assume is on
offer, the coincidence stops holding and the failure is silent.

**What changed.** The function now tests the **signed** value first and takes the documented fallback
explicitly, with a comment saying why the signed test is deliberate. The cast to unsigned moved below
that point, where the value is known to be a genuine bit mask. The header documentation previously
mentioned only the zero case and now covers both.

**Test.** The existing fallback test was extended with an assertion that the error value reports all
three methods available, plus a comment recording that this used to be an accident. A stale comment in
the same test was corrected.

## SSH7 — The known-hosts parser recompiled a regular expression once per line

**File:** `src/ssh/KnownHosts.cpp` lines 218–232.

The parser splits each line into fields on runs of whitespace, and constructed a fresh
regular-expression object **inside the per-line loop**. Constructing one compiles the pattern. A real
known-hosts file on a developer machine or a shared build box runs to hundreds or thousands of lines,

with no behaviour difference, and the existing 32 cases (including tab and carriage-return separators)

## SSH8 — The diagnostic transcript's size cap was untested for a single oversized line

**What was missing.** The routine that appends to the retained diagnostic transcript caps it at 64

## SSH9 — Three tests in this directory used the graphical entry point; the other two did not

**Files:** `src/ssh/tests/tst_knownhosts.cpp` line 689, `tst_sshauth.cpp` line 329,
`tst_sshlogrouter.cpp` line 579.

Qt offers two entry-point macros for tests: one that creates a graphical application object when the

## SSH10 — Two comments asserted that a state is unreachable, and it is reachable

**Files:** `src/ssh/SshConnectionPool.cpp` lines 527–534; `src/ssh/tests/tst_sshauth.cpp` lines 262–265.

**What the code did before.** The comment on the authentication-result classifier said that the
library's "the server has more challenge questions for you" result "is consumed by the

comment said "this client never requests that method".

**Why that is wrong.** Both were left behind by the change that added keyboard-interactive support. The
client *does* request that method now, and the challenge-response loop can exit with that result still
in hand in three real situations: the credential callback supplied no answer, the library rejected an
answer, or the 32-round safety cap was reached. In all three the value is handed straight to the

**What changed.** Both comments were rewritten to describe the three ways that result really does

### Investigated in this area and deliberately left alone

* **The channel-kind enumeration no longer changes any behaviour** after SSH2; it is a pure label.
  Deleting it would be honest, but it is part of this class's public interface and is referenced from
  five other areas and eight test files. It still documents caller intent and is useful in diagnostics.
* **The connection pool's destructor emits Qt signals.** Handlers reached that way see a partially
  destroyed object. This is a genuine hazard, but one of those emissions is load-bearing: it is how a
  channel device that outlives its pool is told to drop its channel handle before the handles are
  freed, and two test files depend on it. Fixing it properly means restructuring teardown ownership
  across another area.
* **Releasing a logging route from the wrong thread is only an assertion.** All routing state is
  thread-local, so a release from the wrong thread leaves a dangling pointer in the original thread's
  stack. There is no way to repair it from the wrong thread — the owning thread's storage is
  unreachable — so the contract can only be documented and asserted, which it already is.
* **The channel device returns zero rather than −1 at end of stream.** Qt's contract permits either for
  this kind of device, the existing comment explains the choice, and the stream-finished signal is what
  consumers actually key on.
* **Rejecting an unknown host key produces no error message.** The connection fails with a state change
  and a transcript line but no banner. Judged intentional: the user just pressed "reject" in a dialog
  that told them exactly what they were rejecting.
* **A "partial success" result from the no-op authentication method is not recorded.** This requires a
  server configured with `none` as a genuine first authentication factor, which OpenSSH cannot express.

### The library version constraint

The standing project rule is that libssh is pinned to 0.12.2, with a workaround that applies only to
0.12.0. The version-conditional code matches that intent: it compares only the leading release token of
the reported version for exact equality with `0.12.0`, so 0.12.1, 0.12.2, 0.12.10 and every 0.11.x are
excluded, and the mitigation is applied on that one release only. An existing test already pins every
one of those cases including the `0.12.10` prefix trap. No change needed.

# RPC — the JSON-RPC client

## RPC1 — A reply that also carried a method name was accepted as a successful answer

**File:** `src/remote/CodeharbordClient.cpp`, the line-processing routine; fix at lines 463–481.
Contract text it violated: `src/remote/CodeharbordClient.h` lines 177–183.

**What the code did before.** Every line the server sends is one JSON object. The client decides what
to do with it by looking at two members: a `method` name, and an `id` — the number the client stamped
on the request it is waiting for. The rules of JSON-RPC are: a message with a method and *no* id is a
one-way notification (for example "a watched file changed") and is emitted as such; a message with an
id and no method is a response and is routed back to the callback of the request that minted that id.

Notifications were handled correctly. But a malformed message carrying *both* a method and a valid id
fell through into the response path, was looked up in the pending table, and then only its result and
error members were inspected. If such a message also carried a result, the client handed that result
to the waiting caller as a normal success, with no warning at all.

The class's own documentation promised the opposite, in as many words: a message carrying a method and
an id "is never dispatched here: it is routed on its id like any response, which fails the matching
caller … and always emits a protocol warning".

**Why that is wrong.** A message carrying a method name is by definition not a reply — it is either a
request aimed at the client, which this client does not implement at all, or a corrupted response.
Either way its result is not an answer to the request that happens to share the id. A buggy or hostile
server emitting an id-bearing message with a method name and a result would resolve that pending
request with a payload that was never a reply to it. In this application such payloads flow straight
into the editor's read and write handling, so a caller would act on file content or a revision token it
never asked for, with nothing in the log. The existing test only covered the case where the malformed
message had *neither* a result nor an error, which landed in a different branch that happened to fail
the caller — so the hole was invisible.

**What changed.** Immediately after the pending entry is looked up and removed, and before any result or
error is inspected, the code now checks for the presence of a method member. If one is there it emits a
protocol warning naming the offending response and fails the caller's callback once with the standard
internal-error code and the message "malformed response: carries a method member". The result is never
delivered.

**Test.** New: `TstRpcClient::responseCarryingMethodIsNeverAResult`. It issues a real request, then feeds
a reply with the matching id plus both a method and a result, and asserts the callback fired with an
error rather than a success, the delivered value is null rather than the bogus payload, no notification
was emitted, at least one protocol warning was emitted, and the pending count dropped to zero.

## RPC2 — An error code that was numeric but not a whole 32-bit integer was silently rewritten to zero

**File:** `src/remote/CodeharbordClient.cpp` lines 500–520.

**What the code did before.** When the server answers with a failure it sends an error object with a
numeric code and a text message. The client validated only that the code was *a JSON number at all*,
warning if it was not, and then converted it with Qt's integer accessor.

That accessor does not clamp or truncate: if the JSON number is fractional or outside the range of a
32-bit integer, it silently returns its default value, which here is zero. So an error code of one
trillion reached the caller as code zero with no warning, because one trillion is a perfectly good JSON
number and passed the "is it a number" check.

**Why that is wrong.** Zero is indistinguishable from a server that genuinely sent zero, and zero is also
what the client's own "malformed error object, best effort" path produces. So a code the client could not
represent was laundered into one that looks deliberate. Callers in this codebase branch on the exact
number — the editor compares against the revision-mismatch code −32001 to decide whether a save collided
with someone else's edit — so a mangled code takes the wrong branch with nothing in the log to explain
it. The neighbouring id decoding already guards against exactly this hazard using a two-default probe;
the error code did not.

**What changed.** The validity check now probes the code with two different defaults, which disagree only
when the number is fractional or out of range. That condition joins the existing checks, so such a
response emits the existing "error object missing code or message" warning. The best-effort behaviour is
unchanged — the code still ends up zero and the callback is still failed, so no caller can hang — but the
loss is now reported instead of silent. A comment explains the two-default technique, mirroring the
wording already used for the id.

**Test.** New: `TstRpcClient::errorCodeOutOfIntRangeWarns`. It feeds an error response with a code of one
trillion and asserts the callback is failed, the message survives intact, the code is the best-effort
zero, and exactly one protocol warning was emitted. Without the fix the warning count is zero.

## RPC3 — Two places could use the client after a warning handler destroyed it

**File:** `src/remote/CodeharbordClient.cpp` lines 284–300 and 725–732.

**What the code did before.** The protocol-warning signal is public. Qt emits signals synchronously, and
a handler is free to do anything — including delete the client. The suite's own
`callbackDeletingClientMidDispatchIsSafe` proves consumers really do delete this object from inside its
own dispatch.

Two places emitted a protocol warning and then called a member function on themselves. The first is the
send path: when a write to the transport succeeds only *partially*, a truncated frame is on the wire and
the byte stream is unrecoverable, so the code emitted the warning and then called the teardown routine.
The second is the heartbeat tick: when the peer has been silent for the configured number of intervals,
the code emitted a "treating transport as dead" warning and then called the same teardown routine.

**Why that is wrong.** It is a latent use-after-free, reachable the moment anyone wires the
protocol-warning signal to logic that tears the session down — which is a completely natural thing to
connect a protocol-error signal to, and these two are precisely the "the connection is dead" cases a
consumer would want to react to. Nothing in the shipped code connects to that signal outside tests today,
so it is a trap left armed rather than an active bug. The rest of this file already defends against
exactly this: the read path takes a `QPointer` to itself before its own warning emission and bails if it
goes null. These two were the outliers.

**What changed.** Both sites now follow the file's existing pattern, taking a `QPointer` before the
emission and checking it before the teardown. Everything after that point is a local variable, so the
failure callback is still invoked exactly once and the request id is still returned even if the client is
gone. No new include was needed.

**Test.** None added. Driving this needs a warning handler that deletes the client from inside a
short-write or heartbeat-death path; the fixture would then have to survive its own client vanishing
mid-call, and the assertion would be "no memory-error report", which this suite cannot express
deterministically. The change is a strict narrowing of an unguarded window to the same pattern already
used three lines away.

## RPC4 — Reconnecting from inside a failure sweep announced the connection twice and drained the wrong stream

**File:** `src/remote/CodeharbordClient.cpp` lines 193–219.

**What the code did before.** Rebinding the client onto a new byte stream must fail every request still in
flight, because the request identifiers it minted mean nothing to a different server process. The order
was: rewire the signal hooks, fail all pending callbacks, read whatever the new stream already had
buffered, then emit the "transport bound" signal that tells consumers the connection is up again and they
should re-register their server-side state.

Those failure callbacks run *synchronously, inside* the rebind function, and the file's own comments
acknowledge that the natural reaction to a transport error is to reconnect — that is, to call the rebind
function again. When one did, the nested call performed a complete bind of its own: rewire, sweep, drain,
and announce. Control then returned to the *outer* call, which carried on using the client's current
stream — now the one the callback bound, not the one the outer call was asked to bind. It drained that
stream a second time and announced a second time.

The drain had a related gap: a queued end-of-stream, or an unframed line past the 16-megabyte cap, can
close the connection *during* the drain. The outer call did not re-check, so it would announce "the
transport is up and usable" immediately after the closed signal had already been emitted for it.

**Why that is wrong.** The "transport bound" signal is documented as the hook where consumers re-establish
server-side state, and the specific case that forced it into existence is file watching: the daemon keeps
subscriptions in a per-process table, so every bind makes the editor re-issue its watch. Announcing twice
for one bind means duplicate subscriptions on the server — the second watch identifier is the one the
client keeps, so the first is leaked for the life of the connection, delivering events nobody will ever
cancel — plus duplicate re-read work. Announcing after a close advertises a usable transport that is
already dead, so the consumer's first request fails immediately and it has no idea why. Both are reachable
from a plausible and explicitly anticipated consumer behaviour.

**What changed.** After the pending sweep, the rebind now checks whether the client's stream is still the
one it was asked to bind; if a swept callback rebound or detached, that nested call has already done the
drain and the announcement for whatever it bound, so the outer call stops rather than acting on a stream it
no longer holds. After the drain it re-checks both that the connection is not closed and that the stream
has not changed, so a drain that ended the connection, or a callback dispatched by the drain that rebound,
suppresses the now-false announcement. Both checks carry comments explaining the scenario, and the
pre-existing "no stream" early exit was folded into the first check.

**Test.** New: `TstRpcClient::rebindFromASweptCallbackAnnouncesBoundOnce`. Three scripted streams: the
client is bound to the first with one request in flight whose failure callback binds the third. The test
then binds the second. It asserts the callback ran exactly once, the surviving stream is the third (the
callback's bind is the one that stands), and the bound signal fired **exactly once** — then round-trips a
real request on the third stream to prove it works. Against the pre-fix source the signal count is 2.

### Cross-check against the daemon

Every wire name in `src/remote/RpcTypes.h` was compared against the daemon's own definitions: the seven
file methods, the three tmux methods, the twenty-one workspace methods, the two watch notifications, the
ping method and `server.info` are all present and byte-identical on both sides. The two error codes match
(−32001 revision mismatch, −32002 database busy). Ping and `server.info` are answered where the header
comments claim. The null-result shape the C++ tests assume for nothing-to-return handlers is real. An
existing test already enforces this set equality in both directions, so drift is guarded. Nothing to fix.

### Investigated in this area and deliberately left alone

* **The read buffer is compacted once per frame, which is quadratic in frames per read.** The obvious fix —
  track a consume offset and compact once at the end — is **wrong here**, and that is worth recording so
  nobody "optimises" it later: a response callback may spin a nested event loop, which can re-enter the
  reader. The current code trims the buffer *before* dispatching each frame, so a re-entrant reader always
  sees a consistent buffer; a deferred-compaction version would let the nested call re-process frames the
  outer loop had logically consumed. Real bursts here are watch notifications of a few hundred bytes.
* **The pending-request count narrows a 64-bit size to a 32-bit integer.** Reaching two billion in-flight
  requests would exhaust memory long first, and widening the return type is a public interface change
  rippling into consumers for no behavioural gain.
* **Repeatedly enabling the heartbeat against a peer that never answers grows two internal collections
  without bound.** Each call retires the in-flight probe without sweeping it, by design: the probe is still
  physically on the wire, so it must stay in the pending table (to be failed exactly once with everyone
  else on transport loss) and in the probe set (to stay excluded from the public pending count). That is
  documented and pinned by a test. Production enables the heartbeat exactly once.

# TM — terminals

## TM1 — Changing the workspace server left old identity lookups running and cached their answers under the new server

**File:** `src/terminal/TerminalFactory.cpp` lines 143–166 and 249–263.

**What the code did before.** The terminal factory asks the server "what tmux session name belongs to this
pane?", caches the answer, and keeps a list of panes waiting on each outstanding question. The setter that
tells it which workspace server it is talking to cleared the *cache* — with a comment explaining that a
name minted on one server is meaningless on another — but did nothing about the questions still on the
wire. The callback for such a question captured only the lookup key, not which server it had been asked of,
so whenever the reply arrived it was written into the cache unconditionally.

**Why that is wrong.** Two failure modes. The first is a wrong-server name: a pane asks against server A,
the setter switches to server B, the reply lands and inserts server A's tmux session name into the cache.
Every later attach for that key skips the round trip and uses it, so the pane attaches to a tmux session
belonging to a workspace the user is no longer looking at — or, because the attach command is "attach to
this session or create it", silently *creates* one under a foreign workspace's name. That is the
server-only-naming rule broken through the back door. The second is a stranded pane: the lookup function
documents that returning true guarantees an answer will be delivered, and the setter was the one path that
could break that promise, leaving panes showing "resolving…" forever with no retry.

This is reachable, though narrowly: in practice a server change is usually accompanied by a transport swap
whose sweep fails outstanding requests, but nothing orders that sweep before the setter.

**What changed.** The setter now, after clearing the cache, takes a snapshot of the outstanding lookup keys
and finishes each one through the existing "the lookup failed, stop waiting, offer Retry" path, with the
reason "the workspace server changed while this terminal was being resolved". The snapshot is required
because finishing a lookup removes it from the waiting table and a waiter is free to react by starting a new
one. Separately, the lookup callback now captures which server the question was asked of and returns
immediately if the server has changed, so a late reply can neither poison the cache nor deliver to waiters
that have already been answered.

**Test.** None added. The lookup needs both a connected SSH pool and a live workspace database; this test
file has neither and there is no injection point for a substitute. Adding one purely for the test would be a
new abstraction. The existing 24 cases still pass.

## TM2 — Detaching could unbind a pane that had just been re-attached from inside its own teardown

**File:** `src/terminal/TerminalFactory.cpp` lines 408–440.

**What the code did before.** Detaching disconnected the device's signals, closed the channel, unbound the
controller, deleted the device, and then walked a live pane to the disconnected state. Closing the channel
ends the read stream, which makes the controller emit a state change, which reaches the QWebChannel bridge
and then the terminal pane's user-interface code — and anything running there is free to call back into this
same factory.

**Why that is wrong.** If that code re-enters attach on *this* pane, the nested attach opens a fresh channel
and binds it. Control then returns to the middle of the outer detach, which throws away the brand-new
binding — leaving a live but orphaned channel and a pane that will never receive another byte — and walks
the freshly attaching pane to disconnected. This file *already* documents exactly this re-entrancy hazard
twice, for two other lookups in the same class; the controller binding was the one place unguarded.

Reachability was checked: today the pane's state handler only clears a flag, and the attach path is guarded,
so nothing currently re-enters. This is therefore latent, not active — but it is one line of user-interface
code away (an automatic reconnect-on-drop handler is the obvious future change).

**What changed.** After closing the channel, the function records whether the controller is still bound to
the device it came here to release, always schedules that device for deletion, and only performs the unbind
and the disconnected transition when the binding is still its own. On the normal path that is always true, so
behaviour is unchanged.

**Test.** None added. Reproducing the re-entrancy needs a real SSH channel device, which needs a connection
pool, and the device is not substitutable at this seam.

## TM3 — The terminal page permanently lost flow-control credit for any batch that decoded to no text

**File:** `src/web/terminal/src/writer.ts` lines 70–93.

**What the code did before.** The writer receives two things: decoded text, and the number of raw bytes that
text was decoded from. The page must report those bytes back to C++ once the terminal emulator has drawn
them, because that is what allows C++ to send the next batch — a credit mechanism that stops a runaway remote
process from filling the browser's memory. When the decoded text was empty, the function returned early and
the byte count was silently discarded.

**Why that is wrong.** A batch legitimately decodes to no text: C++ flushes on a size or time threshold and
will cut a multi-byte character in half, so a flush can consist entirely of the first two bytes of a
three-byte character. The C++ side handles this correctly, carrying the byte weight forward onto the next
batch that *does* produce text — and that is exactly why the page must not throw such a weight away. C++ has
already charged those bytes against the pane's 512-kilobyte credit window; if the page never acknowledges
them, the window shrinks permanently. Repeated over a long session with a lot of non-ASCII output, the credit
reaches zero and the pane stops receiving output altogether.

Today the only caller skips the call when the decode is empty, so the two halves happen to be safe *in
combination*. But this is the exported, documented interface, the two halves of the accounting live in
different languages, and the asymmetry — C++ carries forward, the page discards — is exactly the kind of thing
that becomes a real leak the moment either side is touched.

**What changed.** The byte weight is now accumulated before the empty-text check, mirroring the C++
carry-forward. An empty batch still never becomes an empty chunk handed to the terminal emulator, which an
existing test pins, and closing still zeroes the count.

**Test.** New: "the byte weight of a text-less batch is carried onto the next real chunk". It writes an empty
batch worth 2 bytes and asserts nothing reaches the terminal and the backlog is empty; then writes a one-byte
character, acknowledges, and asserts the callback reported **3** — all three bytes, exactly once. It then
writes one more byte and asserts the carry was not double-counted. Fails on the old code, which reported 1.

## TM4 — Missing coverage for the scrollback eviction scan's direction and its bound

**File:** `src/terminal/tests/tst_terminalcontroller.cpp` lines 911–959.

**What was missing.** When the 2-megabyte rolling output buffer overflows, the controller does not cut at the
raw overflow point — that would land in the middle of a multi-byte character or an escape sequence, and the
buffer is later replayed verbatim into the terminal emulator. Instead it scans *forward* from the overflow
point, up to a 4-kilobyte window, for a line feed (a byte no escape sequence can contain), and failing that
skips continuation bytes to reach a character boundary. Two properties of that scan were untested: that it
starts at the overflow point rather than at the start of the buffer, and that the 4-kilobyte window actually
bounds it.

**Why that matters.** Both are silent-failure properties. If the line-feed search were ever changed to start
from the beginning, it would find a line feed *before* the cut, remove fewer bytes than the overflow required,
and leave the buffer permanently above its cap — the memory bound the whole mechanism exists for would stop
holding, with no visible symptom. If the window were dropped, a stream that offers no resume point (a
full-screen redraw with no line feeds) would scan the whole buffer and evict *everything*, wiping the user's
retained scrollback on a single overflow. Neither is caught by the two existing cases.

**What changed.** Two sub-cases were added to the existing test. The first fills the buffer with two line feeds
— a decoy ten bytes *before* the overflow point and the real resume point ten bytes *after* it — and asserts
the buffer ends at the expected size and, explicitly, at or below the cap; a search from the beginning would
leave it above. The second fills the buffer entirely with continuation bytes and no line feed, so the boundary
scan can never terminate on its own, and asserts exactly the window's worth of bytes were dropped and the
newest bytes are untouched; without the bound the buffer would be emptied.

## TM8 — A styling rule for a terminal state that cannot exist

**File:** `src/web/terminal/index.html`. The page's status strip is styled per state, and there was a rule for

and deliberately *not* mirrored onto a pane. So the selector can never match. It is stale styling that implies
a pane state which does not exist, which is exactly the kind of thing that makes someone add one. Removed and
replaced with a comment enumerating the six values the attribute can actually hold.

### Checked in this area and found correct

Recorded so these are known to have been verified rather than skipped: server-only tmux naming (no client-side
invention remains anywhere in this area, and the only hole found was TM1); escape sequences are never split
destructively (the only destructive cut is the eviction, handled by the forward scan, now better tested;
everywhere else the emulator's parser is stateful across writes and the writer only ever concatenates); the
QWebChannel bridge's lifetime and thread affinity (the bridge holds its controller through a `QPointer`, every
page-callable method is null-guarded, and everything lives on one thread); acknowledgement accounting across a
page reload, traced through all four orderings of the relevant events; the decision not to reset the text
decoder on reload, which is correct because the byte stream is continuous; teardown while a write is in flight;
and the web bundle's staging-and-rename build script, traced through all three of its failure points.

### Investigated in this area and deliberately left alone

* **A one-character display smudge when bytes are evicted between a partial multi-byte character and its
  replay.** Fixing it means resetting the decoder on eviction, which needs a new signal from the controller to
  the bridge, for a cosmetic outcome in a case the eviction already documents as lossy.
* **Creating a controller with no owner returns an unparented object**, which leaks if the caller forgets. Left
  as is: it is the identical signature and default as the editor's equivalent, and changing one of the pair
  would introduce a second convention. Every real caller passes an owner.
* **Releasing retained output can overshoot the credit window** by up to the buffer size. Deliberate and
  documented: splitting the replay would require a second place that decides where a safe cut lands, which is
  the one thing the eviction goes to some trouble to get right. The overshoot is bounded.

# ED — the editor

## ED1 — A background re-read could destroy the buffer of a save that was still in flight

**File:** `src/editor/EditorController.cpp`, the reload reply callback; guard added at lines 987–999.

**What the code did before.** The editor pane holds one buffer — the text the user sees and edits. Two
independent things can replace it. The first is a *system-initiated reload*: the daemon reports that the
file changed on the server, or the reconciliation step after a dropped connection runs, and the controller
re-reads the file and pushes the server's bytes into the page. The second is a *save*: the user presses the
save key, the page hands over its current bytes, and the controller writes them to the server. Both are
asynchronous round trips over SSH, so they can overlap.

The reload's reply handler had one protection: it remembered a counter of how many edits the controller had
been *told about*, and if that counter had moved while the read was in flight it threw the fetched bytes away
rather than overwrite the user's typing. It had no protection at all against a save being in flight.

**Why that is wrong.** That edit counter only advances when the *page* reports an edit, and the page
deliberately delays that report by 500 milliseconds. The save key beats that delay comfortably. So this
sequence is entirely ordinary: the buffer is clean; an external process writes the file; the watch
notification arrives and the controller starts a re-read; within the same few hundred milliseconds the user
types and saves, so the controller has never been told about those keystrokes and its counter has not moved;
and the re-read answers first.

Before the fix, that last step took the "nothing changed, install the bytes" path. It pushed the server's text
into the page — wiping the user's unsaved keystrokes — reset the revision baseline to the server's new
revision, cleared the dirty flag, and truncated the crash-recovery snapshot, which was the only other copy of
those keystrokes. The write's own reply then arrived and, because the file really had moved, was refused as a
revision conflict. The user's edits existed in exactly two places and both were destroyed, while the interface
showed a conflict notice for a save whose content no longer existed anywhere.

This is also an internal inconsistency: the twin path that reconciles after a reconnect already contains
exactly this rule, twice. The reload path simply never grew it.

**What changed.** A guard was added immediately after the existing counter check: a reload the system started
on its own now yields to an in-flight save, and the write's own reply — success, conflict, or error — decides
the pane's next state. Reloads the *user* explicitly asked for (the Reload button, or a page that reloaded and
lost its buffer) still install, because replacing the buffer is the request.

**Test.** New: `TstEditorController::aSaveInFlightIsNotClobberedByASystemReload`. It drives exactly the
sequence above and asserts no content reached the page, the guarded revision is still the one the save was
issued against, the pane still reports "saving", and no extra request went out — so the recovery snapshot was
not truncated either. It then answers the write with the real revision-mismatch payload and asserts the
conflict is reported honestly. Confirmed to fail on the unmodified controller, where one content push reaches
the page.

## ED2 — Clicking Reload on a save conflict could resurrect the edits it had just discarded

**File:** `src/web/editor/src/index.ts` lines 361–372.

**What the code did before.** When a save is refused because the file changed on the server, the page shows a
notice with Reload and Overwrite buttons. Just before building that notice it re-arms its delayed
crash-recovery snapshot timer, which is correct in itself: the buffer is still unsaved. The Reload button then
cleared the notice and asked the host to re-fetch the file. It did not disarm that timer.

**Why that is wrong.** Reload means "throw my local edits away and give me the server's version". The host
honours that by re-reading, replacing the buffer, clearing its dirty flag and truncating the recovery snapshot.
But if the user clicks Reload within 500 milliseconds of the conflict appearing, the armed timer fires during
the reload's round trip and reports the *pre-reload* buffer — the edits the user just discarded. Depending on
which round trip lands first the outcome is either harmless or genuinely wrong: the recovery snapshot on the
server ends up holding discarded edits, so the next time this pane opens this file it offers to restore work
the user explicitly threw away; and the host's dirty flag is raised for a buffer identical to the file, which
suppresses the automatic reload of a clean buffer on the next external change.

**What changed.** The Reload handler now cancels the pending snapshot before asking for the re-fetch, with a
comment noting that the save path cancels for exactly the same reason and that this path bypassed it.

**Test.** None added. The cancel operation is already covered by two existing cases. The button wiring lives in
the file that imports the whole editor runtime and needs a browser document, so it is not reachable from this
package's test harness; extracting it would be a restructure well beyond a bug fix.

**File:** `src/editor/EditorController.cpp` lines 349–364.

## ED6 — A save's reply still rewrote the buffer after a same-path reopen or an explicit reload replaced it

**Files:** `src/editor/EditorController.cpp` — the guard at lines 741–764 and the matching one in the conflict
follow-up at lines 803–812; `src/editor/EditorController.h` lines 285–290.

Found after the round's first commit, by a review note pointing out that `ED1` had closed only one of the ways a
load and a save can collide.

**What the code did before.** A save is one network round trip. While it is in flight the pane can be handed a
completely different buffer by a *load* — either a re-read of the same file or a fresh open of it. The save's reply
handler defended itself against exactly one version of that: it captured the file path when the save was issued and
dropped the reply if the pane had since switched to a **different** file. Nothing else was captured.

**Why that is wrong.** The path check cannot see the case where the path stays the same, and there are three
reachable ways for a load to replace the buffer without changing it:

1. The user presses the page's **Reload** button while a save is in flight. That is explicitly allowed to replace
   the buffer — it means "discard my edits" — so it does.
2. The embedded editor page reloads (a crash, a refresh) while a save is in flight. Because the buffer is dirty at
   that moment, the controller deliberately **re-opens** the file rather than reloading it, so that the
   crash-recovery snapshot is offered back to the user. That is an `open()` of the same path.
3. A host re-opens the file the pane is already showing.

In all three the load finishes first and takes the buffer over: it adopts the server's revision as the new save
guard and pushes the server's bytes at the page. The write's reply then arrived and ran in full against that
freshly loaded buffer.

On success it re-baselined the revision to the one the *old* write produced — so the pane's save guard no longer
described anything on screen, and the next save would be refused as a conflict for no visible reason — cleared the
dirty flag for a buffer nobody had checked, and emitted `saved` for a save the page never asked for.

What it did to the crash-recovery snapshot differs by route, and the difference matters because the two `open()`
routes are the worse ones:

* Route 1 (`reload()`) truncates the snapshot itself as part of committing, so the save's success path merely
  repeated a truncation that had already happened.
* Routes 2 and 3 (`open()`) do **not** truncate it. They reset only their own local bookkeeping and then *re-probe*
  the snapshot, which is exactly how unsaved work gets offered back to the user. So on those routes the superseded
  save's success path truncated a snapshot the load had just re-probed — potentially while the "unsaved changes
  were recovered" offer was on screen, destroying the very work being offered.

On a conflict it was wrong in a third way: that path takes a second network hop to look up the current revision,
giving a load two windows to land in rather than one, and the outcome is a pane parked in "file changed on disk"
offering Reload-or-Overwrite over a revision mismatch that concerns bytes it no longer holds.

**What changed.** `save()` now also captures the controller's existing load counter — the same one every load reply
already checks itself against — and both hops of the save's reply handling drop the reply if it has moved. Silent,
like the neighbouring path check, because the load that superseded the save has already set this pane's state.

No new state was added. A first version of this fix introduced a second counter, bumped only where a load actually
*commits* to the buffer, out of a concern that the existing counter is bumped when a load *starts* — so a
system-initiated reload that starts during a save and is then discarded would bump it and wrongly swallow the
write's real outcome, which is the honest conflict `ED1` exists to report. That concern was tested and found
unreachable: every system-initiated reload site is gated on the buffer being clean, and `save()` marks it dirty for
the whole write, so a system reload cannot begin during a save at all. The second counter was therefore removed in
favour of the counter the file already had, and the invariant that makes that safe is written down at the guard,
together with what to do if a future change ever breaks it.

**Tests.** Two new cases in `src/editor/tests/tst_editorcontroller.cpp`.
`aSaveReplyIsDroppedAfterAnExplicitReloadTookOverTheBuffer` drives route 1 and answers the write
**successfully** — the worst case, because every branch of the success path rewrites pane state — then asserts no
`saved` was emitted, the revision and state are exactly as the reload left them, and no further request went out
(which is what proves the reloaded buffer's recovery snapshot was not truncated).
`aSaveConflictIsDroppedAfterASamePathReopenTookOverTheBuffer` drives route 3 and answers the write with a stale
revision carrying no revision of its own, so the controller would otherwise take its second hop; it asserts no
conflict, no error, no `saved`, and that the stat never reached the wire.

Both were confirmed to fail with the guard removed: the first reports one `saved` signal, the second catches the
superseded save chasing a conflict revision. `ED1`'s own case passes either way, which is what shows the two fixes
are independent rather than one masking the other.

## ED7 — A successful save could leave behind a crash-recovery snapshot holding older text

**Files:** `src/editor/EditorController.cpp` — `writeRecovery()` around lines 896–946, the new
`honourDeferredRecoveryClear()` and `clearRecovery()` at lines 960–990; `src/editor/EditorController.h` lines
212–216 and 322–348.

Found after `ED6`, by a review note. It is the same family of defect — an asynchronous reply acting on stale
knowledge — but on the recovery snapshot rather than the buffer.

**What the code did before.** While the user types, the page periodically reports its buffer and the controller
writes a snapshot of it to a per-pane file on the server, so unsaved work survives a crash. Two pieces of
bookkeeping describe that snapshot: the revision to guard the next write against, and a flag saying whether the
snapshot currently holds anything. **Both are only set when the snapshot write's reply lands.**

A successful save is supposed to retire the snapshot, because the file on the server now *is* the buffer, and it
does that with a revision-guarded truncate. But the truncate routine began by giving up when that flag said no
snapshot was known — a reasonable-looking check that saves a pointless round trip.

**Why that is wrong.** Between issuing a snapshot write and its reply, the controller does not yet know a snapshot
exists. A save that succeeds inside that window called the truncate, hit the "nothing was ever snapshotted" exit,
and did nothing. The snapshot write then answered and recorded a live snapshot — after the save that was supposed to
retire it.

If the user typed nothing between the report and the save, the snapshot and the file hold the same bytes, the next
open compares them, finds them equal and stays quiet. But typing again between the report and the save is
ordinary — the page's report is debounced by 500 milliseconds and the save key beats it — and then the surviving
snapshot holds text **older** than the file that was just saved. The next time the pane opens that file it therefore
offers to restore work the save had already superseded, and accepting the offer walks the buffer backwards over the
saved version. That offer used to be emitted into the void; `QM9` in this same round connected it to a real dialog,
which is what turns this from an invisible inconsistency into a wrong answer the user can act on.

**What changed.** The truncate routine no longer discards the request when it cannot act. If any snapshot write is
outstanding it records the intent, and the reply of the **last** outstanding snapshot write carries it out, guarded
by the revision that reply just supplied. A small helper owns that decision and is called from each path on which a
snapshot write chain ends while the pane still holds the file — including the stale-guard retry, which is kept
counted across its extra lookup hop so a truncate deferred during that hop is not decided on knowledge the retry is
about to replace. The one path that deliberately does not call it is a file switch, because re-opening resets the
recovery bookkeeping and any deferred truncate along with it, so nothing is owed to the file being left behind.

Four details are load-bearing. Each was arrived at by correcting a simpler attempt, and each is defended by its own
test that fails when only that rule is removed:

* **It is a count, not a flag.** Nothing serialises snapshot writes, so two reports in quick succession put two on
  the wire. With a boolean, the first reply would read "idle" while the second was still outstanding, truncate on its
  own revision, and then be overwritten by the write still in flight — putting the snapshot back after the save that
  asked for it to go.
* **A fresh report cancels a deferred truncate.** If the user types again *after* the save succeeded, those bytes are
  unsaved work the save never wrote, and the snapshot holding them must survive. Only a genuinely new report cancels;
  the internal retry that re-sends the same bytes after a stale-guard rejection deliberately does not.
* **The stale-guard retry stays counted across its extra lookup.** When a snapshot write is refused because a
  snapshot from an earlier session already occupies the slot, the controller looks up that slot's current revision
  and re-writes. That is two more round trips. If the chain stops being counted for the lookup, a save succeeding in
  that window finds no snapshot revision at all, drops the truncate request, and the re-write then leaves a snapshot
  of pre-save text behind a successful save.
* **Replies are stamped with a recovery generation, bumped by every `open()`.** The count and the deferred intent are
  shared pane state, so a reply belonging to a file the pane has since left must return before touching either.
  Otherwise the stale decrement releases the *new* file's deferred truncate early, guarded by the wrong revision and
  before the write it was waiting for has answered. This is the same stamping idiom the file already uses for loads
  and for watch subscriptions, rather than a new mechanism.

`open()` also resets the count and the pending intent, because a truncate meant for the file being left behind is not
owed to the new one, and the count is clamped at zero on decrement as a belt-and-braces measure.

**Tests.** Four new cases in `src/editor/tests/tst_editorcontroller.cpp`, one per rule above, each confirmed to fail
when its own rule is removed while the other three stay:

* `aSuccessfulSaveStillClearsASnapshotThatWasStillInFlight` — reports a buffer, saves newer bytes before that
  snapshot answers, answers the save first, asserts nothing is truncated yet (no revision exists to guard against),
  then answers the snapshot and asserts the truncate goes out with empty content guarded by the revision just
  supplied, exactly once. Without the deferral: the snapshot survives the save.
* `aReportAfterASaveCancelsTheTruncateThatSaveDeferred` — the opposite order: the save succeeds, the user types again
  while the first snapshot is still unanswered, then both snapshot writes answer oldest-first. Asserts no truncate is
  issued and the pane still reports unsaved changes. Without the cancellation: the deferred truncate deletes work
  typed after the save.
* `aDeferredTruncateSurvivesTheSnapshotRetryChain` — refuses the snapshot write first, so the retry chain parks on its
  lookup, and lands a successful save in exactly that window. Asserts nothing is truncated during the lookup and that
  the truncate runs after the re-write, guarded by the re-write's revision. Without the retry staying counted: the
  truncate is lost.
* `aStaleSnapshotReplyDoesNotDisturbTheNextFilesBookkeeping` — leaves a snapshot unanswered for one file, switches to
  another, gives the new file its own snapshot and a save that defers a truncate, then answers the *old* file's
  snapshot. Asserts that changes nothing, and that the truncate runs only when the new file's own snapshot answers,
  guarded by its revision. Without the generation stamp: the stale reply releases the truncate early.

### Investigated in this area and deliberately left alone

* **Two rapid saves in a row produce a spurious conflict notice.** If the user presses the save key twice within
  one round trip, both writes go out guarded by the same revision token; the first succeeds and the second is
  refused, so the interface shows "File changed on disk" for a file the user themselves just saved. No data is
  lost — Overwrite resolves it correctly — but it is a confusing and reachable wart. Not fixed because every
  available fix trades one problem for another and the choice is a product decision: dropping the second save
  silently swallows a deliberate user action; reporting "a save is already in progress" replaces a misleading
  notice with a noisy one; and tracking an outstanding-save flag in the page is the cleanest shape but makes the
  save key dead for the rest of the session if any path ever fails to deliver a terminal outcome.
* **Line endings and byte-order marks.** Checked because the brief called it out, and nothing needed fixing: a
  byte-order mark arrives as a leading character inside the content, survives being set into the editor, and
  comes back out unchanged, so it round-trips through a save. Carriage-return line endings likewise — the editor
  detects the line ending from the content it is given and preserves it. Neither the controller nor the bridge
  touches line endings or strips a mark anywhere.
* **Language detection treats a backslash as a path separator.** Remote paths always come from a POSIX server,
  where a backslash is a legal character inside a filename. Left alone: it is deliberate, there is an explicit
  test documenting the intent, and the practical effect is nil because the extension is still found correctly in
  every realistic case.
* **A claim that invalid UTF-8 could be corrupted on save was investigated and disproved.** The reviewer suspected
  the daemon might decode invalid bytes lossily, replacing each bad byte with a replacement character, so that a
  save would write those replacements over the original bytes. The coordinator checked the daemon's read path
  directly: it decodes in *strict* mode, so invalid bytes make the decode fail outright, and the file is then
  returned base64-encoded — which the client already marks unwritable, exactly as it does for a binary file.
  There is no lossy path and nothing to fix.

# VW — viewers

## VW1 — A file read that could not be sent answered before the caller learned its own request identifier, so the pane hung on "Loading…" forever

**Files:** `src/viewers/ViewerModel.cpp` lines 131–192, `src/viewers/ViewerModel.h` lines 79–86. Root cause
observed in `src/remote/CodeharbordClient.cpp`; the victim is `src/qml/ViewerTextView.qml`.

**What the code did before.** Starting a read of a remote file returns a short string — a token — which is that
read's name. When the answer comes back the model emits a signal carrying the same token, and the pane compares
it against the token it is holding to decide "this answer is mine". The pane does this literally: it stores the
return value and ignores any reply whose token is not exactly that string.

The read is dispatched through the JSON-RPC client's send function. That function promises to invoke its callback
exactly once — but it does **not** promise to do so later. When it cannot put the request on the wire at all, it
fails the call *right there*, invoking the callback before it returns. It takes that branch when no transport is
bound, when the transport is closed, when the transport is not writable, or when the write came up short.

So in that case the whole chain ran inside the read function: the callback fired, the error signal was emitted,
and only *afterwards* did the read function return the token to its caller.

**Why that is wrong.** When the pane's error handler ran, its stored token was still empty, because the assignment
had not happened yet — the right-hand side had not returned. The pane therefore rejected its own error and stayed
in the loading state permanently: no content, no message, nothing to retry, and no further event will ever arrive
because the read is already settled and its bookkeeping entry already removed. The trigger is ordinary, not
exotic: any dropped SSH session leaves a live client object whose transport is gone, so opening a file in a viewer
pane after the connection dies wedges the pane. This is precisely the failure the function's own header comment
claimed was impossible — the comment only covered the "no client at all" case and missed the far more common
dead-transport case.

**What changed.** Every reply is now delivered through one deferred hop instead of straight out of the callback.
The reply handling was extracted into a private method (same logic: the cancellation check, the truncation check,
the decode and the signal), and the callback now only re-posts to it as a queued call with the model as the
context object — so if the model is destroyed first, the queued delivery is discarded rather than touching freed
memory. The header comment was rewritten to say *why* the deferral exists, naming the synchronous-failure branch.
Cancellation is not weakened: the handler still starts by removing the token from the in-flight set and bailing
out if it is not there, so a cancellation issued during the extra hop still suppresses the reply.

**Test.** New: `TstViewers::textReadOnADeadTransportStillReachesItsCaller`. It builds a client with no transport
bound — exactly the state that makes the send fail synchronously — and asserts that no error has been emitted at
the instant the read function returns (this is the assertion that fails on the old code); that the read is counted
as in flight at that moment; that the error then arrives carrying that read's own token and path; that no success
signal is emitted and the in-flight count returns to zero, so the deferral does not turn an unsendable read into a
permanent leak; and that a read cancelled before its deferred reply produces nothing at all.

## VW2 — `Makefile` opened as text; `makefile` opened as an unreadable binary

**Files:** `src/viewers/ViewerHandlerRegistry.cpp` lines 28–80 and 200–216;
`src/viewers/ViewerHandlerRegistry.h` lines 23–40.

**What the code did before.** The registry decides which kind of pane opens a file. For a remote file URL it
looked at the extension. Files with no extension and dotfiles have none, so a second table was matched against the
file's name. That table was written in the project's preferred capitalisation — `Makefile`, `LICENSE`, `README` —
and looked up case-**sensitively**. It was also consulted only when the extension was completely absent.

**Why that is wrong.** Three common failures. First, `makefile` and `MAKEFILE` — both spellings GNU make itself
searches for — missed the table entirely and fell through to the binary "download this" pane, hiding plain text
the user simply cannot read; same for `readme`, `license`, `changelog` and `GNUmakefile`. Second, the table was
missing names that are unambiguously text and turn up constantly: `Jenkinsfile`, `Vagrantfile`, `Rakefile`,
`Gemfile`, `Procfile`, `CODEOWNERS`, `.dockerignore`, `.npmrc`, `.nvmrc`, `.clang-format`, `.clang-tidy`,
`.gitmodules`, `.gitconfig`, `.vimrc`, `.pylintrc` and others. Third, because the name table only ran when there
was *no* extension, `Dockerfile.dev`, `Makefile.in`, `.env.local`, `.env.production` and `README.old` all had an
"extension" — `dev`, `in`, `local`, `production`, `old` — none of which means anything, so they went to the binary
pane too.

**What changed.** The duplicated "last path segment" logic was extracted into one helper, whose index variables
were also corrected from a 32-bit integer to the 64-bit type the underlying search actually returns. The table
moved into its own function, spelled in lower case and looked up after lower-casing, so matching is
case-insensitive, and the missing names were added. A stem rule was added: if the full name misses, the part
before the first dot is tried too, searching from the second character so a dotfile keeps its leading dot — that
is what makes `Dockerfile.dev`, `Makefile.in`, `.env.local` and `README.old` resolve as text. Finally, the
resolution order was changed so the extension is tried first and the name table is consulted only when the
extension resolved to "download". That is what keeps the stem rule safe: `archive.zip` and `photo.jpg` never reach
it, and `README.png` still opens in the image pane while `README.md` still renders as markdown. The trailing-slash
directory check still runs before either.

**Test.** The existing resolution table test was extended with two loops — eleven case-varied and newly added
names, six well-known-name-plus-suffix spellings — and four negative cases: `notmakefile.bin` stays a download, so
the stem rule cannot swallow arbitrary binaries; `README.png` stays an image and `README.md` stays markdown, so a
known extension still wins; and a path ending in `LICENSE/` stays a directory.

## VW4 — The internal-URL lookup accepted an address its own request handler refuses

**Files:** `src/viewers/InternalUrlSchemeHandler.cpp` lines 67–90; the twin check it disagreed with is at lines
188–196; documentation at `src/viewers/InternalUrlSchemeHandler.h` lines 56–61.

**What the code did before.** Remote files are shown to the embedded browser through opaque URLs of a fixed shape:
a custom scheme, then the fixed host name `file`, then a random identifier. The code that *answers* such a request
explicitly rejects any other host, with a comment explaining why: in a browser a different host is a different web
origin, and serving the same bytes under several origins hands a rendered page extra origins to play same-origin
games with.

The inverse function — which turns such a URL back into the remote file path, and is exposed to the user-interface
layer — checked only the *scheme*. It took the path component, stripped the leading slash, and looked the
identifier up. So a URL with the same scheme but a different host resolved happily to the real remote file.

**Why that is wrong.** A check applied in one place and missing in its twin. Nothing calls the inverse function
today, so there is no live exploit; the hazard is that the two halves of the subsystem disagree about whether a
given URL is legitimate, and the *accepting* half is the one exposed to the user-interface layer. Any future code
that validates a URL with it and then acts on the result would be validating against weaker rules than the handler
enforces.

**What changed.** The inverse function now rejects any URL of this scheme whose host is not `file`, matched
case-insensitively exactly as the handler matches it. Bare-identifier arguments, which the function also documents
support for, are unaffected. The documentation states the rule.

**Test.** The existing URL-mapping test was extended: two differing hosts must not resolve, and an upper-case
spelling of the correct host must still resolve, so the tightening does not accidentally become case-sensitive.

## VW5 — Wrong specification section cited on the external browser profile

**File:** `src/viewers/ViewerProfiles.cpp` line 54.

The comment read "arbitrary sites stay sandboxed (SPEC 7.2)". Verified against the document: section 7.2 is
"Arbitrary Websites" and describes the *content*; the requirement to use two separate browser profiles is 7.3,
"Browser Profiles". The comment is describing the two-profile split, so it pointed at the wrong section. Now cites
7.3, with a clause noting that 7.2 is what those sites *are*, so the neighbouring 7.2 citations still make sense.
The other citations in this area were judged individually and left alone — two of them genuinely concern untrusted
arbitrary web content and are correct as written.

## VW6 — Directory listings were sorted through a generic value type, paying four map lookups per comparison

**File:** `src/viewers/ViewerModel.cpp` lines 50–73 and 239–258.

**What the code did before.** The directory-listing reply handler built a list of generic key-value maps and then
sorted that list. The comparison function received two generic values, converted each to a map (a shared copy with
an atomic reference-count round trip), then did two string-keyed tree lookups per side to get the entry kind, and
up to two more to get the name.

**Why that is wrong.** Not a correctness bug — the resulting order is right — but it performs four map
constructions and four to eight tree lookups per comparison, of which there are order *n* log *n*, on data that is
two plain strings. It is also harder to read than the thing it is doing. A directory with thousands of entries pays
for it on every listing.

**What changed.** A two-field structure and a free comparison function were added next to the file's existing
helpers. The handler now parses into a list of those, sorts it, and builds the generic list once afterwards. The
ordering rule is byte-for-byte the same — directories first, then case-insensitive name with a case-sensitive
tie-break — and the explanatory comment moved onto the comparison function where it belongs.

**Test.** New: `TstViewers::directoryListingIsSortedDirectoriesFirst`. There was **no unit coverage of the listing
order at all**; it was only exercised by the live gate, which is skipped by default. The new test feeds a
deliberately jumbled listing containing two directories, four files, a pair differing only in case, and an extra
field, and asserts the exact resulting name order, that each entry carries exactly the two keys the pane consumes
(the extra field must not leak through), and that an empty directory comes back as a successful empty listing
rather than an error.

## VW7 — An implicit narrowing in a public accessor

**File:** `src/viewers/ViewerModel.h` lines 99–102. A count was returned from a 32-bit integer function while the
underlying container's size is 64-bit. It cannot overflow in practice — it counts outstanding file reads — but it
is a silent narrowing that becomes a warning-as-error the day the project raises its warning level, and it is free

## VW8 — Nothing verified that the content type and character set actually reach the browser

**File:** `src/viewers/tests/tst_liveviewers.cpp` lines 160–166 and 662–699.

**What was missing.** The request handler picks a content type from the file's extension and, for textual types,
appends the UTF-8 character set — with a comment explaining that without it the browser falls back to a
locale-derived guess and a UTF-8 file with non-ASCII characters renders as unreadable mojibake. The unit suite
tests the type-picking function in isolation. The live gate loaded a real remote file into a real browser view and
read the text back out of the document — but only the text. Nothing anywhere checked that the header the handler
built was received and honoured.

**Why that is a gap.** The header could be dropped, overridden or sniffed away and every existing assertion would
still pass: the fixture file is pure ASCII, so a wrong character set is invisible in the rendered text, and a wrong
content type would still render as some kind of document. The garbled text this code exists to prevent would only
show up on a user's non-ASCII file.

**What changed.** The probe script the live test injects now also reports the document's content type and character
set, and the test asserts them. These are browser-side observations — the only place the delivered header is
visible. This runs in the live gate, which the coordinator executed: it passes.

### Investigated in this area and deliberately left alone

1. **An in-flight remote read is not cancelled when the browser cancels its request.** The request object is
   guarded by a `QPointer`, so a cancelled request is handled safely with no use-after-free and no reply to a dead
   request. But the remote read keeps running and its payload — up to 8 megabytes — still crosses the SSH channel
   and is then thrown away. Fixing this needs a cancel operation in the wire protocol, which does not exist.
2. **No byte-range support in the request handler.** Every reply is a whole buffer. The file service does support
   offsets and lengths, so it is implementable, but nothing routed to an internal view needs ranges today — video
   and audio resolve to "download" — so adding it would be speculative machinery.
3. **A file over the 8-megabyte inline cap fails with no explanation in the image, PDF and binary panes.** The text
   pane gets a "file is too large to display inline" message from the model, but the request-handler path can only
   report a generic failure, which carries no text — so an oversized image or PDF just shows a failed page. The
   handler genuinely cannot do better through that interface; conveying the reason would have to happen in the
   pane, in another area.
4. **The internal-URL table's eviction can invalidate a URL a pane is still displaying.** The table is capped at
   1024 entries and an identifier is only marked recently-used when it is created or resolved. A pane that loaded
   its image hours ago never re-resolves, so after 1024 other files are opened the identifier can age out and a
   reload of that pane fails. Raising the cap or pinning displayed identifiers both change ownership semantics the
   user-interface side depends on; the current behaviour is documented and the window is large.
5. **Two other model methods still report their no-client failure synchronously**, unlike VW1's read. Checked and
   it is *not* the same bug: both are identified by path, which the caller already knows before it calls, and both
   callers set their matching state *before* calling, so a synchronous reply is matched correctly. Deferring them
   anyway would be churn on a working path.
6. **The restrictive content-security policy on active content also blocks style blocks inside an SVG**, so such an
   SVG renders unstyled. This is the documented deliberate trade-off; loosening it would weaken the exfiltration
   defence.
7. **One enumeration value is never produced by any code path.** Checked the specification before touching it: the
   value is part of the resolution vocabulary the specification mandates, so it is a specified placeholder, not
   dead code.

# QM — the user interface layer

## QM1 — A terminal pane could attach to the previous Dev Session's shell, or strand itself forever

**File:** `src/qml/TerminalPaneView.qml` lines 88–106, 393–412 and 464–487.

**What the code did before.** Each terminal pane has to find out which remote tmux session it owns. That is a
question for the server, so the pane asks and waits; the answer comes back on a signal carrying only two things —
which controller it is for, and the session name. The pane recorded, in one variable, a string identifying the
"slot" it had asked about, and when an answer arrived it compared that string against the slot it currently
occupies, ignoring the answer if they differed.

Separately, if the user pointed the pane somewhere else while a question was still travelling, the retarget
routine cleared the "a question is outstanding" flag and immediately asked a **second** question.

**Why that is wrong.** Two bugs fall out of the combination.

The first is the wrong shell. Because the retarget asked the new question straight away, it also overwrote the
recorded slot with the NEW one. The old answer — still in flight, describing the OLD Dev Session's shell — then
arrived, found the recorded slot equal to the pane's current slot, passed the check, and was adopted. The pane
attached to the shell belonging to the Dev Session the user had just left, so two panes shared one remote shell:
precisely the failure the whole resolution mechanism exists to prevent. Reproduced by clicking one Dev Session in
the sidebar and another within the round-trip window, a few hundred milliseconds on a normal link.

The second is a permanent stall. In the cases where the mismatch check *did* fire, the handler returned **without
clearing the outstanding flag**. The attach routine refuses to do anything while that flag is set, so the pane
never asked again and never attached — and its own Retry button, which just calls the attach routine, could not
help either.

**What changed.** The pane now keeps **exactly one lookup outstanding**. A retarget no longer clears the flag and
no longer starts a second lookup; it sets a new "the answer coming back is about a slot we have left" marker. The
answer handler now clears the outstanding flag FIRST, so nothing can be stranded, and if the answer is stale — by
the new marker or by the existing slot comparison — it discards it and calls the attach routine to ask the
question the pane actually has now. Because only one question is ever in flight, an answer that carries no slot of
its own is unambiguous.

**Test.** New: `TstPaneIdentity::aTerminalPaneNeverAdoptsTheAnswerToASupersededLookup`. It drives a real terminal
pane against a new substitute factory, holds a lookup open, retargets the pane, delivers the old answer, and
asserts: no second lookup was started while the first was open; the old target was not adopted and no terminal
attached to it; the pane asked again for the new slot; and the new answer is adopted and attached.

## QM2 — A retargeted terminal pane could open its shell in the previous checkout

**File:** `src/qml/TerminalRegion.qml` lines 349–366.

**What the code did before.** When the region's Dev Session changes it pushes two values onto each pane: the
session identifier and the directory the shell should start in. It assigned the session identifier first and the
directory second.

**Why that is wrong.** Assigning the session identifier is what makes a pane drop its terminal and re-attach, and
the working directory only ever reaches the server as part of "create a tmux session in this directory", which
tmux honours **only when it creates the session**. So a pane that sees the new session identifier while still
holding the old directory creates its shell in the previous project's checkout, and the directory arriving one
line later can no longer move it. The main window documents this at length and pushes the pair the other way
round, which is what has been masking it — the region's own copy of the same push had the order backwards, so any
future caller that did not go through the main window first would hit it.

**What changed.** The two assignments were swapped so the directory is set first, with a comment pointing at the
main window's identical rule.

**Test.** None added: with the host's ordering in place the observable behaviour is unchanged, so a test would
assert internal ordering rather than a user-facing contract.

## QM3 — The viewer address bar kept the fragment the user typed, and then showed the wrong path after the first fix

**File:** `src/qml/ViewerPane.qml` lines 76–85 and 326–349.

**What the code did before.** The address bar shows the pane's current address. Because the field is editable the
pane pushes text into it rather than binding it, and it deliberately never pushed while the field had keyboard
focus, so it could not overwrite what the user was typing.

**Why that is wrong.** Pressing Enter in a text field does not take the keyboard away from it. A user typing a
name **relative** to the directory the pane is showing — `notes.md` in a listing of `/srv/repos/app/` — leaves the
field focused, so the pane opened `/srv/repos/app/notes.md` while the bar still read `notes.md`. The bar then
claimed the pane was showing a file with no directory, and the next Enter resolved that leftover fragment against
whatever directory the pane had moved to.

**What changed, and the second defect found during integration.** The push was extracted into a helper. A change
of the displayed path still pushes only when the field is unfocused (unchanged behaviour), but a change of the
pane's own address — which only ever happens because the pane navigated, i.e. because the user asked it to — now
pushes unconditionally.

The first version of that helper was wrong, and the coordinator's integration run caught it. It pushed a *bound*
property. That property is bound, through one intermediate, to the pane's address — and the new handler runs from
the very notification that refreshes those bindings. Whether they have already been refreshed when a given handler
runs is an ordering detail of the engine, and here they had not been: the handler read the previous value out of
the still-stale binding, so the bar showed the directory the pane had just left rather than the file it had just
opened. This is the same hazard a sibling file avoids by writing the equivalent value as a function instead of a
bound property. The final fix computes the pushed value with a small function — the same rule the bound property
states, applied to the freshly assigned address — instead of reading it off a binding. No assertion was changed.

**Test.** New: `TstPaneIdentity::theAddressBarShowsWhatARelativeNameResolvedTo`. It opens a directory, types a bare
file name, and asserts the pane opened the resolved absolute path AND that the still-focused field now reads that
same absolute path. This test failed in the coordinator's integration run, which is how the binding defect above
was found; it passes now.

## QM4 — Long names ran off the edge of the sidebar and covered the button that creates a Dev Session

**Files:** `src/qml/SessionRow.qml` lines 41–52 and 176–203; `src/qml/GroupHeader.qml` lines 36–50 and 87–108.

**What the code did before.** The Dev Session name, its repository subtitle and the group name are all drawn with
"cut this off with an ellipsis if it does not fit".

**Why that is wrong.** Eliding does nothing to a text item that has no width of its own, and none of these had

So the text grew to its full natural width and painted straight over the edge of the panel — and in the group
header, over the "collapsed" tag and over the "+" button that adds a Dev Session to that group, which is the only

repository paths), so lengths well past a 300-pixel sidebar are ordinary rather than adversarial.

**What changed.** Each label was given an explicit width derived from the space actually available: the session row
measures from its content row's own width, and the group header measures against a new value that is the left edge

**Test.** New: `TstSidebar::longNamesAreElidedInsteadOfOverflowingTheSidebar`. It builds a group and a session with
120- and 160-character names, then asserts that every visible text item inside the row and the header ends inside

is the mechanism but staying inside the panel is the requirement.

## QM5 — The window title could push the Dev Session name under the window buttons

## QM6 — The session row's context menu reached around the sidebar's own contract

**Files:** `src/qml/SessionRow.qml` lines 241–257 and 302–305; `src/qml/SessionsSidebar.qml` lines 354–377.

**What the code did before.** The sidebar states as a contract that it "owns every application call", and the group

## QM9 — Crash recovery was only half built: the user was never offered their unsaved work back

**Files:** `src/qml/EditorPaneView.qml` lines 239–374 and 394–405. Existing counterpart:
`src/editor/EditorController.cpp` line 683 and `src/editor/EditorController.h` line 142.

*Routed to this area from the editor reviewer, who owns the C++ half and correctly identified the missing part as a
user-interface decision.*

**What the code did before.** While the user types, the editor controller periodically writes a snapshot of the
unsaved buffer to a per-pane file on the server. When the same file is opened again it reads that snapshot back and
compares it with the file's current contents; a snapshot that differs means the application died holding unsaved
work, and the controller emits a signal carrying the recovered text. **Nothing anywhere connected to that signal.**
A search across the whole client found only the declaration, the emit, and two assertions in the controller's own
test. The editor pane did not handle it.

**Why that is wrong.** It is the entire point of the specification's unsaved-recovery section. The whole mechanism
ran — including an extra status request and a read on every single file open — and then the recovered text was
dropped on the floor. The user was never told their work had survived and had no way to get it back. Storing and
finding the snapshot without ever offering it is strictly worse than not having the feature: it costs two round
trips per file open and delivers nothing.

**What changed.** The missing user-interface half was added, using the module's own dialog and theming components
and no new visual vocabulary:

* The pane now tracks the revision the page was loaded at, taken from the same signal the page reads its content
  from.
* The recovery signal is handled: the recovered text is held, and a modal dialog titled "Unsaved changes were
  recovered" explains in plain words that unsaved changes to this file are not in the file on the server, and what
  each button does. It offers **Restore** and **Discard**.
* The offer is deliberately **withheld until the page actually holds the file**. An empty loaded revision means the
  controller is still holding the content back until the page reports itself ready; offering earlier would let a
  restore push text at a page with no handler attached, losing the very work being offered.
* **Restore** re-emits the content-loaded signal with the recovered text — the only route content has into the
  editor page, since the JavaScript bridge contract is fixed — using the revision the page already holds, so the
  next save's conflict guard is unchanged. It then reports the content upward, so the host knows the buffer no
  longer matches the server: that is what stops an external change from silently reloading over the restored work,
  and what keeps the snapshot alive until the user actually saves.
* **Discard** leaves the file as the server has it and leaves the snapshot alone; the controller already discards it
  on the next successful save.
* The dialog cannot be dismissed with the Escape key or by clicking outside it. Every other dialog in this module
  asks about something the user can redo; this one asks about work that exists in exactly one place.
* Switching the pane to another file clears the pending offer and the revision, so a previous file's unsaved work
  can never be restored into the new one.

Whether the fix belonged in the C++ controller instead was checked and rejected: the controller already publishes
everything needed — the recovered text on the signal, the revision on the load signal, and a method to mark the
buffer as differing from the server — and what was missing was purely the choice put in front of the user. No C++
was changed.

One mechanism is worth recording: restoring emits a C++-declared signal from the user-interface layer. That this is
possible was verified with an isolated probe rather than assumed.

**Tests.** Two new cases in `tst_paneidentity.cpp`, driven by a new substitute controller and no real editor page.
`theEditorOffersToRestoreARecoveredBuffer` asserts the offer does NOT appear while the page has not yet taken the
file; that it appears once the load completes; and that Restore pushes exactly the recovered text back into the
page, guarded by the revision the page already held, and marks the buffer as differing from the server.
`discardingARecoveredBufferLeavesTheEditorShowingTheFile` asserts Discard closes the offer, pushes nothing into the
page, and does not mark the file as changed.

# AG — agent awareness

## AG1 — Claude Code reported a helper agent finishing as the whole agent finishing

**Files:** `remote/src/adapters/claude-code.ts` lines 8–13 and 28–31; test at
`remote/test/adapters.test.ts` lines 188–193.

**What the code did before.** CodeHarbor learns what a coding agent is doing from small lifecycle messages the
agent's harness sends. For Claude Code the harness fires named hooks, and the adapter translates each hook name
into one of CodeHarbor's agent states. Two hook names were translated to the same state, "finished and the user
has not looked at the result yet": `Stop` and `SubagentStop`.

`Stop` fires when the agent has finished replying to the user. `SubagentStop` fires when a *helper* agent finishes
— the main agent is still working at that moment and will keep going for many more steps.

**Why that is wrong.** That state is not cosmetic. Every event carrying it sets the Dev Session's
unseen-completion badge in the sidebar and triggers a real desktop notification titled "Agent finished". So a
single Claude Code turn that fans out to, say, eight helper agents produced eight false "Agent finished"
notifications and a badge that kept re-arming while the agent was demonstrably still running — the next tool-use
event immediately flipped the state back to running. Worse, that badge is a "have you seen this?" signal:
re-arming it mid-turn destroys its meaning, and it re-arms even after the user has cleared it, because the monitor
deliberately re-arms on *every* such event rather than only on transitions.

**What changed.** `SubagentStop` now maps to "running", which is what the main agent is doing when a helper
finishes; only `Stop` remains a completion. A comment names the reason so the two are not folded back together.

**Test.** The existing lifecycle-mapping case was updated to assert the new mapping, with the reason inline. It
fails on the old mapping.

## AG2 — A blank command-line argument silently disabled the documented environment fallback

**Files:** `remote/src/hooks/oh-my-pi-hook.ts` lines 69–88; test at `remote/test/agent-hook.test.ts` lines 179–200.

**What the code did before.** The installed hook script is run once per lifecycle event with the event name as its
first argument. For a harness that cannot pass arguments to a hook, the name can come from an environment variable
instead. That was written using the "nullish coalescing" operator, which only falls through when the left side is
null or undefined.

**Why that is wrong.** The overwhelmingly common way to write a hook command in a shell configuration is to
interpolate a variable into the argument. When that variable is unset or empty, the shell still passes an argument
— an *empty string*. An empty string is not null, so the operator accepted it as the answer and the environment
variable was never consulted. The hook then printed its usage banner and emitted nothing: the documented fallback
was dead in exactly the configuration that needs it, and the user's agent status silently never updated. A
whitespace-only argument was worse — it passed the "is the event name missing?" guard, so the hook emitted a
message whose event name was a single space, which no adapter can map. That is a wasted socket round trip on every
single hook firing, with no visible symptom at all.

**What changed.** A blank (empty or whitespace-only) argument now counts as absent, so the environment fallback
applies. If both sources are blank the event name stays empty and the script prints usage exactly as it always did
for a genuinely missing name.

**Test.** The existing fallback case was extended: arguments of empty string, three spaces and a tab all resolve to
the environment value, and blank on both sides resolves to empty. Fails on the old version.

## AG3 — Whether an over-sized event was accepted depended on how the operating system chunked the socket

**Files:** `src/agent/AgentStatusMonitor.cpp` lines 98–109; test at `src/agent/tests/tst_agentmonitor.cpp` lines
991–1036.

**What the code did before.** The client reads agent events as newline-delimited JSON: one event per line, on a
stream. The read handler appends whatever arrived to a buffer, then cuts complete lines off the front and parses
each one. After that loop it has a safety valve: if what is *left* in the buffer — a line with no newline yet — is
bigger than one megabyte, the bytes are thrown away and the rest of that frame skipped, so a producer that streams
forever without a newline cannot grow client memory without bound. The loop that cuts complete lines had no size
check of its own.

**Why that is wrong.** The two paths disagree about the same event. Take one event line of 1.2 megabytes. If the
operating system happens to hand it over in pieces, the loop finds no newline, the safety valve fires, and the
event is dropped. If the same line happens to arrive in a single read, the loop sees a complete line and parses
and applies it. Identical bytes on the wire, opposite outcomes, decided by socket buffering that neither the
producer nor a test controls.

This is reachable, not theoretical. The remote relay caps the message it *accepts* at one megabyte and then builds
a strictly larger event line from it — it adds a version, a timestamp and the harness name, and re-escapes the
summary. A harness whose summary is close to a megabyte therefore lands precisely in the window where the two
endpoints disagree, and the client's behaviour is then a coin flip.

**What changed.** The cap is now a property of the frame rather than of the arrival pattern: inside the framing
loop, a complete line longer than the cap is removed and skipped without being parsed, and framing continues at the
following line. No discard-tail bookkeeping is needed, because the newline that closed it was actually seen.
Over-cap frames are now always dropped.

**Test.** New: `overCapCompleteFrameIsDroppedWhateverTheChunking`. It uses an in-memory buffer rather than a socket
pair on purpose, because that is drained in one synchronous read, which is the only way to *guarantee* the
over-cap line is framed as a single complete line — the case a socket pair cannot reproduce reliably. It feeds an
over-cap event followed by a normal one and asserts exactly one state change, for the normal event. Verified to
fail against the pre-fix source, where two state changes occur.

## AG4 — A type's documentation named the wrong key for one of the three harnesses

**File:** `remote/src/adapters/types.ts` lines 3–8. The type describing a harness's own raw event carried a comment
saying "the `type` field names the harness's own event", and declared only that field. That is true for two of the
three adapters. The Claude Code adapter reads a field called `hook`, not `type` — Claude Code has lifecycle hooks

## AG5 — A file header claimed an inference the program never performs

**File:** `remote/src/adapters/fallback.ts` lines 3–8. The header of the generic-harness activity detector read "so

## AG6 — A live-gate comment misnamed the hook's argument position

## AG7 — Three more comments cited the wrong specification section; one cited the right one

**Files:** `src/agent/tests/tst_agentmonitor.cpp` lines 1040–1044; `src/agent/tests/tst_liveagent.cpp` lines
546–548 and 279–283.

*Routed to this area from the build-and-documentation reviewer, with the explicit instruction to judge each site
individually rather than doing a blanket replace.*

Two comments claimed "SPEC 6.2 lists waiting_input and idle_unseen only". That is a claim about the state list,
which lives in 6.4 "Internal Event Schema", not in 6.2 "Supported Harnesses". Both now cite 6.4 for the state names

A third comment was flagged as "probably fine" by the routing reviewer and this area disagreed after checking: the

it lists four harness names. That convention is CodeHarbor's own hook design, documented in the hook source, so the
comment now points there and keeps its existing correct citation of 6.3 for the socket.

One was kept as correct: a comment citing the range "SPEC 6.2–6.5" for the whole harness chain. Every section in
that range is genuinely exercised by that gate — 6.2 the recognised harness, 6.3 the bridge and its socket, 6.4 the
event schema on the wire, 6.5 the state mapping — so it is accurate as written.

### Investigated in this area and deliberately left alone

* **AG-N1: the generic harness produces no agent state at all, end to end.** The adapter lookup deliberately
  returns nothing for the harness kind "generic", so the relay drops every message from one. The intended
  substitute is the fallback activity detector, which infers busy or idle from terminal output — and it has **no
  production caller anywhere in the repository**. Nothing feeds it and nothing publishes its result. This was
  investigated in depth and is recorded as BD14 below, where the plan file that claimed the feature was complete is
  corrected.
* **AG-N2: there is no timeout for an agent that goes silent.** The monitor contains no timers of any kind. If a
  harness dies without emitting a shutdown event — killed, or the host rebooted — the terminal's last known state
  is kept forever. Ageing was deliberately not added: the client cannot distinguish "agent still thinking for ten
  minutes" from "agent died", inventing an expiry would flip live rows to idle under a long tool call, and losing
  the transport is deliberately a connection-state condition rather than an agent state. Any real fix belongs on
  the remote side where the harness process is observable.
* **AG-N3: an error flag outranks a shutdown event in two adapters.** A shutdown that is flagged as an error maps
  to "error" and the terminal never reaches "stopped", so the row stays red for a session that is gone. This is the
  documented behaviour, is asserted by the live gate, and the error state is explicitly not a latch — the next
  event replaces it. Flagged because a producer that sets the error variable once and forgets to unset it turns
  every later event into an error; that is the producer's bug, but an easy one to hit.
* **AG-N4: the hook cannot carry free-form metadata from the command line.** The type declares an optional metadata
  bag and the message builder forwards it, but the reader never populates it from the environment, so only a
  programmatic caller can set it. Adding an environment variable for it would be inventing wire surface nobody
  asked for, and the adapters already derive the one metadata field that matters.
* **AG-N5: one adapter is a byte-for-byte copy of another's mapping.** Deliberate — each file says so, "kept as a
  distinct adapter so the two can diverge" — and defended by a test that drives thirteen events through both and
  fails the moment one file is edited alone.
* **AG-N6: the read buffer is shifted down for every line consumed**, so one read carrying many events costs order
  *n* times the byte count. Agent events are small and arrive at human pace, so this is invisible today; converting
  to a consume-offset ring is a restructure of working code for no measurable gain.
* **AG-N7: re-entrancy of the read handler was investigated and there is no defect.** The event type promises
  events are applied strictly in arrival order, and the handler calls into other code from inside its framing loop,
  so the question was whether something that spins the event loop could re-enter and apply a newer event before an
  older buffered one. It cannot: the re-entrant call appends new bytes to the *end* of the same buffer and frames
  from the *front*, so the oldest complete line is always consumed first. The notifier's delivery was also
  confirmed to be asynchronous, so the realistic re-entry path does not even exist. No guard was added — it would
  have been a fix for a bug that is not there.
* **AG-N8: a suspected hook-process hang was raised, implemented, measured and reverted.** The hypothesis was that
  the hook disarms its inactivity watchdog as soon as its write succeeds, and since the runtime keeps a process
  alive while a socket handle is open, a relay configured to allow half-open connections would hold the hook — and
  the agent run blocked on it — open forever. The fix and a test were written, then measured: the runtime already
  destroys the socket as soon as the writable side finishes with the readable side never consumed, verified against
  a real half-open-permitting server. The hazard does not exist and the test could not distinguish the two
  versions, so **the change and the test were both deleted** rather than shipping a fix for an imaginary bug. The
  comment on the disarm line now records why disarming is correct and why the process can still exit, so the next
  reader does not have to redo the measurement.

# WS — the workspace half of the daemon

## WS1 — Copying a Dev Session silently lost any pane whose identifier collided with a built-in JavaScript name

**Files:** `remote/src/workspace.ts` lines 400–420, 1233 and 1255.

**What the code did before.** "Duplicate Dev Session" copies a session's panes into brand-new database rows with
brand-new identifiers, then rewrites the saved window-split layout so its leaves point at the copies instead of the
originals. The old-to-new translation table was a plain JavaScript object, and the rewrite looked an identifier up
with plain property access.

A plain object in JavaScript inherits properties from the language's base object — `constructor`, `toString`,
`valueOf`, `hasOwnProperty` and so on. So looking up `"constructor"` does not return "not found"; it returns the
built-in constructor **function**.

**Why that is wrong.** The pane identifiers inside a layout tree come from the desktop client, which is free to put
any string there — the terminal region legitimately stores human-authored slot labels. A leaf whose identifier was
the literal string `constructor` (or `toString`, `valueOf`, …) therefore resolved to a function instead of a string.
The rewritten tree is then serialised to JSON, and JSON serialisation **drops** properties whose value is a
function. The result: the copied leaf came out with no identifier at all, so the duplicated session showed an empty
pane where the original showed content, with no error anywhere. Reproduced directly: the old code produced a leaf
with no identifier; the new code preserves it.

**What changed.** Both translation tables are now real map objects and the rewrite uses their lookup method. A map
has no inherited keys, so an unmapped identifier always reads back as "not found" and the existing fallback keeps
the original string. This also matches the project's own rule that runtime-inserted keys belong in a map rather
than a plain object.

**Test.** New: "duplicateSession leaves a paneId named after an Object.prototype member alone". It duplicates a
session whose layout holds `constructor` in one leaf and a real identifier plus `toString` in the other, then
asserts the unmapped `constructor` survives verbatim, the real identifier is still remapped to the copied pane, and
the unmapped one is dropped rather than turned into a function. The first assertion fails on the old code.

## WS2 — A null for a column that cannot be null was accepted, discarded, and answered with "success"

**Files:** `remote/src/workspace.ts` lines 1920, 1951, 1952, 2000 and 2037; new guard at
`remote/src/validate.ts` lines 67–86.

**What the code did before.** Update requests carry only the fields the caller wants to change. Some of those
fields are genuinely nullable — sending a null task description means "clear it" — so the shared validation guard
accepts three things: absent, null, or a string.

That same permissive guard was also used for the fields that are **not** nullable: a group's name, a Dev Session's
name and repository root, a viewer pane's address, a terminal pane's name. When one of those arrived as null, the
guard let it through, and the store then fell back to the value already in the row, because the fallback operator
treats null exactly like absent.

**Why that is wrong.** A silent-failure path. A caller that sent an update with a null name got a normal success
response containing a session object, and the row was completely unchanged. Nothing told anyone the request had
been thrown away. Every other bad value on those same fields — a number, an array — is rejected with a clear
"invalid params" error; null alone was swallowed. It is also an inconsistency: the code deliberately distinguishes
"absent" from "null" for the fields that *can* be cleared, so the two families are handled by two different rules
while sharing one guard. Confirmed reachable in process: an update with a null name returned the old name.

**What changed.** A new guard was added — identical to the existing one except that it rejects an explicit null —
and applied to exactly those five non-nullable fields. The genuinely nullable fields keep the permissive guard and
keep their clear-on-null behaviour.

**Test.** New: "a null is rejected for the fields that cannot be cleared". It drives all five method-and-field pairs
through the real handler table and asserts each throws.

## WS3 — A negative or fractional ordering position was written straight into the database

**File:** `remote/src/workspace.ts` lines 1913, 1921, 1944, 1955, 1994, 2003, 2020 and 2042.

**What the code did before.** Every group, Dev Session and pane carries an integer position that fixes its order in
the sidebar. Every internal path keeps those numbers packed as contiguous integers starting at zero, and listing
queries sort by them. A client may optionally supply a position on create or update, and that value was validated
with a guard that accepts **any** finite number, including −5 and 2.5. The supplied value was then stored verbatim.
SQLite's integer column affinity does not coerce 2.5; it stores the real number as-is.

**Why that is wrong.** Reproduced against a live database: creating a group at position 2.5 stored 2.5, and the
*next* created group got 3.5, because the "next position" query is the maximum plus one. So once one fractional
value is in a scope, the corruption is sticky and spreads to every subsequent row. A negative position pins a row
permanently above whatever the user dragged to the top. This is the same class of defect the code already went to
some trouble to fix in the move-between-groups method, whose comment explains that storing a requested position
verbatim leaves two rows sharing one slot; the create and update paths never got the same treatment.

**What changed.** The position guard on all eight create and update handlers was switched to the existing guard
that requires a non-negative whole number, rejecting fractions, negatives and not-a-number with a precise message.
The C++ client's serializers were checked: the client omits the field when unset and sends a plain integer
otherwise, so nothing it can send is newly rejected. The move-between-groups method deliberately keeps the
permissive guard, and a comment now says why: there the value is a drag *index*, not a stored position, and the
method truncates and clamps it into the target group's range on purpose — pinned by an existing test that passes
−5.

**Test.** New: "a fractional or negative position is rejected by every create/update" — a table of all eight
handlers crossed with 2.5, −1 and not-a-number, asserting each is rejected.

## WS4 — Any failure reading the stored schema version was reported as "this database is empty"

**File:** `remote/src/workspace.ts` lines 894–911.

**What the code did before.** On open, the daemon reads the stored schema version to decide which migrations to
run. That read was wrapped in a bare catch-all that turned *every* failure into "version 0", i.e. a brand-new
unmigrated database.

**Why that is wrong.** Only one failure actually means "unmigrated": the version table not existing yet. Every
other failure — the file is not a SQLite database at all, the database image is malformed, the version column has
an unexpected shape, a lock outlasted the busy timeout — was swallowed. The daemon then went on to re-apply the
entire schema, and whatever failed *second* in that sequence became the error the operator saw, burying the real
cause. Demonstrated: given a database whose version table has a differently named column, the old path re-ran the
schema and failed on a later statement; the fixed path reports "no such column: version", which is the actual
problem.

**What changed.** The version read now returns zero only when the caught error is the specific "no such table"
case, and rethrows everything else, so the original diagnosis propagates.

**Test.** New: "openWorkspace reports why an unreadable database failed, not a downstream error". It hand-builds a
database whose version table lacks the version column and asserts the open throws with that exact message.

## WS5 — A helper read like a general-purpose function but only ever inspected one hard-coded table

**File:** `remote/src/workspace.ts` lines 651–675, with call sites at 780, 785 and 816.

A helper named "which unique index covers exactly these columns" took a database and a list of column names. Its
name and signature say nothing about a table, but its body queried a literal, hard-coded table name. The name
promises generality the function does not have: a future caller asking about a real unique constraint on a
*different* table would get "not found" back and would conclude the constraint is missing, then create a duplicate
one — and nothing in the signature or the call site would look wrong. Renamed to name the table it actually
inspects, with the documentation updated and all three call sites changed. No behaviour change; the two migration
steps that use it are already pinned by existing tests.

## WS6 — A "nesting depth counter" that can only ever be zero or one

**File:** `remote/src/workspace.ts` lines 921–925 and 1834–1859.

The transaction wrapper groups writes into one database transaction and is re-entrant, because SQLite rejects a
nested begin and some methods call each other. Re-entrancy was tracked by a field named "transaction depth",
commented as "nesting depth on this connection". It is not a depth counter: a nested call returns immediately
without incrementing, and the outer call assigns the literals 1 and 0 rather than incrementing and decrementing, so
the value can only ever be 0 or 1. The name and comment invite a future maintainer to "fix" the nested branch to
increment, at which point the assignments in the outer commit and rollback paths become wrong and a genuine
three-level nesting would leave a transaction open. Renamed to a boolean flag, with a comment stating that a flag
is deliberate because a nested call never opens a transaction of its own. Behaviour identical; the observable
contract is already pinned by an existing test.

### Verified in this area and found correct

Recorded so these checks are not repeated. **Write-ahead log and busy timeout** (the standing project rule): the
busy timeout is set **before** the journal-mode switch, and the pragma routine runs before the foreign-key pragma,
before migration and before the index definitions — so contention during schema changes is covered too. The
journal-mode attempt is wrapped because some network filesystems cannot host its side file, which is correct. Both
are pinned by tests. **Transaction boundaries and rollback**: every read-then-write method is inside the wrapper,
which takes a write lock before reading so two daemons serialise rather than clobber, and rolls back on any throw;
the migration runner has its own transaction around the whole upgrade. **Parameter binding**: no user-controlled
value is ever interpolated into SQL; the only interpolated identifiers are table and column names typed as closed
sets of string literals, and the type is what prevents a caller-supplied name reaching the query text. **Cascade
deletes and orphans**: children are deleted before parents, because the foreign keys reject rather than cascade;
pinned by tests including one proving a naive parent delete really is rejected. **Migrating an old database
forward**: an era-appropriate database was hand-built on disk in the shape where a constraint is expressed as an
automatic index SQLite cannot drop, and opened with this build; the table rebuild ran correctly, the version
advanced, rows survived, the constraint that should be kept was preserved, the one that should go was gone. **Index
recreation after that rebuild**: dropping the table takes its index with it, but the index definitions are applied
unconditionally *after* migration, so it comes back; pinned by a test. **The layout upsert**: keyed on the schema's
unique constraint, inside one transaction with the parent lookup and the read-back, so two concurrent writers
cannot both insert and neither can be handed the other's tree. **The wire name mirror**: every workspace method
name is set-compared against the C++ header in both directions, and a separate test asserts every contract name has
a server handler; the handler table is typed so a missing handler is a compile error. **Every handler validates
before use**: all twenty check that the parameter is an object first, then apply a guard per field; unknown extra
fields are ignored, null and wrong types are rejected, and the one enumerated field is checked against a closed set
rather than being left to a database constraint.

### Investigated in this area and deliberately left alone

1. **A migration renames duplicate slot labels that the very next migration makes legal again.** The first instinct
   was that the rename is now pure data damage. It is intentional: a test pins it explicitly and its comment states
   the renames are still what makes the legacy by-label lookup land on exactly one row.
2. **One table rebuild runs with foreign keys enabled.** SQLite's documented rebuild procedure asks for them to be
   off, which is impossible here — the relevant pragma is a no-op inside a transaction and the migration runner is
   inside one. If a legacy database contained a pane row whose parent no longer exists, the rebuild's copy would
   fail and the whole database would become unopenable. Left alone: orphans should not exist, the affected path only
   triggers for databases from one narrow build window, and every workaround applicable inside a transaction still
   fails at commit time. Flagged rather than half-fixed.
3. **Statements are re-prepared on every call.** Listing the whole workspace costs one query for the groups, one per
   group for its sessions, and three per session for panes and layouts — each compiling its SQL afresh. Two other
   methods already hoist their statements out of their loops with a comment about exactly this cost, so the listing
   path is inconsistent with them. Fixing it properly means either a prepared-statement cache or rewriting the
   listing as four set-based queries; both are reorganisations of working code rather than bug fixes.
4. **Index names are quoted with JSON escaping** rather than SQL identifier escaping, which differ for an embedded
   double quote. Unreachable today — the names come from querying our own tables and are either database-generated
   or literals in this file — so introducing a second quoting helper for a value that can never contain a quote was
   not worth it.
5. **Creating a row with an explicit position does not re-pack the scope**, so two rows can legitimately end up
   sharing a position, with the listing breaking the tie by identifier. The move-between-groups method was fixed for
   precisely this. The *validation* was tightened (WS3) but re-packing was not added: that is a semantic change to
   what "create at position N" means, the move method already exists as the intentional placement interface, and no
   test or client currently exercises create-with-position.
6. **One test file opens raw in-memory connections without applying the connection pragmas**, although the pragma
   routine's documentation says to. Harmless for an in-memory database with no second connection, and the file where
   it matters does follow the rule.

# DF — the file-serving and process half of the daemon

## DF1 — A single line reading `null` on the bridge socket killed the whole bridge process

**Files:** `remote/src/bridge.ts` lines 50–67 and the socket line handler around line 176.

**What the code did before.** The bridge is a small helper that listens on a Unix socket for status messages posted
by harness hooks, converts each line of JSON into a CodeHarbor agent event, and prints it for the desktop client.
The line processor parsed the line inside a try/catch, and if the parse succeeded it went straight on to read fields
off the result. Its documentation comment claims the function is "pure and total: never throws".

**Why that is wrong.** Parsing the four characters `null` does **not** throw — it returns the value null, so the
catch never runs — and reading a property off null throws a type error. That throw happens inside the socket's line
handler, where nothing catches it, and an exception escaping an event handler in this runtime terminates the
process. So any producer that writes four bytes and a newline — a buggy hook, a truncated write, a stray shell
command — takes the bridge down, and with it every harness's status reporting for the whole session. That is exactly
the failure mode the specification says must not happen: "a broken line is dropped, never thrown". Arrays and bare
numbers did not crash, but they are not messages either and were only rejected by accident, further down.

**What changed.** After the parse, the processor now rejects anything that is not a plain object using a guard it
already imports, and only then treats the value as a message. Because a decoded object may legitimately be missing
any field, the message type's four required members were made optional, which is what the wire actually looks like;
the per-field guards below are unchanged.

**Test.** The existing "drops malformed, unknown-harness, and no-op lines" case was extended with the lines `null`,
`[]` and `42`, all of which must return nothing. The first throws before the fix.

## DF2 — The bounded notification queue was defeated whenever a large reply stalled the output stream

**Files:** `remote/src/codeharbord.ts` line 385, lines 430–535 and lines 585–635.

**What the code did before.** The daemon writes two kinds of output on the same stream: replies to requests, and
unsolicited "this file changed" notifications from the file watcher. A stream write returns false to mean "my
internal buffer is full, stop writing" and later emits a drain event. The notification relay implements careful
backpressure: on a false return it flips a stalled flag and starts putting notifications in a bounded, coalescing
queue instead of writing them, reporting anything it had to drop. But it only ever saw the return value of **its
own** writes. Replies were written directly and their return value discarded.

**Why that is wrong.** The two writers share one stream, so the stall is a property of the stream, not of the
writer. If the client's end stops reading and the write that first reports the full buffer happens to be a large
reply — a file read of a big file, by far the most likely candidate — the relay never learns the output stalled.
From then on every notification is written straight through and appended to the runtime's internal buffer, which has
no limit. A churning directory then grows the daemon's memory until it dies, killing the whole workspace connection.
That is precisely the failure the bounded queue exists to prevent, and the bound simply did not apply in that
ordering.

**What changed.** The relay gained an explicit "someone else's write to the same stream reported a full buffer"
method, which sets the same flag its own writes set and is cleared by the existing drain handler. All three
reply-writing sites now go through one small helper that calls it when the write returns false.

**Test.** New: "a stall caused by a response write still bounds the relay's queue". It stalls the fake stream and
reports the stall through the new method — i.e. the reply writer stalled it, not the relay — delivers two events,
and asserts nothing was written and both are queued; then drains and asserts both flush. Without the fix the relay
writes both into the full buffer.

## DF3 — The line framer copied quadratically, and framed the tail of an over-sized frame as if it were a request

**File:** `remote/src/codeharbord.ts` lines 293–361.

**What the code did before.** The daemon reads newline-delimited JSON from its input with a hand-written framer.
Every incoming chunk was appended to one growing buffer by concatenation, then scanned for newlines. When the
unfinished line passed the 16-megabyte cap the framer emptied the buffer and reported an overflow — but kept framing
whatever arrived next as if it were the start of a fresh line.

**Why that is wrong.** Two distinct problems.

The cost: concatenation copies everything received so far, on every chunk. A 16-megabyte request — which is routine,
because writing a large file sends its contents base64-encoded on one line — arriving in 64-kilobyte reads costs on
the order of 2 gigabytes of memory copying for a single request, and the cost grows with the square of the frame
size.

The correctness: after an overflow, the remainder of the over-sized frame is not a request the peer sent; it is the
middle of a payload the peer never finished. The old code emitted everything between the overflow point and the next
newline as a line and handed it to the dispatcher, which parsed it as a request. It also re-reported an overflow for
every further 16 megabytes of the same frame, so one runaway producer produced an unbounded number of "closing
connection" messages and stream-destroy calls. In production the caller destroys the input on the first overflow, so
this was latent rather than active — but it is exactly the kind of thing a reordering or a second caller turns into
a live bug, and the exported helper has no such contract written down.

**What changed.** The framer now holds unfinished input as a *list* of chunk slices with a running byte count and
joins once when the newline arrives — one copy per line instead of one per chunk. A discarding state was added:
after an overflow the framer drops everything up to and including the next newline and then resumes framing
normally. Behaviour for well-formed input is unchanged.

**Test.** New: "createLineFramer discards the rest of an over-cap frame instead of framing it". It floods past the
cap, asserts exactly one overflow report, floods four more megabytes and asserts still exactly one, then feeds
trailing garbage followed by a valid line and asserts only the valid line is framed. The two existing framer tests
still pass unchanged.

## DF4 — Saving a file with a long name always failed

**File:** `remote/src/files.ts` lines 309–329 and 338.

**What the code did before.** An atomic save writes the new contents to a temporary file in the same directory and
then renames it over the target. The temporary name was a dot, plus the target's filename, plus a dot, plus twelve
random hexadecimal characters, plus `.tmp` — the original name plus 18 characters.

**Why that is wrong.** A single filename component is limited to 255 bytes on Linux and macOS. A file named with 250
bytes is perfectly legal and not exotic — generated files, long test-case names, some data exports. For any target
name longer than 237 bytes the temporary name exceeds the limit, the open fails with "file name too long", and
**every** save of that file fails with an error the user can do nothing about. The file itself opens and reads fine,
so it looks like the editor is broken.

**What changed.** The temporary-name construction was extracted into its own function, which clips the base-name
part so the whole name fits in 255 **bytes**. Clipping is measured in bytes rather than in string length — the
kernel limit is a byte count while a JavaScript string is counted in 16-bit units — and never cuts a multi-byte
character in half. Uniqueness comes from the random suffix, which is preserved intact.

**Test.** New: "writeFile saves a file whose name nearly fills the 255-byte limit". It creates a 250-character name,
saves it once (the create path), saves it again (the overwrite path, which resolves the target through the real path

fails with "file name too long" before the fix.

**What changed.** The constant was set to 0.1.8, with a comment naming the package manifest as the source of truth

## DF6 — The output sink stacked one close-listener per stall cycle on the same socket

**File:** `remote/src/bridge.ts` lines 133–163.

**What the code did before.** When the bridge's output stalls, the sink pauses the producer socket that fed the
event, adds it to a paused set, and subscribes to that socket's close event so a producer that disconnects
mid-stall is removed from the set. The subscription was made every time the socket was paused.

**Why that is wrong.** A long-lived producer is paused and resumed once per stall, and a busy agent stalls the
output repeatedly. Each pause added another close listener to the same socket; none of them fire until the socket
actually closes, so they accumulate. At eleven, the runtime prints a "possible memory leak" warning to its error
stream — which the client displays as session diagnostics — and every one of those closures is retained for the
life of the connection. Same class of leak as the one the surrounding comment was written to fix, one level up.

**What changed.** A weak set of sockets that already carry the cleanup listener was added, and the subscription now
happens only the first time. Weak, so a closed socket stays collectable.

**Test.** New: "makeStreamSink subscribes to a source's close only once across stalls", running three full
stall-and-drain cycles and asserting exactly one subscription. The shared fake-source helper gained a counter,
because it previously overwrote its record of the handler and so could not see the duplicates.

## DF7 — The file-status reply mixes information about a link with information about its target, with no explanation

**File:** `remote/src/files.ts` lines 135–144 (comment only).

For a symbolic link, the file-status reply returns the kind, size, modification time and permission bits describing
the **link itself**, but the revision token and the writability flag describing the **file the link points at**.
Each of those two decisions is separately justified in a comment; the fact that the result is a mixture is not
stated anywhere.

That is a hazard because the size through a symbolic link is the length of the link's own path text — a couple of
dozen bytes — not the size of the file a read would return. Any future caller that uses the size to decide "is this
file small enough to load inline?" would wave through a link to a multi-gigabyte file. No consumer in either
language reads that field today, so this is latent rather than active, and the client explicitly documents the
permission bits as link-blind, so changing which node those fields describe would contradict a deliberate
cross-language contract. Documentation only: an explicit comment now states which fields describe the link and
which describe the target, why, and that a consumer wanting the target's size must resolve the link itself.

### Investigated in this area and deliberately left alone

* **Writing to a dangling symbolic link replaces the link with a regular file.** The status check follows links, so
  a link pointing at a missing file looks like "no file here": a create-only write succeeds and the rename drops a
  regular file over the link, whereas a plain create would have created the link's *target*. Reaching this needs a
  user to open a broken link in the editor — whose read fails first — and then save to it. Fixing it properly means
  a third code path in the save routine for a case that could not be constructed from the interface.
* **A directory with hundreds of thousands of entries produces a listing longer than the 16-megabyte line cap.** The
  server writes it happily; the client's bounded reader then drops the transport. A real fix is pagination or a
  truncation flag, i.e. a wire-format change plus a schema version bump plus client work — out of proportion to a
  case that needs roughly half a million entries in one directory, and not a decision to make unilaterally inside
  one module.
* **No signal handlers in the daemon.** The orderly shutdown path is the input stream closing, which releases every
  watch handle. On a signal the process dies immediately, which is safe here: file writes are flushed to disk before
  the rename, the database has its own durability, and tmux sessions are meant to outlive the daemon. Adding a
  handler would add a shutdown path with no state to protect.
* **The tmux session parser accepts a partly-numeric field**, because the standard integer parse stops at the first
  non-digit. The fields come from tmux's own formatting behind an unguessable per-call record marker, so nothing
  hostile reaches them.
* **No cap on the number of live file-watch subscriptions.** Each holds an operating-system watch handle plus a poll
  timer. The producer is our own client, driven by open editor panes, so a server-side cap would only convert a
  client bug into a different client bug — and it would need a wire error the client does not understand.

### The routed fallback-detector question

The coordinator routed the question of whether the unwired fallback activity detector (AG-N1) could simply be
connected up inside the daemon. The answer, with evidence, was **no — this is a missing feature, not missing
wiring**, and the plan file should be corrected instead (BD14).

The reasoning: the specification's fallback section needs exactly one input, a stream of terminal output bytes. The
specification keeps three SSH channels separate — the terminal channels, the request-and-response channel, and the
agent-status channel — and they do not meet on the server. The daemon reads only newline-delimited requests from its
input; the bridge reads only hook-posted messages from a Unix socket; and the tmux module runs exactly two commands,
listing sessions and killing a session — there is no output-capture or output-piping command anywhere under
`remote/` (the only matches in the repository are C++ live tests). Terminal output exists **only on the client**,
where the terminal controller owns the channel and receives every byte, right beside the agent monitor that already
consumes the event stream.

So making the detector work would require building either a per-pane server-side output tap with its own lifecycle
and a way to mint events for panes that have no hook and therefore no session coordinates, or a new
client-to-daemon stream duplicating every terminal byte over SSH purely to compute a three-state heuristic. Either
is a new subsystem, not a connection between two things that already meet.

# BD — build system, continuous integration, packaging, documentation

## BD1 — A tagged release could publish a server tarball stamped with the wrong version

**File:** `.github/workflows/release.yml`, the server job; the new gate sits at lines 369–375.

**What the code did before.** The project's version number is written in several places: the top-level build file,
four package manifests, and the dependency lock file, which records the version of the root package and of every
workspace separately. The lock file is the one nothing updates automatically. A script exists whose whole job is to
fail when those disagree, and the ordinary continuous-integration workflow runs it. The **release** workflow — the
one that actually builds and publishes the downloadable artefacts — did not run it anywhere.

**Why that is wrong.** The release workflow's server job runs a clean install, and a clean install does not merely
install: it rewrites a workspace's own manifest version to whatever the lock file says. So if the lock lagged the
manifests — the exact drift this repository has already suffered once, with the lock at 0.1.7 while every manifest
said 0.1.8 — the job would quietly downgrade the server manifest and then package that file up. The result is a
release named v0.1.8 whose server component reports itself as 0.1.7, with nothing going red. The publishing job does
assert a version, but only on the Windows installer's filename; the server tarball is not covered.

**What changed.** A version-agreement step was added to the release workflow's server job, running immediately after
checkout and **before** the clean install, mirroring the placement and reasoning already used in the ordinary
workflow. A comment explains why the ordering matters and why the publishing job's existing assertion does not cover
this.

## BD2 — The release-bump script silently clobbered uncommitted edits to the lock file

**File:** `.omp/skills/bump-version/bump.sh` lines 116–125.

The script has a safety guard: before rewriting any version file it checks whether any of them has uncommitted
changes and refuses to continue if so. That list contained the build file and the four manifests. It did **not**
contain the lock file — even though a block further down in the same script rewrites three version fields inside the
lock file and then stages it into the release commit.

That defeats the guard for exactly one file. A developer with an in-progress edit to the lock file — say a dependency
bump not yet committed — runs the bump, has part of that file overwritten, and then has the whole thing staged into
a commit titled "Release vX.Y.Z". No warning; the unrelated dependency change is now part of a release commit and
their own edit to the version fields is gone. The guard's own comment says it exists so that "in-progress version
edits are never clobbered", which is precisely what happened.

The dirty check now covers the lock file too, with a comment stating why it is checked despite the rewrite loop
deliberately not including it — the loop applies a manifest-shaped edit that would be wrong for the lock, which
needs three fields updated rather than one.

## BD3 — The release-bump script left the tree half-bumped if a version file was missing

**File:** `.omp/skills/bump-version/bump.sh`; the existence checks are now hoisted to lines 128–134.

The script rewrote the top-level build file first, then looped over the four manifests checking each exists and
aborting on a missing one, then separately checked the lock file exists and aborted if not.

Every one of those existence checks ran *after* at least one file had already been rewritten. If one of the
manifests had been deleted or renamed, the script would have already bumped the build file and up to three
manifests, and then died. Because it dies before staging or committing, the developer is left with a working tree
that is bumped in some files and not in others, with no commit and no tag to show for it — the "partially applied
version bump" state that the version-checking script exists to detect. The abort message names the missing file but
says nothing about the files it already modified.

All the existence checks were moved into a single loop placed before the first rewrite. The two now-redundant
in-line checks were removed. A comment states that discovering a missing file halfway through would leave the tree
bumped in some files and not others.

## BD4 — The release-bump script could abort with no message at all on a repository with many tags

**File:** `.omp/skills/bump-version/bump.sh` lines 69–73.

The script resolved the current version from the newest version tag by piping the tag list through a command that
prints one line and exits. The script runs with the shell options that make any failing command abort the script and
that make a pipeline fail if *any* stage fails.

If the tag-listing command still has output to write when the reader exits, its write fails and the kernel kills it
with a broken-pipe signal, so it exits with a failure status. The pipeline option propagates that to the whole
pipeline, and because this is a command substitution feeding an assignment, the abort-on-error option kills the
script right there — with no error message, no partial output, and nothing pointing at the cause. It works today
only because the repository has few enough tags that the tag list finishes writing before the reader exits (the
entire output fits in the pipe buffer). It becomes a hard, silent failure once the tag list exceeds that, i.e. after
a few thousand releases, or immediately if the tag listing is ever asked for a longer format. This is a well-known
footgun and worth removing on sight rather than reasoning about pipe-buffer sizes.

The two-command pipeline was replaced with a single text-processing step that consumes the entire stream and so can
never generate a broken pipe, with a comment naming the shell option as the reason. Verified behaviour-identical on
the current repository with a dry run.

## BD5 — The release-bump skill documentation omitted the lock file

**File:** `.omp/skills/bump-version/SKILL.md`, step 3 and the safety section.

The documentation said the script "rewrites the version in the build file and in every workspace manifest", naming

## BD6 — On Windows, most test executables emit no diagnostics when they fail

**Files:** a `WIN32_EXECUTABLE FALSE` block was added to the test build files in eight directories:

**Verification.** No new test — this is a build-system property and its observable effect is only visible on a

## BD7 — A failed web-bundle build was announced with an ordinary status line, and a stale bundle was embedded

**File:** `src/qml/CMakeLists.txt` lines 211–222.

**What the code did before.** The editor and terminal web bundles are build artefacts that are not committed; the

no summary at the end of the configure. The concrete scenario: you edit an editor source file, introduce a syntax

**What changed.** The message was promoted to a warning and its text rewritten to state the actual consequence:
that a previously built bundle will be embedded as-is and the pane will run stale code. The build output from the
package manager is still included. The comment explains why a status line was the wrong level. Behaviour is
otherwise unchanged — configure still succeeds, which is deliberate: failing outright would make a tree with no
network or no package manager unconfigurable, and an existing option already covers the intentional case.

## BD15 — The version bump missed a file, and the version checker had a matching blind spot

**Files:** `.omp/skills/bump-version/bump.sh` lines 107–127 and 145–175;
`.github/scripts/check-versions.mjs` lines 6–20 and 49–61; `.omp/skills/bump-version/SKILL.md` lines 27–42.

*Routed to this area by the coordinator; the constant itself was already corrected by the reviewer who owns the
server source, which this area did not touch (see DF5).*

**What the code did before.** Two things are supposed to keep the release version consistent across the tree: the
bump script, which rewrites it everywhere and creates the tag, and the checking script, which runs in continuous
integration and fails when the copies disagree. The bump script's file list held the top-level build file and the
four manifests, plus special handling for the lock file, and the checking script compared exactly those. Neither
knew about the server source file that hand-carries a version constant.

**Why that is wrong.** That constant is what the server daemon puts in its information reply, and the client prints
it to the user verbatim in the message "Server too old: codeharbord <version> …". Because no bump ever touched it, it
sat at 0.1.0 while the released tag was v0.1.8 — users were shown a version three releases stale, in the one message
whose entire purpose is to tell them which version they are running. The deeper defect is the second half: the
checking script reported "all version strings agree" the whole time. A consistency checker that does not know about
one of the files is worse than no checker, because it converts a drift into a green tick. The two lists had to be
brought back into agreement *and* the reason recorded, or the next hand-carried version string will do the same
thing.

**What changed.** Three parts. First, the bump script: the four manifests were split into their own array, because
they share one edit shape, and the main list became the complete set of seven files that carry the version — the
build file, the server source file, the four manifests, and the lock file. That single list now drives both the
dirty-tree guard and the pre-write existence check, so the lock file no longer needs to be tacked on at each use
site. A rewrite step was added for the new file: a pattern anchored on the whole constant declaration which **exits
with a failure if it does not match**, because a silent no-op substitution is precisely the failure that let the
constant fall behind. The comment on the list states the rule: a file that carries the version and is not in the
list is a file the bump silently skips. Second, the checking script now reads the same declaration and compares it
like every other copy, and treats a *missing* declaration — for example if somebody renames the constant — as its
own distinct failure rather than as "nothing to compare", which is how a rename would quietly switch the check back
off. Third, the skill documentation's step 3 now enumerates all seven files, names the constant and why it is in the
list, and states that the script and the checker must be kept in step with each other.

**Verification.** Three ways, since the checker *is* the gate. Running it reports agreement at 0.1.8. A negative
test: the constant was temporarily reset to 0.1.0 and the checker re-run — before this change that produced a green
"all version strings agree"; it now fails naming the file and the stale value, with a failure exit code. The file was
restored and the checker re-run green, so it now catches the exact historical defect it missed. An end-to-end test of
the bump: a throwaway repository was built containing only the seven version files, the bump was run with an explicit

### Investigated in this area and deliberately left alone

* **Continuous integration never builds on Windows or macOS.** The client is built only on Linux; the Windows job
  there merely warms a dependency cache and the macOS path is exercised for the first time when a tag is pushed. The
  development guide itself records that the release workflow's first real run "failed on **each** platform for a
  different reason". Adding real Windows and macOS build jobs would roughly triple the cost and time per
  pull request; that is a project-level budget decision, not a defect to silently fix in a bug hunt.
* **One build option is not formally declared.** The top-level build file argues, for its sibling option, that an
  undeclared cache variable is invisible in the interactive configuration tools, and both documents advertise this
  one on the command line — so the same argument would suggest declaring it. It is nonetheless correct as written:
  the user-interface build file explains that a *cached* default would stick to whatever the build type was on the
  first configure of a directory, so re-configuring a debug tree as a release build would keep embedding roughly 15
  megabytes of source maps. Declaring it would reintroduce exactly that bug.
* **The scaffolding scan only covers two source directories and a fixed extension list.** Markers left in the
  workflows, the packaging directory, the documents or the skills directory would not be caught. The script's own
  comment scopes it to "the sources humans ship", and widening it risks the script matching its own pattern list.
* **The release workflow does not type-check the web bundles the way the ordinary workflow does**, and its server job
  runs the tests but not the separate type check. Both are mitigated: that job's build step *is* the type checker, so
  it would fail on a type error, and tags are cut from the main branch, which the ordinary workflow has already
  gated.
* **The ordinary workflow passes an output-on-failure flag that its test preset already sets.** Harmless redundancy
  that also makes the command copy-pasteable.
* **The readme carries a "verified for v0.1.0" note.** The current version is 0.1.8, so the note is old, but it is
  an explicitly dated statement about a past verification run — which the plan file also refers to — not a claim
  about the present. Rewriting it would mean either deleting real evidence or claiming a verification that was not
  performed.
* **One bump-script flag can create a tag whose tree carries a different version**, which the publishing job's
  filename assertion would then reject. That is the documented purpose of the flag, and the failure it causes is
  loud and happens before publication.

## ORCH4 — A new user-interface test failed in the integrated tree, exposing a second defect in its own fix

Covered in full as QM3. Recorded here as well because it is the clearest illustration of why the coordinator runs the
gates rather than trusting per-area verification.

Every area verified its own work in isolation — several went to the trouble of building test binaries in private
temporary directories against the shared static libraries, precisely so as not to disturb concurrent editors — and
the user-interface reviewer, which could not build at all while others were editing, verified with a static linter
plus an isolated probe. That is a reasonable division, but it cannot catch an engine-ordering defect.

The full build was clean and the portable suite came back 35 of 36 with one skip and **one failure**: a newly added
case asserting that the viewer address bar shows the absolute path a relative name resolved to. It reported the
directory the pane had just left instead of the file it had just opened.

The failure was routed back to the owning area with the exact assertion output and an explicit instruction to
diagnose it rather than loosen the assertion, and to say so if the fix turned out to be unsafe. The diagnosis was
that the test was right and the production change was wrong: the new code read a *bound* property from inside the
very notification that refreshes that property's bindings, and whether the refresh has happened by then is an
ordering detail of the engine. It had not. The fix computes the value with a small function instead of reading it off
a binding — the same technique a sibling file already uses to avoid this exact hazard. No assertion was changed. The
suite is now clean.

## ORCH6 — A concern about the verification commands themselves
